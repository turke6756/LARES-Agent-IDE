## Flow

- Session log events enter through `SessionLogDispatcher.pollOne`, which reads provider logs, dedupes events, mutates assistant patches, marks the first batch as `initialLoad`, then emits `chat-events` (`src/main/supervisor/session-log-dispatcher.ts:264`, `src/main/supervisor/session-log-dispatcher.ts:309`, `src/main/supervisor/session-log-dispatcher.ts:315`). `AgentSupervisor` forwards those batches to `EventBridge.onChatEvents` (`src/main/supervisor/index.ts:355`).
- For a live assistant completion, `EventBridge.onChatEvents` maps `assistant-text` or `assistant-text-patch` with `turnComplete === true` to `statusMonitor.forceIdle(agentId, 'turnComplete')`; initial replay batches are ignored so stale log history cannot flip status (`src/main/supervisor/event-bridge.ts:170`, `src/main/supervisor/event-bridge.ts:178`, `src/main/supervisor/event-bridge.ts:189`, `src/main/supervisor/event-bridge.ts:220`).
- `StatusMonitor.forceIdle` is the first authoritative write for this idle path: it latches idle, updates the DB status, audits a `status_change`, and emits `statusChanged` with `{ status: 'idle', fromStatus, source: 'monitor' }` (`src/main/supervisor/status-monitor.ts:229`, `src/main/supervisor/status-monitor.ts:236`, `src/main/supervisor/status-monitor.ts:239`, `src/main/supervisor/status-monitor.ts:247`). Poll inference can also detect idle after `inferStatus` and emit the same contract (`src/main/supervisor/status-monitor.ts:454`, `src/main/supervisor/status-monitor.ts:476`, `src/main/supervisor/status-monitor.ts:486`).
- `AgentSupervisor` receives monitor status changes, republishes them, and calls `bridge.onStatusChanged`; direct non-monitor status changes are also bridged separately (`src/main/supervisor/index.ts:318`, `src/main/supervisor/index.ts:325`, `src/main/supervisor/index.ts:332`).
- `EventBridge.onStatusChanged` filters to supervised non-supervisor workers, trigger statuses including `idle`, non-duplicate transitions, and a live supervisor. The supervisor is selected through `getSupervisorForWorker`, currently `getSupervisorAgent(worker.workspaceId)` (`src/main/supervisor/event-bridge.ts:87`, `src/main/supervisor/event-bridge.ts:90`, `src/main/supervisor/event-bridge.ts:92`, `src/main/supervisor/event-bridge.ts:100`, `src/main/supervisor/index.ts:285`).
- The bridge enriches the raw status change with log tail, context stats, last clean assistant message, recent file activity, exit code, titles, ids, and waiting metadata before delivery (`src/main/supervisor/event-bridge.ts:112`, `src/main/supervisor/event-bridge.ts:121`, `src/main/supervisor/event-bridge.ts:126`). If the supervisor is idle/waiting, detached, and the user is not typing, it builds `[DASHBOARD EVENT] Agent status changed` and sends it through `AgentSupervisor.sendInput`, which writes into the supervisor PTY/tmux chat (`src/main/supervisor/event-bridge.ts:329`, `src/main/supervisor/event-bridge.ts:351`, `src/main/supervisor/event-payload-builder.ts:132`, `src/main/supervisor/event-payload-builder.ts:170`, `src/main/supervisor/index.ts:1937`, `src/main/supervisor/index.ts:2001`).

## Key types and contracts

- `StatusChangedEvent` is the status pipeline handoff: `agentId`, `status`, optional `fromStatus`, `source`, and waiting metadata for prompt events (`src/main/supervisor/status-monitor.ts:241`, `src/main/supervisor/status-monitor.ts:480`).
- `TurnLatchEntry` in `StatusMonitor` is the high-confidence state overlay for idle/waiting/working; `forceIdle`, `forceWaiting`, and `forceWorking` own writes to it (`src/main/supervisor/status-monitor.ts:112`, `src/main/supervisor/status-monitor.ts:229`, `src/main/supervisor/status-monitor.ts:598`).
- `ChatEventBatch` is the session-log-to-bridge contract; `initialLoad` is important because bridge latch updates must only reflect live events (`src/main/supervisor/session-log-dispatcher.ts:309`, `src/main/supervisor/event-bridge.ts:178`).
- `EventBridgeDeps` keeps the bridge infrastructure-free: DB lookup, supervisor resolution, input delivery, audit, logs, stats, timers, chat preview, and file activity are injected (`src/main/supervisor/event-bridge.ts:28`, `src/main/supervisor/index.ts:283`).
- `SupervisorEvent` is the enriched event payload shape consumed by `buildEventPayload`; for idle it carries status, context, output preview, files touched, and worker identity (`src/main/supervisor/event-payload-builder.ts:19`, `src/main/supervisor/event-bridge.ts:126`).

## Suspicions

- No literal `TODO` or `FIXME` comments were observed in the requested files.
- `EventBridge` has one global `supervisorQueuedEvents` array and one drain timer, but delivery chooses a supervisor id when arming/draining. That looks risky for multiple simultaneous supervisors or workspaces because a drain for one supervisor could flush unrelated queued events (`src/main/supervisor/event-bridge.ts:373`, `src/main/supervisor/event-bridge.ts:415`).
- Supervisor routing is explicitly still workspace-based, with a comment saying a future multi-supervisor migration should use `worker.supervisorId`; that is a known architectural pressure point (`src/main/supervisor/event-bridge.ts:31`, `src/main/supervisor/index.ts:285`).
- `assistant-text-patch` waiting events intentionally lose the excerpt, leaving only log tail; acceptable per comment, but supervisors get weaker context for that split-batch corner case (`src/main/supervisor/event-bridge.ts:213`).
- Team events are mentioned as not currently emitted, with payload branches to restore if Teams reintroduce them (`src/main/supervisor/event-payload-builder.ts:12`).

## Notes for the supervisor

- Idle notifications are not just PTY quietness; live chat `turnComplete` is preferred, then the monitor emits the same status-change contract.
- If the supervisor is working, launching, attached, or recently typed into, events queue and later arrive as a consolidated `[DASHBOARD EVENT]` batch (`src/main/supervisor/event-bridge.ts:322`, `src/main/supervisor/event-bridge.ts:330`, `src/main/supervisor/event-bridge.ts:344`, `src/main/supervisor/event-bridge.ts:415`).
- For idle/done/crashed, the message should include cleaner assistant prose when available, with PTY tail only as fallback; recent files touched are appended separately (`src/main/supervisor/event-payload-builder.ts:163`, `src/main/supervisor/event-payload-builder.ts:175`).

plan fully implementable on the planning surface. B3 (parse the
`kind: work-packages` supplement and/or ARC's `## Work packages` ledger into
`plan_work_packages` rows on folder adoption/refresh) is the keystone, but a
codex spot-check established B3 alone does NOT unlock Implement. Your design
must cover the whole chain:

1. **WP ingest schema.** The current WP supplement is prose, not a stable

   `package` playbook must emit for the parser to be reliable (if you propose a
   structured block, specify it exactly).
2. **Disk↔DB reconciliation semantics.** "Disk is truth" cannot blindly
   overwrite runtime state: define conflict behavior when disk changes after DB
   lifecycle state / assignment / execution exists; removal/tombstone policy;
   transactionality (a partial write must never archive/delete live DB
   packages).
3. **responsible_supervisor_id reconciliation.** Folder adoption deliberately
   omits the supervisor write today. Define how `plan.json.responsibility_events`
   reconciles into the authoritative DB supervisor relationship, with validation
   for missing/deleted/cross-workspace agents.
4. **Readiness transitions.** How a skill-driven plan reaches Implement:
   `hardening → ready` (Mark Ready), ≥1 `ready` WP, and interaction with the
   per-tab overview gate (note: overview-band design is a SEPARATE intent,

   interface you need from it).
5. **Host + trigger.** Where the ingest runs (`plan-folder-watcher.ts` is the
   proposal's candidate) and when (adoption, refresh, manual).

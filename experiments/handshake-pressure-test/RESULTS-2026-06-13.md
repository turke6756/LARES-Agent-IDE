## Windows vs. WSL divergence (highest-value finding)

Both handshake suites **pass cleanly on Windows but cannot start on WSL**. The
divergence is purely a **runtime/ESM-interop issue, not a logic regression**:

- Windows node **v24.13.0** permits `require()` of an ES module (Node ≥ 22
  enables `require(esm)` by default), so `require("uuid")` works.
- WSL node **v18.19.1** forbids `require(esm)` → `ERR_REQUIRE_ESM` the moment
  the supervisor/database require chain touches the ESM-only `uuid` package.

Net: no case passes on one runtime and fails (assertion) on the other; the WSL
side simply fails to load. The actionable finding is that these compiled
suites are **not runnable under WSL's node 18** — either bump WSL node to ≥ 22
or downgrade/shim `uuid` to a CJS build if WSL execution is required.

Feature flag system

Introduce a comprehensive feature-flag system enabling dark deployments, gradual product rollouts, and instant kill-switches without redeployment. This lift spans schema definition, an ultra-fast evaluation engine, and a control dashboard.

Success criteria

1. Engineers can evaluate flags in the two main backend languages within under 1ms at p99.

2. Non-backend clients can evaluate flags via a JSON-over-HTTP endpoint.

3. Product and Support teams can toggle flags, view audit logs, and set rollout percentages via a UI without engineering assistance.

4. Flag evaluations accurately bucket users deterministically based on user ID and flag salt.

Scope

In scope: Postgres schema for flags, typed accessor libraries, in-memory caching with invalidation, SDKs for two backend languages, JSON HTTP endpoint, deterministic bucketing, environment inheritance (staging defaults from production), telemetry sampling, admin UI with RBAC and audit history.

Out of scope: Full approval workflows, A/B-test statistics/analytics, scheduled rollouts, mobile SDKs.

Constraints

No new external SaaS dependencies may be introduced. The evaluation path must not add a network hop to request handling. Admin UI and HTTP endpoint must be protected by existing auth middleware. The project is constrained to a 3-engineer team over approximately 6 weeks.

Assumptions

In-memory caching of all active feature flags will easily fit within the memory constraints of existing application instances.

The JSON-over-HTTP endpoint can be co-located within an existing core service to avoid standing up completely new infrastructure.

Phase 1: Flag schema and storage

Establish the foundation of the feature flag system by defining the data model and the primary storage mechanism. Create the database migrations, seed data, and a typed data access layer.

Phase goal

Deliver a fully migrated database schema capable of representing complex feature flags (booleans, percentages, multivariate), along with a basic typed accessor library to interact with this data securely and audit changes.

Alternatives considered

Considered a config-file-in-repo approach (GitOps) for flag storage. Rejected because it requires a deployment/commit for every flag change, which contradicts the goal of allowing support to kill misbehaving features instantly without deployments.

Design and implement PostgreSQL migrations

Create `feature_flags` and `feature_flag_audit_logs` tables. The flags table will store key, description, owner, type, targeting rules, default values, and lifecycle state. Ensure indices on keys and environments.

Generate seed data for local development

Create a script to populate the local development database with a diverse set of active, archived, boolean, and percentage-based flags to facilitate UI and Engine testing.

Develop typed accessor library

Build the core repository layer that reads and writes flags to the database. Implement the logic to automatically append a record to the audit log upon any mutation.

Phase 2: Evaluation engine

Build the highly performant evaluation engine ensuring sub-millisecond local responses. This includes the deterministic bucketing logic and cache invalidation strategies.

Phase goal

Deploy local evaluation SDKs in the two primary backend languages that sync state in the background and evaluate rules entirely in memory. Expose a JSON endpoint for external consumers.

Alternatives considered

Evaluated using Redis as a centralized evaluation cache instead of local in-memory processing. Rejected because network round trips to Redis would violate the constraint of not adding a network hop during the evaluation path.

Implement core bucketing and evaluation algorithms

Create the deterministic bucketing function using a standard hashing algorithm (e.g., MurmurHash3) combining the user ID and flag salt. Implement targeting rule ordering semantics.

Develop Language 1 SDK

Implement the evaluation library for the primary backend language. Add background thread synchronization for cache updates and telemetry event batching.

Develop Language 2 SDK

Port the evaluation logic, background sync, and telemetry batching to the second main backend language in the monorepo.

Build JSON-over-HTTP evaluation endpoint

Create a lightweight internal HTTP endpoint behind the standard auth middleware to serve evaluations for clients not utilizing the native SDKs.

Phase 3: Admin UI

Construct the internal dashboard allowing stakeholders to manage flag lifecycles without engineering intervention.

Phase goal

Implement Flag editor and percentage slider

Build the form for creating and editing flags. Create a custom slider component for percentage rollouts that dynamically shows how many test users fall into the bucket based on live previews.

Wire Role-Based Access Control (RBAC)

Enforce restrictions so that only flag owners and designated admins can modify production values, while general engineers can only modify staging values.

Build audit history component

Create a timeline view on the flag details page showing the chronological sequence of changes, who made them, and when, reading from the audit log data.

Database backing over GitOps configuration

Rationale: Using a Postgres database with a read-through cache fits the operational requirements much better than a config-file-in-repo. Support teams need to hit kill-switches instantly; waiting for a CI/CD pipeline and code review is too slow for incident mitigation.

GitOps provides free audit history and rollback capabilities natively through Git, requiring less custom code.

SDK Cache staleness causes inconsistent state

If the background polling or push notification mechanism fails, servers might evaluate flags using outdated rules, causing varying behavior across instances. Mitigation: implement cache TTLs as a fallback and emit alerts if background sync fails repeatedly.

Telemetry volume overloads observability stack

Emitting a sampled event for every evaluation could flood the telemetry backend in high-throughput services. Mitigation: implement dynamic sampling rates controllable via the flag system itself, allowing operations to dial down verbosity if needed.

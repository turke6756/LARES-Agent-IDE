Feature Flag System Implementation

Implement a robust, low-latency feature flagging system to enable dark launches, gradual rollouts, and instant kill-switches without redeploys. This six-week initiative covers schema design, a high-performance evaluation engine, and a management dashboard.

Success criteria

  • Flags can be toggled in production without a code deploy or restart.
  • Flag evaluation latency is under 1ms at the p99.
  • Deterministic rollout bucketing ensures a consistent user experience for percentage rollouts.
  • Audit logs capture every change to flag configurations, including who made the change and when.

Scope

In Scope:

  • Postgres schema for flags and audit history.
  • Evaluation logic supporting boolean, percentage, and multivariate flags.
  • Backend SDKs for the two primary monorepo languages.
  • Admin UI for flag management and per-environment overrides.

Out of Scope:

  • Mobile SDKs.
  • Scheduled/automated rollout transitions.
  • Advanced A/B testing analytics and statistical significance reporting.
  • Complex approval workflows/pull-request style reviews for flag changes.

Constraints

  • No new external SaaS dependencies (e.g., LaunchDarkly, Split.io).
  • Evaluation must not add a network hop to request handling (must use local in-memory state).
  • Must integrate with existing authentication and authorization middleware.
  • Delivery within a 6-week window by a team of three engineers.

Assumptions

Existing Postgres infrastructure can handle the additional write load for flag updates and audit logging.

Consistent hashing for rollouts can be implemented identically across both monorepo languages using standard libraries.

Phase 1: Schema and Storage

Establishing the source of truth for feature flags, including the database model, migration scripts, and the initial typed accessors.

Phase goal

Deploy a stable Postgres schema and a typed data access layer that supports CRUD operations for flag configurations and audit history.

Alternatives considered

Chose a Postgres-backed model over a config-file-in-repo approach to allow for instant updates without CI/CD cycles and to facilitate a rich Admin UI.

Recommendations

Use a JSONB column for targeting rules to allow for future flexibility in rule types without frequent schema migrations.

Open questions

Should we enforce a naming convention for flag keys at the database level?

Design Postgres Schema

Create the feature_flags table (key, type, state, etc.) and the flag_audit_log table for change tracking.

Implement Database Migrations

Write and test migration scripts for the new tables. Include seed data for core system flags.

Build Typed Accessor Library

Develop a shared library to read/write flag configurations with strict type safety for the supported flag types.

Phase 2: Evaluation Engine

Building the high-performance logic that decides which variant a user sees based on the current environment and targeting rules.

Phase goal

Deliver a sub-millisecond evaluation SDK that uses local in-memory caching and deterministic hashing for rollouts.

Alternatives considered

Considered a sidecar service for evaluation but opted for a library-first approach to avoid the network hop and meet the <1ms latency constraint.

Recommendations

Implement a "polling with fallback" strategy for cache invalidation initially; move to Redis Pub/Sub only if propagation delay becomes an issue.

Open questions

What sampling rate should we use for evaluation telemetry to avoid flooding our analytics pipeline?

Implement Bucketing Logic

Develop the MurmurHash3-based deterministic bucketing for percentage rollouts, ensuring user ID + salt leads to stable variants.

Develop In-Memory Cache and Poller

Create a background poller that refreshes local memory from Postgres every 30 seconds, with a TTL-based fallback.

Expose JSON-over-HTTP Endpoint

Build a lightweight internal endpoint for non-SDK consumers (e.g., frontend or scripts) to request flag evaluations.

Add Telemetry Instrumentation

Emit sampled evaluation events containing the flag key, selected variant, and targeting context.

Phase 3: Admin UI

Providing a user-friendly dashboard for non-technical stakeholders and engineers to manage the lifecycle of feature flags.

Phase goal

A functional dashboard behind existing auth that allows creating, editing, and auditing flags across all environments.

Alternatives considered

Considered a CLI-only management tool but decided a UI was necessary for Product and Support accessibility.

Recommendations

Implement a "Search/Filter" capability early as the number of flags is expected to grow rapidly after launch.

Open questions

Should we allow "cloning" flags between environments or force manual recreation?

Build Flag Management Dashboard

Create the main list view with search, filter, and archive capabilities. Integrate with existing Auth middleware.

Implement Per-Environment Overrides

Build the UI for toggling flags in Staging vs. Production, with clear visual indicators of environment state.

Develop Rollout Slider Component

Create an interactive slider for percentage rollouts with a live preview of how many users will be bucketed.

Audit History View

Implement a timeline view of all changes made to a specific flag, pulled from the audit log table.

Centralized Postgres vs Distributed Config

Rationale: Postgres allows for real-time updates and an easier build-out of the Admin UI, which are critical for the 'kill-switch' use case.

A distributed config approach would be more resilient to DB outages but slower to update and harder to build a UI around.

Stale Cache on Evaluation Engine

If the poller fails or lags, production nodes may evaluate flags using outdated rules. Mitigation: Implement a TTL and health check on the cache.

Performance Degradation under Heavy Load

Complex targeting rules could slow down evaluation logic. Mitigation: Profile the evaluation engine with 100+ rules before production launch.

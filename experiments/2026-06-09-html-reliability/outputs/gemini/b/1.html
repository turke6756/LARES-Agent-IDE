Feature Flag System Implementation

Implementation of a robust, low-latency feature flagging system to support dark launches, gradual rollouts, and operational kill-switches without external SaaS dependencies.

Success criteria

  • Flags can be toggled in production via UI and take effect in under 30 seconds across the fleet.
  • Evaluation latency adds less than 1ms (p99) to request handling.
  • Zero external SaaS dependencies for flag storage or evaluation.
  • Audit trail captures 100% of flag configuration changes.
  • Deterministic percentage rollouts ensure consistent user experience across requests.

Scope

  • In Scope: Multi-variate flag support, percentage rollouts, environment-specific overrides, typed SDKs for monorepo languages, and an admin dashboard.
  • Out of Scope: Mobile SDKs, scheduled rollouts (auto-start/stop), and native A/B testing statistical analysis.

Constraints

  • Evaluation path must not add a network hop (must use in-memory state).
  • System must integrate with existing authentication and authorization middleware.
  • Timeline: 6 weeks with a 3-engineer pod.

Assumptions

The system only needs to provide native SDKs for the two primary backend languages currently in the monorepo.

A read-through cache (e.g., Redis) is available and acceptable for distributing flag state to the evaluation engine.

Phase 1: Schema and Storage

Establishing the source of truth for flag configurations and the data access layer.

Phase goal

Define and deploy the Postgres schema for flags and audit logs, and provide a typed library for managing flag data.

Alternatives considered

Considered a config-file-in-repo approach (GitOps). Chose Postgres-backed storage to allow non-engineering stakeholders (Product, Support) to toggle flags without requiring a code deploy or PR workflow.

Recommendations

Use a JSONB column for targeting rules to allow flexible rule expansion without frequent schema migrations.

Should we enforce a naming convention for flag keys (e.g., prefixing by team or service)?

Database Migration

Create feature_flags and flag_audit_log tables in Postgres with appropriate indexes on key and environment.

Data Access Object (DAO)

Implement the backend service layer for CRUD operations on flags, including validation logic for rule schemas.

Audit Logging Integration

Ensure every write operation to the flags table triggers a synchronous entry in the audit log table capturing the actor and delta.

Phase 2: Evaluation Engine

The high-performance core that determines which variant a user sees.

Phase goal

Build the SDKs and evaluation logic that provide sub-millisecond variant resolution using in-memory state.

Alternatives considered

Considered a centralized sidecar for all evaluations. Chose an in-process SDK approach for the primary languages to meet the "no network hop" constraint, with a sidecar/HTTP endpoint only as a fallback for other services.

Recommendations

Use MurmurHash3 for deterministic bucketing to ensure uniform distribution and stability across different language implementations.

What sampling rate should we use for evaluation telemetry to avoid overloading our analytics pipeline?

Bucketing Logic

Implement deterministic hashing using hash(userId + flagSalt) % 100 to support percentage rollouts.

In-Memory Sync Engine

Implement a background poller/refresher that keeps the local SDK cache in sync with the primary store via the cache layer.

Telemetry Emitter

Add a non-blocking background emitter to the SDK that sends sampled evaluation events (flagKey, variant, context) to the telemetry service.

Phase 3: Admin UI

The interface for managing the feature lifecycle.

Phase goal

Deliver a dashboard for creating and managing flags, featuring per-environment overrides and audit visibility.

Alternatives considered

Considered building a CLI-only tool first. Decided on a Web UI to empower Product Managers and Support staff immediately.

Recommendations

Include a "Live Preview" feature in the percentage rollout slider that shows how many users in a sample set would be affected.

Should we allow "Global" flags that apply to all environments, or force explicit overrides?

Flag Dashboard View

Build the searchable list view of all flags with status indicators (active, archived) and ownership info.

Environment Override Editor

Implement the per-environment configuration UI, ensuring production edits require higher-level permissions.

Audit Log Viewer

Create a view within the flag details page to show the history of all changes made to that specific flag.

Centralized Postgres Store

Rationale: We need a single source of truth that is easily editable by non-engineers. Existing Postgres infrastructure is reliable and avoids new SaaS costs.

Cache Invalidation Latency

If the in-memory cache update fails or lags, different instances may evaluate the same user differently.

Mitigation: Implement a heartbeat/version check and a "stale data" warning in the UI.

Flag Accumulation (Technical Debt)

Flags may stay in the code long after they are 100% rolled out.

Mitigation: Add "Archived" state and a dashboard view for "Old Flags" that have been at 100% for > 30 days.

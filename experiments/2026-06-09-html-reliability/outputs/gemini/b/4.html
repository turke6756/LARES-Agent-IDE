Feature Flag System Implementation

Implementation of a robust, low-latency feature flagging system to support dark launches, gradual rollouts, and emergency kill-switches without redeployment.

Success criteria

  • Flags can be toggled in production via UI with changes reflected in SDKs within 60 seconds.
  • Evaluation latency is under 1ms at p99 for local SDK calls.
  • Zero new external SaaS dependencies introduced for flag storage or evaluation.
  • Audit logs capture every change to flag configurations, including the actor and previous state.
  • Deterministic bucketing ensures a user consistently sees the same variant for a percentage rollout.

Scope

In Scope: Database schema and migrations, evaluation engine/SDKs, admin dashboard, audit history, and environment-based overrides.

Out of Scope: A/B testing statistical analysis, scheduled automated rollouts, mobile-specific SDKs, and complex multi-stage approval workflows.

Constraints

  • Timeline: 6 weeks total for a team of 3 engineers.
  • Performance: Evaluation path must not add a network hop to critical request handling.
  • Security: Must integrate with existing authentication middleware; no bypasses allowed.
  • Infrastructure: Use existing Postgres and Redis (cache) instances; no new SaaS.

Assumptions

Current primary Postgres and Redis instances have sufficient headroom to handle flag storage and polling/push traffic.

The SDKs only need to support the two primary backend languages currently in use in the monorepo.

Phase 1: Flag Schema and Storage

Establish the source of truth for feature flags and the underlying data structures.

Phase goal

A fully versioned database schema and a typed accessor library to read/write flag configurations with audit trails.

Alternatives considered

Config-file-in-repo: Rejected because it requires a full CI/CD deploy cycle to toggle flags, failing the "support can kill a feature without a deploy" requirement.

Recommendations

Use a JSONB column for targeting rules to allow flexibility without frequent schema migrations.

Open questions

Should we use a soft-delete or a separate archive table for retired flags?

Design and execute Postgres migrations

Create feature_flags and flag_audit_log tables. Include fields for key, type, targeting JSONB, and lifecycle state.

Develop Internal Management SDK

Build a typed library for the backend to perform CRUD operations on flags with mandatory audit logging.

Seed initial system flags

Provide seed data for existing features to be wrapped in flags immediately upon rollout.

Phase 2: Evaluation Engine

Build the logic that determines which variant a user receives based on the current context.

Phase goal

Highly performant SDKs and a sidecar service providing sub-millisecond flag evaluation with deterministic bucketing.

Alternatives considered

Direct DB lookup on every evaluate call: Rejected due to latency and DB load concerns. In-memory caching with background polling is required.

Recommendations

Use MurmurHash3 for deterministic user bucketing to ensure uniform distribution and stability.

Open questions

What sampling rate should we use for evaluation telemetry to avoid overloading the event bus?

Implement core evaluation logic

Write the logic for rule matching, environment inheritance, and deterministic hash-based bucketing.

Build In-Memory Cache and Poller

Implement a background thread in the SDKs that polls the DB/Redis and refreshes a local thread-safe map of flag configs.

JSON-over-HTTP Sidecar

Create a small Go or Node.js service that exposes an /evaluate endpoint for languages/services without a native SDK.

Telemetry Integration

Add sampled event emission to the evaluation path to track variant distribution in production.

Phase 3: Admin UI

The interface for human interaction with the flag system.

Phase goal

A self-service dashboard allowing non-engineers to manage flag rollouts safely across environments.

Alternatives considered

Command-line tool only: Rejected as it doesn't meet the "Product can run rollouts" requirement.

Recommendations

Include a "Live Preview" in the rollout slider to show how many users are impacted in real-time based on recent traffic patterns.

Open questions

Do we need a 'dry-run' mode for targeting rules before saving?

Build Flag List and Search View

Standard CRUD interface for listing, filtering, and basic metadata editing of flags.

Environment Override and Rollout UI

Implement the per-environment configuration view with percentage sliders and targeting rule builders.

Audit Log Viewer

A searchable history view showing who changed what flag and when.

RBAC Integration

Connect the UI to existing auth to restrict production edits to admins and flag owners.

Database-centric storage over Repo-based config

Rationale: Requirements for real-time updates and non-engineering access mandate a dynamic storage layer. Postgres with a read-through cache provides the best balance of consistency and performance.

Repo-based config is easier to version control and review but introduces unacceptable latency for emergency "kill-switch" scenarios.

Performance regression in evaluation path

Mitigation: Strict load testing of SDK evaluation logic and mandatory p99 monitoring in production.

Inconsistent state across nodes

Mitigation: Implement a standard TTL for local caches and explore Redis Pub/Sub for immediate invalidation if polling proves too slow.

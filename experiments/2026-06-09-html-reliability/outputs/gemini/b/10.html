Feature Flag System Implementation

Implementation of a robust, low-latency feature flagging system to support dark launches, gradual rollouts, and kill-switch capabilities without requiring redeploys.

Success criteria

  • Flags can be toggled in the Admin UI and take effect across the system in under 30 seconds.
  • Evaluation latency is sub-1ms at p99 for backend SDKs.
  • Deterministic bucketing ensures a user consistently sees the same variant for a given percentage rollout.
  • Zero new external SaaS dependencies introduced.
  • Full audit trail for every flag modification in production.

Scope

In Scope:

  • Postgres-backed flag storage and schema.
  • Targeting by User ID, Organization, and Environment.
  • Boolean, Percentage, and Multivariate flag types.
  • Evaluation engine SDKs for the two primary backend languages.
  • Admin dashboard for flag management and audit history.

Out of Scope:

  • Mobile SDKs.
  • Scheduled rollouts or automated ramp-ups.
  • A/B testing statistical analysis or significance calculators.
  • Approval workflows (e.g., peer review for flag changes).

Constraints

  • Timeline: 6 weeks total for a team of 3 engineers.
  • Performance: Evaluation must not add a network hop to the request path.
  • Security: Must integrate with existing authentication and RBAC middleware.

Assumptions

The primary Postgres instance has sufficient capacity to handle the feature flag table and audit logs without impacting core application performance.

A sidecar service or local cache provider can be seamlessly integrated into existing deployment manifests.

Phase 1: Flag Schema and Storage

Establishing the source of truth and data models for the flagging system.

Phase goal

Define the database schema, implement migrations, and provide a typed library for interacting with flag configurations.

Alternatives considered

We considered a config-file-in-repo approach (GitOps style), but rejected it because the "kill-switch" requirement necessitates updates faster than a CI/CD pipeline typically allows.

Recommendations

Use a JSONB column for targeting rules to allow for flexible future rule types without frequent schema migrations.

Open questions

Should archived flags be moved to a separate table or just marked with a status flag for performance?

Database Schema Migration

Create the feature_flags and feature_flag_audit_log tables in Postgres. Include indexes on key and environment.

Data Model & Types

Define the TypeScript/Go/Python types for flags, including enums for type (BOOLEAN, ROLLOUT, MULTIVARIATE) and state.

Typed Accessor Library

Build a persistence layer library to handle CRUD operations on flags with validation logic for targeting rules.

Seed Data & Testing

Create seed scripts for common flag patterns (e.g., 'beta-testers' group, 'internal-only') to facilitate local development.

Phase 2: Evaluation Engine

Building the high-performance logic that determines which variant a user sees.

Phase goal

Deliver a sub-millisecond evaluation SDK that supports deterministic bucketing and local caching with invalidation.

Alternatives considered

A centralized evaluation service (network hop) was considered but rejected due to the sub-1ms p99 constraint.

Recommendations

Use MurmurHash3 for bucketing to ensure uniform distribution across the 0-100 range for percentage rollouts.

Open questions

Should we use Redis Pub/Sub or a simple polling mechanism for cache invalidation?

Deterministic Bucketing Logic

Implement the hashing algorithm (user_id + flag_salt) to map users to a stable 0.0-1.0 float.

In-Memory Cache & Synchronizer

Implement a background thread/routine that polls the DB (or listens to a stream) to keep the local flag set warm.

Backend SDK Implementation

Create the evaluate(key, context) interface for the primary backend languages, ensuring thread safety.

Telemetry Emitter

Add sampled event emission (e.g., 1% of evaluations) to the SDK to track flag usage and distribution.

Phase 3: Admin UI

The control plane for managing flags across environments.

Phase goal

Provide a user-friendly dashboard for product and engineering to safely manage flags and view history.

Alternatives considered

Considered adding flags to existing internal admin tools, but decided a dedicated UI is cleaner for the complex rollout sliders and audit views.

Recommendations

Include a "Live Preview" in the rollout slider that shows how many users in the current environment would be affected by a specific percentage.

Open questions

Do we need a search-by-owner feature immediately, or is simple key search sufficient for launch?

Flag Management Dashboard

Build the list and detail views for creating and editing flags using existing UI components.

Rollout Slider & Rules Editor

Implement the complex UI for percentage rollouts and targeting rule blocks (AND/OR logic).

Audit History View

Create a timeline view showing who changed what flag value and when.

RBAC Integration

Wire the Admin UI into existing auth middleware; restrict production write access to owners and admins.

Postgres over Config Files

Rationale: The requirement for immediate kill-switch capability and UI-based management for non-engineers makes a database-backed system superior to Git-based config, despite the slightly higher complexity.

Config files offer easier version control and change reviews via PRs, but are too slow for emergency toggles.

Stale Cache on Evaluation Nodes

If the invalidation mechanism fails, nodes might evaluate flags based on old data, leading to inconsistent user experiences during rollouts.

Database Single Point of Failure

If the feature_flags table becomes unavailable, the SDK must fail-open or fail-closed gracefully without crashing the host application.

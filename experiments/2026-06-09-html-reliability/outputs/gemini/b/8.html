Feature Flag System Implementation

Implement a robust, low-latency feature-flag system to enable dark launches, gradual rollouts, and kill-switches without redeploys. This system includes a unified schema, high-performance evaluation engine, and a secure admin UI.

Success criteria

  • Flags can be toggled in production without code deployment or restart.
  • Flag evaluation adds < 1ms at p99 to request latency.
  • Deterministic rollout: the same user gets the same variant for a specific flag version and rollout percentage.
  • Audit trail captures every change to flag configuration (who, what, when).
  • Admin UI provides clear visibility into flag states across different environments.

Scope

  • In Scope: Postgres-backed flag storage, Redis/In-memory caching, evaluation SDKs for two backend languages, HTTP/JSON endpoint, Admin Dashboard, targeting rules (user/org/env), audit history.
  • Out of Scope: Third-party SaaS (LaunchDarkly, etc.), A/B testing statistical analysis, scheduled rollouts, mobile-specific SDKs, complex approval workflows.

Constraints

  • No new external SaaS dependencies.
  • Evaluation must not add a network hop to the primary request handling path.
  • Must integrate with existing internal authentication middleware.
  • Timeline: ~6 weeks with a team of 3 engineers.

Assumptions

Existing auth middleware provides sufficient user and organization context for targeting rules in the evaluation path.

A standard hashing algorithm (e.g., MurmurHash3) is available in both backend languages to ensure cross-language bucketing consistency.

Phase 1: Flag Schema and Storage

Establish the source of truth for flag configurations and the data access layer.

Phase goal

Define a flexible flag schema in Postgres, implement audit logging, and provide a typed accessor library for management operations.

Alternatives considered

We considered a config-file-in-repo approach to simplify deployments, but rejected it because it requires a deploy/restart to change flags, which violates the "kill-switch without deploy" requirement.

Recommendations

Use a single JSONB column for targeting rules to allow for future flexibility without frequent schema migrations.

Should we enforce a naming convention for flag keys (e.g., prefixing by team or service)?

Database Schema Migration

Create the feature_flags and flag_audit_log tables in Postgres. Include fields for key, type, targeting rules, and lifecycle state.

Data Access Layer

Implement the flag repository with methods for CRUD operations and automated audit log entry creation within the same transaction.

Management SDK

Create a typed library for defining and reading flag configurations, to be used initially by seed scripts and later by the Admin UI.

Phase 2: Evaluation Engine

Build the high-performance logic that decides which variant a user sees.

Phase goal

Deliver deterministic, low-latency flag evaluation via in-memory caching and language-specific SDKs.

Alternatives considered

Considered a centralized evaluation service but decided on SDK-level evaluation with local caching to meet the <1ms p99 latency constraint by avoiding network hops.

Recommendations

Use a "Poll with long-polling or Pub/Sub" model for cache invalidation to keep flag updates near-instant across the fleet.

What sampling rate should we start with for evaluation telemetry to avoid overloading the analytics pipeline?

Deterministic Bucketing Engine

Implement hashing logic (Hash of userID + flagSalt) to map users to percentage buckets (0-9999).

Local Cache & Synchronizer

Implement in-memory storage for flags with a background thread that polls Postgres or listens to Redis Pub/Sub for updates.

Backend SDKs (Language A & B)

Implement evaluate(key, context) in both primary languages. Ensure context includes user and org IDs.

Evaluation Sidecar/HTTP API

Provide a JSON-over-HTTP endpoint for non-monorepo services to query flag states, using the same in-memory cache.

Phase 3: Admin UI

Create the dashboard for product and engineering to manage the system.

Phase goal

Provide a user-friendly interface for flag lifecycle management and environment-specific overrides.

Alternatives considered

Considered adding complex multi-stage approvals, but decided on simple "Flag Owner" based permissions to maintain shipping velocity for the MVP.

Recommendations

Include a "Live Preview" in the percentage slider to show how many active users (based on sampled telemetry) might be affected by a change.

How do we visually distinguish between 'Staging' and 'Production' to prevent accidental changes?

Flag Management Dashboard

Build the main list view with search, filtering by owner, and lifecycle state toggles.

Rollout Editor

Implement the targeting rule editor and the percentage rollout slider with bucketing visualization.

Audit Log Viewer

Create a view to inspect history of changes for a specific flag, showing diffs and the actor responsible.

Postgres over Config Files

Rationale: To support real-time kill-switches and percentage updates without redeploying services. The risk of Postgres availability is mitigated by the local in-memory cache in the SDKs.

Config files would be simpler to version control but fail the requirement for instant runtime updates.

Cache Invalidation Latency

If the signal to update the local cache is delayed, different nodes may serve different variants briefly. Mitigation: Implement short TTLs on local caches and use Redis Pub/Sub for immediate invalidation.

Database Load

If all nodes poll Postgres simultaneously on startup, it could spike DB load. Mitigation: Use jitter in polling intervals and leverage a read-replica for flag fetches.

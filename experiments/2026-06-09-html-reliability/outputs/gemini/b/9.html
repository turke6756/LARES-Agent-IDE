Feature Flag System

Implementation of a robust, low-latency feature flagging system to support dark launches, gradual rollouts, and instant kill-switches across the monorepo services.

Success criteria

  • Engineering can deploy code with features disabled (dark launch).
  • Product can increase rollout percentage from 0% to 100% without code changes.
  • Support can disable a feature globally in production in under 10 seconds.
  • Evaluation adds less than 1ms overhead to request processing at p99.
  • Deterministic bucketing ensures users see consistent variants.

Scope

  • In-scope: Postgres schema, read-through cache, evaluation SDKs (Node.js/Go), JSON-over-HTTP evaluation endpoint, Admin UI for flag management, audit history, targeting by User/Org/Env.
  • Out-of-scope: A/B testing statistical analysis, scheduled rollouts (auto-enable at time T), mobile SDKs, approval workflows.

Constraints

  • No new external SaaS dependencies (e.g., LaunchDarkly).
  • Evaluation path must not add a network hop to the primary request flow (local cache required).
  • Must integrate with existing authentication middleware.
  • Timeline: 6 weeks with 3 engineers.

Assumptions

Existing request context objects in all services contain consistent userId and orgId fields for targeting.

A Redis-based pub/sub or a lightweight polling mechanism is sufficient for cache invalidation across the cluster.

Phase 1: Flag schema and storage

Establishing the source of truth for flag definitions and the underlying persistence layer.

Phase goal

Define the Postgres schema and provide a typed accessor library for managing flag state with full audit history.

Alternatives considered

Considered a config-file-in-repo approach (GitOps). While safer for deployment, it fails the "kill switch without a deploy" requirement. DB storage with a read-cache was chosen for runtime agility.

Recommendations

Use a JSONB column for targeting rules to allow flexible expansion without frequent schema migrations.

Open questions

Should we support global flags that ignore environment inheritance?

Postgres Schema Migration

Create feature_flags and flag_audit_log tables. Include fields for key, description, type, targeting rules, and lifecycle state.

Backend Persistence Library

Implement a CRUD library for flags with validation logic for targeting rules and types.

Audit Log Middleware

Ensure every write operation to the flags table captures the user identity and previous/new state in the audit log.

Typed Accessor Generation

Create a script to generate TypeScript/Go types from flag definitions to prevent typo-based bugs in application code.

Phase 2: Evaluation engine

The high-performance core that decides which variant a user sees.

Phase goal

Deliver a sub-millisecond evaluation library that supports deterministic percentage rollouts and environment inheritance.

Alternatives considered

Sidecar service vs. Library. A sidecar adds a network hop (localhost) which might hit the 1ms p99 budget. We will prioritize an in-process library with local cache, providing a sidecar only for non-monorepo languages.

Recommendations

Use MurmurHash3 for deterministic bucketing to ensure uniform distribution across the 0-100 range.

Open questions

What sampling rate should we use for evaluation telemetry to avoid flooding the event bus?

Deterministic Bucketing Logic

Implement hashing logic: hash(userId + flagSalt) % 100. Verify uniform distribution with a unit test suite.

Local In-Memory Cache

Implement a thread-safe cache in the SDK that periodically polls Postgres or listens for invalidation events via Redis.

Rule Evaluation Engine

Implement logic for targeting rules (e.g., "if user.email ends with @company.com"). Support rule ordering and environment-level overrides.

Telemetry Integration

Emit a sampled event on every evaluate() call containing the flag key, variant, and context summary for analysis.

Phase 3: Admin UI

The control plane for product and engineering to manage feature state.

Phase goal

Provide a secure, intuitive dashboard for managing flags, visualizing rollouts, and auditing changes.

Alternatives considered

Considered building into the existing internal admin tool. Decided on a standalone page within the main app behind admin-role gates to leverage existing UI components.

Recommendations

Include a "Live Preview" feature that shows which users fall into which bucket based on a sample set of IDs.

Open questions

Do we need to support "dry run" mode where a flag change is staged but not applied until a second confirmation?

Flag Management Dashboard

Build the list and detail views for flags. Support searching by key, owner, and state (active/archived).

Rollout Slider Component

Implement a visual slider for percentage rollouts with immediate feedback on targeting logic.

Environment Override RBAC

Implement strict access controls: only flag owners or system admins can modify production values; anyone can edit staging.

Audit History View

Create a timeline view for each flag showing who changed what, when, and in which environment.

Postgres + Redis Cache over GitOps

Rationale: We require "instant kill" capability which GitOps (config-in-repo) cannot provide due to deployment pipeline lag. Redis pub/sub will ensure sub-second propagation of state changes.

GitOps provides better history via Git and naturally aligns with existing deployment workflows.

Stale Cache on App Nodes

If the invalidation signal is missed, different nodes might evaluate the same flag differently. Mitigation: Implement a fallback polling mechanism every 60 seconds.

Performance regression in Hot Path

If targeting rules become complex (deep JSON nesting), evaluation might exceed 1ms. Mitigation: Benchmark with 100+ rules and optimize the rule engine (e.g., pre-compiling rules).

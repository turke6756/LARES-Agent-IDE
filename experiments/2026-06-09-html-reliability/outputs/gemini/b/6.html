Feature Flag System Implementation

Implementation of a robust, low-latency feature flagging system supporting dark launches, gradual rollouts, and kill-switches. This system includes a Postgres-backed schema, a sub-millisecond evaluation engine, and a management dashboard.

Success criteria

  • Flag evaluation latency is under 1ms at p99 for backend SDKs.
  • Zero network hops added to the critical request path for flag evaluation.
  • Engineers can perform a 10% rollout of a new feature via the Admin UI without a code deploy.
  • Full audit trail exists for every change made to a flag configuration.
  • Support staff can disable a misbehaving feature globally in under 10 seconds.

Scope

In Scope: Postgres schema design, audit logging, deterministic bucketing for rollouts, backend SDKs (2 languages), JSON-over-HTTP sidecar/endpoint, and an Admin UI for lifecycle management.

Out of Scope: Mobile SDKs, automated A/B testing statistical analysis, scheduled rollouts, and multi-step approval workflows.

Constraints

  • No new external SaaS dependencies (e.g., LaunchDarkly, Statsig).
  • Must integrate with existing internal authentication and authorization middleware.
  • Execution timeframe: 6 weeks with a team of 3 engineers.
  • Evaluation path must avoid additional network hops during request handling.

Assumptions

We assume the primary Postgres instance and an accompanying Redis cache are sufficient for storage and rapid invalidation propagation.

We assume the core evaluation logic (hashing and rule matching) can be implemented consistently across the two primary backend languages in the monorepo.

Phase 1: Flag Schema and Storage

This phase focuses on the source of truth for feature flags. We will define the data model and implement the persistence layer including audit capabilities.

Phase goal

A stable Postgres schema for flag definitions and audit logs, supported by a typed accessor library for management operations.

Alternatives considered

Config-file-in-repo: Rejected because it requires a deployment for every flag change, which violates the requirement for support to "kill" features without a deploy.

Recommendations

Use a JSONB column in Postgres for targeting rules to allow flexibility in rule types without frequent schema migrations.

Open questions

Should we support flag dependencies (e.g., Flag B only active if Flag A is true)?

Database Schema Migration

Create the feature_flags table and flag_audit_log table. Include columns for key, type, owner, targeting rules (JSONB), and lifecycle state.

Typed Accessor Library (DAL)

Implement the Data Access Layer to handle CRUD operations for flags, ensuring every write triggers an entry in the audit log.

Seed Data and Testing

Create seed scripts for representative flag types (boolean, 10% rollout) and unit tests for the DAL.

Phase 2: Evaluation Engine

Implementation of the high-performance logic that determines which variant a user should see based on the flag rules and context.

Phase goal

A low-latency SDK and sidecar capable of deterministic flag evaluation with local caching and efficient invalidation.

Alternatives considered

Short-lived TTL polling: Considered for simplicity, but rejected in favor of Redis Pub/Sub invalidation to meet the "under 10 seconds" kill-switch requirement.

Recommendations

Use MurmurHash3 for deterministic bucketing to ensure consistent user experience across different services.

Open questions

What sampling rate should we use for evaluation telemetry to avoid overloading the analytics pipeline?

Deterministic Bucketing Implementation

Implement hashing logic: hash(user_id + flag_salt) % 100. Port this logic to both backend languages.

Local In-Memory Cache with Invalidation

Develop the local cache layer that subscribes to Redis Pub/Sub for immediate invalidation when flags are updated in the DB.

JSON-over-HTTP Sidecar

Provide a lightweight HTTP endpoint for services not using the native SDKs, ensuring it uses the same local cache logic.

Evaluation Telemetry

Instrument the evaluation call to emit sampled events containing flag key, user ID, and the result variant.

Phase 3: Admin UI

Building the user interface for product and engineering teams to manage flag lifecycles and targeting rules.

Phase goal

A functional dashboard for creating, editing, and monitoring feature flags across environments.

Alternatives considered

CLI-only management: Rejected as it creates a barrier for Product and Support teams who need to use the system.

Recommendations

Implement a "Draft/Preview" mode for percentage rollouts so users can see the estimated impact before saving.

Open questions

Should we allow bulk-archiving of stale flags?

Flag List and Search View

Build the main dashboard listing all flags with search, filtering by owner, and status indicators.

Flag Editor and Percentage Slider

Create the edit form including targeting rule builders and a visual slider for percentage rollouts.

Audit History View

A dedicated tab in the flag details page showing the chronological log of all changes and who made them.

RBAC Integration

Apply existing auth middleware to ensure only authorized users can modify flags, especially in the production environment.

Centralized Postgres with Local Caching

Rationale: Using Postgres as the source of truth ensures consistency and leverages existing backup/security infra. Local in-memory caching in the SDKs satisfies the 1ms latency requirement without adding network hops.

Cache Invalidation Race Conditions

If the Redis Pub/Sub message is lost, local caches may become stale. Mitigation: Implement a fallback periodic poll (e.g., every 60s) to resync the full state from Postgres.

Database Load during Cold Start

If many service instances restart simultaneously, they may overwhelm Postgres fetching flag configurations. Mitigation: Implement a staggered start or use the sidecar as a read-through proxy.

Feature Flag System

Introduce a robust, highly-performant feature flag system allowing engineering to ship code dark, product to run gradual rollouts, and support to kill misbehaving features without deployments.

Success criteria

  • Flags can be evaluated locally in memory in under 1 millisecond at p99.
  • Support can toggle a kill-switch for a feature in production and have it propagate globally within seconds, without triggering a deploy.
  • Product managers can adjust percentage rollouts deterministically with predictable user bucketing.

Scope

In scope: Postgres table schema, read-through cache, audit history, deterministic bucketing evaluation engine, two backend SDKs, a JSON HTTP endpoint, and an internal Admin UI with RBAC.

Out of scope: A/B-test statistical analysis, scheduled rollouts, mobile SDKs, and full multi-step approval workflows.

Constraints

  • No new external SaaS dependencies.
  • The evaluation path must not add a network hop to request handling (must use local in-memory state).
  • Must integrate behind existing authentication middleware.
  • Team of three engineers, budget of roughly six weeks.

Assumptions

The primary Postgres database can comfortably handle the read-through caching and polling/push invalidation overhead for flag state changes.

The existing authentication middleware provides user role claims that we can directly extract to enforce flag ownership and Admin UI RBAC.

Phase 1: Flag schema and storage

Define the core flag data model and setup persistence in the primary database. Includes migrations, basic accessor layers, and historical audit tracking.

Phase goal

Deliver the canonical data model in Postgres with typed accessors and an audit history table, establishing the foundation for flag state.

Alternatives considered

We heavily considered a config-file-in-repo approach (GitOps). However, we chose a Postgres-backed runtime approach to ensure support can kill misbehaving features in seconds without waiting for a CI/CD pipeline to process a repository change.

Recommendations

Implement an event-sourced audit table (`feature_flag_events`) rather than just storing the "last updated" state, to allow point-in-time debugging of flag rules.

Open questions

Should we utilize Postgres LISTEN/NOTIFY for propagating cache invalidation events to application nodes, or a separate pub/sub mechanism?

Phase 2: Evaluation engine

Build a lightning-fast library that resolves flag rules locally in memory, keeping its cache fresh via background synchronization.

Phase goal

Provide sub-millisecond `evaluate(flagKey, context)` capabilities via an in-memory cache synchronized with the database, exposed across our backend environments.

Alternatives considered

Considered calling a centralized evaluation sidecar via gRPC, but decided against it to strictly adhere to the no-network-hop constraint, opting instead for embedded SDK evaluators with synchronized state.

Recommendations

Use MurmurHash3 for generating deterministic hashes of the `userID + flagSalt` to map users predictably into the 0-100 buckets for percentage rollouts.

Open questions

What is the optimal sampling rate for telemetry events to ensure we get useful diagnostic data without overwhelming our analytics pipeline?

Postgres table over configuration files

Rationale: We opted for a database-backed store for feature flags over keeping them as JSON files in the repository. The need for customer support to instantly toggle a kill switch in the event of a severe bug outweighs the version-control benefits of GitOps.

GitOps provides better out-of-the-box code reviews and history tracking without needing custom audit tables.

Memory bloat in SDK instances

As the number of stale flags grows over time, the embedded in-memory caches could cause container memory pressure. Mitigation: Introduce rigorous archiving mechanisms and hard caps on the total number of active flags transmitted.

Telemetry swamping network capacity

Emitting an event for every evaluation might overwhelm node network capacities. Mitigation: Enforce aggressive, configurable sampling algorithms in the SDK before events are ever serialized.

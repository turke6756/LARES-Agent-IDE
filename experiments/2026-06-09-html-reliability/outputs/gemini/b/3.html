Feature Flag System Design

A resilient, low-latency feature flagging infrastructure to support dark launches, gradual rollouts, and kill-switches across the monorepo, without external SaaS dependencies.

Success criteria

  • Evaluation latency under 1ms at p99 for backend SDKs.
  • 100% deterministic bucketing for user-based rollouts.
  • Full audit trail for all configuration changes.
  • Zero additional network hops required during request-time flag evaluation.

Scope

In Scope: Flag schema (Postgres), evaluation library with in-memory caching, SDKs for primary backend languages, sidecar for HTTP access, and an Admin UI for management.

Out of Scope: A/B testing statistical analysis, scheduled automated rollouts, and native mobile SDKs.

Constraints

  • Timeline: 6 weeks with a 3-engineer pod.
  • Infrastructure: No new external SaaS; must use existing Postgres/Redis/Auth.
  • Performance: Evaluation must not block the main request path significantly.

Assumptions

Primary Postgres instance can handle the additional write load for flag updates and audit logs without impacting core application performance.

The existing Redis infrastructure supports a pub/sub or polling mechanism sufficient for sub-second cache invalidation across services.

Phase 1: Flag Schema and Storage

Establish the source of truth for flag configurations and the persistence layer.

Phase goal

Define and deploy the Postgres schema for flags and audit logs, along with a typed library for direct database access.

Alternatives considered

Config-in-repo (YAML/JSON): Rejected because it requires a full CI/CD cycle for "kill-switch" scenarios, failing the "no-deploy" requirement.

Recommendations

Use Postgres JSONB for targeting rules to allow flexible expansion of attributes (e.g., browser, region) without schema migrations.

Open questions

Should we support flag archiving or hard deletion? Archiving is safer for audit but requires more complex UI filtering.

Database Schema Migration

Create feature_flags and flag_audit_logs tables. Include columns for key, type, targeting rules, and metadata.

Typed Flag Model

Define the Flag entity in the shared types library, including enums for FlagType (boolean, percentage, multivariate).

Audit Log Trigger

Implement database-level triggers or application-level middleware to capture every change to the flags table.

Phase 2: Evaluation Engine

The core logic that determines which variant a user sees based on context and rules.

Phase goal

Deliver a high-performance evaluation library that supports deterministic hashing, rule ordering, and local caching.

Alternatives considered

Centralized Evaluation Service: Rejected because it adds a network hop to every evaluation, violating the p99 latency constraint.

Recommendations

Use MurmurHash3 for deterministic bucketing to ensure uniform distribution across rollouts.

Open questions

What sampling rate should we use for telemetry to balance observability with performance and storage costs?

Core Evaluation Logic

Implement rule engine: target by user ID, org ID, and environment. Support default fallbacks.

Deterministic Bucketing

Implement percentage rollout logic using hash(userID + salt) % 100.

In-Memory Cache Sync

Implement a background poller or Redis Pub/Sub listener to refresh local cache when flag state changes.

HTTP Sidecar / SDKs

Expose the evaluation engine via a JSON-over-HTTP endpoint for non-monorepo services and wrap it in typed SDKs.

Phase 3: Admin UI

The interface for managing flags without engineering intervention.

Phase goal

A functional dashboard for creating and managing flags with environment-specific overrides and safety controls.

Alternatives considered

CLI-only management: Rejected because Product and Support teams need a visual, discoverable way to toggle features.

Recommendations

Include a "Live Preview" in the percentage rollout slider that shows which buckets (0-99) are currently active.

Open questions

How do we strictly enforce RBAC for production changes while allowing developers to experiment in staging?

Flag List and Search

Build the main dashboard view for discovering and filtering flags by owner and environment.

Flag Configuration Editor

Implement forms for basic flag metadata and targeting rules (JSON editor or builder).

Percentage Rollout Slider

Visual UI component to adjust rollout percentages with real-time feedback.

Audit View

Display the history of changes for a specific flag, showing who changed what and when.

Postgres-First Storage

Rationale: Using the primary Postgres ensures ACID compliance for flag updates and simplifies the stack. It avoids the deployment overhead of a config-in-repo approach while meeting the "no external SaaS" constraint.

Adds load to the primary DB and requires a caching strategy to meet latency goals.

Stale Cache Outage

If the invalidation signal is missed, different service instances might evaluate the same flag differently, causing inconsistent UX or data corruption.

Mitigation: Implement a mandatory TTL on local caches and a health-check comparison between local state and DB state.

Accidental Production Kill-Switch

Without an approval workflow, a user could accidentally disable a critical production feature.

Mitigation: Strict RBAC ensuring only owners/admins can edit production values, and mandatory confirmation modals for broad rollouts.

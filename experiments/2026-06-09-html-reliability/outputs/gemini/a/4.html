Feature Flag System Deployment

Implementation of a comprehensive feature-flag system enabling engineering to deploy dark code, product to execute gradual rollouts, and support to disable misbehaving features without requiring a full code deployment.

Success Criteria

  • Evaluation engine resolves flags in under 1ms at p99 with no external network hops.
  • Support staff can toggle a flag to an inactive state in the Admin UI and have it take effect globally within seconds.
  • Rollout bucketing is fully deterministic given a user ID.
  • All changes to flag states are audited and trackable.

Scope

In Scope:

  • Flag schema modeling (boolean, percentage, multivariate, targeting rules, environments, lifecycle state).
  • Postgres storage with read-through caching.
  • Evaluation engine SDKs for the two backend languages and a JSON-over-HTTP endpoint.
  • Telemetry emission for evaluation sampling.
  • Admin UI dashboard for CRUD, overrides, rollout previews, and audit history.
  • Role-based access (RBAC) integrated with existing auth middleware.

Out of Scope:

  • A/B test statistical analysis.
  • Scheduled rollouts based on time.
  • Mobile SDKs.
  • Multi-step approval workflows.

Constraints

  • Zero new external SaaS dependencies.
  • Evaluation path must not add a network hop to request handling.
  • Must integrate natively behind the existing auth middleware.
  • Resource limit: 3 engineers for roughly 6 weeks.

Assumptions

Context Data Availability

We assume that all application layers where feature flags will be evaluated currently receive standard request context objects injected by the auth middleware, guaranteeing access to targetable attributes like user ID and organization ID.

Cache Invalidation Latency Acceptability

We assume that a short cache-sync propagation delay (e.g., polling every 10-30 seconds or asynchronous push) is acceptable for flag updates, including emergency kill-switches.

Phase 1 — Flag Schema and Storage

Design and deploy the foundational data model, database migrations, and basic programmatic access layer for the feature flags.

Phase Goal

Provide a robust, versioned data store in Postgres to hold flag definitions, targeting rules, and audit trails that can seamlessly sync to an in-memory cache.

Alternatives Considered

We evaluated a config-file-in-repo approach (GitOps style) but rejected it. While it provides excellent versioning out of the box, it violates the requirement that non-engineering support staff must be able to kill a misbehaving feature without triggering a deployment pipeline.

Recommendations

Utilize the primary Postgres instance to create a new `feature_flags` table storing a JSONB payload for rules/environments, accompanied by a `feature_flags_audit` table. This approach satisfies the centralized source-of-truth requirement while keeping infrastructure complexity low.

Open Questions

Audit Table Structure

Should the audit history table store entire JSON snapshots of the flag per revision, or just the structural diffs representing the specific modification?

Database Migrations

Write and test database migration scripts to provision the `feature_flags` and `feature_flags_audit` tables, ensuring appropriate indices are placed on flag keys and lifecycle states.

Typed Accessor Library

Develop a robust, typed database accessor library to handle CRUD operations on flags, including enforcing environment inheritance (e.g., falling back to production values if staging isn't explicitly overridden).

Audit Logging Hook

Implement the application logic wrapper that ensures any mutation to a feature flag record automatically writes a corresponding row to the audit table capturing the actor, timestamp, and before/after states.

Seed Data Scripts

Create seed data scripts providing a standard set of active, archived, and percentage-rollout flags for local development and CI test suites.

Phase 2 — Evaluation Engine

Construct the highly performant runtime component responsible for deciding which variant a specific execution context receives.

Phase Goal

Deliver an evaluation mechanism capable of sub-millisecond p99 resolution via local caching, supporting deterministic bucketing and reliable telemetry.

Alternatives Considered

We considered deploying a separate centralized gRPC service for evaluation, but this would introduce a network hop violating the primary latency constraint. Local evaluation using an SDK pulling rules into memory is mandatory.

Recommendations

Implement a memory-resident evaluation core distributed as an SDK. The SDK will maintain a background worker that polls the Postgres configuration every 15 seconds. For non-backend services, provide a lightweight sidecar JSON HTTP wrapper around this core.

Open Questions

Cache Sync Mechanism

Can we rely entirely on background polling, or should we implement Postgres LISTEN/NOTIFY for immediate push-based cache invalidation when a flag is killed?

Deterministic Bucketing Algorithm

Implement MurmurHash3 against the combination of `userID` + `flagKey` (serving as the salt) modulo 100 to consistently assign contexts to rollout buckets.

In-Memory Cache & Invalidation

Build the background synchronization thread that fetches updated flag configurations from Postgres and atomically swaps the local rule cache without blocking concurrent reads.

Monorepo Backend SDKs

Package the evaluation core into idiomatic SDKs for the two primary backend languages, exposing an `evaluate(flagKey, context)` interface.

JSON-over-HTTP Endpoint

Construct a lightweight HTTP server bridging the local evaluation SDK, intended for usage by internal auxiliary services that cannot run the native SDKs.

Evaluation Telemetry

Integrate an asynchronous telemetry buffer inside the SDKs to emit sampled evaluation events (e.g., 1% sample rate) to the metrics pipeline for later coverage analysis.

Phase 3 — Admin UI

Develop the internal management interface allowing product, engineering, and support teams to control the system securely.

Phase Goal

Create a secure, intuitive dashboard for managing feature flag lifecycles, rollout configurations, and exploring historical changes.

Alternatives Considered

Building a completely independent React application was weighed against integrating into our existing internal admin dashboard. We opted to integrate into the existing dashboard to inherit auth, RBAC, and standard UI components seamlessly.

Recommendations

Utilize the existing admin UI framework. Focus heavily on providing a "live preview" of the bucketing algorithm to give product managers confidence when sliding percentage rollouts.

Open Questions

Bucketing Visualization

How do we effectively visualize the deterministic bucketing preview? Should we allow users to input a comma-separated list of test user IDs to see which variant they map to in real-time?

Flag Dashboard and Search

Implement the primary index view listing all flags, with robust filtering by state (active/archived), owner, and name.

Flag Editor & Environments

Build the complex form allowing users to define flag rules, set default variants, and establish environment-specific overrides (e.g., Production vs. Staging).

Percentage Rollout Slider & Preview

Create the interactive slider component for percentage distributions, accompanied by a live preview widget demonstrating the deterministic distribution mapping.

Audit History View

Integrate a timeline or table view fetching from the `feature_flags_audit` table, showing exactly who changed what values and when.

RBAC Enforcement

Hook the UI and API endpoints into the existing authorization middleware, ensuring only flag owners or system administrators can mutate flag states within the Production environment.

Use Postgres instead of Config-in-Repo

Decided to store all flag schemas and states in the primary database rather than static files. This enables immediate support intervention without waiting for CI/CD pipelines, lowering MTTR for misbehaving code.

Config-in-repo would inherently provide a perfect Git-backed audit log, code reviews for flag changes, and simpler integration with existing developer workflows.

Cache Synchronization Lag

If the background polling mechanism in the SDKs fails or backs off too aggressively, different application instances may evaluate the same flag differently, leading to an inconsistent user experience.

Telemetry Volume Flood

Feature flags are checked constantly. Even with sampling, emitting telemetry events for evaluations might overwhelm the internal metrics pipeline or drastically increase storage costs if not throttled correctly.

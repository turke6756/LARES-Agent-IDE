Feature Flag System

A full-stack feature-flag system enabling dark shipping, gradual rollouts, and kill switches, comprising a Postgres-backed schema, a sub-millisecond evaluation engine, and a secure internal Admin UI.

Success Criteria

The feature flag evaluation engine must respond in under a millisecond at p99 without introducing any extra network hops to the core request handling path. The admin interface must allow product and support personnel to efficiently search, edit, and safely archive feature flags via role-based access controls. The system must natively support the two backend monorepo languages, plus JSON-over-HTTP fallback for other services.

Scope

In scope: A robust Postgres schema mapping keys, rules, environments, and owners. An in-memory evaluation engine employing deterministic hashing for rollouts and caching. Two native backend SDKs and one JSON-over-HTTP endpoint. A telemetry sampler for evaluation events. A UI dashboard for flag CRUD operations, live bucketing previews, environment overrides, and audit log history tracking.

Out of scope: Advanced A/B testing analytics and stats, scheduled or time-based rollouts, mobile application SDKs, and full multi-stage approval workflows.

Constraints

We cannot introduce any new external SaaS dependencies. The flag evaluation process must add zero network hops. The admin dashboard must be deployed behind our existing authentication middleware. Delivery is strictly bounded to a three-engineer team across a six-week timeline.

Assumptions

The primary Postgres database can comfortably handle the read loads as long as our read-through cache operates effectively in normal states.

Providing native SDKs for the two primary monorepo languages covers all latency-sensitive core evaluation paths.

Phase 1 — Flag Schema and Storage

Design and implement the core feature flag data model, lifecycle schemas, and foundational data access layer.

Phase Goal

Establish a versioned, scalable Postgres schema to safely store flags, targeting rules, environments, and audit histories, supported by a typed accessor library and read-through caching.

Alternatives Considered

A config-file-in-repo pattern was evaluated but discarded. While highly auditable, it mandates a full CI/CD deployment to trigger a kill switch, which fails the requirement for rapid support intervention.

Recommendations

Utilize a new `feature_flags` table in the primary Postgres instance. Model the targeting rules as a robust JSONB column to afford future flexibility if new targeting dimensions emerge. Use Postgres triggers or strict application-level wrappers to guarantee audit history consistency.

Open Questions

Should we partition the audit history table immediately, or will standard indexing suffice for the expected volume of flag changes over the next two years?

Design Data Model & Migrations

Write and test database migrations for the new tables: `feature_flags`, `environments`, `flag_targeting_rules`, and `audit_log`.

Build Typed Accessor Library

Develop the data access logic for CRUD operations, ensuring strict typing for targeting configurations (user ID, org, environment).

Implement Read-Through Cache Layer

Create a read-through cache mechanism over the accessor library to mitigate direct load on the Postgres database.

Implement Audit Logging

Wire up hooks within the accessor library so that every state change or rule update inherently writes a record to the audit table.

Phase 2 — Evaluation Engine

Build the highly optimized, in-memory evaluation machinery for zero-network-hop feature flagging.

Phase Goal

Deliver the two native backend SDKs and the JSON-over-HTTP fallback endpoint capable of reliably answering `evaluate(flagKey, context)` in <1ms p99 via local caching and deterministic hashing.

Alternatives Considered

Creating a standalone centralized evaluation microservice was firmly rejected. Any network hop inherently breaches the strict sub-millisecond p99 latency constraint mandated by the brief.

Recommendations

Employ MurmurHash3 for bucketing due to its speed and excellent uniform distribution properties. Implement environment inheritance such that staging configurations dynamically fall back to production values unless explicitly overridden.

Open Questions

What is the optimal short-polling interval for the local cache invalidation story to balance database load against kill-switch responsiveness?

Develop Deterministic Bucketing

Implement the core hashing algorithm (hash of user ID + flag salt) and bucketing logic to handle reliable percentage-based rollouts.

Build In-Memory Cache & Invalidation

Develop the local cache module inside the evaluation library, including the polling mechanism for fetching updates from the central repository.

Develop Primary Native SDK

Package the evaluation rules engine and cache into an idiomatic library for the primary backend language.

Develop Secondary Native SDK

Replicate the evaluation engine architecture as an idiomatic library for the secondary backend language.

Implement HTTP Fallback Endpoint

Wrap the evaluation engine inside a high-throughput JSON-over-HTTP sidecar/service to support miscellaneous internal clients.

Add Telemetry Sampling

Introduce a non-blocking sampling emitter that logs evaluation outcomes asynchronously for future diagnostics and analysis.

Phase 3 — Admin UI

Construct the internal web dashboard to provide intuitive, secure management of flags and rollouts.

Phase Goal

Deliver a role-secured web interface empowering non-engineers to manage flag lifecycles, configure complex targeting rules, and visualize percentage rollout distributions.

Alternatives Considered

Managing flags purely via internal CLI tools was deemed insufficient as it imposes an engineering barrier on product and support teams needing to operate rapid kill switches.

Recommendations

Leverage the existing internal UI component library to build the dashboard quickly. Mount the entire UI application behind the current enterprise authentication proxy to fulfill the auth middleware constraint effortlessly.

Open Questions

Should the live preview of the percentage rollout use randomly generated mock user IDs or allow manual input of specific IDs for debugging?

Implement Management API

Create the backing REST API endpoints that the Admin UI will consume to perform CRUD and audit log retrieval.

Enforce RBAC Policies

Integrate role checks ensuring only explicitly assigned flag owners and global admins can modify production environment values.

Build Dashboard List View

Develop the frontend view mapping all active and archived flags, complete with search and owner filtering.

Build Flag Detail & Rollout Slider

Create the flag editing interface containing environment specific tabs and the interactive percentage rollout slider with bucketing preview.

Integrate Audit History UI

Add a dedicated audit log panel within the flag detail page displaying all historical mutations and status changes.

We will construct our own Postgres-backed schema rather than integrating an external vendor tool to manage flag state.

Integrating a SaaS solution violates the strict constraint against new external dependencies and introduces unacceptable risks to our p99 latency guarantees.

We will handle environment overrides via inheritance, explicitly defaulting non-production environments to match production configurations unless deliberately overridden in the UI.

Local in-memory cache invalidation delays might lead to brief windows of inconsistent evaluation across clustered application nodes immediately following a kill-switch toggle.

A poorly chosen flag salt strategy might cause hashing collisions, inadvertently bucketing the same users into experiments consistently instead of providing uniform pseudo-random distributions.

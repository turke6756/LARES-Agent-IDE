Feature Flag System Implementation

A comprehensive system to enable dark launches, gradual rollouts, and kill-switch capabilities across the monorepo, providing a low-latency evaluation engine and a centralized management dashboard.

Success Criteria

  • Evaluation latency (p99) is under 1ms for backend services.
  • Zero additional network hops required for the evaluation path in production.
  • Product and Support can toggle features without engineering intervention or deployments.
  • Targeting rules support user ID, organization, and environment-level overrides.
  • Audit trail exists for all configuration changes in production.

Scope

  • Phase 1: Postgres schema, audit logging, and a typed SDK for flag retrieval.
  • Phase 2: Deterministic evaluation engine with local caching and invalidation logic.
  • Phase 3: Admin dashboard for flag management and environment-specific overrides.

Constraints

  • No new external SaaS dependencies (e.g., LaunchDarkly).
  • Must integrate with existing authentication middleware.
  • Timeline: 6 weeks with 3 engineers.
  • Evaluation must be performed locally to avoid network hops.

Assumptions

In-Memory Configuration

We assume the total size of all active feature flag definitions is small enough to fit comfortably in the memory of each application instance.

Monorepo SDK Compatibility

We assume the evaluation logic can be effectively ported or shared between the two primary backend languages in the monorepo while maintaining deterministic results.

Phase 1: Flag Schema and Storage

Establish the source of truth for feature flags and the baseline access patterns.

Phase Goal

Define the database model, implement migrations, and provide a basic persistence layer with audit history.

Alternatives Considered

Config-file-in-repo: Rejected because it requires a deployment to change flags, failing the requirement for "no deploy" kill-switches.

Recommendations

Use Postgres as the source of truth and implement a JSONB column for complex targeting rules to allow for schema flexibility without frequent migrations.

Open Questions

Audit Granularity

Should we store the full flag object snapshot in the audit table or just a diff of changes?

Database Schema Migration

Create `feature_flags` and `feature_flag_audit_logs` tables. Include fields for key, type, targeting rules, and lifecycle state.

Entity Model & Data Access Layer

Implement the backend models and repository pattern for CRUD operations on flags, ensuring audit logs are written on every write.

Initial Seed Data & Environment Setup

Establish the standard environments (dev, staging, production) in the database and seed basic flags for testing.

Phase 2: Evaluation Engine

Build the core logic that computes flag values for specific users/contexts.

Phase Goal

Develop a high-performance evaluation library that supports deterministic bucketing and local caching.

Alternatives Considered

Centralized Sidecar: Considered for consistency across languages, but rejected if it introduces even a 1ms localhost network hop; sticking to native SDKs where possible.

Recommendations

Use MurmurHash3 for deterministic bucketing to ensure a user stays in the same bucket for a given flag across different services.

Open Questions

Invalidation Strategy

Should we use Redis Pub/Sub for push-based invalidation or a 30-second poll for the initial version?

Deterministic Bucketing Logic

Implement the hashing algorithm (User ID + Flag Salt) to support percentage rollouts consistently.

Local In-Memory Cache & Synchronizer

Implement a background worker that fetches flag state from Postgres and updates a local thread-safe map.

Backend SDKs (Lang A & Lang B)

Expose the `evaluate` function in both primary backend languages, ensuring identical rule processing logic.

JSON-over-HTTP Sidecar/Endpoint

Create a lightweight internal endpoint for other services to query flag state if they cannot use the native SDKs.

Phase 3: Admin UI

Provide a graphical interface for non-technical users to manage the system.

Phase Goal

Deliver a dashboard that allows creating, editing, and monitoring feature flags across all environments.

Alternatives Considered

Direct SQL updates for Support: Rejected due to risk of corruption and lack of audit context; a UI is mandatory for the "kill switch" requirement.

Recommendations

Build the UI as a new section within the existing internal admin tool to leverage existing auth and component libraries.

Open Questions

Live Preview Accuracy

How do we represent the "live preview" of bucketing if we don't know the exact user base distribution in the UI?

Flag Management Dashboard

Implement the list view, search, and archive functionality for flags.

Rule & Rollout Editor

Build the form for targeting rules and the percentage-rollout slider with interactive feedback.

Environment Overrides UI

Implement tabs or views to set different values for staging vs. production for a single flag.

Audit Log Viewer

Create a view to see the history of changes for a specific flag, including who changed what and when.

Decision: Use MurmurHash3 for Bucketing

Rationale: It provides excellent distribution with very low computational overhead, which is critical for the <1ms evaluation requirement.

Cryptographic hashes (like SHA-256) were considered for better collision resistance but were deemed too slow for a high-frequency evaluation path.

Stale Configuration on Invalidation Failure

If the invalidation signal (pub/sub or poll) fails, a service might use an old "active" value for a flag that has been "killed" in the dashboard.

Database Load from Polling

If we have 500+ service instances polling Postgres every 10 seconds, it could create significant unnecessary load.

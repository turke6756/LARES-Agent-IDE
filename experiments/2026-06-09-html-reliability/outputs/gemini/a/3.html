Feature Flag Infrastructure & Admin UI

A comprehensive three-phase initiative to implement a high-performance feature-flagging system for dark shipping, gradual rollouts, and emergency feature disabling, without external SaaS dependencies.

Success Criteria

  • Evaluation latency (p99) remains under 1 millisecond.
  • Zero external SaaS dependencies for flag management or evaluation.
  • Reliable deterministic bucketing for percentage rollouts across multiple SDKs.
  • Admin UI allows flag creation and rollout adjustment without engineering intervention.
  • Complete audit trail for all configuration changes in production.

Scope

Design and implementation of the Postgres schema, an evaluation engine with local caching, SDKs for the two primary backend languages, a JSON-over-HTTP endpoint for generic consumers, and a React-based Admin UI with role-based access control.

Constraints

  • No new external SaaS dependencies.
  • The evaluation path must not add a network hop to primary request handling.
  • System must integrate with existing authentication middleware.
  • Project must be delivered within six weeks by a team of three engineers.

Assumptions

The existing primary Postgres instance has sufficient capacity to handle the new `feature_flags` and audit tables.

Internal networking allows for efficient polling or push notifications for cache invalidation across the monorepo services.

Phase 1: Flag Schema and Storage

This phase focuses on defining the source of truth for all feature flags, including the data model and the underlying storage mechanism in Postgres.

Phase Goal

Establish a robust Postgres schema for flags, implement an audit trail, and provide a typed data access library for basic CRUD operations.

Alternatives Considered

Config-file-in-repo: While simpler for versioning, it lacks the ability for non-engineers to toggle flags without a full deployment cycle.

Recommendations

Use a separate schema or table prefix in the primary DB to keep feature flag logic isolated but accessible.

Open Questions

Should we store audit history in a JSONB column or a separate audit log table?

Postgres Schema Migration

Create the `feature_flags` table with columns for key, description, owner, type, targeting rules (JSONB), and lifecycle state.

Audit Log Implementation

Implement a `feature_flag_history` table and triggers/hooks to record every change, including the previous state and the user who made the change.

Typed Data Access Layer (DAL)

Build a shared library for the monorepo to interact with the flag tables, ensuring consistent data validation.

Phase 2: Evaluation Engine

The evaluation engine is the "hot path" that determines which variant a user sees based on the defined rules and context.

Phase Goal

Deliver a high-performance evaluation library with deterministic bucketing and a local cache to meet sub-millisecond latency requirements.

Alternatives Considered

Centralized sidecar vs. SDK Library: A library minimizes network hops but requires more effort to keep multiple language implementations in sync.

Recommendations

Use MurmurHash3 for bucketing to ensure uniform distribution across variants.

Open Questions

What is the optimal polling interval for cache invalidation before switching to a push-based mechanism?

Deterministic Bucketing Logic

Implement hashing logic (User ID + Salt) to provide stable percentage rollouts that persist across sessions.

In-Memory Cache with Polling

Develop a local cache for the SDK that periodically refreshes flag definitions from the DB to avoid network hops on every evaluation.

Multi-language SDKs

Implement the evaluation interface in the primary monorepo languages, ensuring parity in rule processing logic.

Telemetry and Sampling

Add instrumentation to emit sampled evaluation events for observability and future analysis.

Phase 3: Admin UI

The user interface for managing flags, allowing product and engineering teams to control features in real-time.

Phase Goal

Create a secure, user-friendly dashboard for flag lifecycle management and environment-specific overrides.

Alternatives Considered

Building from scratch vs. UI Component Library: We will use existing internal UI components to ensure consistency and speed.

Recommendations

Implement a "Live Preview" of the bucketing logic so users can see how a percentage change affects a sample set of IDs.

Open Questions

How granular should the RBAC permissions be (e.g., per-flag vs. per-environment)?

Dashboard and Flag CRUD

Build the main list view and creation forms for flags, including metadata like owners and descriptions.

Rollout Slider & Rules Editor

Develop interactive components for adjusting percentage rollouts and complex targeting rules (e.g., by User ID or Org).

Audit and History Viewer

Implement a view to browse the history of changes for any given flag, showing who changed what and when.

RBAC Integration

Hook into the existing auth middleware to enforce that only admins or owners can modify production flag values.

Postgres over Config Files

We chose Postgres as the source of truth to allow real-time updates and an easier path for building an Admin UI, accepting the slight complexity of cache invalidation.

Config files would provide easier "as-code" versioning but would require a CI/CD cycle for every toggle change.

Cache Invalidation Staleness

If the polling interval is too long, feature toggles (like kill-switches) might take too long to propagate across the fleet.

Logic Parity across SDKs

Different implementations of the rule engine in multiple languages might lead to inconsistent evaluation results for the same user.

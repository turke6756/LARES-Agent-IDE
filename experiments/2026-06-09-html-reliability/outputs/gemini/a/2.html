Feature Flag System Implementation

This plan outlines the design and implementation of a robust, low-latency internal feature-flagging system to support dark launches, gradual rollouts, and emergency circuit breakers across the monorepo.

Success Criteria

  • Evaluation latency is under 1ms at p99 in both backend languages.
  • Engineering can toggle features without a code deployment.
  • Zero external SaaS dependencies for the core evaluation path.
  • Deterministic percentage rollouts across different services for the same user.
  • Full audit trail of who changed which flag and when.

Scope

  • Backend SDKs for the two primary monorepo languages.
  • JSON/HTTP endpoint for generic evaluation.
  • Postgres-based storage with local caching and invalidation logic.
  • Admin dashboard for flag management and overrides.
  • Targeting by User ID, Org ID, and Environment.

Constraints

  • No network hops added to the evaluation path during request handling.
  • No new external SaaS services (e.g., LaunchDarkly, Statsig).
  • Must integrate with existing authentication and authorization middleware.
  • Execution timeline: 6 weeks with a team of 3 engineers.

Assumptions

The total number of active feature flags will remain small enough (under 5,000) to fit entirely in memory on each application node.
The application servers can support a background process or thread to handle periodic flag updates/cache invalidation without impacting the main request loop.

Phase 1: Flag Schema and Storage

Establish the source of truth for flag definitions and the database infrastructure required to support them.

Phase Goal

Define and deploy the Postgres schema, typed data models, and an audit-logged management API.

Alternatives Considered

Config-file-in-repo: While simple and provides Git history, it requires a full CI/CD cycle for every toggle, failing the "no-deploy" requirement for emergency kills.

Recommendations

Use a centralized Postgres table for persistence and a Read-Through cache (Redis or local) for the evaluation engine to fetch updates.

Open Questions

Should we support nested targeting rules (AND/OR logic) in Phase 1, or keep rules as a flat list of matchers?

Database Schema Migration

Create `feature_flags` and `feature_flag_audit_log` tables in the primary Postgres instance. Include fields for key, type, targeting rules (JSONB), and metadata.

Data Access Layer

Implement the internal service layer for CRUD operations on flags, ensuring every write triggers an entry in the audit log.

Typed Accessor Library

Create a shared library/package for the backend languages that defines the Flag and Targeting Rule types to ensure consistency between the UI and the engine.

Phase 2: Evaluation Engine

Build the core logic that determines which variant a user sees based on the defined rules and context.

Phase Goal

A sub-millisecond evaluation library with local caching and deterministic bucketing.

Alternatives Considered

Sidecar Service: A sidecar avoids library duplication but adds a network hop (localhost) which might exceed the 1ms p99 budget in high-traffic scenarios.

Recommendations

Implement as a native library for the two main languages to ensure zero-network-hop evaluation, with a background poller to refresh the local cache.

Open Questions

What sampling rate should we use for evaluation telemetry to avoid overloading our analytics pipeline?

Deterministic Bucketing Logic

Implement the hashing algorithm (e.g., MurmurHash3) to bucket users consistently based on `userId + flagSalt` for percentage rollouts.

Local In-Memory Cache & Poller

Develop a background worker within the SDK that polls the Postgres/Cache API every 30 seconds and updates a thread-safe local map of flags.

Evaluation SDKs

Provide the public `evaluate(key, context)` method for both primary languages, handling rule precedence and environment inheritance.

Telemetry Middleware

Add sampled event emission to the SDK to track which flags were evaluated and which variants were served.

Phase 3: Admin UI

Create the dashboard for non-technical stakeholders and engineers to manage flags safely.

Phase Goal

A functional dashboard for managing flags with per-environment overrides and audit visibility.

Alternatives Considered

CLI-only management: Faster to build but prevents Product and Support teams from using the system independently.

Recommendations

Use a simple React-based dashboard integrated into the existing admin console to leverage existing auth/RBAC.

Open Questions

Should we implement a "test mode" in the UI where users can see what a specific User ID would evaluate to?

Flag Management Dashboard

Build the list and detail views for flags, allowing users to create, search, and archive flag definitions.

Targeting Rule Editor

Implement the UI for complex targeting: environment overrides, percentage sliders with live bucketing previews, and multi-variant selection.

Audit History View

Expose the audit log in the UI so users can see the history of changes for a specific flag, including who made the change.

RBAC Integration

Enforce the "owner/admin only" rule for production edits within the UI and the underlying API.

Use MurmurHash3 for Bucketing

We will use MurmurHash3 for deterministic bucketing of users in percentage rollouts. It is fast, has good distribution, and is widely available in libraries for multiple languages.

SHA-256 was considered but is overkill for bucketing and slower to compute in hot paths.

Cache Inconsistency

With a polling-based invalidation, different app nodes may see different flag states for up to 30 seconds. This could lead to flickering UI or inconsistent behavior during a rollout.

Database Bottleneck

If the polling interval is too short and the number of nodes is too high, the flag-fetch endpoint could put significant pressure on the Postgres primary.

Feature Flag System

Implementing an internal, low-latency feature flag system to support dark launching, gradual percentage rollouts, and kill switches without needing full deployments.

Success Criteria

The system is adopted by engineering, product, and support. Flag evaluation latency must be consistently under 1ms at the 99th percentile, with no added network hops. A full self-service Admin UI provides intuitive controls over rollouts across environments, completely eliminating engineering intervention for day-to-day flag modifications.

Scope

Phase 1 covers Postgres schema design, migrations, and a typed data accessor library. Phase 2 covers a fast, deterministically bucketed evaluation engine with local memory caching, telemetry, two backend SDKs, and a JSON-over-HTTP endpoint. Phase 3 covers the Admin UI dashboard with audit history, environment overrides, preview functionality, and RBAC.

Constraints

No new external SaaS dependencies are permitted. The evaluation process must be local to the request handling (no network hops). Must be secured behind existing auth middleware. Total budget is three engineers over six weeks.

Assumptions

The total volume of active feature flag configuration data is small enough to be aggressively cached entirely in memory on each application instance.

The existing authentication middleware correctly maps user groups that we can use to easily delineate "Admins" and "Owners" for RBAC.

Phase 1 — Flag Schema and Storage

Focuses on establishing the foundational data model, database schema, and data access layer, paving the way for the engine and UI.

Phase Goal

Deploy a robust, audited Postgres database schema for feature flags and ship a typed accessor library to handle DB queries securely.

Alternatives Considered

We evaluated a config-file-in-repo approach (GitOps). While this simplifies auditing, it requires an active deployment to turn off a flag, violating the "kill switch without deploy" requirement.

Recommendations

Store flags in a dedicated feature_flags table in the primary Postgres instance. Utilize triggers or an application-layer interceptor to automatically record changes into a feature_flags_audit table.

Open Questions

Should the audit history table have an automated data retention policy (e.g., pruning records older than 1 year), or keep records indefinitely?

Schema Design & Migration

Create the database schema including flag keys, descriptions, owner references, flag types, targeting rules (JSONB), environments, default values, and lifecycle states.

Audit History Implementation

Implement an audit table that captures the user ID, timestamp, and a before/after snapshot of the flag state for any mutation.

Seed Data Pipeline

Write idempotent scripts to seed default flags for the local development environments and CI pipelines.

Typed Accessor Library

Develop a standard, typed library for reading and writing flag definitions to the database. Ensure this library masks direct database queries from the rest of the application.

Phase 2 — Evaluation Engine

Constructs the highly performant local evaluation engine that determines flag variants based on rules, context, and determinism.

Phase Goal

Provide a sub-millisecond p99 flag evaluation library with deterministic bucketing, environment inheritance, and an in-memory cache.

Alternatives Considered

We considered a centralized gRPC evaluation service, but the network hop alone would violate the strict sub-millisecond p99 latency constraint. A sidecar service was considered but dismissed in favor of an embedded library to reduce operational complexity.

Recommendations

Implement deterministic percentage bucketing using MurmurHash3 on the user ID concatenated with the flag salt. Use an embedded in-memory cache synchronized via a periodic background polling thread.

Open Questions

What is the optimal background polling interval to sync the in-memory cache with Postgres without overloading the database?

Core Evaluation Logic

Implement the rule evaluation logic, including parsing targeting rules, establishing rule order semantics, and the deterministic bucketing algorithm for percentage rollouts.

In-Memory Cache & Synchronization

Build the local cache module and a background worker that polls the Postgres tables for changes and hot-swaps the cache safely without blocking evaluations.

Backend SDKs

Create developer-friendly SDK surfaces for both of the monorepo's backend languages that wrap the evaluation engine and expose a simple `evaluate(flagKey, context)` signature.

JSON-over-HTTP Endpoint

Expose a lightweight HTTP endpoint that accepts a context payload and returns evaluated flag variants for clients that cannot use the native SDKs.

Evaluation Telemetry

Integrate a sampled telemetry emitter within the evaluation path to log which flags are evaluated, their results, and latency metrics for downstream analysis.

Phase 3 — Admin UI

Delivers the user interface for product managers, support teams, and engineers to manage flags effectively without writing code.

Phase Goal

Create a secure, comprehensive dashboard for managing the lifecycle, targeting, and environments of feature flags.

Alternatives Considered

We debated building a completely standalone service with its own auth for this UI. We decided against it as leveraging the existing backoffice application provides out-of-the-box RBAC integration and consistent design.

Recommendations

Build the Admin UI as a set of modules inside the existing backoffice application. Ensure the UI heavily features "live preview" widgets to build trust in percentage rollouts.

Open Questions

How do we source realistic mock contexts (user IDs, attributes) for the live preview feature to show accurate bucketing?

Dashboard & CRUD Operations

Build the main list view, search functionality, and the forms necessary to create, edit, and archive feature flags.

Environment Specific Controls

Implement the UI for environment inheritance and the ability to define specific overrides (e.g., forcing a flag on in staging while off in production).

Percentage Rollout Slider

Develop an interactive slider for percentage rollouts, paired with a visual, live preview component that demonstrates how an arbitrary user context will be bucketed.

Audit Log View & RBAC

Hook up the existing auth middleware to enforce role-based access control (only owners and admins can edit prod) and build an intuitive view for inspecting flag change histories.

Postgres will be the primary source of truth for feature flag definitions, backed by an aggressively refreshing local memory cache.

We strongly considered storing flags as config files in the Git repository to leverage existing PR review flows. However, this model forces product and support teams to perform Git commits and wait for full application deployments to disable broken features, violating the core requirement for instant, out-of-band kill switches.

Evaluation logic will be embedded as libraries within the application runtimes rather than running as a standalone HTTP/gRPC service.

Centralizing evaluation simplifies updates to the engine, but introduces a network hop that makes it impossible to guarantee sub-millisecond p99 latency reliably.

Cache Invalidation Latency

If the background polling mechanism is delayed or fails, applications may evaluate against stale flag rules. A kill-switch might not propagate fast enough during an incident.

Evaluation Engine Overhead

Highly complex targeting rules involving large sets of specific user IDs or deep JSON matching might break the 1ms p99 latency target on the CPU side, even if no network hop is made.

Telemetry Data Flood

Emitting an event for every single flag evaluation across high-traffic endpoints could DDOS the internal telemetry or observability stack if sampling is not strictly tuned.

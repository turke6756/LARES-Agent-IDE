Feature Flags System

Build an internal feature-flag system enabling dark deployments, gradual rollouts, and rapid kill switches without relying on third-party SaaS, delivered by 3 engineers over 6 weeks.

Success Criteria

  • Engineering can deploy code behind dark flags.
  • Product managers can execute gradual rollouts via deterministic percentage bucketing.
  • Support and engineering can use kill switches without deploying code.
  • The evaluation engine guarantees sub-millisecond p99 latency with zero additional network hops on the hot path.

Scope

  • In Scope: Flag schema (boolean, percentage, multivariate), Postgres storage, evaluation engine with in-memory caching and polling/push invalidation, SDKs for two backend languages, JSON-over-HTTP fallback, Admin UI (dashboard, flag management, environment overrides, live bucketing preview, RBAC for production), Audit history of flag changes.
  • Out of Scope: A/B-test stats, scheduled rollouts, mobile SDKs, full approval workflows.

Constraints

  • No new external SaaS dependencies.
  • The evaluation path must not add a network hop to request handling.
  • Everything must reside behind the existing auth middleware.
  • Resource limit: Team of 3 engineers.
  • Time limit: 6 weeks.

Assumptions

Existing auth middleware provides all necessary context (User ID, Org ID) in the request lifecycle for targeting rules.

The total volume of active feature flags and rules will comfortably fit into application memory for localized evaluation without massive overhead.

Phase 1: Schema and Storage

This phase focuses on defining the underlying data model for flags, their targeting rules, and audit history, establishing the foundation in our primary Postgres database.

Phase Goal

Deliver a robust data model and typed accessor library capable of storing flag states, environments, and audit logs.

Alternatives Considered

Considered a config-file-in-repo approach (GitOps). Rejected because it fails the requirement for support teams to rapidly toggle kill switches without waiting for a CI/CD deployment pipeline.

Recommendations

Use a normalized Postgres schema for flags and environments, but store the targeting rules as JSONB to allow flexible schema evolution for rule engines.

Open Questions

Should we retain audit history indefinitely in the primary Postgres, or partition the audit table by date to allow archiving?

Design Database Schema

Create DDL scripts for `feature_flags`, `flag_environments`, `flag_rules`, and `flag_audit_log` tables in Postgres.

Write Migrations and Seed Data

Implement the database migrations to provision the tables and seed essential built-in flags.

Implement Typed Accessor Library

Create a strictly typed internal DAO layer to perform CRUD operations on flags and audit trails, ensuring valid JSON boundaries.

Internal Configuration API

Expose a basic CRUD API module for the admin UI to consume, properly secured behind the auth middleware.

Phase 2: Evaluation Engine

This phase builds the core, ultra-fast evaluation logic. It distributes the state from the database to application memory and handles localized processing.

Phase Goal

Provide a sub-millisecond local evaluation mechanism via backend SDKs, ensuring accurate deterministic bucketing and rapid cache invalidation.

Alternatives Considered

Considered a centralized evaluation sidecar over gRPC. Rejected because the brief mandates no network hops for request handling; an in-process SDK approach guarantees local memory lookup speeds.

Recommendations

Implement MurmurHash3 for deterministic bucketing (hashing `flag_salt + user_id`) to ensure fast and consistent percentage rollouts across all SDK languages.

Open Questions

For cache invalidation, should we rely purely on a 10-second polling interval, or implement a hybrid pub/sub push model using Redis?

Implement Deterministic Bucketing

Write the hashing algorithm (user ID + salt modulo 100) to safely assign users to buckets for percentage rollouts.

Build Rule Evaluation Semantics

Develop the rule engine enforcing rule ordering and environment inheritance (falling back to production defaults if staging is unconfigured).

In-Memory Cache & Invalidation

Implement a read-through local cache inside the SDK with a background worker that polls for updates to avoid network hops during evaluation.

Develop Native Backend SDKs

Author the evaluation libraries for the two primary languages in the monorepo, wrapping the cache and evaluation logic securely.

JSON-over-HTTP Endpoint

Create a lightweight, highly cached HTTP endpoint for services outside the monorepo to query flag state (acknowledging this will incur a network hop for those specific edge cases).

Telemetry and Sampling

Add an asynchronous, sampled event emitter within the evaluation function to log bucketing decisions for observability without slowing down execution.

Phase 3: Admin UI

Providing the interface for product, engineering, and support to interact with the system.

Phase Goal

Deliver a complete management dashboard that visualizes flag states, handles safe production overrides, and previews rollout bucketing.

Alternatives Considered

Considered a CLI-only admin tool to save time. Rejected because PMs and Support need a highly discoverable and visual way to see active flags and rollouts.

Recommendations

Utilize the existing internal component library to quickly build out forms and data tables to stay within the 6-week timeframe.

Open Questions

How do we best present environment inheritance visually so users understand when a staging flag is overriding the production value?

Flag Dashboard View

Build the main listing page with search, filtering by active/archived state, and ownership tags.

Flag Editor & Targeting UI

Develop the form to create and edit flags, manage environment-specific overrides, and define complex targeting rules (User ID, Org).

Percentage Slider with Live Preview

Implement an interactive slider for percentage rollouts that uses the SDK's hashing logic via a dry-run endpoint to show sample bucketed users.

Audit History View

Create a timeline component on the flag detail page displaying all state changes, who made them, and when.

Implement RBAC Guardrails

Enforce UI and API-level role-based access control, ensuring that only designated flag owners and super-admins can toggle or edit values in the production environment.

Use Postgres with a read-through cache rather than a config-file-in-repo approach for flag storage.

A config-file approach would offer native audit logging via git history and simplify deployment. However, it fails the primary requirement to allow support staff to quickly disable a misbehaving feature (kill switch) without invoking a potentially slow CI/CD deploy pipeline.

SDK In-memory cache polling introduces a window of eventual consistency (e.g., 10 seconds). Critical kill-switches might not take effect instantaneously across all fleet nodes.

Complexity in rule evaluation logic (especially if we allow deeply nested attributes) could breach the sub-millisecond p99 latency target on the hot path.

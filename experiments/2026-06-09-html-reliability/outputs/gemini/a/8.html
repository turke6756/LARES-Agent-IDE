Feature Flag Infrastructure

A comprehensive system for dark-shipping features, managing gradual rollouts, and providing emergency kill-switches without redeployment. This plan covers the core schema, a high-performance evaluation engine, and a management dashboard.

Success Criteria

  • Evaluation latency (p99) is under 1 millisecond.
  • Changes to flags propagate to all services within 30 seconds.
  • Audit trails capture every change to flag state, including who and when.
  • Zero external SaaS dependencies for the core evaluation path.
  • Product managers can independently manage rollouts without engineering support.

Scope

  • In Scope: Multi-environment support (Staging/Production), Boolean and Multivariate flags, Percentage rollouts with deterministic bucketing, Targeting by User/Org ID, and Audit logs.
  • Out of Scope: Mobile SDKs, A/B test statistical analysis, scheduled automated rollouts, and complex approval workflows.

Constraints

  • No new external SaaS dependencies.
  • Must integrate with existing authentication middleware.
  • Evaluation path must avoid additional network hops during request handling.
  • Timeline: 6 weeks with a 3-engineer team.

Assumptions

The primary Postgres database has sufficient capacity for the `feature_flags` and `flag_audit_history` tables.
The monorepo continues to use the two primary backend languages for the duration of the build.

Phase 1: Flag Schema and Storage

Establish the source of truth for all feature flags and the internal data access patterns.

Deliver a robust Postgres-backed storage layer with a typed accessor library and audit tracking.

Config-file-in-repo: Rejected because it requires a deployment for every flag change, defeating the "kill switch" and "dynamic rollout" requirements.

Use a JSONB column for targeting rules to allow flexible rule schemas without frequent migrations.
How long should we retain audit history before archiving to cold storage?

Database Schema Design

Design and implement the `feature_flags` and `flag_audit_log` tables in Postgres. Include fields for key, type, targeting JSON, and metadata.

Typed Accessor Library (DAO)

Build a shared library for reading and writing flags from the database, ensuring all targeting rules are correctly serialized/deserialized.

Seed Data & Migration Scripts

Create baseline flags for existing features and scripts to migrate any hardcoded toggles into the new system.

Phase 2: Evaluation Engine

Implement the high-performance logic that determines which variant a user sees.

Create a millisecond-latency evaluation library with deterministic bucketing and local caching.

Centralized sidecar for all evaluations: Considered, but rejected to avoid the network hop. We will prefer in-process libraries with local cache.

Use MurmurHash3 for deterministic bucketing to ensure consistent user experience across different services.
What is the optimal sampling rate for telemetry events to balance observability vs. storage costs?

Deterministic Bucketing Logic

Implement the hashing algorithm (ID + salt) to handle percentage rollouts consistently across all SDKs.

In-Memory Cache & Invalidation

Develop the local cache within the SDK and a polling mechanism (initially) to fetch updates from the DB every 30s.

JSON-over-HTTP Sidecar

Create a small Go or Rust sidecar for non-monorepo services to query flag state locally.

Telemetry Emitter

Add logic to emit sampled evaluation events (flagKey, variant, userId) to the existing logging/analytics pipeline.

Phase 3: Admin UI

Provide a user-friendly interface for managing the lifecycle of feature flags.

Launch a secure dashboard for flag management, rollouts, and audit visibility.

Using a CLI for management: Rejected because Product and Support teams need a visual, low-friction interface.

Implement a "Draft/Preview" mode for percentage rollouts so users can see how a 10% change affects bucketing before saving.
Should we enforce a "tags" system (e.g., 'ops', 'marketing') for better flag discoverability?

Flag Management Dashboard

Build the main list and detail views for creating and editing flags using the existing internal UI kit.

Rollout Slider & Preview

Develop a visual slider component for percentage rollouts that displays a live preview of user IDs being bucketed.

RBAC Integration

Hook into existing auth to ensure only owners or admins can modify flags in the Production environment.

Audit History View

Build a view to browse the audit log, filtered by flag key or user, to track historical changes.

Postgres for Source of Truth

We will use the primary Postgres instance for flag definitions to leverage existing ACID compliance and backup strategies. Redis will be considered later only if polling the DB becomes a bottleneck.

Cache Staleness

A 30-second polling interval might be too slow for emergency kill-switches. We may need to upgrade to a Push (WebSockets/PubSub) model if this is insufficient.

Evaluation Logic Bugs

If the evaluation library crashes or returns incorrect values, it could break core application flows across the entire platform.

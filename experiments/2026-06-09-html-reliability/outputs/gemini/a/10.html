Feature Flag System

Implementation of a comprehensive feature-flag system enabling engineering to ship dark code, product to execute gradual rollouts, and support to disable misbehaving features without deployments.

Success Criteria

The system must evaluate flags in under 1 millisecond at the 99th percentile without adding a network hop to the request handling path. Deterministic bucketing must consistently map users to variants. A functional Admin UI must exist behind existing auth for CRUD operations, overrides, and role-based access control.

Scope

In scope: Flag schema definition and Postgres storage with read-through cache, evaluation engine with SDKs for backend languages and a JSON-over-HTTP endpoint, telemetry for evaluations, deterministic percentage rollouts, environment inheritance, an Admin UI for flag management, and audit history of changes.

Out of scope: Full approval workflows, A/B-test statistics, scheduled rollouts, and mobile SDKs.

Constraints

No new external SaaS dependencies are permitted. The evaluation path must run locally in memory to avoid network latency. Admin UI must be placed behind the existing auth middleware. The project must be completed by a team of three engineers within a roughly six-week timeframe.

Assumptions

The primary Postgres database can support the initial read-through cache population and audit history write volumes.

The backend languages in the monorepo support maintaining an efficient, thread-safe in-memory cache for flag evaluations.

Phase 1 — Flag schema and storage

Define the core flag model and establish the primary data store and basic access patterns.

Phase Goal

Deliver a robust data schema for feature flags and a typed accessor library to support creating, reading, and auditing flags.

Alternatives Considered

We considered a config-file-in-repo approach (GitOps style) but rejected it due to the requirement for rapid, deploy-free intervention by support and the need for a rich Admin UI with an audit history.

Recommendations

Store flags in a new `feature_flags` table in the primary Postgres database to easily leverage existing backup strategies and ensure transactional integrity for audit logs.

Open Questions

Should we implement a soft-delete for archived flags to preserve relational integrity in the audit log, or move them to a cold storage table?

Schema Definition

Design the Postgres schema for flags including key, description, owner, type, targeting rules, default value, and lifecycle state. Include tables for environment overrides and audit logs.

Database Migrations

Write and test database migration scripts to provision the new tables, indices, and constraints.

Typed Accessor Library

Implement a core library for CRUD operations against the flag schema with strong typing.

Audit History Implementation

Integrate triggers or application-level hooks to automatically write to the audit log upon any flag mutation.

Phase 2 — Evaluation engine

Build the core evaluation logic and local caching mechanisms to meet strict latency requirements.

Phase Goal

Deliver a high-performance evaluation engine capable of sub-millisecond responses without network hops.

Alternatives Considered

Considered an independent sidecar service (like Envoy) for evaluation, but opted for native SDKs with in-memory caching to minimize deployment complexity and IPC overhead for monorepo services.

Recommendations

Implement a standard push-or-poll invalidation mechanism where SDKs poll every 15-30 seconds or listen to a Redis pub/sub channel for immediate invalidation.

Open Questions

What specific hashing algorithm should be used for deterministic bucketing (e.g., MurmurHash3 vs MD5) to balance speed and distribution uniformity?

Deterministic Bucketing Algorithm

Implement the bucketing logic using a hash of the target user ID and a flag-specific salt to ensure consistent percentage rollouts.

In-Memory Cache & Invalidation

Build the local cache layer within the SDK and implement the chosen push-or-poll invalidation strategy to keep evaluation rules up to date.

Native SDKs

Develop the evaluation SDK surface for the two primary backend languages in the monorepo.

JSON-over-HTTP Endpoint

Create a lightweight internal HTTP endpoint wrapping the evaluation engine for clients outside the monorepo ecosystem.

Telemetry Emisson

Integrate a sampled telemetry emitter within the evaluation path to log evaluation outcomes for later offline analysis.

Phase 3 — Admin UI

Develop the user interface for managing the complete lifecycle of feature flags.

Phase Goal

Provide a comprehensive, secure dashboard for product and engineering to control feature rollouts and environments.

Alternatives Considered

Considered a CLI-first approach for management, but a UI is necessary for product managers and support staff to visualize rollouts and quickly kill misbehaving features.

Recommendations

Embed the dashboard directly within the existing internal administration portal to seamlessly inherit current authentication and role definitions.

Open Questions

Should the live preview of bucketing operate against production data or require manual input of test IDs?

Flag Management Dashboard

Build the main views for searching, creating, editing, and archiving flags.

Environment Overrides

Implement the UI controls for environment inheritance and configuring per-environment specific overrides.

Rollout Slider & Preview

Develop an interactive percentage slider component with a real-time preview mechanism demonstrating bucketing distribution.

Audit Log View

Create a chronological view displaying the history of changes for each flag.

Role-Based Access Control

Enforce RBAC rules ensuring that only flag owners and designated admins can modify production environment values.

Use Postgres as the source of truth rather than repository-based configuration files.

Config-in-repo ensures infrastructure-as-code purity but fails the requirement for instantaneous, deploy-free intervention by support staff and complex dynamic UI needs.

Cache Invalidation Latency: If the invalidation mechanism fails or lags, production applications may evaluate using stale rules, delaying emergency kill-switches.

Memory Consumption: Fetching and storing the entire active flag ruleset in-memory across all application pods might lead to OOM errors if the ruleset grows unbounded.

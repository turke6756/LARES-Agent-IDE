Feature Flag System Plan

Designing and implementing a comprehensive feature-flag system with three phases: flag schema and storage, a high-performance evaluation engine, and an administrative UI. This will enable safe code deployment, gradual rollouts, and rapid incident mitigation without needing code changes.

Success Criteria

Engineers can ship code dark, product teams can run gradual rollouts, and support can safely toggle flags without requiring a new deployment. The system supports targeting by user, org, and environment. Evaluation engine answers queries in under a millisecond at p99 without adding a network hop, and includes audit history.

Scope

In scope: Flag schema design, Postgres storage, read-through cache, migrations, seed data, evaluation engine (deterministic bucketing, rules, environment inheritance), SDK surface for two backend languages, JSON-over-HTTP endpoint, telemetry, and an internal admin UI with role-based access.

Out of scope: A/B-test statistics, scheduled rollouts, mobile SDKs, and full approval workflows.

Constraints

No new external SaaS dependencies. The evaluation path must not add a network hop to request handling. Everything must sit behind the existing auth middleware. The work must be completed by a team of three engineers in roughly six weeks.

Assumptions

The primary Postgres database has enough capacity to handle the storage of feature flags and the read queries required to populate the in-memory cache without impacting existing workloads.

The existing auth middleware provides sufficient user, org, and environment context on all requests to feed into the feature flag evaluation engine.

Phase 1 - Flag schema and storage

Establish the foundation of the feature flag system, including database models, audit logs, and data access layers.

Phase Goal

Define a robust and scalable storage schema for feature flags, targeting rules, and audit history, backed by Postgres with a caching layer.

Alternatives Considered

We considered storing flags in a configuration file within the repository, but opted for a database approach to enable real-time toggling by product and support teams without requiring code changes or deployments.

Recommendations

Use a single primary `feature_flags` table combined with a `feature_flag_audit_logs` table. Rely on Postgres JSONB columns for flexible targeting rules and multivariate options.

Open Questions

Should the read-through cache invalidate based on Postgres LISTEN/NOTIFY, or a simpler polling mechanism?

Design Database Schema

Draft the SQL schema for `feature_flags`, environments, and audit history. Include fields: key, description, owner, flag type, default value, and lifecycle state.

Implement Postgres Migrations

Create and run the necessary migration scripts to establish the tables, indexes (specifically on flag key and environment), and primary keys in the database.

Develop Typed Accessor Library

Build a data access layer (DAL) with strict typing that abstracts the CRUD operations for feature flags and ensures all changes are automatically logged to the audit table.

Seed Initial Data

Write scripts to populate the database with a standard set of environments (e.g., development, staging, production) and dummy flags for testing.

Phase 2 - Evaluation engine

Build the highly performant engine responsible for resolving flag values based on context.

Phase Goal

Deliver an evaluation library that resolves flags in under a millisecond at p99 using deterministic bucketing and local caching, without introducing a network hop.

Alternatives Considered

Considered a standalone microservice for evaluation, but rejected it to meet the strict "no network hop" constraint. Instead, we are utilizing an embedded library with a synchronized local cache.

Recommendations

Implement deterministic hashing using MurmurHash3 on the user ID and flag salt for percentage rollouts to guarantee consistent bucketing across all nodes and languages.

Open Questions

What is the most efficient serialization format for the in-memory cache to ensure rapid environment inheritance resolution?

Implement Core Evaluation Logic

Write the core logic handling rule ordering, environment inheritance, and deterministic bucketing for percentage rollouts.

Build In-Memory Cache and Invalidation

Develop the local cache layer that stores rules in memory and a background worker to keep it synchronized with the primary database (via poll or push).

Create Language SDKs

Develop native SDKs for the two primary backend languages in the monorepo, wrapping the core evaluation logic and telemetry emission.

Develop JSON-over-HTTP Endpoint

Expose an HTTP endpoint from a core service to allow other systems (not using the native SDKs) to evaluate flags securely.

Integrate Telemetry Pipeline

Hook up the evaluation engine to emit sampled events (flag key, context hash, variant) for downstream data analysis and debugging.

Phase 3 - Admin UI

Provide a frontend dashboard for product, support, and engineering to manage the lifecycle of feature flags.

Phase Goal

Create a secure and intuitive web interface behind existing auth to allow users to create, modify, and monitor feature flags, with role-based protections for production environments.

Alternatives Considered

Considered buying an off-the-shelf admin UI but rejected it due to the "no new external SaaS dependencies" constraint and the need to integrate tightly with our bespoke auth middleware.

Recommendations

Build the dashboard as a module within the existing internal tooling portal to leverage the existing auth middleware and design system.

Open Questions

How granular should the role-based access control (RBAC) be for staging environments?

Implement Flag Management Views

Build the screens to list, search, create, edit, and archive feature flags.

Build Percentage Rollout Slider

Create the UI component for adjusting percentage rollouts, including a live preview calculating the approximate number of affected users based on historical traffic.

Integrate Role-Based Access Control

Enforce the rule that only flag owners and global admins can edit values in the production environment.

Develop Audit History View

Create a view displaying the timeline of changes for each flag, pulling data from the `feature_flag_audit_logs` table.

Store flag configurations in a centralized PostgreSQL database instead of static repository files.

Repository files offer simple version control out of the box, but fail to meet the requirement for support teams to kill a feature without a deployment.

Use local, embedded caching in application instances for flag evaluation.

An external Redis cache would provide stronger consistency but would introduce an unacceptable network hop during the evaluation path.

The local cache synchronization mechanism could fall behind, resulting in stale flag values being served to users for extended periods.

High volumes of telemetry events from flag evaluations could overwhelm the existing data pipeline.

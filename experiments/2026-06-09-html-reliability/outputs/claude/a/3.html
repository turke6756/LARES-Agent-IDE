Feature Flag System

Add a first-class feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill misbehaving features without a deploy. Three phases over six weeks — flag schema & storage, evaluation engine, and admin UI — delivered by a team of three engineers with no new external SaaS dependencies.

Success Criteria

  • Any feature flag evaluates to a variant in under 1 ms at p99 with zero additional network hops on the hot request path.
  • Engineers, PMs, and support staff can create, toggle, and archive flags through a browser UI without a code deploy.
  • Percentage-rollout bucketing is deterministic and stable: the same userId + flagSalt always maps to the same bucket across all instances and languages.
  • Every flag mutation (create, update, archive, restore) is captured in an append-only audit log with actor identity, timestamp, and before/after snapshots.
  • Native typed SDKs exist for both backend languages in the monorepo; all other callers can use the JSON-over-HTTP evaluation endpoint.
  • Role-based access control prevents non-owners and non-admins from modifying production flag values.
  • Zero new external SaaS dependencies are introduced anywhere in the stack.
  • The evaluation engine degrades gracefully: if Postgres is unreachable, the last cached value is returned rather than erroring.

Scope

In scope:

  • Flag data model: key, description, owner, type (boolean / percentage / multivariate), targeting rules (user ID, org ID, environment), default value, per-environment overrides, lifecycle state (active / archived).
  • Postgres feature_flags table, feature_flag_audit_log table, migrations, seed data, and a database trigger that auto-records audit rows.
  • In-process read-through cache with TTL-based refresh and Postgres LISTEN/NOTIFY push invalidation.
  • Typed accessor libraries for both backend languages (Language A and Language B).
  • Evaluation engine: deterministic MurmurHash3 bucketing, ordered rule evaluation, environment inheritance (staging inherits production defaults), circuit-breaker fallback.
  • Sampled telemetry event emission on every evaluation (configurable sample rate; no raw PII).
  • POST /internal/flags/evaluate JSON-over-HTTP endpoint for non-native callers.
  • Admin UI: flag list with search/filter, create/edit form, per-environment overrides, percentage-rollout slider with live bucketing preview, audit history view.
  • RBAC: flags:edit-production permission gated to flag owner and flag-admin role; flags:edit-nonprod open to all authenticated engineers.
  • Audit history read API and UI.

Out of scope:

  • A/B-test statistical analysis and significance reporting.
  • Scheduled or time-based rollout automation.
  • Mobile SDKs (iOS, Android).
  • Full change-request / approval workflow for flag edits.
  • External SaaS flag services (LaunchDarkly, Split, Flagsmith, etc.).
  • Real-time analytics dashboards on flag evaluation volume.

Constraints

  • No new external SaaS dependencies. The entire system must run on infrastructure already present in the stack (Postgres, existing auth layer, existing internal event bus).
  • No extra network hop on the evaluation hot path. Evaluation must complete in-process using a local memory cache; Postgres is only accessed for cache misses or background refresh.
  • Everything behind existing auth middleware. Both the HTTP evaluation endpoint and the admin UI must authenticate via the current auth stack — no new auth integration.
  • Three engineers, approximately six weeks. Phases are sequenced so Phase 2 begins once Phase 1's storage contract is stable (end of week 2), and Phase 3 backend begins once Phase 2's SDK interface is agreed (week 3).
  • Backward compatibility. Introducing the flag system must not alter any existing request path. A missing or unavailable flag must always return a safe default — never throw or degrade the calling service.
  • Append-only audit log. Audit rows may never be updated or deleted via application code; only admins with direct DB access can manage retention.

Assumptions

a1: The monorepo contains exactly two backend languages requiring first-class typed SDKs. All other services and scripts will consume the JSON-over-HTTP evaluation endpoint.

a2: Postgres is the primary operational database, is reachable from every service that will call the evaluation SDK, and the team has CI permission to run schema migrations against it.

a3: Per-instance in-memory caching is sufficient for the anticipated flag evaluation volume. A shared external cache such as Redis is not required within the six-week scope.

a4: The existing frontend stack (assumed React with the current internal component library) can accommodate the admin UI — including the rollout slider and diff viewer — without introducing new frontend framework dependencies.

a5: An internal analytics event bus already exists and can accept sampled evaluation events from within the monorepo services without additional onboarding work.

Phase 1 — Flag Schema & Storage

Establish the canonical data model, Postgres schema, migration pipeline, audit trail, in-process cache, and typed accessor libraries that all subsequent phases depend on. Phase 1 delivers the single source of truth for flag definitions and ensures every mutation is durably recorded. Target completion: end of week 2.

Phase Goal

By the end of Phase 1, a flag can be created, read, updated, and archived via a Postgres-backed store; every mutation automatically writes an audit row; and both backend language SDKs expose a typed getFlag(key) accessor reading from an in-process cache with TTL-plus-push-invalidation backed by Postgres. The evaluation engine team (Phase 2) can begin building against the stable accessor interface without waiting for Phase 3.

Alternatives Considered

Config file in repository (YAML/JSON): All flags live as a checked-in file; git history serves as the audit trail; rollback is a revert commit. Pros: zero infrastructure, no migrations, simple local development. Cons: any flag change requires a commit + CI + deploy cycle, which defeats the "no deploy required for a toggle" requirement. Ruled out.

Redis as primary store: Flags live in Redis with Pub/Sub for invalidation and TTL for expiry. Pros: purpose-built for fast key/value reads, native expiry. Cons: introduces Redis as a new dependency (violating the no-new-external-dependency constraint), adds an operational runbook, and provides weaker query semantics for the admin search and audit log. Ruled out.

Separate flag microservice with its own database: A standalone service owns the flag store and exposes a gRPC/REST API. Pros: strong isolation, independent scaling. Cons: adds a network hop to every evaluation (violates the latency constraint), creates a new service to operate and monitor. Ruled out.

Recommendations

  • Use a feature_flags table in the primary Postgres instance. Leverage JSONB columns for targeting_rules and environments to allow flexible rule schemas without a migration for every new predicate type.
  • Use a separate feature_flag_audit_log table written by a Postgres trigger on every INSERT / UPDATE to feature_flags, capturing before_snapshot and after_snapshot as JSONB. This makes the audit trail tamper-evident at the application layer.
  • Implement the in-process cache as a concurrent hash map with a configurable TTL (default 30 s) and a LISTEN/NOTIFY subscriber thread that invalidates individual keys on flag mutation. The TTL is a safety net; LISTEN/NOTIFY is the fast path.
  • Publish a language-agnostic JSON Schema for the flag envelope early in Phase 1 so both SDK teams can work from the same contract.

Open Questions

oq1.1: What is the appropriate default cache TTL? 30 s is a reasonable starting point but may be too long for kill-switch scenarios where support needs a flag disabled within seconds. Should we support a per-flag maxStaleSecs override in the schema, or enforce a shorter global default?

oq1.2: What is the agreed data-retention policy for feature_flag_audit_log? The table is append-only by application convention, but we need legal/compliance sign-off on whether rows must be retained indefinitely or can be archived/pruned after N months. This affects schema design (partition by month?) and operational storage planning.

Design and document the flag data model and JSON Schema envelope

Write a short design doc defining the flag fields: id (UUID), key (unique URL-safe slug), description (text), owner (user/team identifier), flag_type (enum: boolean | percentage | multivariate), targeting_rules (ordered JSONB array of rule objects), default_value (JSONB), environments (JSONB map of environment name → override object), state (enum: active | archived), created_at, updated_at. Publish a JSON Schema that both SDK teams and the admin UI team will use as the contract. Get team sign-off before writing migrations.

Write Postgres migrations for feature_flags and feature_flag_audit_log

Write the forward migration creating both tables. For feature_flags: add a unique index on key, a GIN index on targeting_rules for JSONB containment queries, a check constraint on state and flag_type enums. For feature_flag_audit_log: add an index on (flag_id, occurred_at DESC) for the audit history query. Write a Postgres trigger function trg_flag_audit() that fires AFTER INSERT OR UPDATE on feature_flags and inserts a row into feature_flag_audit_log with actor taken from a session-local variable (SET LOCAL app.current_user_id = '...'). Provide a rollback migration that drops the trigger before dropping the tables.

Implement typed accessor library for Language A

Expose: createFlag(input: CreateFlagInput): Flag, getFlag(key: string): Flag | null, listFlags(filter: FlagFilter): Flag[], updateFlag(key: string, patch: UpdateFlagInput): Flag, archiveFlag(key: string): void, getAuditHistory(key: string, opts: PaginationOpts): AuditEntry[]. All public types are generated from the JSON Schema defined in t1.1 (using a code-gen step in CI). Mutation methods must set the Postgres session variable app.current_user_id before executing the statement so the audit trigger captures the actor. Include unit tests that run against a real Postgres container in CI using a test database.

Implement typed accessor library for Language B

Mirror the Language A accessor surface for the second backend language, sharing the same JSON Schema contract. The cache interface must use an identical abstract type so the Phase 2 evaluation engine can be ported without redesigning the storage boundary. Produce the same unit test coverage as Language A — including tests against a Postgres container. Add a golden-file test that feeds identical inputs through Language A and Language B accessor outputs and asserts identical flag representations, catching any envelope divergence at the source.

Implement in-process read-through cache with TTL and LISTEN/NOTIFY invalidation

Build the cache layer shared by both accessor libraries: a concurrent hash map keyed by flag key, populated on first read, refreshed by TTL expiry or by a Postgres LISTEN/NOTIFY event on channel flag_changes (published by a NOTIFY call inside the audit trigger). The NOTIFY payload is the flag key so only the affected entry needs invalidation. Expose forceRefresh(key) for admin UI kill-switch flows and test helpers. Make TTL configurable via environment variable (FLAG_CACHE_TTL_SECS, default 30). Integration tests must verify that a flag update is visible in the cache within one TTL cycle with LISTEN/NOTIFY disabled, and within 500 ms with LISTEN/NOTIFY enabled.

Write seed data and developer CLI tooling

Provide a seed script that inserts three representative flags into a local development database: a boolean kill-switch (enable-new-checkout), a 20% percentage rollout (new-dashboard-rollout), and a three-variant multivariate flag (pricing-page-variant). Add a developer CLI with commands flags list, flags get <key>, flags enable <key>, flags disable <key> usable from the monorepo dev toolchain. Document migration, seed, and teardown steps in the service README.

Phase 2 — Evaluation Engine

Build the low-latency evaluation library that resolves evaluate(flagKey, context) → variant entirely in-process using the Phase 1 cache. This phase covers the deterministic bucketing algorithm, rule evaluation semantics, environment inheritance, the circuit-breaker, telemetry emission, and the JSON-over-HTTP fallback endpoint. Target start: week 3 (parallel with Phase 3 backend).

Phase Goal

By the end of Phase 2, any service can call evaluate(flagKey, context) in either backend language and receive the correct variant in under 1 ms at p99 with no network round-trip. The HTTP endpoint is live for non-native callers behind the existing auth middleware. Sampled telemetry events are flowing to the internal analytics bus. A benchmark run confirms p99 < 1 ms on a warm cache with 500 active flags.

Alternatives Considered

Sidecar service per host (Unix socket): Move evaluation logic into a small sidecar process; app processes call it over a Unix socket. Pros: single language-agnostic implementation, logic deployed independently of app. Cons: even a Unix socket adds ~50–100 µs per call (violates p99 target), adds a new process to manage and monitor, complicates local development, and introduces a new failure mode (sidecar crash). Ruled out on latency and operational grounds.

Server-side evaluation with no cache (direct Postgres per call): Every evaluate() call queries Postgres directly. Pros: always-fresh, trivially correct. Cons: adds ~1–5 ms of network latency per call and scales database read load linearly with request rate — catastrophically violates the p99 constraint. Ruled out immediately.

Separate gRPC evaluation service: A standalone service exposes a gRPC Evaluate RPC. Pros: protocol-buffer contract is language-agnostic, easy to version. Cons: adds a network hop even over gRPC (~0.2–1 ms on LAN), requires a new service to operate, and is disproportionate for two backend languages. Ruled out; the JSON-over-HTTP endpoint satisfies the minority of non-native callers at acceptable latency.

Recommendations

  • Bucketing: Use murmur3_32(userId + ":" + flagSalt) mod 100 where flagSalt is a stable random string set at flag creation. The salt decouples rollout distributions so that users in the 20% bucket for flag A are not automatically in the 20% bucket for flag B.
  • Rule ordering: Evaluate targeting_rules in array order; the first matching rule wins and its variant is returned. Supported predicates in v1: user_id_in, org_id_in, env_is, percentage_rollout. New predicates can be added without a schema migration.
  • Environment inheritance: When evaluating in environment staging, if no staging-specific default is set, inherit from the production default. Staging targeting rules always override inherited defaults, so staging can always diverge from production for testing purposes.
  • Telemetry: Emit a sampled event (default 10% sample rate, configurable via FLAG_TELEMETRY_SAMPLE_RATE) to the internal analytics bus containing flagKey, variant, environment, contextHash (SHA-256 of userId, truncated to 8 hex chars for privacy), and evaluatedAt. Never include raw PII.
  • Circuit breaker: If the cache has no entry for a key and Postgres is unreachable, return the statically-configured fallback default (provided at SDK initialization) and log a warning. Never throw an exception into caller code.

Open Questions

oq2.1: Should LISTEN/NOTIFY be the primary invalidation path with TTL as a fallback, or should TTL be the primary path with LISTEN/NOTIFY as a best-effort optimisation? The answer determines how quickly a kill-switch takes effect during a database connection interruption — a product and operations trade-off that the team lead should decide with input from the on-call team.

oq2.2: Which hash function should be used for bucketing — MurmurHash3, xxHash, or FNV? If the monorepo already uses one of these for consistent hashing elsewhere (e.g., sharding), we should reuse it to avoid confusion in documentation and audits. Needs a quick grep of the existing codebase.

oq2.3: What is the correct telemetry sample rate default? 10% is a starting guess. We need an estimate of peak evaluations/sec at production scale to determine whether 10% creates unacceptable write pressure on the analytics bus, or whether a higher rate (50%?) would still be safe and provide better signal for anomaly detection during rollouts.

Implement and specification-test the deterministic bucketing algorithm

Write the bucketing function bucket(userId: string, flagSalt: string): number returning an integer in [0, 99] using the agreed hash function over the concatenated string userId + ":" + flagSalt. Write: (1) property-based tests verifying that over 100,000 synthetic user IDs the distribution is within ±2% of uniform per bucket; (2) stability tests confirming that the same inputs always produce the same output across restarts and implementations; (3) independence tests confirming that changing the salt produces a statistically independent distribution. Publish the algorithm as a short algorithm-spec document so it can be audited and identically re-implemented in Language B and the HTTP endpoint.

Build the core evaluation engine with rule ordering and environment inheritance

Implement evaluate(flagKey: string, context: EvalContext): EvalResult where EvalContext carries userId, orgId, environment, and an open attributes map. Traverse targeting_rules in order; return the first matching rule's variant. Supported v1 predicates: user_id_in: string[], org_id_in: string[], env_is: string, percentage_rollout: {threshold: number}. On no match: check environment-specific default (inheriting production's if staging default is null), then global default. Return an EvalResult containing variant and a reason string (e.g., "rule:2", "env-default:staging", "global-default") for observability. Include a NoopEvaluator that always returns the global default, usable in unit tests of callers.

Wire the evaluation engine to the Phase 1 cache and run latency benchmarks

Connect the evaluation engine to the in-process cache (t1.5). On a cache miss, block once to fetch from Postgres and prime the cache; subsequent calls for the same key are fully in-memory. Implement the circuit breaker: if Postgres is unreachable at cache-miss time, return the caller-supplied fallback default and emit a warning-level log event — never propagate the database error. Write a benchmark (using the language's native benchmark tooling) that runs 10,000 sequential evaluate() calls on a warm cache with 500 distinct flags loaded and asserts p99 < 1 ms. The benchmark must be reproducible in CI and block the build if the p99 regression exceeds 20%.

Port the evaluation engine to Language B with cross-language parity tests

Implement the full evaluation engine in Language B, reusing the bucketing algorithm specification from t2.1 and the cache interface from t1.4. Write a golden-file parity test suite: a JSON fixture file containing 50 flag definitions and 200 evaluation contexts with expected variant outputs. Both Language A and Language B engines must produce identical outputs for every fixture entry; divergence is a build-blocking failure. Run the same latency benchmark as t2.3 against the Language B implementation to confirm consistent p99 performance.

Build the JSON-over-HTTP evaluation endpoint and telemetry emitter

Expose POST /internal/flags/evaluate behind the existing auth middleware. Request: {"flagKey": "...", "context": {"userId": "...", "orgId": "...", "environment": "...", "attributes": {...}}}. Response: {"variant": ..., "reason": "..."}. The handler calls the Language A evaluation engine in-process (no extra network hop). Add request-level rate limiting (configurable, default 1,000 req/s per caller identity) and document the endpoint SLA. Implement the telemetry emitter as a shared module used by both Language A and Language B SDKs: on each evaluate() call, with configurable sampling probability, emit an event to the internal analytics bus. Hash userId before inclusion. Wire the emitter into both SDKs and verify via integration test that events appear on the bus.

Phase 3 — Admin UI

Build the self-service dashboard that lets engineers, PMs, and support staff manage flags from a browser without touching code or the database directly. The admin backend REST API is built in parallel with Phase 2 from week 3; the React UI follows once the API shape is stable. All surfaces sit behind the existing auth middleware and enforce RBAC.

Phase Goal

By the end of Phase 3, any authorized user can create, edit, archive, and search flags from a browser. Percentage rollouts are adjusted via a slider that shows a live bucketing preview. The audit history for any flag is one click away. Only flag owners and flag-admin role holders can modify production values; all other authenticated engineers can modify non-production values. The entire UI is integrated into the existing admin shell with no new auth flow.

Alternatives Considered

GraphQL API for the admin backend: A GraphQL schema would provide flexible querying for the flag list with arbitrary filter/sort combinations and efficient field selection. Pros: elegant for complex nested flag data. Cons: the existing admin surfaces all use REST, introducing GraphQL only for this feature adds a new framework dependency and operational surface area disproportionate to its benefit at this scale. Ruled out in favour of conventional REST endpoints consistent with the rest of the admin backend.

Standalone SPA served from a separate origin: Deploy the flag admin as a standalone app at a subdomain. Pros: isolated deployment, independent release cycle. Cons: requires a separate CORS policy, a duplicated auth integration, and a new build pipeline — significant overhead for a team of three under a six-week constraint. Ruled out; the flag admin is added as a route inside the existing admin shell.

Recommendations

  • Build the admin backend under the path prefix /api/admin/flags/ using the existing admin REST conventions (pagination, filter params, error shapes). This keeps the API consistent and makes it immediately familiar to any engineer who has touched the admin backend before.
  • Use optimistic UI updates: when an operator saves a change, update the local UI state immediately and roll back with an error banner on API failure. This makes the interface feel fast even if the Postgres write takes 50–100 ms.
  • Visualise the percentage slider as a 0–100 horizontal bar with a colour-coded segment for "in rollout." Include a "test user bucketing" input field: the operator types any user ID and the UI shows which variant that user would receive given the current (unsaved) slider value, using the same murmur3 bucketing logic re-implemented in JavaScript client-side.
  • Start building the UI against mock API responses (using an API contract derived from the JSON Schema) so the frontend engineer does not block on the backend being fully deployed.

Open Questions

oq3.1: Should the owner field be a single user ID, a team/group identifier, or support both? If team ownership is needed, we must resolve how team membership is sourced (from the existing identity/directory service?) before implementing the RBAC check for flags:edit-production.

oq3.2: Should non-owner engineers be able to freely edit staging and development environment values while production remains gated, or should all environment edits require owner/admin status? The UX diverges significantly: the former means showing enabled fields for non-prod and disabled fields for prod on the same form; the latter means the entire edit form is read-only for non-owners.

Implement and enforce role-based access control across API and UI

Extend the existing RBAC middleware with two new permission checks: flags:edit-production (granted to flag owner and any user with the flag-admin role) and flags:edit-nonprod (granted to all authenticated engineers). In the PATCH /api/admin/flags/:key handler, resolve which environments are being modified and apply the appropriate check per environment. In the admin UI, reflect permission state per environment section: disable production-value fields and show a lock icon with a tooltip; staging/dev fields remain editable. Add an "Request access" link pointing to the internal access-request workflow for users who need flag-admin escalation. Write integration tests covering: owner can edit production; non-owner engineer can edit staging but not production; flag-admin role holder can edit any environment.

Store flags in Postgres with an in-process cache rather than a config file or dedicated key-value store

Flags must be togglable without a deploy, which rules out a config file in the repository. Using Postgres as the store of record lets us leverage ACID transactions for the flag schema and audit log, LISTEN/NOTIFY for push cache invalidation, and row-level security for future access-control refinements — all on infrastructure that is already present and operationally understood. The in-process cache eliminates any network hop on the evaluation hot path, satisfying the p99 < 1 ms constraint without introducing Redis or any other new dependency.

Config-in-repo was appealing for its simplicity: zero new tables, free git history as the audit trail, and trivial local development. We chose against it because it requires a commit + CI + deploy cycle for every flag change, which defeats the stated goal of enabling support to kill a misbehaving feature without a deploy. If the team ever needs to dramatically simplify the stack, migrating back to config-in-repo would be feasible but would sacrifice self-service toggles.

Ship the evaluation engine as an in-process library, not a sidecar service

A sidecar would allow a single language-agnostic implementation and let evaluation logic be deployed independently of the main application. However, even a Unix-socket call adds ~50–100 µs of latency per evaluation, the sidecar becomes a new critical-path dependency (its crash degrades all flag evaluations), and it complicates local development setup. Since the monorepo has only two backend languages, writing thin native SDKs is tractable within the six-week scope. The in-process approach meets the hard p99 < 1 ms constraint and keeps the operational footprint flat.

The sidecar approach would have made it trivial to add support for additional languages (Python scripts, Go CLIs, etc.) without re-implementing evaluation logic. We should revisit this decision if the number of backend languages in the monorepo grows beyond two, or if flag logic becomes complex enough that maintaining two identical implementations is error-prone.

Use MurmurHash3 with a per-flag salt for deterministic percentage bucketing

Deterministic percentage rollout requires a fast, uniformly-distributed, stable hash function that can be identically re-implemented in multiple languages. MurmurHash3 (32-bit variant) is non-cryptographic (microsecond-fast), has excellent empirical distribution, has reference implementations in both target languages, and is simple enough to implement correctly in JavaScript for the admin UI's live bucketing preview. Hashing userId + ":" + flagSalt (where the salt is a stable random string set at flag creation) decouples rollout distributions across flags — a user in the 20% bucket for flag A is not automatically in the 20% bucket for flag B.

Implement the audit log via a Postgres trigger rather than application-layer writes

Capturing audit rows in a trigger on feature_flags guarantees that no mutation can bypass the audit trail, even if a future code path forgets to call the accessor library or a developer uses a raw SQL client in an emergency. The trigger reads the actor from a session-local variable (SET LOCAL app.current_user_id) set by the accessor library before each mutation. This approach is tamper-evident at the application boundary and eliminates an entire class of audit-gap bugs.

Application-layer audit writes (insert the audit row in the same transaction as the flag mutation) would be easier to test in isolation and more portable across databases. We chose the trigger approach because it is impossible to accidentally omit — the cost is that it requires careful session-variable management and makes the accessor library tests slightly more involved.

Stale cache during emergency kill-switch scenarios

If the Postgres LISTEN/NOTIFY channel is disrupted — for example due to a database connection drop or network partition — instances will not receive push invalidation events and will continue serving the cached flag value until TTL expiry. With a 30 s TTL, a broken feature could remain active for up to 30 s after support archives the flag, which may be unacceptably long depending on the severity of the incident.

Likelihood: Low — connection drops are rare in stable infrastructure, but they do occur during deployments and maintenance windows, precisely when operators may be actively toggling flags.

Mitigations: (1) Support a per-flag maxStaleSecs override so kill-switch-style boolean flags can use a shorter TTL (e.g., 5 s). (2) Expose a POST /api/admin/flags/:key/invalidate endpoint that triggers forceRefresh across all instances (via a broadcast NOTIFY). (3) Monitor LISTEN/NOTIFY connection health and alert on-call if a listener has been disconnected for >60 s.

Skewed percentage rollout due to non-uniform user-ID distribution

If production user IDs are not uniformly distributed (e.g., sequential integers from an auto-increment primary key, or UUIDs v1 with a MAC-address prefix), a hash function that performs poorly on structured inputs could produce a skewed bucket distribution. A "20% rollout" could actually reach 17% or 25% of users, undermining product's confidence in gradual rollouts and potentially causing unintended overexposure of a feature.

Likelihood: Medium — MurmurHash3 is generally robust, but it has known weaknesses on short structured inputs. The severity depends on the actual user-ID format in production.

Mitigations: Property-based tests in t2.1 verify distribution is within ±2% of uniform over 100,000 synthetic IDs. Before Phase 2 ships to production, run the same distribution test over a sample of 10,000 real (anonymised) user IDs from the production database and confirm the deviation remains within tolerance.

Evaluation latency regression as the flag count grows over time

The evaluation engine currently assumes a bounded number of active flags with modest targeting-rule counts. If the product accumulates hundreds of active flags, each with many complex rules, the in-process cache memory footprint and linear rule-evaluation time could grow to the point where p99 exceeds 1 ms under high concurrency.

Likelihood: Low in the first six months; medium over 12–18 months if the flag system becomes widely adopted.

Mitigations: (1) Enforce a soft limit of 20 targeting rules per flag in the admin UI and API (configurable by admins). (2) Run the latency benchmark (t2.3) with 500 flags and confirm p99 < 1 ms before Phase 2 ships. (3) Add a p99 evaluation-latency metric to the service dashboard so any regression is visible before it becomes user-facing.

Team timeline risk: Phase 1 slip compresses Phases 2 and 3

Phase 1 is on the critical path for both Phase 2 (evaluation engine depends on the accessor library) and Phase 3 (admin REST API depends on the storage layer). If Phase 1 slips past end of week 2 — due to schema iteration, migration issues, or engineer availability — the downstream phases are compressed and the six-week delivery window is at risk.

Likelihood: Medium — schema design often requires more iteration than estimated, and schema decisions made in Phase 1 are relatively hard to reverse once Phase 2 builds on them.

Mitigations: (1) Complete the flag data model design document (t1.1) in week 1 and get team sign-off before writing any migrations. (2) Phase 3 backend work (t3.1) can begin as soon as the JSON Schema envelope from t1.1 is agreed, using a temporary in-memory flag store — the Postgres layer can be swapped in once it is ready. (3) Maintain a lightweight weekly milestone check: if Phase 1 is not in CI by end of week 2, immediately triage scope to protect the admin UI launch.

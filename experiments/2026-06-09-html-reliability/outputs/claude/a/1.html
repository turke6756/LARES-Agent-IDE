Feature Flag System

A three-phase initiative (schema & storage, evaluation engine, admin UI) that lets engineering ship code dark, product run gradual rollouts, and support disable misbehaving features without a deploy. Estimated lift: three engineers over six weeks, no new external SaaS dependencies.

Framing

Success Criteria

  • Dark shipping: An engineer can merge code gated behind a boolean flag and deploy it to production without the feature being visible to any user until the flag is explicitly enabled.
  • Percentage rollouts: Product can ramp a feature from 0 % to 100 % of users in configurable increments; the same user always receives the same variant (stable bucketing).
  • Kill switch: Support can disable any active feature flag in under 30 seconds via the admin UI, without a code deploy or engineering intervention.
  • Evaluation latency: evaluate(flagKey, context) completes in under 1 ms at p99 in production, measured from within the application process.
  • Auditability: Every flag create, edit, archive, and environment-override action is recorded with actor, timestamp, and before/after values. Audit records are queryable from the admin UI.
  • Targeting correctness: Rules targeting by user ID, org ID, or environment resolve deterministically; unit tests cover all rule-ordering edge cases.
  • Multivariate support: At least one flag type supports N named variants (e.g., control, treatment-a, treatment-b) in addition to boolean on/off.

Scope

In scope:

  • Flag data model: key, description, owner, type (boolean / percentage / multivariate), targeting rules (user ID list, org ID list, environment), default value, lifecycle state.
  • A new feature_flags table and associated tables (flag_rules, flag_audit_log, flag_environments) in the primary Postgres database.
  • Database migrations, initial seed data (a system.kill-switch-example demo flag), and a rollback migration for each forward migration.
  • A typed accessor library (internal package) exposing getFlag(key), setFlag(…), and archiveFlag(key), usable from both backend languages in the monorepo.
  • A read-through in-memory cache inside the accessor library, invalidated via Postgres LISTEN/NOTIFY with a configurable poll-fallback TTL.
  • An evaluation engine library: deterministic hash-bucketing, ordered rule evaluation, environment inheritance, and the evaluate(flagKey, context) → variant surface.
  • A JSON-over-HTTP endpoint (POST /internal/flags/evaluate) for services in languages without a native SDK.
  • Sampled evaluation telemetry emitted to the existing internal event bus (one event per N evaluations, where N is configurable).
  • An admin dashboard page: flag list/search, create/edit form, per-environment overrides, percentage-rollout slider with live bucketing preview, and an audit-history view.
  • Role-based access: only the flag owner and users with the flag-admin role may edit production flag values.

Out of scope: A/B-test statistical analysis, scheduled rollouts, mobile SDKs, approval workflows, external SaaS feature-flag services, and any UI for managing the sampling rate of evaluation telemetry.

Constraints

  • No new external SaaS dependencies. All components must run on infrastructure already operated by the team. This rules out LaunchDarkly, Split, Flagsmith (cloud), or any managed service.
  • No network hop on the hot evaluation path. Flag evaluation inside a request must be served from an in-process cache. The Postgres or HTTP fallback may only be used on cache miss during startup or invalidation.
  • Existing auth middleware. The admin UI and HTTP evaluation endpoint must sit behind the same authentication and authorization middleware used by the rest of the application. No new auth primitives.
  • Team size and timeline. Three engineers, approximately six weeks. The design must be scope-controlled to fit; the evaluation engine and schema must be mergeable independently of the admin UI so parallel development is possible.
  • Backward compatibility. Adding flag evaluation to an existing request handler must not require changes to the handler's signature or response contract.

Assumptions

Auth middleware exposes user ID and org ID on every request context

The evaluation engine needs a context object containing at minimum userId and orgId to resolve user- and org-level targeting rules. We assume the existing auth middleware populates these fields in the request context object before any handler runs.

Invalidates if: the middleware does not set userId/orgId — we would need a middleware shim or a different targeting strategy.

Postgres LISTEN/NOTIFY is available and reliable in the production environment

The primary cache-invalidation mechanism relies on Postgres LISTEN/NOTIFY to push flag changes to all app instances. We assume the production database and network allow persistent connections with notification delivery. A poll-fallback TTL (default 30 s) exists as a safety net, but the design assumes NOTIFY is the primary path.

Invalidates if: the production Postgres is behind a connection pooler that drops async notifications — we would fall back to polling only and need to adjust the TTL.

Both backend languages can produce identical hash outputs for bucketing

Deterministic bucketing requires hash(userId + flagSalt) mod 10000 to return the same integer regardless of which language computes it. We assume both languages have access to MurmurHash3 (or a comparable algorithm) and that the monorepo already uses a shared hash utility, or one can be added trivially.

Invalidates if: one language lacks a suitable hash library — we would need to add a dependency or cross-validate with test vectors before shipping percentage rollouts.

The internal event bus can absorb sampled evaluation telemetry at production volume

Evaluation telemetry will be emitted to the existing internal event bus at a configurable sample rate (default 1 in 100 evaluations). We assume the bus has sufficient headroom; a load estimate should be confirmed in Phase 2 before finalizing the default sample rate.

Invalidates if: bus throughput is already near capacity — we would need to lower the default sample rate or write telemetry to a separate sink.

Implementation

Phase 1 — Flag Schema and Storage

Weeks 1–2. Establish the canonical data model, migrations, typed accessor library, and audit log. This phase produces the shared foundation that Phase 2 (evaluation) and Phase 3 (admin UI) both build on. No production flag evaluation happens yet; the accessor library is the only public surface.

Phase Goal

Ship a versioned Postgres schema for feature flags—including flag definitions, per-environment overrides, targeting rules, and audit history—paired with a typed accessor library that both backend languages can import to read and write flag records. The schema must be stable enough that Phase 2 can be built without further migrations; changes after this phase should be additive only.

Alternatives Considered

Config file in repo (YAML/JSON): Flags live in a version-controlled file, deployed with the application. Simple to reason about and inherently audited by git history. Rejected because it requires a code deploy to change any flag—defeating the kill-switch and instant-rollout use cases—and it scales poorly as flag count grows into the hundreds.

Dedicated key-value store (Redis primary): Flags stored directly in Redis, treating it as the source of truth. Fast reads, but Redis lacks relational querying for rule sets, has weaker durability guarantees than Postgres, and adds an operational dependency for what is essentially configuration data. Rejected in favour of Postgres-as-source-of-truth with a read-through cache.

Separate flags microservice with its own database: Flags owned by an independent service. Rejected because it introduces a network dependency on the hot evaluation path (violates the no-network-hop constraint) and adds operational complexity beyond a three-engineer team's budget.

Recommendations

Use the primary Postgres database with a new feature_flags schema namespace. Store flag definitions, rule sets, and per-environment overrides in normalized tables. Write a trigger-based audit log (flag_audit_log) that captures row-level changes automatically, so application code does not need to manually record every mutation. The typed accessor library wraps all SQL behind a stable interface; callers never write raw queries. Keep the schema simple in Phase 1—no complex JSONB blobs for rules; use a proper flag_rules table so rules are queryable and individually auditable.

Open Questions

Should environment inheritance be modeled at the schema level or deferred to the evaluation engine?

The brief says "staging defaults from production." One option is a parent_environment_id foreign key on the environments table. Another is to handle inheritance purely in the evaluation library (Phase 2). Deciding now affects whether Phase 1 migrations need to support the parent relationship, or whether Phase 2 can add it without a schema change.

What environments need to exist at seed time?

The seed migration should create the canonical environment records (production, staging, development). We need to confirm whether "development" is a single shared environment or a per-developer one, as this affects the cardinality of per-environment override rows.

Define flag data model and write Postgres migrations

Create the feature_flags schema with the following tables:

  • flags: id, key (unique), description, owner, flag_type (enum: boolean, percentage, multivariate), default_variant, lifecycle_state (enum: active, archived), created_at, updated_at.
  • flag_variants: named variants for multivariate flags (e.g., control, treatment-a).
  • flag_environments: per-environment override of enabled, default_variant, and rollout_percentage for a flag.
  • flag_rules: flag_id, environment_id, rule_type (enum: user_id, org_id), operator (enum: in_list, not_in_list), values (text array), variant, priority (integer for ordering).
  • environments: id, name, parent_environment_id (nullable FK to self).

Write a forward migration and a rollback migration. All migrations use the existing schema-migration tooling already in the monorepo.

Write seed data and example flags

Create a seed migration that inserts: the three canonical environments (production, staging, development); one example boolean flag (system.kill-switch-example) in the archived state; and one example percentage-rollout flag (system.percentage-example) set to 0% in all environments. Seed data is idempotent (uses INSERT … ON CONFLICT DO NOTHING). Document the seed migration as dev/test only; the production deployment pipeline applies forward migrations but skips seed migrations flagged as dev_only.

Implement trigger-based audit log

Create a flag_audit_log table: id, table_name, row_id, operation (INSERT/UPDATE/DELETE), changed_by (application user ID, set via SET LOCAL app.current_user_id = … in each transaction), before_value (JSONB), after_value (JSONB), changed_at. Write a PL/pgSQL trigger function that fires on AFTER INSERT OR UPDATE OR DELETE on flags, flag_environments, flag_rules, and flag_variants. The accessor library must set app.current_user_id at the start of every write transaction. Add an index on (table_name, row_id, changed_at DESC) for efficient audit-log queries.

Reversibility: High Blast radius: Low

Build typed accessor library

Create an internal package (@internal/feature-flags or the monorepo equivalent) exposing:

  • getFlag(key: string): Promise<Flag | null> — fetch flag definition from Postgres (used by admin operations, not the hot path).
  • listFlags(filter?: FlagFilter): Promise<Flag[]> — paginated list with optional filter by state, owner, environment.
  • createFlag(input: CreateFlagInput): Promise<Flag>
  • updateFlag(key: string, patch: FlagPatch): Promise<Flag>
  • archiveFlag(key: string): Promise<void>
  • setEnvironmentOverride(key: string, env: string, override: EnvOverride): Promise<void>
  • getAuditLog(key: string, options?: AuditLogOptions): Promise<AuditEntry[]>

All write methods accept and propagate actorId for the Postgres session variable used by the audit trigger. Unit tests cover the happy path and constraint violations (duplicate key, archive of already-archived flag).

Reversibility: High Blast radius: Low

Wire LISTEN/NOTIFY for cache invalidation signaling

Add a Postgres trigger on flags and flag_environments that calls pg_notify('flag_changed', NEW.key) on any INSERT, UPDATE, or DELETE. The notification payload carries only the flag key (not the full row) to keep payloads small. This is the push channel that Phase 2's in-memory cache will subscribe to. The trigger must be created in the same migration as the audit trigger to avoid a window where audit fires but invalidation does not. Write a smoke test that verifies the notification fires when a flag is updated via the accessor library.

Reversibility: Medium Blast radius: Low

Phase 2 — Evaluation Engine

Weeks 2–4 (overlaps Phase 1 after migrations land). Build the in-process evaluation library, in-memory cache with invalidation, language SDK wrappers, the HTTP evaluation endpoint, and sampled telemetry. This phase is the performance-critical core of the system; the 1 ms p99 target must be validated with benchmarks before Phase 3 begins.

Phase Goal

Deliver a production-ready evaluation library that any request handler can call synchronously to resolve a flag variant from an in-memory snapshot of all active flags, with sub-millisecond latency at p99. The cache must stay consistent with Postgres via LISTEN/NOTIFY push-invalidation; a time-bounded poll fallback ensures correctness even if the notification channel silently drops a message. Both backend languages in the monorepo must have idiomatic SDK wrappers. A JSON/HTTP endpoint covers all other callers.

Alternatives Considered

Sidecar service for evaluation: A small local process on each host serves evaluation requests over a Unix socket, allowing the cache to live outside the application process. Rejected: adds process management complexity, increases p99 latency by a local IPC round-trip (~0.05–0.2 ms), and offers no benefit over an in-process cache for a monorepo where we control both languages.

Poll-only invalidation (no LISTEN/NOTIFY): A background goroutine/thread re-fetches all active flags from Postgres every N seconds. Simpler to implement but means flag changes can take up to N seconds to propagate. Rejected as primary mechanism: a kill switch that takes 30 s to propagate is acceptable, but LISTEN/NOTIFY gives near-instant propagation at negligible cost given Phase 1 already wires it up.

Store evaluation results in Redis: Pre-compute and cache the result for each (flagKey, userId) pair. Rejected: the key space is too large to pre-warm, adds a network hop for any cache miss, and invalidation on rule changes would require flushing large key ranges.

Recommendations

Build a single FlagEvaluator object (instantiated once per process) that holds an in-memory snapshot of all active flag definitions and rules, loaded eagerly at startup. Subscribe to the Postgres LISTEN channel in a background goroutine/thread; on notification, reload only the changed flag record rather than the entire snapshot. The poll fallback should run every 30 seconds and reconcile any keys whose NOTIFY was dropped. The bucketing algorithm should use MurmurHash3 on "${userId}:${flagKey}:${salt}", map to the range [0, 9999], and compare against the rollout threshold. Document the exact algorithm and test vectors so both language SDKs can be verified to produce identical bucketing results.

Open Questions

What is the acceptable staleness window, and does the poll interval need to be configurable per environment?

A 30-second poll fallback is proposed. If a NOTIFY is dropped in production, a flag change could take up to 30 seconds to propagate. For the kill-switch use case, is 30 seconds acceptable, or should the TTL be shorter (e.g., 10 seconds) in production? Making the interval configurable per environment (shorter in prod, longer in dev) avoids over-polling in low-stakes environments.

What should the evaluator return when the flag store is unavailable at startup?

If the initial flag load from Postgres fails (e.g., DB is not yet reachable during a rolling deploy), the evaluator has no snapshot. Options: (a) block startup until flags load (fail-fast, safer for kill-switch integrity); (b) start with an empty snapshot and serve all default values. The choice has implications for zero-downtime deployments.

Implement deterministic hash-bucketing algorithm

Write a pure function bucket(userId: string, flagKey: string, salt: string): number that returns an integer in [0, 9999]. Use MurmurHash3 (32-bit, seed 0) applied to the concatenated string ${userId}:${flagKey}:${salt}. The salt is stored on the flag record and is generated once at flag creation time (UUID v4); it allows re-bucketing a flag without changing the user IDs by rotating the salt. Implement the function in both backend languages and write a shared test-vector file (JSON) with 50 known (userId, flagKey, salt) → bucket inputs and expected outputs. Both implementations must pass all 50 vectors. This ensures percentage rollouts are consistent regardless of which language handles a given request.

Reversibility: High Blast radius: Low

Build rule evaluation engine with ordering and environment inheritance

Implement evaluate(flagKey: string, context: EvalContext): EvalResult. Evaluation order:

  • If the flag is archived or disabled for the current environment, return the default variant immediately.
  • Evaluate rules in ascending priority order; the first matching rule wins and returns its variant.
  • If no rule matches and the flag is a percentage rollout, compute bucket(context.userId, flagKey, flag.salt) and compare against the rollout threshold.
  • Fall back to the per-environment default variant, then the global default variant.
  • Environment inheritance: if the current environment has a parent_environment_id, inherit any rule or override not explicitly set on the child environment.

Write table-driven unit tests for every branch (archived, disabled, rule match, percentage boundary, environment inheritance, fallback).

Reversibility: High Blast radius: Low

Build in-memory cache with LISTEN/NOTIFY push and poll fallback

Implement the FlagEvaluator singleton:

  • Startup: execute SELECT * FROM flags JOIN flag_rules … WHERE lifecycle_state = 'active'; build an in-memory map keyed by flag key.
  • Push invalidation: maintain a persistent Postgres connection subscribed to the flag_changed channel. On notification, fetch only the changed flag record and update the map atomically (reader-writer lock or copy-on-write slice).
  • Poll fallback: a background goroutine/thread re-fetches the full snapshot every 30 seconds (configurable) and merges updates. This corrects any missed notifications.
  • Metrics: expose cache hit count, notification count, and last-refresh timestamp for monitoring.
Reversibility: Medium Blast radius: Low

Build language SDK wrappers for both backend languages

Wrap the evaluation engine in idiomatic interfaces for each backend language in the monorepo:

  • Expose a top-level function matching each language's conventions (e.g., a package-level function in Go, a module singleton in Node/TypeScript).
  • Provide typed helper variants: evaluateBool(key, context), evaluateString(key, context) that assert the return type.
  • Add a getAll(context) method that returns a snapshot of all flag evaluations for the given context, useful for bootstrapping frontend applications.
  • Write integration tests that spin up a test Postgres instance (via the monorepo's existing test helpers), insert a flag record, call evaluate, then update the record and verify the cache reflects the new value within 100 ms.
Reversibility: High Blast radius: Low

Build JSON-over-HTTP evaluation endpoint

Register POST /internal/flags/evaluate behind the existing auth middleware. Request body: { "flagKey": string, "context": { "userId": string, "orgId": string, "environment": string } }. Response: { "variant": string, "reason": string }. The endpoint calls the same in-process evaluator as the SDKs—no additional Postgres calls. The reason field indicates which rule matched or whether the result is the default, aiding debugging. Rate-limit the endpoint to 10 000 req/s per instance to prevent accidental hot-path abuse; document that callers should use a native SDK where available.

Reversibility: High Blast radius: Low

Add sampled evaluation telemetry

After each evaluate() call, emit a telemetry event to the existing internal event bus at a configurable sample rate (default: 1 in 100 evaluations, controlled by the flags.telemetry_sample_rate config key). Event payload: flagKey, userId (hashed/pseudonymised), environment, variant, reason, latency_us. Sampling is implemented as if bucket(userId, flagKey, "telemetry") % 100 < sampleRate—using the same bucketing function ensures the same users are consistently sampled across rollouts, making per-user analysis coherent. The event emission must be non-blocking (fire-and-forget with a bounded buffer); a dropped event is acceptable.

Reversibility: High Blast radius: Low

Phase 3 — Admin UI

Weeks 4–6 (starts after Phase 2's evaluation library is stable; can be parallelized from week 4 with one engineer dedicated to the UI while the other two finalize Phase 2 integration tests and benchmarks). Delivers the dashboard page for creating, editing, searching, and archiving flags; per-environment overrides; a percentage-rollout slider; an audit-history view; and role-based access enforcement.

Phase Goal

Ship a fully functional admin UI that covers every flag management operation without requiring direct database access. The UI must enforce the RBAC policy (flag owners and flag-admin role may edit production values; all authenticated users may read flag state) and provide enough context—including the audit log—for support to safely operate the system without engineering assistance.

Alternatives Considered

Auto-generated CRUD UI (e.g., Retool, AdminJS): Rapid to scaffold but exposes raw database structure, makes custom interactions (the rollout slider, live bucketing preview) difficult, and typically requires an additional dependency. Rejected in favour of a hand-built page using the existing frontend stack for consistency and control.

CLI-only admin interface: Engineers use a CLI tool to manage flags; no UI. Acceptable for engineers but insufficient for the support-team kill-switch use case (non-technical users need a UI) and for product managers running percentage rollouts. Rejected.

Recommendations

Build the admin UI as a new route in the existing internal dashboard application (not a separate deployment). Use the existing design system components for forms, tables, and modals to minimise design work. The percentage-rollout slider should show a live preview of the bucketing boundary: given the current rollout % and the flag's salt, display a count of "approximately X% of production user IDs will receive the treatment variant" alongside a small sample of hashed user IDs that would fall in/out of the rollout—computed client-side using the same bucketing function exposed via the HTTP endpoint. RBAC must be enforced server-side in the API handlers (the UI should reflect it, but the server is the authority).

Open Questions

Who should hold the flag-admin role at launch, and how is the role assigned?

The RBAC model requires a flag-admin role distinct from the flag owner. We need to decide: (a) which existing roles or groups map to flag-admin; (b) whether role assignment is managed in the admin UI itself or via an existing user-management tool; and (c) whether support staff receive flag-admin or a narrower "can disable but not edit rules" capability.

Should the percentage slider operate in increments (e.g., 1%, 5%, 10%) or be fully continuous?

A fully continuous 0–100 slider stored as an integer percentage is simple. However, fine-grained control (0.1%) may be needed for very large user bases where even 1% represents a significant user count. The schema stores rollout_percentage as a smallint (0–10000 representing 0.00%–100.00%) to allow sub-percent precision if needed; the UI can expose either granularity.

Decisions

Store flags in Postgres, not a config file or dedicated key-value store

Decided 2026-06-09 · Team

Flag definitions, rules, and environment overrides are stored in normalized tables in the primary Postgres database, not in a YAML/JSON config file checked into the repo and not in a standalone Redis or etcd instance.

Rationale: The config-file approach requires a code deploy to change any flag, directly violating the kill-switch requirement. A standalone key-value store introduces a new operational dependency for a team of three and provides no meaningful latency benefit over Postgres when reads are served from an in-process cache. Postgres is already operated, backed up, and monitored; its LISTEN/NOTIFY mechanism provides the push-invalidation channel without additional infrastructure. Relational tables allow targeted rule queries and enable the trigger-based audit log.

Against: Postgres is not purpose-built for high-frequency configuration reads. If the in-process cache is ever bypassed (e.g., during a bug), direct Postgres reads could add latency to request handling. Mitigation: enforce cache-always in the evaluation path via code review policy and integration tests that verify no evaluation call reaches the database.

Use in-process cache with LISTEN/NOTIFY push invalidation and a poll fallback

Decided 2026-06-09 · Team

The evaluation engine maintains an in-process copy of all active flag definitions. Changes are propagated via Postgres LISTEN/NOTIFY (push) with a 30-second poll fallback to cover dropped notifications.

Rationale: In-process cache eliminates all network I/O from the hot evaluation path (satisfying the no-network-hop constraint). LISTEN/NOTIFY is available without additional infrastructure and provides near-instant propagation for the kill-switch use case. The poll fallback bounds worst-case staleness at 30 seconds even if the notification channel is interrupted, providing a safety net with no operational complexity.

Against: Each application instance holds its own independent in-memory copy; during the window between a flag change and cache invalidation, different instances may return different variants for the same user. This is an inherent tradeoff of in-process caching. For flag types where absolute consistency is critical (e.g., a kill switch), operators should accept a brief (~1 s on average with NOTIFY) propagation lag as acceptable.

Use MurmurHash3 for deterministic percentage bucketing

Decided 2026-06-09 · Team

Percentage rollout bucketing is computed as murmur3_32("${userId}:${flagKey}:${salt}") mod 10000. The salt is a UUID generated once when the flag is created and stored on the flag record.

Rationale: MurmurHash3 has well-tested implementations in every major language, is fast (sub-microsecond), and produces a uniform distribution that ensures percentage rollouts are actually uniform. The per-flag salt ensures that users who are in the top 10% of the hash space for one flag are not systematically correlated with the top 10% for every other flag. The salt rotation mechanism allows "re-bucketing" a flag (assigning users to different variants) without changing user IDs, which is useful for resetting a botched rollout.

Against: Changing the hashing algorithm in the future (e.g., to add a new input to the hash) would re-bucket all users on all percentage flags simultaneously, which could cause a sudden treatment → control reassignment for users in the middle of a rollout. Mitigation: treat the hash algorithm as a fixed contract; document it prominently; any change requires a coordinated rollout with all flag percentage thresholds reset to 0% first.

Scope the admin UI to the existing internal dashboard; do not create a separate deployment

Decided 2026-06-09 · Team

The flag admin UI is a new route within the existing internal tools/dashboard application rather than a standalone deployment or a Retool/AdminJS auto-generated interface.

Rationale: A separate deployment adds CI/CD pipeline work, separate auth wiring, and operational overhead. Auto-generated admin tools lack the customization needed for the rollout slider and audit diff view. The existing dashboard already handles auth, routing, and uses the established design system; adding a route is straightforward and leverages what the team already knows. With only six weeks and three engineers, minimising deployment complexity is a priority.

Risks

Cache staleness during rapid flag changes could cause a kill switch to be ineffective

Likelihood: Low. Severity: High.

If a flag is disabled (kill switch activated) but the application instances' in-process caches still hold the previous "enabled" value—due to a dropped NOTIFY and before the poll fallback fires—the feature will continue operating for up to 30 seconds (the poll interval) for users on those instances.

Mitigations: (1) Confirm LISTEN/NOTIFY reliability in the production environment before shipping Phase 2. (2) Consider making the poll interval configurable and defaulting to 10 seconds in production. (3) Document the propagation window in the runbook so support staff know that a kill switch takes effect within ~10–30 seconds, not instantly. (4) For features where instantaneous kill is required, the application handler can be coded to do a lightweight "is this flag archived?" database check on every request—trading latency for consistency only for that flag.

Hash bucketing algorithm change re-buckets all users simultaneously

Likelihood: Low. Severity: High.

If the bucketing algorithm or its inputs are ever changed (new field added to the hash string, algorithm swapped, salt column altered), all users on all active percentage rollouts would be re-assigned to different variants instantaneously. For a flag at 50% rollout, approximately 50% of users could flip from treatment to control or vice versa—invalidating any ongoing product experiments and potentially surfacing the old code path to users who had been shielded from it.

Mitigations: (1) Declare the algorithm a versioned contract; encode the version in the flag schema (bucketing_version column defaulting to 1). Any future algorithm change increments the version and can be adopted per-flag. (2) Write a prominent "do not change the hash algorithm" note in the evaluation engine code. (3) Before any bucketing change, require all affected flags to be set to 0% rollout in production.

Six-week timeline is at risk if auth middleware integration is more complex than anticipated

Likelihood: Medium. Severity: Medium.

The evaluation engine and admin UI both depend on the auth middleware exposing user ID, org ID, and role information in the request context. If this information is not currently available or requires a non-trivial middleware change, it could delay both Phase 2 (evaluation SDK context population) and Phase 3 (RBAC enforcement).

Mitigations: (1) Confirm auth middleware capabilities in week 1 as a prerequisite to Phase 2 work. (2) If role information is not available in the middleware, implement a lightweight flag_admin_users lookup table as a stopgap rather than blocking on middleware changes. (3) If user ID is not in context, fall back to no user-level targeting rules and percentage-only rollouts as a reduced-scope MVP.

Postgres LISTEN/NOTIFY is silently dropped by a connection pooler

Likelihood: Medium. Severity: Medium.

Many Postgres connection poolers (PgBouncer in transaction mode, RDS Proxy) do not support persistent connections required for LISTEN/NOTIFY. If the production environment routes database connections through such a pooler, push invalidation will silently fail; the system will degrade to poll-only without any error.

Mitigations: (1) Audit the production Postgres connection setup in week 1. (2) The LISTEN/NOTIFY connection must be a dedicated, persistent connection that bypasses any transaction-mode pooler—this is common practice and most poolers support a session-mode passthrough or a direct connection option. (3) If the pooler truly cannot support persistent connections, fall back to poll-only with a shorter interval (10 s) and log a startup warning.

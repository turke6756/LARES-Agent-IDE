Phase 3 — Admin UI

Weeks 5–6 · Operator-facing dashboard enabling flag management without engineering intervention.

Phase Goal

Deliver a fully functional admin dashboard integrated into the existing internal tools application. A product manager or support engineer with the appropriate role can create, target, adjust, and archive any flag without writing code or contacting engineering. Every change is captured in the audit history visible from the same UI. Role-based access is enforced server-side on all mutation endpoints.

Alternatives Considered

CLI-only admin interface

Limiting flag management to the CLI helper from t1.6 and deferring the UI was considered to reduce Phase 3 scope. Rejected because support engineers — the primary kill-switch users — do not have terminal access to production, and product managers should not require engineering involvement for routine rollout adjustments.

Generic low-code admin panel (self-hosted)

Using a self-hosted generic admin tool to generate CRUD screens from the schema was considered to reduce frontend work. Rejected because: (a) it would be a new infrastructure dependency; (b) the percentage-rollout slider with live bucketing preview requires custom UI logic poorly suited to generic admin frameworks; (c) the existing internal tools application provides a component library and auth integration we can reuse at no extra cost.

Recommendations

  • Build all flag UI pages within the existing internal tools React application — same component library, routing conventions, and auth context. No new app to deploy.
  • Enforce RBAC at the API layer (not only in the UI): flag mutation endpoints must check roles server-side so UI bypass is impossible.
  • Implement the rollout-slider bucketing preview client-side using the FNV-1a JS module (small, no external dependency) to give instant feedback without a round trip.
  • Audit history should be paginated, filterable by actor and date range, and deep-linkable by entry ID — the primary forensic tool during flag-related incidents.

Who is the default owner for flags migrated from the existing config-file store?

Store flags in Postgres with Redis read-through cache, not in config files

Decided 2026-06-09 · platform-engineering-lead

We evaluated two storage approaches: (1) a feature_flags table in the primary Postgres database with a Redis read-through cache, and (2) YAML/JSON files committed to the monorepo and deployed with the application.

We chose Postgres + Redis because:

  • Config files require a commit, CI pipeline, and deploy to change a flag — directly defeating the goal of killing a misbehaving feature without a deploy.
  • Runtime per-user and per-org targeting rules cannot be expressed in a static file without building a custom interpreter.
  • Postgres provides a natural home for the audit log with atomic transactional writes alongside flag mutations.
  • Redis is already in the stack and keeps read latency well inside the <1 ms p99 budget.

Argument against: Config files have zero operational overhead, are automatically reviewed in pull requests, and require no running infrastructure for local development and CI. If the Postgres + Redis stack proves operationally expensive to maintain for a flags system, a hybrid (config files for local/CI, database for production) could be revisited in a follow-up iteration.

Evaluation engine runs in-process as a shared library, not as a sidecar service

Decided 2026-06-09 · platform-engineering-lead

We evaluated two deployment models: (1) an in-process library linked directly into each consuming application, and (2) a sidecar process per pod communicating over a local Unix socket.

We chose the in-process library because:

  • The explicit constraint is zero additional network hops on the evaluation path. Even a Unix socket adds latency variance at p99 and complicates the deployment topology.
  • An in-process memory cache warmed at startup can serve evaluations in under 100 µs — well inside the 1 ms budget — with no IPC overhead.
  • A sidecar requires its own deployment artifact, health checks, resource limits, and runbook. That operational surface is disproportionate for a team of three.

Argument against: A sidecar isolates flag-store logic from application code and enables independent deployments of the evaluation engine without redeploying every consuming service. If the consuming service count grows beyond roughly 10, or if the evaluation logic becomes significantly more complex (ML-based targeting, remote experiments), a shared evaluation service would become the better trade-off and should be re-evaluated at that time.

Use FNV-1a (32-bit) hash modulo 10 000 for percentage bucketing

Decided 2026-06-09 · platform-engineering-lead

We chose FNV-1a (32-bit) over MurmurHash3, SHA-256-truncated, or simple integer modulo of the user ID. Reasons: FNV-1a is trivially implementable in both Go and TypeScript with no external library; it is fast enough to execute allocation-free on the hot evaluation path; and its avalanche properties are sufficient for the uniform-distribution requirement verified by property-based tests. Modulo 10 000 gives 0.01% granularity on rollout percentages — more than adequate for any realistic rollout. Per-flag salt ensures two flags at the same percentage do not always include the same users, preventing correlated exposure.

Redis outage stalls flag-change propagation to running instances

Likelihood: Low–Medium. Impact: Medium — during a Redis outage, new flag writes are durable in Postgres but will not propagate to in-process caches until Redis recovers or instances restart. Old evaluations continue from the in-memory snapshot; a flag kill-switch activated during the outage will not take effect until recovery.

Mitigations:

  • The 60-second poll fallback re-reads from Postgres (bypassing Redis) so the maximum staleness window during an outage is bounded by the poll interval.
  • Instrument a flags.cache_source{source="postgres_fallback"} metric that alerts on-call when the Redis path is unavailable.
  • Add a runbook section: during a prolonged Redis outage, a rolling restart of affected services will immediately re-warm caches from Postgres, picking up any flag changes made during the outage.

Bucketing divergence between Go and TypeScript SDKs causes inconsistent user exposure

Likelihood: Medium — subtle integer-overflow or string-encoding differences between languages can produce different FNV-1a outputs for the same inputs without being caught in casual testing. Impact: High — a user bucketed "in" by one service and "out" by another experiences inconsistent feature behaviour within a single request path, which is difficult to diagnose and erodes trust in the system.

Mitigations:

  • Canonical test-vector file (task t2.1): a JSON array of {userId, salt, expectedBucket} tuples generated by the Go reference. Both SDKs must pass all vectors in CI; a divergence blocks merging.
  • Cross-SDK integration test calling both implementations with identical inputs and asserting byte-identical outputs.
  • Code review of both FNV-1a implementations against the IETF reference spec before Phase 2 ships.

Admin UI scope creep pushes Phase 3 past the six-week deadline

Likelihood: Medium — stakeholders typically expand requirements once they interact with a working flag UI (scheduled rollouts, analytics, approval workflows). Impact: Medium — a late Phase 3 means support and product teams cannot self-serve flag changes, reducing the value of Phases 1 and 2.

Mitigations:

  • The out-of-scope list is documented in the framing tab and must be communicated to stakeholders at the Phase 3 kick-off meeting.
  • Weekly scope check-ins with the product owner during Phase 3 to surface and explicitly park new requests before they enter the sprint.
  • Any new request received during Phase 3 goes into a backlog item for a follow-up initiative, not into the current scope.

PgBouncer configuration blocks Postgres NOTIFY, breaking push invalidation

Likelihood: Medium — PgBouncer in transaction-pooling mode (common in high-concurrency stacks) silently drops LISTEN/NOTIFY without error. Impact: Low–Medium — without push invalidation, flag changes propagate only via the 60-second TTL poll, introducing a staleness window that may be unacceptable for an emergency kill-switch use case.

Mitigations:

  • Validate NOTIFY viability with the infrastructure team in Sprint 1 (assumption a4). Do not design the invalidation path assuming NOTIFY works until confirmed.
  • If PgBouncer blocks NOTIFY, open one dedicated long-lived Postgres connection (outside the pool) used solely for LISTEN flags_changed. Most stacks can afford one extra connection for this purpose.
  • If a dedicated connection is also infeasible, the 60-second TTL poll is the fallback. Document the staleness window in the operator runbook and evaluate whether it is acceptable for kill-switch scenarios.

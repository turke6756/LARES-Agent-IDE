Feature Flag System

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases over six weeks with a team of three engineers: (1) flag schema and storage, (2) evaluation engine, (3) admin UI. No new external SaaS; evaluation must stay in-process.

Success Criteria

  • Engineers can define a boolean, percentage-rollout, or multivariate flag and have it evaluated in production without a new deploy.
  • Flag evaluation resolves at p99 < 1 ms, measured end-to-end within the calling process with no synchronous network call on the hot path.
  • Percentage rollouts are deterministic: the same user always lands in the same bucket for a given flag and salt, consistently across all SDK languages.
  • An admin dashboard allows product and support to create, edit, override per environment, and archive flags — without writing code or filing an engineering ticket.
  • Every flag mutation is captured in an immutable audit log with actor, timestamp, old value, and new value; the audit log is viewable in the UI.
  • Only flag owners and users with the admin role can write production flag values; the restriction is enforced at the API layer.
  • The system introduces zero new external SaaS dependencies and runs entirely behind the existing auth middleware.
  • All three backend-language SDKs pass a shared canonical bucketing compatibility test table before any SDK ships to production.

Scope

In scope:

  • Flag model: key (slug), description, owner, type (boolean / percentage rollout / multivariate), targeting rules (user ID, org ID, environment), default value, lifecycle state (active / archived).
  • Postgres-backed storage in a new feature_flags table on the existing cluster; per-environment override table; append-only audit log with DB trigger.
  • Read-through in-memory cache with push-or-poll invalidation; migrations; seed/fixture data.
  • Typed accessor library in each of the monorepo's two backend languages.
  • Evaluation engine: deterministic percentage bucketing, rule ordering, environment inheritance (staging inherits production default when no override row exists).
  • JSON-over-HTTP evaluation endpoint for services that cannot embed a native SDK.
  • Sampled evaluation telemetry events routed through the existing analytics pipeline.
  • Admin UI: flag list/search, create/edit forms, per-environment override panel, rollout slider with client-side bucketing preview, audit history view, RBAC enforcement.

Out of scope:

  • Full approval/change-management workflow (PR-style review before flag mutations).
  • A/B test statistical analysis or significance calculations.
  • Scheduled (time-based) rollouts.
  • Mobile SDKs (iOS, Android).
  • Any new external SaaS (LaunchDarkly, Unleash, Statsig, Split, etc.).

Constraints

  • No external SaaS: The entire system must be self-hosted on existing infrastructure. No new vendor contracts or third-party API dependencies.
  • Zero added network hops on the evaluation hot path: Flag evaluation must resolve entirely in-process from a local cache; no synchronous RPC during a live request.
  • Existing auth middleware: All admin UI routes and internal API endpoints must be protected by the existing auth middleware; no new authentication surface area.
  • Existing Postgres cluster: The primary Postgres cluster is the source of truth. No new database engines or infrastructure components.
  • Audit log immutability: Audit records may never be updated or deleted once written; enforced at the DB layer via trigger and missing DELETE/UPDATE grants on the audit table.
  • Team and timeline: Three engineers, approximately six calendar weeks.

Assumptions

Exactly two backend language runtimes in the monorepo

We assume the monorepo runs exactly two server-side language runtimes (e.g., Go and TypeScript/Node). The native evaluation SDK will be written for those two; every other consumer uses the JSON-over-HTTP fallback. If a third runtime is in active use, SDK scope must be renegotiated or it must be declared a fallback consumer.

Cache is seeded from a source with negligible replication lag

We assume the read-through cache is populated from the Postgres primary or a synchronous replica. If flags are read from an asynchronous replica, the in-process cache version counter may race with replica catch-up, requiring additional fencing in the invalidation logic.

Evaluation telemetry can flow through the existing analytics pipeline at low sample rate

We assume a 1–5% sample rate produces a volume of evaluation events that the existing structured-logging or analytics pipeline handles without modification. If evaluation volume is extremely high (e.g., billions of requests/day), the telemetry story will need a dedicated ingestion path — a separate workstream.

The admin dashboard can be added as a route group in the existing admin web app

We assume the existing admin web application's stack (component library, routing, session handling) is capable of hosting the flag management UI as a new route group, avoiding the need to build and deploy a standalone SPA.

Phase 1 — Flag Schema and Storage

Establish the foundational data model, Postgres migrations, caching layer, typed accessor library, and audit history. This phase is entirely backend infrastructure — no user-visible product surface — and is the prerequisite for Phases 2 and 3. Target completion: end of week 2.

Phase Goal

Any backend service can read a flag value via a typed accessor call that resolves from a local in-memory cache. Every flag mutation is durably recorded in an append-only audit log enforced at the database layer. The Postgres schema is deployed and migrated in all environments; seed data covers at least three representative flags (one of each type); the accessor library has ≥ 80% branch coverage in CI tests.

Alternatives Considered

  • Config files checked into the monorepo (rejected): YAML/JSON flag definitions in the repo were attractive because git history provides a free audit trail and PRs provide a review gate. Rejected because any flag change requires a deploy, which defeats dark shipping, emergency kill-switches, and gradual rollout as core use cases.
  • Redis as primary store (rejected): Redis was considered for its sub-millisecond reads. Rejected because Redis introduces a new required infrastructure component, its durability guarantees are weaker than Postgres, and it cannot easily serve as the backing store for a SQL-queryable audit log. Redis remains available as a future caching layer if Postgres LISTEN/NOTIFY proves insufficient.
  • Third-party flag storage SaaS (rejected by constraint): LaunchDarkly, Unleash, and Statsig all offer managed flag storage. Ruled out by the no-new-external-SaaS constraint.

Recommendations

Use a feature_flags table in the existing Postgres cluster as the source of truth. Layer a process-local in-memory cache (immutable snapshot pattern — swap atomically on update, read without locks) on top, seeded at service startup. Use Postgres LISTEN/NOTIFY as the preferred invalidation signal; fall back to a 60-second TTL so a lost connection never leaves a process permanently stale. The typed accessor library should be the only way application code reads flag values — no direct table queries from services.

Keep the audit log as a separate table with a DB-level trigger; this ensures no mutation — even a direct SQL UPDATE by a DBA — can bypass logging.

Open Questions

Cache invalidation: LISTEN/NOTIFY vs. short-poll

Postgres LISTEN/NOTIFY delivers invalidation in < 100 ms but requires a persistent idle connection per process — potentially costly if we run hundreds of service instances. Short-polling every 30 s is simpler but allows up to 30 s of stale flag data. We need to know our process count and connection-pool headroom before committing to LISTEN/NOTIFY as the primary mechanism.

Audit log retention and archival policy

The brief requires an immutable audit log but does not specify retention duration or whether old records need to be moved to cold storage. This affects schema design (range partitioning by month vs. a single large table) and the operational runbook. Engineering needs a decision from legal/compliance before finalising the schema.

Define and migrate the feature_flags Postgres schema

Write the reversible migration that creates feature_flags with: id (UUID PK), key (unique text, slug-validated), description (text), owner (text, references users table), flag_type (enum: boolean | percentage | multivariate), targeting_rules (JSONB — ordered array of rule objects each carrying field, operator, values, and variant), variants (JSONB — named variant map for multivariate flags), default_value (JSONB), state (enum: active | archived), created_at, updated_at. Add a partial unique index on key where state = 'active' to prevent duplicate active keys while allowing re-use of archived keys. Down migration must cleanly drop the table.

Define and migrate the flag_audit_log table and trigger

Create append-only flag_audit_log: id (UUID PK), flag_id (FK to feature_flags), actor_id (text — user identifier from session), action (enum: created | updated | archived), old_value (JSONB, nullable for creates), new_value (JSONB), changed_at (timestamptz, default now()). Install a Postgres trigger on feature_flags AFTER INSERT/UPDATE that appends a row to flag_audit_log automatically. Revoke DELETE and UPDATE privileges on flag_audit_log from the application DB role to enforce immutability. The trigger must be tested in the migration integration test.

Define and migrate the flag_environment_overrides table

Create flag_environment_overrides: composite PK on (flag_id, environment), where environment is an enum (production | staging | development); override_value (JSONB); updated_at; updated_by (text). When evaluating a flag, the engine checks this table for the requested environment first; if no row exists, it falls back to the base feature_flags.default_value (i.e., staging inherits production unless explicitly overridden). Attach the same audit-log trigger pattern from t1.2.

Implement the read-through in-memory cache with invalidation

Build a cache module shared by both language SDKs: at startup, load all active flags and environment overrides from Postgres into an immutable snapshot map keyed by flag key. On each write, atomically swap the snapshot reference so readers never observe a partially updated state. Implement the chosen invalidation mechanism (LISTEN/NOTIFY preferred; polling fallback). Expose metrics counters for cache hits, misses, and invalidation events. The cache module is a shared dependency — instantiated once per process at startup, injected into the accessor library.

Build the typed accessor libraries (one per backend language)

Write a thin accessor library in each of the monorepo's two backend languages. Public API: FlagClient.getBool(key, context, defaultValue) → bool, FlagClient.getVariant(key, context, defaultValue) → string, FlagClient.getRawFlag(key) → FlagRecord | null. The library reads from the shared cache (t1.4) and never issues a DB query on the hot path — Postgres is only hit at startup or after an invalidation triggers a cache refresh. Typed return values; no JSONB leaking into application code. Include a quickstart README and ≥ 80% branch test coverage.

Seed data and end-to-end integration test

Write seed/fixture data covering all three flag types: enable_new_checkout (boolean, default false), new_search_algorithm (percentage, 10% rollout), and homepage_hero_variant (multivariate, three variants: control, banner_v2, banner_v3). Write a CI integration test that validates the full round-trip: seed → accessor reads correct default → mutate flag → audit log row appears → cache invalidates → accessor reads updated value. This test must run against a real Postgres instance (not mocks) and is a CI gate for Phase 1 completion.

Phase 2 — Evaluation Engine

Harden and expose the evaluation logic built on the Phase 1 foundation: deterministic percentage bucketing, rule ordering semantics, environment inheritance, a JSON-over-HTTP fallback endpoint, and sampled evaluation telemetry. Phase 2 ships the SDKs to production and establishes the performance gate. Target completion: end of week 4.

Phase Goal

Any service in the monorepo can call evaluate(flagKey, context) → variant in under 1 ms at p99 with no network call. Both native SDK languages pass the canonical cross-language bucketing compatibility test table. The JSON-over-HTTP endpoint is deployed, documented in the internal API catalog, and used by at least one non-SDK consumer in staging. Sampled evaluation telemetry is flowing into the analytics pipeline and queryable.

Alternatives Considered

  • Sidecar process for evaluation (rejected for hot path): Placing evaluation in a per-host sidecar daemon would simplify the SDK to a thin HTTP client and centralise cache management. Rejected because a loopback HTTP call still violates the "no added network hop" constraint for latency-sensitive request paths. The sidecar concept survives only as the implementation strategy for the JSON-over-HTTP fallback endpoint, where callers already accept network latency.
  • WebAssembly for cross-language bucketing parity (deferred): Compiling the bucketing function to a WASM module and calling it from all languages would guarantee byte-for-byte equivalence. Deferred because WASM tooling complexity exceeds the time budget; the canonical test table (t2.2) achieves the same safety guarantee with simpler tooling.
  • FNV-1a vs. MurmurHash3 for bucketing (open): Both produce fast, well-distributed 32-bit hashes suitable for percentage bucketing. MurmurHash3 has more prior art in flag systems. FNV-1a is simpler to implement identically across languages from a specification. Decision deferred to implementation; the compatibility test table enforces equivalence regardless of choice.

Recommendations

Embed the evaluation algorithm in the Phase 1 accessor library — same package, no new deployment unit. Evaluation algorithm: (1) load flag snapshot from in-process cache; (2) if flag is archived, return default; (3) walk targeting rules in declaration order, return the first matching rule's variant; (4) if flag type is percentage, apply deterministic bucketing: hash(userId + ":" + flagSalt) mod 10000 / 100.0 → float in [0, 100); fire if result < threshold; (5) fall through to the environment-resolved default value.

Environment inheritance: if no flag_environment_overrides row exists for the requested environment, use the base feature_flags.default_value. Do not automatically promote staging overrides from production — the inheritance is one-way from the base flag, not environment-to-environment, to avoid unintended cascades.

Open Questions

Telemetry sample rate: global vs. per-flag configuration

A single global sample rate (e.g., 1%, configurable via an env var) is operationally simple and avoids SDK API complexity. Per-flag sample rates allow high-traffic flags to be sampled more aggressively while leaving low-traffic flags at 100%. Since we are not doing A/B statistics in this phase, a global rate is likely sufficient — but product should confirm before we hard-code the SDK interface, as changing it later is a breaking change.

JSON-over-HTTP endpoint: embedded route vs. shared sidecar

Should the HTTP endpoint live as an additional route in each existing service, or as a dedicated shared microservice? Embedding avoids a new deployment unit but ships extra surface area to every service. A shared service is a single deployment but adds a real network hop (not just loopback) and a new service to operate. The answer depends on how many non-SDK consumers we expect and whether the operations team is comfortable with a new service.

Implement the core evaluation algorithm

Write the evaluate(flagKey string, ctx EvalContext) EvaluationResult function (naming follows the primary SDK language; mirror in the second). EvalContext carries: userId, orgId, environment, and an open attributes map[string]any for forward compatibility. EvaluationResult carries: variant (the resolved value, typed), source (enum: rule | percentage | default), matchedRule (index of matched rule or -1), flagVersion (for telemetry correlation). Rule operators to support at launch: in (value in list), not_in, equals. Target fields: userId, orgId, environment, and top-level keys from attributes.

Implement deterministic bucketing with cross-language compatibility tests

Write the bucketing function: bucket(userId, flagSalt string) float64 — hash the UTF-8 bytes of userId + ":" + flagSalt, take the unsigned 32-bit result mod 10000, divide by 100.0 to produce a float in [0, 100). Produce a canonical reference CSV of 50 rows: (userId, flagSalt, expectedBucket rounded to 4 decimal places). Check this CSV into /testdata/bucketing_compat.csv. Port the bucketing function to both SDK languages and write a parameterised test that reads the CSV and verifies all 50 cases match exactly. Any future SDK must pass this table as a CI gate before merging.

Package and document native SDKs for both backend languages

Ensure each SDK language has a first-class importable package: exports evaluate, getBool, getVariant, and a NewFlagClient(cache) constructor. SDKs share the in-process cache instance from Phase 1 — passed in as a dependency, not re-created. Write a five-line quickstart example, full type signatures, and a note that NewFlagClient must be called once at service startup (not per-request). Add the package to the internal developer portal's SDK catalog. Write integration tests that exercise a full evaluation round-trip in each language.

Build the JSON-over-HTTP evaluation endpoint

Implement POST /internal/flags/evaluate. Request body: {"flagKey": "...", "context": {"userId": "...", "orgId": "...", "environment": "...", "attributes": {...}}}. Response: {"variant": ..., "source": "rule|percentage|default", "flagVersion": "..."}. Protect with the existing auth middleware (internal token or session). Validate request schema; return 400 on missing flagKey; return 404 if flag does not exist. Apply a 10 ms server-side timeout on the evaluation call. Document in the internal API catalog with curl examples. Rate-limit at the service level to prevent abuse.

Add sampled evaluation telemetry

After each evaluate() call, asynchronously emit a structured event at the configured sample rate (default 1%, overridable via env var). Event schema: flag_key, variant, source, user_id, org_id, environment, flag_version, evaluated_at (ISO-8601). Emit via the existing structured-log or analytics event emitter — no new infrastructure. The emit call must be non-blocking (fire-and-forget on a background goroutine/promise) and must never cause evaluate() to block or throw. Write a test that runs 10,000 synthetic evaluations and asserts the emit count is within ±20% of the expected sample rate.

Write p99 latency benchmark and establish CI performance gate

Add a micro-benchmark that runs 100,000 sequential evaluations against an in-memory flag set (no Postgres I/O, no network) and reports p50, p95, p99, and p999 latencies. Benchmark scenarios: (a) boolean flag — simplest path, (b) 50% rollout — bucketing path, (c) five-rule targeting chain — worst-case rule walk. Assert p99 < 1 ms. Wire the benchmark into CI as a non-blocking advisory check during Phase 2; promote to a blocking merge gate before Phase 3 ships to production. Record the baseline numbers in the architecture decision log.

Phase 3 — Admin UI

Build the operator-facing dashboard within the existing admin web application: create, edit, search, and archive flags; manage per-environment overrides; visualise percentage-rollout bucketing; browse the audit history; and enforce role-based access. Target completion: end of week 6.

Phase Goal

A non-engineer product manager can, without writing code: create a boolean flag, set a 10% rollout in production, verify that specific test user IDs fall inside or outside the cohort using the bucketing preview, and kill-switch the flag — all in under five minutes. Every action produces a visible audit log entry. An unauthorised user attempting to write a production override is rejected with a clear error message both in the UI and at the API layer.

Alternatives Considered

  • Extend existing settings admin panel (rejected): Reusing the existing key-value settings editor would save scaffolding effort. Rejected because the existing panel has no concept of structured rules, multi-environment views, or percentage sliders — adapting it would require more refactoring than building a dedicated route group.
  • Standalone SPA (rejected): A fully separate single-page application would allow independent deployment. Rejected because it duplicates auth session handling, component library, and deployment pipelines — unnecessary complexity for a feature that lives inside the same operator-facing domain as the rest of the admin app.
  • Read-only UI, API-only mutations (rejected): Requiring curl/Postman for mutations was considered as a scope-reduction option. Rejected because it undermines the self-service goals for product and support, which are the primary non-engineering users of this system.

Recommendations

Add the flag dashboard as a new route group (/admin/flags/...) in the existing admin web app, sharing the existing session, component library, routing, and form validation utilities. Implement RBAC at the API handler layer (not just UI guards) so that unauthorised mutations are rejected with HTTP 403 even from direct API calls. For the rollout slider bucketing preview, re-implement the bucketing hash function in JavaScript (derived from the canonical test table in t2.2) so the preview runs entirely client-side without a round-trip — this makes the interaction feel instant.

Define a Phase 3 MVP cut-line before week 4: the minimum viable admin UI is flag list, create, edit (boolean only), and kill-switch toggle. The richer features (rollout slider, audit view, multivariate editing, RBAC) follow as the second half of Phase 3.

Open Questions

RBAC: single-user owner vs. team/group ownership

The brief specifies "flag owners and admins can edit production values." Ownership as a single user is simple to implement but creates bottlenecks when the owner is unavailable. Team-based ownership requires group primitives that may not exist in the user system today. Engineering needs product to decide before the edit form and API authorisation logic are built.

Targeting rule builder UI scope at launch

The data model supports arbitrary JSONB rule arrays with AND/OR semantics, but building a full visual rule builder is significant UI work. A simpler first cut could support only user-ID allowlists and percentage rollouts in the UI, with org and environment targeting only editable as raw JSON. Product should specify the minimum required rule types before UI development starts.

Build the flag list and search page

Create GET /admin/flags: a server-rendered or client-paginated table of all flags. Columns: key, description, type badge, state badge, owner, last-modified date. Filters: state (active / archived / all), flag type, owner. Full-text search over key and description, debounced. Archived flags shown in a secondary tab or with visual dimming. Clicking a row navigates to the flag detail page. Empty state with a "Create your first flag" CTA.

Build the flag create and edit forms

Create /admin/flags/new and /admin/flags/:key/edit. Fields: key (slug-validated, kebab-case, immutable after first save with a tooltip explaining why), description, owner (user picker from existing user directory), flag type selector (changing type resets the value fields with a confirmation), default value (rendered as a boolean toggle, a 0–100 number input, or a variant-name list depending on type), targeting rules section (MVP: user-ID allow-list textarea and environment multi-select), state toggle (active / archived with a confirmation modal for archiving). API-enforced: production edits restricted to owner or admin role; UI reflects this with disabled fields and explanatory tooltip.

Implement the per-environment override panel

On the flag detail page, add an "Environments" section showing a row for each environment (production, staging, development). Each row displays: the current override value (if any), or "Inheriting base default" in muted text; an "Edit Override" button that expands an inline form; and a "Reset to base default" action for staging and development. Saving writes to flag_environment_overrides via the admin API. Visual distinction is critical: overrides render with a solid border; inherited values render with a dashed border. RBAC: production override edits gated to owner/admin; staging/development edits available to any authenticated user.

Build the percentage-rollout slider with live bucketing preview

For flags of type percentage, add a rollout slider (0–100%, 1% steps) on the edit form. Below the slider, a textarea accepts a newline-separated list of user IDs (up to 500). As the slider value or the user-ID list changes, a client-side JavaScript function (derived directly from the canonical bucketing test table, verified against t2.2 values) recomputes which listed users would receive the rollout variant and displays: "N of M users listed would see the new variant." Colour-code matched vs. unmatched users in the list. This preview is purely informational — it matches the production bucketing algorithm exactly and requires no server round-trip.

Implement the audit history view

On the flag detail page, add an "Audit History" tab that fetches from a paginated GET /admin/flags/:key/audit endpoint (reads from flag_audit_log). Display a reverse-chronological timeline: actor avatar/name, action label, relative timestamp (hover for absolute), and a collapsed diff that expands on click to show old vs. new values as pretty-printed JSON side-by-side. Pagination: 25 entries per page. No edit or delete controls — display only. Include a "Export CSV" button for compliance use cases; the export covers the current flag's full audit history (not paginated).

Enforce RBAC at the API layer with integration tests

Add an authorisation middleware to all flag mutation API endpoints. Rules: (a) any authenticated user may read flags and write staging/development overrides; (b) only the flag's owner or a user with role admin may write production overrides, archive a flag, or change the flag owner. Enforce these rules in the API handler before any DB write — not just in the UI. Write integration tests covering: owner can edit production, admin can edit production, non-owner non-admin is rejected with 403, unauthenticated request is rejected with 401. Mirror these rules in the UI by disabling edit controls and showing a tooltip explaining the restriction when the current user lacks permission.

Postgres as source of truth; no config-file-in-repo approach

We chose mutable Postgres storage over YAML/JSON flag definitions checked into the monorepo. The defining constraint is that flag changes must take effect immediately without a deploy — that is the primary value proposition of the entire system (dark shipping, emergency kill-switch, gradual rollout). A config file in the repo cannot satisfy this because any change requires a commit and a CI/CD pipeline run, which may take minutes to hours. Postgres gives us immediate consistency, transactional writes, SQL-queryable history, and the trigger-based audit log that enforces immutability of changes. The in-process cache satisfies the read latency requirement without making Postgres the bottleneck on the hot path.

Config files would have been preferable if mandatory peer review before any flag change was a hard requirement, since git PRs provide that workflow for free and with full history. We are explicitly deferring a formal approval workflow to a future iteration, so this advantage does not apply today. If compliance requirements later demand a review gate, the config-file approach should be revisited as a complementary mechanism (e.g., flags must be defined in config before they can be enabled via the DB).

Evaluation is an in-process library; no sidecar on the hot path

The evaluation engine ships as a library embedded in each service process, not as a sidecar or remote microservice on the request hot path. This is a direct consequence of the "no added network hop" constraint: even a loopback HTTP call to a localhost sidecar adds measurable latency at p99 and introduces a failure mode (sidecar unavailable) on every request. The JSON-over-HTTP endpoint exists as a development convenience and fallback for services that cannot embed a native SDK, but those callers explicitly accept the latency and availability tradeoff. Telemetry emits are fire-and-forget and asynchronous, so they do not block the evaluation return path.

A shared sidecar would centralise cache management, reducing per-process memory usage and making cache invalidation state globally consistent across all processes on a host. If we run a large number of service instances and per-process cache memory becomes a material cost (e.g., a large flag set across hundreds of services), a shared sidecar model should be re-evaluated. This is worth tracking as the flag count grows.

Cache invalidation lag causes stale flag evaluations

If the invalidation mechanism (LISTEN/NOTIFY or polling) fails, is delayed, or a connection is silently dropped, processes will continue serving stale flag values until the next successful invalidation or TTL expiry. For a kill-switch flag (disabling a broken feature), this lag could mean the broken code path continues running for tens of seconds or minutes after the flag is toggled off. Likelihood: Medium. Impact: High (the kill-switch use case is safety-critical). Mitigation: (1) Set a maximum TTL of 60 s as an unconditional fallback — even if push invalidation is working, the cache is re-validated every 60 s. (2) Instrument a metric for cache-version drift between the DB and each process; alert when any process is more than 2 TTL periods behind. (3) Document an emergency runbook: rolling service restart forces full cache rehydration in under 2 minutes for typical fleet sizes.

Bucketing hash divergence across SDK languages corrupts percentage rollouts

If the two native SDK languages implement the bucketing hash function with subtle differences — different byte encoding of the input string, different handling of signed vs. unsigned integer overflow, different floating-point rounding — users will land in different buckets depending on which service evaluates the flag. This silently corrupts percentage-rollout semantics: the same user might be in the rollout cohort in Service A but not in Service B, producing inconsistent feature experiences. Likelihood: Medium (cross-language hash equivalence is easy to get wrong in subtle ways). Impact: High (undermines the core correctness guarantee of percentage rollouts). Mitigation: The canonical bucketing test CSV (t2.2) is a CI-blocking gate for both SDKs. A shared specification document (not just code) defines the exact byte encoding of the input. Any future SDK must pass the same table before merging.

Six-week timeline is tight; Phase 3 UI may be squeezed

If Phase 1 encounters unexpected schema complexity (e.g., the audit log retention decision requires partitioning), or Phase 2 cache-invalidation design takes longer to settle, Phase 3 will compress. Phase 3 contains the most surface area (CRUD forms, slider, audit view, RBAC) and requires UI work that is harder to parallelise across the three engineers than pure backend work. Likelihood: Medium. Impact: Medium (the system still functions without the admin UI; flag changes fall back to direct API calls). Mitigation: Define an explicit Phase 3 MVP cut-line before week 4: at minimum, flag list, create (boolean type only), and a kill-switch toggle. Richer features (rollout slider, audit view, multivariate editing, full RBAC) are the second half of Phase 3 and can slip to a fast-follow if needed. Communicate the cut-line to product as a known risk before coding starts.

Postgres connection pressure from LISTEN/NOTIFY invalidation

If LISTEN/NOTIFY is chosen as the primary invalidation mechanism (see oq1.1), each service process holds an idle persistent connection to Postgres. On a large fleet (many service instances per host), this could exhaust the Postgres connection limit or create connection-pool contention. Likelihood: Low–Medium (depends on fleet size, which engineering must check before committing to LISTEN/NOTIFY). Impact: Medium (connection exhaustion degrades the entire application, not just flags). Mitigation: Count current fleet process count and Postgres connection limit before choosing the invalidation mechanism. If connection headroom is tight, default to polling with a configurable interval (30–60 s). A single LISTEN connection per host (not per process) is a viable middle ground via a shared in-process subscription, but adds implementation complexity.

Feature Flag System

Add a first-party feature-flag system that lets engineering ship code dark, product run gradual rollouts, and support kill a misbehaving feature without a deploy. The work is organized across three phases over six weeks with a three-engineer team: (1) flag schema and Postgres storage with a read-through cache, (2) a sub-millisecond in-process evaluation engine with SDKs and sampled telemetry, and (3) an admin dashboard with per-environment overrides, rollout controls, audit-history browsing, and role-based access. No new external SaaS dependencies are introduced; the evaluation path stays strictly in-process.

Success Criteria

  • An engineer can define a flag in the schema, deploy code gated on it, and target it to a subset of users within one working day — no second deployment required.
  • The evaluation engine returns a variant in under 1 ms at p99 for all in-process callers, verified under production-representative load.
  • A percentage rollout can be moved from 0% to 100% via the admin UI; in-process caches across all service instances converge within 30 seconds, with no manual cache-flush step.
  • Every flag mutation is durably recorded in the audit log with actor, timestamp, before-value, and after-value. No mutation goes unrecorded.
  • Support can disable a flag in the admin UI and observe convergence within 30 seconds across all running instances.
  • Role-based guardrails prevent users who are neither the flag owner nor an admin from modifying production flag values; the UI communicates the restriction clearly.
  • All flag reads on the critical request path remain in-process — zero additional network hops.
  • Both backend-language SDKs produce identical bucketing results for the same (flagSalt, userId) inputs, validated by a shared test-vector fixture in CI.

Scope

In scope:

  • Flag model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (by user ID, org, environment), default value, per-flag salt, lifecycle state (active, archived).
  • Postgres-backed storage: feature_flags table, feature_flag_environments for per-environment overrides, migrations, and seed data.
  • Read-through in-memory cache per service process, with Postgres LISTEN/NOTIFY invalidation and a polling fallback.
  • Audit history table (feature_flag_audit_log) recording every mutation with before/after snapshots.
  • Typed accessor library in both backend languages for CRUD and read operations.
  • In-process evaluation engine: rule ordering, deterministic percentage bucketing, environment inheritance, multivariate support.
  • Native SDKs (typed) for both backend languages; JSON-over-HTTP endpoint for all other callers.
  • Sampled evaluation telemetry events (configurable sample rate) on a non-blocking write-behind path.
  • Admin dashboard: flag list/search, create/edit form, per-environment overrides, percentage-rollout slider with live bucketing preview, audit-history view, archive flow, role-based access enforcement.

Explicitly out of scope:

  • A/B-test statistical analysis or significance testing.
  • Scheduled rollouts (time-based activation / deactivation).
  • Mobile SDKs (iOS, Android, React Native).
  • Full approval workflow for flag changes (audit capture only — no gating or review queue).
  • Any new external SaaS dependency (no LaunchDarkly, Split, Unleash, etc.).

Constraints

  • No new external SaaS dependencies. The feature-flag system must be fully self-hosted on existing infrastructure; no third-party flag services may be introduced.
  • Zero additional network hops on the evaluation path. In-process callers must evaluate flags locally from a process-resident cache; the HTTP endpoint exists only for non-native callers and is not on the hot path for request handling.
  • Everything behind existing auth middleware. The admin API, the HTTP evaluation endpoint, and the dashboard page must be protected by the same authentication and authorization layer already used throughout the application.
  • Postgres is the source of truth. No separate datastore may be introduced as the primary flag store; the primary Postgres database is the system of record.
  • p99 evaluation latency ≤ 1 ms in-process under production-representative concurrency.
  • Team of three engineers, approximately six calendar weeks. The plan must fit this resource envelope without assuming heroics or outside help.

Assumptions

A1 — Postgres is the uncontested system of record and schema migrations are a normal part of the deployment process.

The product's primary Postgres database is writable via the standard migration tool used throughout the codebase. There is no schema-freeze or extended review gate beyond standard PR review.

A2 — Exactly two backend languages in the monorepo require native typed SDKs.

All other callers (frontend services, scripts, third-party integrations) can use the JSON-over-HTTP endpoint without material degradation of their use-case. Maintaining exactly two SDK implementations is within the team's capacity for this project.

A3 — Auth middleware already exposes sufficient targeting context per request.

The existing auth middleware attaches at minimum a user ID, org ID, and environment name (e.g., staging / production) to the request context object so the evaluation engine can extract targeting inputs without requiring changes to the auth layer.

A4 — A push or notify mechanism is available for cache invalidation.

At least one mechanism exists (Postgres LISTEN/NOTIFY on a non-pooled connection, an internal event bus, or an equivalent pub/sub channel) to push flag-change events to running service instances within seconds of a mutation, enabling the convergence SLO without requiring polling intervals shorter than 10 seconds.

A5 — The existing application RBAC model includes at least an admin role and a resource-owner concept that can be mapped to flag ownership.

The admin dashboard's access-control requirements ("only flag owners and admins can edit production values") can be implemented by mapping to existing roles rather than designing a new role taxonomy from scratch.

Phase 1 — Flag Schema and Storage

Establish the durable foundation for all flag data: the Postgres schema, read-through cache layer, typed accessor library, and audit logging. This phase produces no user-visible feature, but every subsequent phase depends on it. Target completion: end of week 2.

Phase Goal

Any application code in the monorepo can call the typed accessor library to read a flag value and receive a cached, correctly-typed result sourced from Postgres, with every mutation durably recorded in an audit log. The cache warms on startup and stays current via LISTEN/NOTIFY (or polling fallback). All of this works within the existing deployment pipeline with no new infrastructure dependencies.

Alternatives Considered

Config files checked in to the Git repository (YAML/JSON)

Flag values live in version-controlled files, giving free audit history via Git blame and zero new database tables. Rejected because: (a) changing a flag value requires a code deploy, defeating the primary use-case of runtime flag control; (b) complex per-user and per-org targeting rules are awkward to express statically; (c) percentage rollout state cannot be represented in a static file.

Redis as the source of truth (standalone KV store)

Redis offers sub-millisecond reads natively. Rejected because: Redis lacks the relational structure needed for rich targeting rules and foreign-key audit references; it does not provide the strong durability guarantees needed for the audit log; and it would introduce a new required infrastructure dependency not already present in the stack.

Recommendations

Store flag state in Postgres as the authoritative source of truth. On every flag mutation, the accessor library writes to Postgres and then issues a Postgres NOTIFY on the feature_flag_changes channel. Each service process maintains a process-local in-memory map of all active flags, pre-warmed at startup and refreshed on NOTIFY. The audit log is an append-only table written by the accessor library on every mutation — not a Postgres trigger, to stay consistent with the project's migration philosophy and avoid trigger-based surprises during schema evolution.

Open Questions

Q1.1 — Is Postgres LISTEN/NOTIFY reliably delivered in the current connection-pooler setup?

PgBouncer in transaction mode suppresses persistent LISTEN subscriptions, which would cause cache-invalidation events to be silently dropped. The infrastructure team needs to confirm whether a dedicated non-pooled connection for LISTEN is feasible, or whether we must rely solely on polling (and at what interval to meet the 30-second convergence SLO).

Q1.2 — How should multivariate flag variants be serialized in Postgres?

Booleans fit a single column; percentage rollouts need a number; multivariate flags need a list of (variant name, weight, value) tuples. Options: a single JSONB column for all flag value types (uniform schema, flexible, harder to query); three nullable typed columns; or a companion flag_variants table (normalized, but adds a join on every read). The decision affects query patterns in the accessor library and the type model in both SDKs.

reversibility: highblast: low

Index on (flag_id, occurred_at DESC) for efficient audit-view pagination.

Implement the audit-write logic as an explicit call inside the accessor library's write operations (not a Postgres trigger), so the audit row is written in the same transaction as the flag mutation. Write an integration test confirming that every CRUD operation on a flag produces exactly one audit row with correct before/after snapshots.

T1.3 — Typed accessor library for both backend languages

reversibility: highblast: low

Implement thin accessor modules in each of the two backend languages exposing: CreateFlag(input), GetFlagByKey(key) (cache-first, Postgres fallback), UpdateFlag(id, input, actor), ArchiveFlag(id, actor), ListFlags(filter). All write operations must record an audit row in the same transaction. Return typed structs/records — no raw query rows exposed at the call site. Write integration tests against a real Postgres instance (no mocks) covering the happy path, cache-miss fallback, archived-flag read, and concurrent-write safety.

T1.4 — In-memory read-through cache with LISTEN/NOTIFY invalidation

reversibility: highblast: low

Implement a process-local flag cache in each backend language: pre-warmed at startup from a full SELECT of active flags, keyed by flag key, protected by a read-write lock (goroutine-safe / thread-safe). Subscribe to the Postgres feature_flag_changes NOTIFY channel on a dedicated non-pooled connection; on receipt of a notification (containing the changed flag's key), refresh only that entry from Postgres. If the LISTEN connection is unavailable (PgBouncer transaction mode), fall back to a polling loop with a configurable interval (default 10 s, minimum 5 s). Expose cache statistics (hit count, miss count, last-refresh timestamp, entry count) via an internal metrics interface for observability.

T1.5 — Seed data and developer-experience tooling

reversibility: highblast: low

Write seed migrations that populate a baseline set of flags for local development and staging: a new_dashboard_ui boolean flag defaulting to false, a rollout_new_api percentage flag at 0%, and a payment_provider multivariate flag with two variants. Provide a Makefile target (or equivalent) to reset flags to the seed state in local environments without touching production. Add a brief flags/README.md inside the accessor library directory documenting the naming convention (snake_case, domain prefix), lifecycle states, and how to add a new flag.

Phase 2 — Evaluation Engine

Build the core logic that maps (flagKey, context) → variant, wire it into the SDKs and HTTP endpoint, and instrument every evaluation with sampled telemetry. Target completion: end of week 4.

Phase Goal

Any caller — whether a native typed SDK or an HTTP client — can resolve a flag variant in under 1 ms p99 (in-process) with deterministic, reproducible bucketing. The same (flagSalt, userId) inputs produce identical bucket values across both language SDKs. Evaluation results feed a sampled, non-blocking telemetry stream that provides a data foundation for future flag-usage analysis without affecting hot-path latency.

Alternatives Considered

Sidecar service for evaluation (language-agnostic, IPC-based)

A sidecar would provide a single implementation to maintain, independent deployment cadence, and strict memory isolation. Rejected because it introduces a mandatory network or IPC hop on every flag evaluation for in-process callers, violating the core constraint and adding non-trivial latency and a new failure dependency to every request that evaluates a flag.

Simple modulo bucketing (userId % 100 ≤ rolloutPct)

Trivially simple to implement and explain. Rejected because sequential integer user IDs produce heavily skewed distributions — early-registered users always fall into or out of a rollout, creating a systematic bias. Hash-based bucketing over the concatenation of flagSalt and userId produces a uniform distribution regardless of ID structure at negligible CPU cost.

Recommendations

Implement evaluation as a pure-function library (no I/O, no network calls) that operates on the flag map held in the in-memory cache from Phase 1. Algorithm: (1) look up the flag by key — return a safe configured default if not found; (2) if the flag is archived, return the default value; (3) walk targeting rules in declaration order, returning the first matched rule's variant; (4) for percentage-rollout flags with no rule match, compute hash(flagSalt + ":" + userId) mod 10000 / 100.0 and compare against the rollout percentage; (5) return the flag's default value if nothing matches. Environment inheritance: if no per-environment override exists for the requested environment, fall back to the production row's value and rules. Emit a sampled evaluation event on a non-blocking write-behind channel after returning the result.

Open Questions

Q2.1 — Should the telemetry sampling rate be global or per-flag?

A global 1% sample rate keeps event volume manageable but may miss short-lived activations on low-traffic flags. High-traffic gate flags may still produce millions of events per day at 1%. The data team should weigh in: do they want per-flag sample-rate configuration, or is a global rate with a minimum-event-count floor sufficient for their analytics use-case?

Q2.2 — Exact semantics of "staging defaults from production" for environment inheritance.

The brief states staging should inherit from production. Does this mean: (a) staging reads the production flag row's default_value and targeting_rules when no staging override exists (value + rule inheritance), or (b) staging can have its own default value but inherits production targeting rules? The semantics must be nailed down before implementing T2.1 to avoid a breaking schema change later.

T2.1 — Core evaluation algorithm (pure function, both languages)

reversibility: highblast: low

Implement the pure-function evaluation core in both backend languages. Signature: Evaluate(flag FlagSnapshot, ctx EvalContext) EvalResult. EvalContext carries: userId, orgId, environment, and a freeform traits map. EvalResult carries: variant (typed), source (which rule matched, or "default"), and flagKey. The function must never panic or throw on any input — unknown or archived flags return the caller-provided default. Write exhaustive table-driven unit tests: booleans, percentage boundaries (0%, 1%, 50%, 99%, 100%), multivariate, rule priority ordering, archived-flag behavior, nil/missing context fields.

T2.2 — Deterministic percentage bucketing with cross-SDK validation

reversibility: highblast: low

Implement bucket(flagSalt, userId string) float64 returning a value in [0, 100) using MurmurHash3 (or FNV-1a if MurmurHash3 requires a new package dependency) applied to the UTF-8 bytes of flagSalt + ":" + userId. Normalize the 32-bit hash output to [0, 10000] and divide by 100.0. Commit a testdata/bucketing_vectors.json fixture containing 1,000 triples of (salt, userId, expectedBucket). Both SDK test suites must pass the same fixture in CI — any future SDK must also do so before merging. Run a chi-squared uniformity test against a 100,000-sample set to confirm distribution quality.

T2.3 — SDK wrappers for both backend languages

reversibility: highblast: low

Wrap the evaluation core and Phase 1 cache into ergonomic SDK packages. Public API: flags.Bool(key, ctx, defaultVal), flags.String(key, ctx, defaultVal), flags.Variant(key, ctx, defaultVal). These functions must never raise exceptions or panic; unknown keys return the provided default and the miss is logged at debug level. Provide flags.Init(config) / flags.Close() lifecycle methods that start cache warm-up and the LISTEN/NOTIFY subscription. Write integration tests confirming that a flag created in Postgres is correctly evaluated via the SDK within 30 seconds without a process restart.

T2.4 — JSON-over-HTTP evaluation endpoint

reversibility: highblast: medium

Add a POST /api/v1/flags/evaluate route behind the existing auth middleware. Request body: {"flagKey": "...", "context": {"userId": "...", "orgId": "...", "environment": "...", "traits": {...}}}. Response: {"variant": ..., "source": "rule|default", "flagType": "...", "flagKey": "..."}. This route calls the same in-process evaluation core as the native SDKs — it is not a proxy to a separate service. Return HTTP 400 for malformed requests, 401 for unauthenticated, and a safe default variant (not 404) for unknown flag keys (with a "notFound": true field). Document the endpoint in the internal API reference. Write smoke tests covering authenticated success, missing flagKey, and unauthenticated access.

T2.5 — Sampled evaluation telemetry

reversibility: highblast: low

After every evaluation, emit a sampled event to the internal event bus (or a write-behind channel draining to the event bus). Event schema: {flagKey, variant, userId, orgId, environment, matchedRule, sampledAt}. The sample rate is controlled by the environment variable FLAG_TELEMETRY_SAMPLE_RATE (default 0.01 = 1%). Sampling and the channel write must not block the Evaluate call; use a non-blocking send and drop the event if the buffer is full. Expose a flag_telemetry_dropped_total counter metric and document that it should be alerted on if non-zero. Confirm in a load test that the telemetry path does not increase p99 evaluation latency.

Phase 3 — Admin UI

Deliver the product-facing dashboard: flag management, per-environment overrides, rollout controls, audit-history browsing, archive flow, and role-based access enforcement. Target completion: end of week 6.

Phase Goal

A non-engineer (product manager, support agent) can create, edit, and archive flags, adjust rollout percentages with a live bucketing preview, inspect who changed what and when, and understand at a glance whether they have permission to edit a given flag's production values — all without involving an engineer or requiring a deployment. RBAC guardrails are enforced on both the UI and the API.

Alternatives Considered

Standalone app rather than an embedded admin-panel page

A standalone flag-management app would have its own routing, auth integration, and deployment artifact. Rejected: embedding in the existing admin panel reuses shared navigation, existing auth guards, permission-check patterns, and the component library — substantially reducing implementation surface and avoiding a parallel auth integration.

Numeric text input for rollout percentage instead of a slider with live preview

A plain <input type="number"> is sufficient for precision. Rejected in favor of a slider with live preview because mis-set rollout percentages are among the most common flag-system incidents, and the preview substantially reduces cognitive load when doing gradual rollouts — the user sees concretely how many of their test accounts would be included. The implementation cost is bounded (see T3.3).

Recommendations

Build the admin UI as a new section within the existing admin panel, protected by the existing auth middleware and augmented with a flag-specific RBAC check resolved at the API layer. Reuse existing component library primitives for tables, forms, sliders, and modals; do not introduce a new component framework. The percentage-rollout preview should call a dedicated read-only GET /api/v1/flags/:id/preview-bucket endpoint that accepts a candidate percentage and returns an estimated affected-user fraction (computed from a random sample of real user IDs from the database) — this keeps the slider interaction informative without mutating state. Audit history should default to cursor-based pagination to remain performant on flags with thousands of mutations.

Open Questions

Q3.1 — Which existing application roles map to "flag admin" and "flag owner"?

The brief specifies that only flag owners and admins can edit production values. We need to know: can we map "flag admin" directly to an existing admin role, and is resource-level ownership already representable (e.g., by storing a created_by user ID and comparing it to the current session user)? If new role types are needed, the RBAC migration must be scoped and budgeted within Phase 3.

Q3.2 — Should the live bucketing preview use sampled real user IDs or synthetic examples?

Real user IDs give the most actionable preview ("your staging test accounts will be included") but require a query against the user table on every slider interaction. A synthetic fixed set is fast but less meaningful. Recommended middle path: a random sample of ~1,000 real user IDs pre-fetched when the flag edit form opens, used client-side for instant preview computation without per-interaction queries. Needs data-team and product sign-off.

D1 — Postgres + in-memory cache over config files in the repository

Flag state will be stored in a feature_flags Postgres table with a per-process in-memory cache, not in version-controlled YAML or JSON files. Postgres supports runtime mutations without deploys, rich JSONB targeting rules, a natural audit-log foreign key, and strong durability. Config files were ruled out because any flag change would require a code deployment, directly undermining the primary use-cases of emergency disables and gradual rollouts.

Config files would have provided free audit history via Git history, no schema migration surface, and immunity to database availability issues affecting flag reads. The decisive downside — requiring a deploy for every flag change — was judged fatal to the core product requirements.

D2 — Embedded in-process library over a sidecar evaluation service

The evaluation engine ships as an in-process library in both backend languages (plus an HTTP façade for non-native callers), not as a separate sidecar process. This is driven by the hard constraint that the evaluation path must not add a network hop to request handling. An in-process library with a process-resident cache can comfortably achieve p99 < 1 ms; a sidecar call over loopback typically adds 0.5–5 ms of latency, violating the SLO at p99.

A sidecar would mean a single implementation to maintain regardless of how many languages exist in the monorepo, independent deployment and rollback of the evaluation engine, and strict process isolation for memory and CPU. These benefits do not outweigh the latency and failure-surface costs for the in-request evaluation use-case.

D3 — MurmurHash3 for deterministic percentage bucketing with a per-flag salt

Percentage rollouts use MurmurHash3 applied to the UTF-8 encoding of flagSalt + ":" + userId, normalized to a float in [0, 100). The per-flag random salt ensures that two concurrent rollouts are statistically independent — a user in the first 10% of one rollout is not systematically in the first 10% of every rollout. MurmurHash3 was chosen over FNV-1a for its superior avalanche properties; both are available without new package dependencies in the target languages.

R1 — Postgres LISTEN/NOTIFY may be suppressed by PgBouncer transaction mode

If the deployment uses PgBouncer in transaction-mode pooling, persistent LISTEN subscriptions are not maintained and NOTIFY events will be silently dropped, causing in-process caches to serve stale flag values beyond the 30-second convergence SLO — potentially indefinitely.

Mitigation: Implement a polling fallback (configurable interval, default 10 s) that activates automatically when the LISTEN connection fails or is not feasible. Investigate whether a dedicated non-pooled connection for the LISTEN channel is acceptable to the infrastructure team (it bypasses PgBouncer entirely for this one use-case). Track via open question Q1.1. Emit a metric when falling back to polling so the team knows which mode is active.

R2 — Bucketing implementation drift between the two backend SDKs

If the two SDK implementations of the bucketing hash function diverge — due to character-encoding differences, endianness, or hash library behavior — the same user will receive different variants depending on which language handles their request. This is silent in production and hard to detect without explicit cross-language testing.

Mitigation: Commit a shared test-vector JSON fixture (1,000 triples) in T2.2 and require both SDK CI test suites to pass it before any merge. This fixture becomes the contract for any future SDK. Add the fixture path and requirement to the contributor guide.

R3 — RBAC scope creep delays Phase 3 completion

If the existing application RBAC model does not cleanly express "flag owner" or "flag admin" concepts, designing new role types requires additional migrations, API surface, and UI work that was not budgeted in the six-week timeline. This risk is highest if the current model only has coarse global roles with no resource-ownership concept.

Mitigation: Resolve open question Q3.1 in the first three days of Phase 3. If new roles are required, timebox the RBAC design to two days and accept a simpler initial model (owner = created_by user ID compared to session user; admin = existing app_admin role) as a deliverable, with a follow-on ticket for a richer role model.

R4 — Telemetry write-behind buffer overflow under high-traffic flags

High-traffic feature gates (e.g., a boolean flag evaluated on every API request) can generate millions of evaluation events per minute. If the write-behind consumer falls behind and the buffer fills, events are silently dropped. Without monitoring, the team will not know that flag-usage telemetry is incomplete, leading to incorrect rollout analysis.

Mitigation: Expose a flag_telemetry_dropped_total counter and alert on any non-zero value over a 5-minute window. Consider making the default sample rate configurable per-flag (override the global rate) so high-traffic flags can be sampled at 0.01% without sacrificing coverage on low-traffic ones. Confirm in a load test that at the default 1% sample rate the buffer does not fill under peak load.

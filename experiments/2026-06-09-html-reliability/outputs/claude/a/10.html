Feature Flag System

Three-phase, six-week plan for three engineers to build a first-party feature-flag system: a Postgres-backed flag schema with in-process caching (Phase 1), a sub-millisecond evaluation engine with multi-language SDKs (Phase 2), and an admin dashboard with RBAC and audit history (Phase 3). No new external SaaS. No network hop on the evaluation path.

Success Criteria

  • Flag evaluation returns the correct variant in <1 ms at p99 under representative production load, with no additional network hop in the hot request path.
  • All three flag types (boolean, percentage rollout, multivariate) work end-to-end: schema, evaluation, and UI.
  • Targeting rules covering user ID, org ID, and environment are evaluated in a documented, deterministic order.
  • Percentage-rollout bucketing is stable: the same userId + flagSalt always produces the same bucket across services and restarts.
  • Every flag mutation (create, update, archive) produces an immutable audit-log row with actor, timestamp, and a before/after diff — including writes made outside the application (e.g., migration scripts).
  • The admin UI supports flag creation, editing, search, archiving, per-environment overrides, a live rollout preview, and a paginated audit-history view.
  • Production flag values can only be edited by the flag owner or a user holding the admin role.
  • SDK wrappers exist for both backend languages in the monorepo; a POST /internal/flags/evaluate HTTP endpoint serves all other consumers.
  • All endpoints and UI pages sit behind the existing auth middleware; no new auth surface is introduced.
  • Zero new external SaaS dependencies.

Scope

In scope:

  • Flag model: key, description, owner, flag type, targeting rules (user ID / org / environment), default value, lifecycle state (active / archived).
  • feature_flags table in the primary Postgres database; flag_audit_log append-only table.
  • Read-through in-process LRU cache with Postgres LISTEN/NOTIFY push invalidation and TTL fallback.
  • Typed accessor library (pkg/featureflags or equivalent) exposing evaluate(flagKey, context) → variant.
  • Database migrations (with rollbacks) and development seed data.
  • Evaluation engine: rule ordering, deterministic HMAC bucketing, environment inheritance (staging falls back to production defaults).
  • Language SDKs for both backend languages in the monorepo.
  • JSON-over-HTTP evaluation endpoint for non-monorepo consumers.
  • Sampled telemetry event per evaluation (configurable rate, default 1%).
  • Admin dashboard: flag CRUD, per-environment override panels, percentage-rollout slider with live bucketing preview, audit-history view, RBAC enforcement.

Explicitly out of scope:

  • A/B-test statistical analysis or experiment frameworks.
  • Scheduled or time-based rollouts.
  • Mobile SDKs.
  • Multi-step approval workflow for flag changes.
  • External flag-management SaaS (LaunchDarkly, Statsig, etc.).
  • Self-service flag archiving by non-owners (requires admin action).

Constraints

  • No network hop on evaluation path: The evaluation engine must be an in-process library embedded in the service binary. A sidecar or remote service is not acceptable for the hot path.
  • Latency budget: p99 evaluation (warm cache) must not exceed 1 ms, measured under representative concurrency.
  • No new external SaaS: The entire system must run on infrastructure already present in the stack (Postgres, existing cache layer, existing auth).
  • Auth surface: Every API endpoint and admin UI page must be gated by the existing auth middleware. No new login flows or auth integrations.
  • Team and timeline: Three engineers, approximately six calendar weeks.
  • Monorepo-internal SDKs: Language SDK packages are internal to the monorepo; no external package-registry releases are required for initial delivery.

Assumptions

A1 — A shared Postgres client or ORM is already available in the monorepo

The accessor library and migration tooling can reuse an existing Postgres abstraction. If this does not exist, Phase 1 scope expands to include standing up a new client, which risks the week-2 target.

A2 — An in-process LRU cache or equivalent is available as an existing dependency

The read-through cache layer in Phase 1 assumes a well-tested LRU library is already present or easily added without introducing a new infrastructure component (e.g., a Redis cluster that does not yet exist).

A3 — Both backend languages can implement the same HMAC-SHA256 bucketing spec with standard library primitives

The deterministic bucketing algorithm (HMAC-SHA256 of userId + flagSalt, normalized to [0, 1)) is assumed to be expressible with standard-library HMAC in both languages without third-party crypto dependencies.

A4 — The existing auth middleware exposes role or group claims

The Phase 3 RBAC check (canEditFlag(user, flag, environment)) relies on role claims already present in the authenticated request context. No separate RBAC service or new identity integration is needed for the initial implementation.

A5 — Adding a new admin dashboard page is a well-worn path in the monorepo

Phase 3 assumes that the existing internal frontend framework (whatever it is) makes it straightforward to add a new admin page, reuse layout/auth guards, and call internal APIs — without requiring a new frontend build pipeline or separate deployment.

Phase 1 — Flag Schema & Storage

Establish the canonical data model, Postgres migrations, append-only audit trail, read-through cache, and typed accessor library. This phase produces the foundation that Phases 2 and 3 build on. Target: end of week 2.

Phase Goal

Deliver a stable, versioned Postgres schema for feature flags and their audit history; a read-through in-process cache that keeps evaluation independent of database round-trip time; and a typed internal library exposing a preliminary evaluate() stub. After Phase 1, any service in the monorepo can define and read flags in code, even before the real evaluation engine exists.

Alternatives Considered

Config-file-in-repo (YAML/JSON checked into git): Flags as versioned files benefit from code review, are always in sync with the deployed revision, and require no database migrations. Rejected because this approach fundamentally cannot support runtime changes without a deploy — defeating the kill-switch use case — and it makes runtime percentage-rollout changes impossible.

Separate flags microservice with its own Postgres instance: Full isolation of flag storage in a dedicated service. Rejected because it introduces a network hop on the evaluation path (violating the hard constraint) and adds operational complexity that a three-person team cannot absorb within six weeks.

Redis as primary storage (not just cache): Use Redis hashes as the source of truth. Rejected because Redis offers weaker durability guarantees than Postgres and complicates the audit-log requirement; Postgres remains the durable source of truth, with Redis or in-process LRU serving as the cache layer.

Recommendations

  • Use a single feature_flags table with a JSONB column for targeting rules and variant definitions — avoids join-table proliferation while remaining queryable via Postgres JSON operators.
  • Keep flag_audit_log strictly append-only: no UPDATE or DELETE is permitted on audit rows; enforce this with a Postgres trigger that also fires on direct SQL writes, not just application-layer mutations.
  • Implement the in-process cache as an LRU with a 30-second TTL plus Postgres LISTEN/NOTIFY-based push invalidation on every flag write. This gives near-real-time propagation without polling overhead.
  • The typed accessor library should expose a single evaluate(flagKey, context) → variant call. Even the Phase 1 stub (which returns the default value) must go through this path so that cache warm-up and telemetry hooks are in place before Phase 2 replaces the body.
  • Expose environment as a first-class column (not embedded in JSONB) so queries by environment are index-efficient.

Open Questions

OQ 1.1 — Should there be a "draft" lifecycle state?

A "draft" state would let engineers create a flag definition without it being evaluated yet (useful for dark shipping). However it adds a branch in the evaluation-path logic and complicates the admin UI state machine. Needs a decision before the schema migration is finalized.

OQ 1.2 — Global flag key namespace vs. service-namespaced keys?

Flag keys could be globally unique strings (simple, but collision-prone at scale) or namespaced by service prefix (e.g., payments.new_checkout). Namespacing reduces collision risk in a large monorepo but adds complexity to the accessor API and search UI. This choice affects the unique constraint on the key column.

T1.1 — Write and test the feature_flags migration

reversibility: high blast-radius: low

Create the initial Postgres migration defining feature_flags with columns: id (UUID PK, gen_random_uuid()), key (unique text, not null), description (text), owner_id (FK → users), flag_type (enum: boolean | percentage | multivariate), targeting_rules (JSONB array, default '[]'), variants (JSONB), default_value (JSONB, not null), environment (text, not null), state (enum: active | archived, default active), created_at, updated_at (both with timezone). Add a partial unique index on (key, environment) where state = 'active'. Include a rollback migration that drops the table.

T1.2 — Write the flag_audit_log migration and Postgres trigger

reversibility: high blast-radius: low

Create the append-only flag_audit_log table: id (UUID PK), flag_id (UUID FK → feature_flags), actor_id (UUID, nullable for system writes), action (enum: created | updated | archived), before_state (JSONB, nullable on create), after_state (JSONB, not null), occurred_at (timestamptz, default now()). Attach an AFTER INSERT OR UPDATE trigger on feature_flags that writes the log row automatically, capturing the full row as JSONB. The trigger ensures audit capture survives migration scripts and runbook SQL. Apply a row-level-security policy (or a CHECK-based rule) that prevents DELETE and UPDATE on flag_audit_log.

T1.3 — Implement read-through cache with LISTEN/NOTIFY invalidation

reversibility: high blast-radius: low

Build an in-process LRU cache (configurable max-entries, default 30 s TTL) wrapping SELECT reads on feature_flags. Subscribe to a flag_changes NOTIFY channel; the write path (application layer) publishes NOTIFY flag_changes, '<flagKey>' after each INSERT/UPDATE, triggering immediate eviction of that key from the cache. Fall back to TTL-based expiry if the NOTIFY connection is lost; alert if the connection has been absent for more than 60 seconds. Expose a get(key, environment) method returning the flag row or null, and a flush(key?) method for emergency use.

T1.4 — Build the typed accessor library

reversibility: high blast-radius: low

Create the internal package (e.g., pkg/featureflags) exposing: a Flag struct/class mirroring the DB model with typed fields; a FlagStore backed by the read-through cache; and a evaluate(flagKey, ctx EvaluationContext) (Variant, error) function whose body is initially a stub returning the flag's default_value (Phase 2 replaces this body without changing the signature). Write unit tests against a mock store covering: flag-not-found returns a typed sentinel; archived flags return the default; context struct is validated. The stub ensures Phase 2 and Phase 3 have a stable integration target immediately.

T1.5 — Seed data, dev tooling, and developer documentation

reversibility: high blast-radius: low

Write a seed script populating representative flags across all three types for development and staging environments. Include at least one flag with a complex targeting rule set (user-ID list override + org-level override + percentage bucket) to exercise the full evaluation surface in Phase 2. Add a simple CLI command (bin/flags list --env=staging, bin/flags get <key>) wrapping the accessor library for quick operator inspection without needing psql. Document local environment reset steps and the cache-flush endpoint in the internal developer guide.

Phase 2 — Evaluation Engine

Replace the Phase 1 stub with a complete, high-performance evaluation engine. Deliver multi-language SDKs, a JSON-over-HTTP endpoint, and sampled telemetry. Target: end of week 4.

Phase Goal

Ship a production-ready evaluation engine that resolves any flag to a variant in under 1 ms at p99 (warm cache, in-process path) with correct deterministic bucketing, documented rule ordering, and environment inheritance. Two backend-language SDKs wrap the engine. A thin HTTP adapter exposes the same logic for external consumers. Every evaluation emits a sampled telemetry event without materially affecting latency. A CI latency gate prevents regressions.

Alternatives Considered

Sidecar service (separate process per pod, localhost socket): Packages the engine as a local sidecar, making it language-agnostic for all consumers. Rejected: even a Unix-socket loopback adds ~50–200 µs at p99, risking the 1 ms budget when combined with rule evaluation work. Adds process-management and health-check overhead that a three-person team cannot afford.

WebAssembly core shared across languages: Compile a single Rust or Go evaluation core to WASM and embed it in each language runtime — one implementation, perfect cross-language consistency. Attractive in principle, but the WASM toolchain is not yet standardized in the monorepo and the build complexity is not justified for two languages. Deferred to a future iteration if a third or fourth language is added.

Recommendations

  • Implement rule evaluation as a pure function with no I/O: evalRules(flag Flag, ctx EvaluationContext) Variant. Keeps it trivially testable and benchmarkable in isolation.
  • Documented rule-ordering precedence (highest to lowest): explicit user-ID match → org-ID match → environment match → percentage bucket → flag default value. Publish this as a specification, not just an implementation comment.
  • Deterministic bucketing: HMAC-SHA256(secret=flagSalt, data=userId) → take the first 4 bytes as a big-endian uint32 → divide by 2³²−1 → compare to rollout percentage threshold. Distribute test vectors alongside the spec so both SDK implementations must pass the same fixture suite.
  • Environment inheritance: at cache-load time (not evaluation time), if a flag has no record for the requested environment, substitute the production row. This keeps the hot evaluation path free of extra lookups.
  • Telemetry: emit a 1-in-N sampled event (default 1%, configurable via FEATURE_FLAG_TELEMETRY_SAMPLE_RATE) to the agreed sink. Include flag key, resolved variant, hashed user ID (no raw PII), environment, UTC timestamp, and reason code. The telemetry write must be non-blocking (fire-and-forget to a buffered channel); drop events rather than back-pressuring evaluation if the sink is slow.

Open Questions

OQ 2.1 — Telemetry sink: existing event bus, Postgres table, or deferred?

Does the monorepo already have an internal event bus (Kafka, SQS, internal pubsub)? If yes, evaluation events should fan out to it. If not, a simple flag_evaluation_events Postgres table (append-only, partitioned by day) is a pragmatic alternative. Writing to Postgres at 1% sample rate is acceptable at most realistic evaluation volumes, but this needs to be confirmed before T2.5 is started. Deferring telemetry entirely is a fallback if neither option is ready within Phase 2.

OQ 2.2 — HTTP endpoint cache: NOTIFY or poll?

The in-process SDK uses LISTEN/NOTIFY for near-real-time cache invalidation. The HTTP adapter is a separate process (or at least a separate connection pool context). Should it maintain its own NOTIFY subscription (lower propagation latency, more connections) or poll the database on a short interval such as 5 seconds (simpler, resilient to connection drops)? The answer affects the adapter's connection count at scale.

T2.1 — Implement core rule evaluation logic

reversibility: high blast-radius: low

Replace the Phase 1 stub body in evaluate() with full rule-ordering logic: iterate targeting rules in the specified precedence order (user-ID match → org match → environment match → percentage bucket → default). Return the matching variant. Handle edge cases with explicit tests: empty rule set returns default; archived flag returns default; unknown flag key returns typed ErrFlagNotFound sentinel (not a panic or nil); malformed JSONB rule is skipped with a logged warning (not a crash). Aim for >95% unit-test line coverage on this function.

T2.2 — Implement and validate deterministic bucketing

reversibility: high blast-radius: low

Implement the HMAC-SHA256 bucketing algorithm per the Phase 2 spec. Write a property-based or statistical test confirming that distribution is within ±0.5% of uniform for 100 k distinct user IDs at rollout thresholds of 1%, 10%, 50%, and 99%. Write a stability test confirming the same userId + flagSalt always produces the same bucket across cold restarts and concurrent calls. Publish the bucketing spec as a checked-in document with reference test vectors; the second-language SDK (T2.3) must pass the same vector file without modification.

T2.3 — Language SDKs for both backend languages

reversibility: high blast-radius: low

Wrap the evaluation engine in thin idiomatic packages for each monorepo backend language. Each SDK exposes at minimum: evaluate(flagKey, ctx) → Variant, boolVariation(flagKey, ctx, default) → bool, stringVariation(flagKey, ctx, default) → string, and floatVariation(flagKey, ctx, default) → float64. Both SDKs share a single in-process cache instance and LISTEN/NOTIFY connection — do not instantiate a second cache per language. Write cross-language integration tests that call evaluate() in both SDKs for the same flag and user ID and assert identical variant output.

T2.4 — JSON-over-HTTP evaluation endpoint

reversibility: high blast-radius: low

Add POST /internal/flags/evaluate behind the existing auth middleware. Request body: {"flagKey": "...", "context": {"userId": "...", "orgId": "...", "environment": "..."}}. Response: {"variant": "...", "reason": "rule:user_id_match" | "rule:org_match" | "rule:percentage" | "default"}. The handler calls the same in-process evaluate() function — no duplicated logic. Apply existing rate-limiting middleware. Write a contract test pinning the request/response schema so external consumers have a stable target; breaking schema changes must bump a version path or be backwards-compatible.

T2.5 — Sampled telemetry emission

reversibility: high blast-radius: low

Instrument the evaluate() function to emit a sampled event (default 1%, controlled by FEATURE_FLAG_TELEMETRY_SAMPLE_RATE env var). Event payload: flag key, resolved variant, hashed context (no raw PII), environment, UTC timestamp, reason code. Write to the agreed telemetry sink (resolve OQ 2.1 first). Wrap the write in a non-blocking, buffered channel with a circuit breaker: if the sink is unavailable or slow, drop events silently rather than blocking evaluation. Confirm in a load test that 1% sampling does not increase p99 evaluate() latency by more than 50 µs.

T2.6 — CI latency benchmark and gate

reversibility: high blast-radius: low

Write a repeatable microbenchmark (e.g., Go testing.B, pytest-benchmark) measuring warm-cache evaluate() latency across: boolean flag with no rules, 10-rule percentage rollout, and a 5-rule multivariate flag. Run the benchmark in CI on a fixed machine class; fail the build if the p99 sample exceeds 1 ms. Document benchmark methodology (CPU class, concurrency, data set) in a BENCHMARKS.md so results are reproducible across engineers.

Phase 3 — Admin UI

Deliver the operator-facing dashboard: flag management, per-environment overrides, rollout controls with live preview, audit history, and role-based access control. Target: end of week 6.

Phase Goal

Ship a production-usable admin dashboard that lets product managers and engineers manage flags without writing SQL or deploying code. Per-environment overrides are editable from the UI. Percentage rollouts are controlled with a slider that previews bucketing impact using the same HMAC algorithm as production. Every change is visible in a paginated, filterable audit-history view. Production flag edits are restricted to flag owners and admin-role users, enforced both in the UI and at the API layer.

Alternatives Considered

Embed in an existing internal admin portal: If an internal back-office portal already exists with the required RBAC hooks, adding a flags section there avoids building a new page layout and authentication flow. This is preferred over building from scratch — investigate whether the existing portal's release cycle and RBAC model are compatible before starting T3.1.

Low-code / internal tooling platform (Retool, Airplane, etc.): Rejected outright — violates the no-new-SaaS constraint and cannot support the custom live bucketing preview widget without significant workarounds.

Recommendations

  • Build within the existing frontend framework (resolve OQ 3.1 first) to avoid introducing a new build pipeline or deployment unit.
  • The rollout slider should debounce calls to a backend preview endpoint (GET /internal/flags/bucket-preview?percentage=N&flagKey=X&sampleSize=1000) rather than implementing bucketing in client-side JavaScript — this ensures the preview always matches production behavior.
  • Implement canEditFlag(user, flag, targetEnvironment) as a shared utility used by both API middleware and UI rendering (show/hide edit controls). The single source of truth prevents UI and API permission divergence.
  • The audit history view reads directly from flag_audit_log with server-side pagination; render before/after JSONB diffs as a collapsible key-by-key diff view. No client-side diffing needed.
  • Get explicit sign-off from a security stakeholder on the initial RBAC permission matrix (see T3.5) before building the UI — late RBAC changes are expensive to retrofit.

Open Questions

OQ 3.1 — Which frontend framework and routing model does the monorepo use for admin pages?

The implementation approach for the admin UI differs significantly between a server-rendered MPA (e.g., Rails ERB, Django templates) and a SPA (React, Vue). The rollout slider live preview and the per-environment override panels may require different state-management strategies. This must be confirmed before any frontend work begins in Phase 3.

OQ 3.2 — Single owner vs. shared ownership (team-owned flags)?

The current schema stores one owner_id per flag. If product teams want flags owned by a group (e.g., the payments squad), the schema needs a flag_owners join table and the RBAC check changes. Adding this after launch requires a non-trivial migration and RBAC update. The decision should be made before Phase 3 ships to avoid retrofitting.

T3.5 — RBAC middleware, permission matrix, and integration tests

reversibility: medium blast-radius: medium

Implement canEditFlag(requestingUser User, flag Flag, targetEnvironment string) bool as a shared utility: returns true if user.ID == flag.OwnerID or user.Roles contains "admin". Wire it into all write API endpoints (create, update, archive, environment override) and into UI rendering (show/hide edit controls, disable save buttons). D1 — Store flags in Postgres, not in a config file

Flags are stored in the primary Postgres database with a read-through in-process cache, rather than as YAML or JSON files checked into the repository. Postgres allows runtime changes without a code deploy, supports an append-only audit log enforced at the database layer via trigger, and enables the admin UI to perform live reads and writes. The in-process LRU cache with NOTIFY-based invalidation ensures that the database round-trip does not appear on the hot evaluation path.

Config-in-repo was attractive for its simplicity and the built-in code-review audit trail via git history. It was ruled out because it fundamentally cannot satisfy the kill-switch use case (disable a flag instantly without a deploy) or the runtime percentage-rollout use case (change rollout percentage without merging a file change). These are stated requirements, not nice-to-haves.

D2 — Evaluation engine as an in-process embedded library, not a sidecar service

The evaluation engine is implemented as an in-process library linked directly into each service binary. Non-monorepo consumers use the JSON-over-HTTP endpoint, which is not on the critical request path. This satisfies the hard constraint that evaluation must not add a network hop, and keeps operational complexity within the reach of a three-person team. The HTTP adapter is a thin wrapper around the same in-process evaluation function — no logic is duplicated.

A sidecar would unify the evaluation path across all languages without per-language SDKs. Even a Unix-socket loopback connection adds approximately 50–200 µs at p99 on a loaded host, which risks violating the 1 ms budget once rule evaluation work is included. The added process-management, health-check, and deployment complexity was judged too high for the available bandwidth.

D3 — Audit log captured via Postgres trigger, not solely via application-layer hooks

The flag_audit_log is populated by an AFTER INSERT OR UPDATE Postgres trigger on feature_flags, not exclusively by application-layer audit calls. This ensures the audit trail is complete even for writes made outside the application layer — migration scripts, runbook SQL, emergency patches — and removes the possibility of a future code path accidentally skipping audit logging.

Application-layer audit hooks can carry richer context (HTTP request ID, user agent, business action name) than a trigger can easily access. This richness is sacrificed for completeness guarantees. The two approaches are not mutually exclusive: if richer metadata becomes necessary, the application layer can supplement the trigger-written row by updating additional columns, while the trigger remains the integrity backstop.

R1 — Cache invalidation failure leaves stale flag values in production

If the Postgres LISTEN/NOTIFY connection drops silently (network partition, Postgres restart, connection-pool recycle), in-process caches may serve stale flag values for the full TTL duration (default 30 s). In a kill-switch scenario, a 30-second delay before a misbehaving feature is disabled may be operationally unacceptable.

Mitigation: Monitor NOTIFY connection health via a heartbeat NOTIFY every 10 s; alert on-call if the connection has been absent for >60 s. Expose an operator endpoint (POST /internal/flags/flush-cache) for emergency manual cache eviction. Consider a reduced TTL (5–10 s) for flags explicitly tagged as kill-switches. Document the worst-case staleness window in the runbook.

R2 — Bucketing algorithm divergence between language SDKs

If the two language SDK implementations of the HMAC-SHA256 bucketing algorithm differ in a subtle way (byte-order handling, HMAC key encoding, floating-point division) the same user could land in different buckets depending on which service handles the request. This causes inconsistent feature exposure and corrupts telemetry analysis.

Mitigation: Publish a shared bucketing specification with reference test vectors (specific userId + salt → expected bucket value triples). Both SDK implementations must pass the same vector file in CI. Add a cross-language integration test that compares evaluate() output for the same inputs across both SDKs running against a shared test database.

R3 — Phase 3 RBAC scope creep delays delivery

RBAC edge cases (shared ownership, delegated admin, environment-specific roles, service-account access) tend to surface during demo or security review and can significantly expand scope. The initial single-owner model may be challenged by product or security stakeholders once the UI is visible.

Mitigation: Document the initial permission matrix explicitly and obtain security stakeholder sign-off at the Phase 3 kickoff meeting. Defer shared ownership to a post-launch iteration (tracked in OQ 3.2) rather than expanding scope mid-phase. If sign-off is blocked, Phase 3 ships read-only UI first; edit controls follow in a fast-follow.

R4 — Telemetry volume saturates write path at high evaluation rates

If the per-service evaluation rate is much higher than anticipated, even a 1% sample rate may produce a write volume that overwhelms a Postgres-backed telemetry table or a slow event bus. This could cause back-pressure that blocks evaluation if the telemetry channel is not properly isolated.

Mitigation: The telemetry write path must be fire-and-forget via a buffered channel with a drop policy (not block). Default sample rate is 1% and is configurable per service. Add monitoring on the telemetry sink write rate and table/partition growth. Document escalation path if growth exceeds expected projections during rollout.

Feature Flag System

Add a production-grade feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases — flag schema and storage, an in-process evaluation engine, and an admin UI — targeting three engineers over six weeks with no new external SaaS dependencies.

Success Criteria

  • Flag evaluation returns the correct variant in under 1 ms at p99 under production load, with no additional network hop added to any request path.
  • All three flag types — boolean, percentage rollout, and multivariate — are supported and covered by automated tests exercising real targeting rules.
  • Deterministic bucketing for percentage rollouts produces identical results for the same (userId, flagSalt) pair in both backend-language SDKs, verified by a shared cross-language fixture test running in CI.
  • Targeting rules by user ID, organization ID, and environment are evaluated in correct priority order; environment inheritance (staging defaults from production) works correctly and is tested.
  • Every flag mutation — create, update, archive — is recorded in the audit log with actor identity, timestamp, old value, and new value, and is visible in the admin UI's audit history view.
  • Role-based access control prevents non-owner, non-admin users from editing production flag values; server-side enforcement exists independently of the UI layer.
  • Zero new external SaaS dependencies are introduced; all components run on existing infrastructure.
  • A non-engineer product manager can create a new percentage-rollout flag, set per-environment overrides, preview which users are bucketed in, and archive the flag without engineering assistance.

Scope

In Scope

  • Flag model: key, description, owner, flag type (boolean / percentage rollout / multivariate), targeting rules (by user ID, by org, by environment), default value, lifecycle state (active / archived).
  • feature_flags and flag_audit_log tables in the primary Postgres database; DDL migrations integrated with the existing migration toolchain; idempotent seed data for development and CI.
  • Typed accessor library (FlagStore) shared across the monorepo; read-through in-process cache with push-or-poll invalidation to meet the 1 ms p99 budget.
  • Evaluation engine: deterministic bucketing via hash(userId + flagSalt) mod 10000, rule ordering semantics, environment inheritance (staging inherits production defaults when no override is set).
  • Native SDKs for both backend languages in the monorepo, plus a JSON-over-HTTP fallback endpoint for non-primary clients.
  • Sampled telemetry event emitted on every evaluation at a configurable sampling rate for downstream analysis.
  • Admin UI: flag list with search and filters, flag create/edit form with rule builder, per-environment overrides panel, percentage-rollout slider with live bucketing preview, audit history view with keyset-paginated results.
  • RBAC enforcement for production flag mutations (flag owners and admins only).

Out of Scope

  • A/B-test statistics or experiment analysis dashboards.
  • Scheduled or time-based flag transitions.
  • Mobile SDKs (iOS, Android).
  • Full approval or change-management workflow (four-eyes sign-off, approval queues).
  • Flag dependency graphs or inter-flag overrides.
  • Automated canary analysis or auto-rollback based on metrics.

Constraints

  • No new external SaaS. Managed flag services (LaunchDarkly, Unleash Cloud, Flagsmith hosted) are prohibited. All components must run on existing infrastructure.
  • No network hop on the evaluation path. Flag evaluation must happen in-process so that calling it from a request handler does not increase per-request latency beyond the 1 ms p99 target. A sidecar or RPC call on the hot path is disqualified regardless of transport speed.
  • Existing auth middleware. All endpoints — the HTTP evaluation fallback and the admin API — must sit behind the existing authentication and authorization middleware. No new auth paths or separate identity flows.
  • Team size and calendar. Three engineers, approximately six weeks total; target two weeks per phase, with Phase 3 frontend work allowed to overlap Phase 2 backend work once the API contract is stable.
  • Postgres as primary store. Flag definitions live in the existing Postgres cluster. No new stateful infrastructure (dedicated Redis, etcd, ZooKeeper) unless already present in the deployment.

Assumptions

Primary database is Postgres with an existing DDL migration toolchain

We assume the product runs Postgres as its primary OLTP database and that schema migrations are managed by an existing tool (Flyway, Liquibase, Alembic, or equivalent). Phase 1 is scoped to that toolchain. If a different database is in use, the schema design, JSONB usage, and LISTEN/NOTIFY invalidation strategy will all require rework.

Both backend languages support equivalent deterministic hashing with no library dependency required

Deterministic percentage-rollout bucketing depends on hashing userId + flagSalt with a consistent algorithm. We assume FNV-1a 32-bit can be implemented in ~10 lines in each backend language with no external library, and that outputs are bit-identical. If a language imposes incompatible integer overflow or string encoding behavior, the bucketing algorithm may need to switch to SHA-256 (universally available) with additional cross-language normalization.

Auth middleware exposes userId and orgId in request context

The evaluation engine requires userId and orgId to evaluate targeting rules. We assume the existing auth middleware populates these as structured values in the request context (a context map, thread-local, or request-scoped object) so callers do not need to pass them explicitly on every evaluate() call. If the middleware stores only a raw JWT and callers must parse it themselves, SDK initialization will require a custom context-extractor hook.

The admin UI can be added as a route within the existing frontend application

We assume the internal admin dashboard page can be implemented inside the existing frontend application — same framework, build pipeline, and design system — without standing up a new frontend service. If the existing internal tooling frontend is a completely separate legacy system, Phase 3 will need a dedicated scoping exercise and the timeline estimate is likely to expand.

Phase 1 — Flag Schema and Storage

Establish the data model, database schema, migration toolchain integration, audit logging, and the typed accessor library that Phases 2 and 3 build upon. This phase produces no user-visible features but is the load-bearing foundation for the entire system.

Phase Goal

By the end of Phase 1, any service in the monorepo can call a typed FlagStore accessor to read a flag definition (from Postgres or a warm in-process cache), and any flag mutation is recorded atomically in the audit log. Migrations are applied, reversible, and run cleanly in CI. Seed data covers all three flag types and multiple targeting rule shapes. The FlagStore interface is stable enough for Phase 2 to build the evaluation engine on top of it.

Alternatives Considered

Config file committed to the repository (YAML / JSON)

Store flag definitions as a checked-in YAML file. Pros: zero infrastructure change, full git history, easy to review in PRs. Cons: cannot support a real-time kill-switch (a change requires a deploy), cannot support dynamic targeting rules or percentage rollouts at runtime, and audit history collapses to coarse git blame. Rejected — the kill-switch requirement alone disqualifies this approach.

Self-hosted open-source flag service (Unleash, Flagsmith)

Run an off-the-shelf flag service in the infrastructure. Pros: rich SDK ecosystem and admin UI out of the box. Cons: adds a new stateful service to operate and on-call; the evaluation path requires either a sidecar call (violates the no-network-hop constraint) or a client-side SDK with its own cache (which is essentially what we are building anyway). Rejected — operational overhead and constraint violations outweigh convenience at current scale.

Recommendations

  • Use Postgres JSONB for targeting_rules and default_value columns to accommodate boolean, percentage, and multivariate payloads in a single column without future schema changes as variant shapes evolve.
  • Write audit rows in the same transaction as every flag mutation — no triggers, no async side-effects — so the audit trail is consistent, transparent, and testable.
  • Define a single FlagStore interface in the shared internal library so Phase 2 and Phase 3 depend on the interface rather than the implementation, and the cache layer can be swapped without callers changing.
  • Use a GIN index on targeting_rules to support future queries over rule contents; accept the minor write overhead now to avoid a painful reindex later.

Open Questions

Should percentage rollout be sticky if the flag salt is changed?

Deterministic bucketing using a per-flag salt naturally provides user stickiness as long as the salt does not change. If we expose the salt as a mutable field (allowing operators to re-randomize which users are bucketed in), operators can recover from bad rollouts without changing the percentage. If we lock the salt at creation time, stickiness is guaranteed but recovery requires archiving and re-creating the flag. The decision affects both the schema design (whether salt is editable in the UI) and the audit story. Needs product input before the bucketing algorithm is finalized in Phase 2.

What is the retention policy for audit log rows?

The flag_audit_log table will grow unboundedly. Does the admin UI need to display complete history indefinitely, or do we archive rows older than N days to cold storage or a data warehouse? The answer affects Phase 3's audit history view design (whether it needs to query across stores) and whether a background archival job is in scope. Needs platform and product input before Phase 3 is finalized.

Audit log table and write path reversibility: high blast: low

Create the flag_audit_log table with columns: id (UUID PK), flag_id (UUID FK to feature_flags), actor_id (UUID FK to users), action (enum: created / updated / archived), old_value (JSONB snapshot of the entire flag row before change, null for creates), new_value (JSONB snapshot after change), occurred_at (timestamptz, not null). Add a composite index on (flag_id, occurred_at DESC) for the admin UI history query. Implement a FlagAuditWriter that writes a row in the same transaction as any flag mutation. Write a unit test asserting that no FlagStore mutation method can succeed without a corresponding audit row committed in the same transaction.

Seed data and CI fixtures reversibility: high blast: low

Write an idempotent seed script (safe to re-run, upserts on key) that creates at least one flag of each type: a boolean kill-switch, a 25% percentage rollout with a user-ID targeting rule, and a multivariate A/B variant flag. Include at least one archived flag. Include a targeting rule that matches by org ID and one that matches by environment. Ensure the seed runs as part of the CI pipeline's database-setup step. Document the seed command in the monorepo's developer-environment README alongside the migration instructions.

Typed accessor library — FlagStore interface and Postgres implementation reversibility: high blast: low

Define the FlagStore interface in the shared internal library with methods: getFlag(key) → FlagDefinition | null, listFlags(filter) → FlagDefinition[], upsertFlag(definition) → FlagDefinition, and archiveFlag(key) → void. Include full type definitions for FlagDefinition, TargetingRule, RuleCondition, and FlagVariant. Implement PostgresFlagStore backed directly by Postgres (no cache at this layer — the cache wraps this in t1.5). Write integration tests against a real test database with no DB-layer mocks; tests must cover create, read, update, archive, and list-with-filter code paths.

Read-through in-process cache — CachingFlagStore reversibility: medium blast: low

Implement CachingFlagStore that wraps PostgresFlagStore and keeps an in-memory map of all active flag definitions. On startup, eagerly load all flags. Refresh on a configurable TTL (default 30 s). Invalidate immediately on any local write call. Expose a forceRefresh() method for the push-invalidation path to be wired in Phase 2 (t2.3). The cache must be safe for concurrent reads (read-write mutex or lock-free map). Benchmark warm-read (cache hit) latency and assert p99 is below 200 µs on the CI runner. Add a cacheStats() diagnostic method returning hit/miss counts and last-refresh timestamp.

Phase 2 — Evaluation Engine

Build the in-process evaluation library that any service calls to resolve a flag key to a variant in a single function call. This phase delivers the core bucketing algorithm, rule-matching semantics, environment inheritance, cache invalidation over Postgres NOTIFY, both backend-language SDKs, the HTTP fallback endpoint, and the sampled telemetry path.

Phase Goal

By the end of Phase 2, any service in the monorepo can call flagClient.evaluate(flagKey, context) in either backend language and receive the correct variant from a warm cache in under 1 ms at p99. A cross-language bucketing fixture test passes for both SDKs in CI. A JSON-over-HTTP endpoint is available for clients that cannot use the native library. Every evaluation emits a sampled telemetry event to the agreed destination.

Alternatives Considered

Sidecar service (gRPC or HTTP loopback)

Run a small evaluation sidecar per pod. Pros: single implementation of evaluation logic, language-agnostic. Cons: even a Unix-socket loopback call adds ~0.1–0.5 ms at p99 plus serialization overhead, and the constraint explicitly prohibits adding a network hop to the request path. Under high concurrency the tail latency degrades further. Rejected — hard constraint violation.

Poll-only cache invalidation (no push path)

Rely solely on TTL-based polling (e.g., every 30 s) with no push-invalidation mechanism. Pros: trivially simple — no pub/sub or long-lived connection required. Cons: up to 30 s of stale state after an operator kills a misbehaving feature, which defeats the primary kill-switch use case. Accepted as a fallback (used when the push channel is unavailable) but not the primary invalidation story.

Separate in-memory store process (Valkey / Redis) as broadcast bus

Use an existing Redis/Valkey instance (if present) for pub/sub invalidation instead of Postgres NOTIFY. Pros: richer pub/sub semantics. Cons: introduces a dependency on Redis being present in all environments; Postgres NOTIFY is sufficient and uses infrastructure we already guarantee. Deferred — revisit if Postgres NOTIFY proves unreliable in the specific deployment (see oq2.1).

Recommendations

  • Use Postgres LISTEN/NOTIFY on the channel flag_changes for push invalidation. The writer calls SELECT pg_notify('flag_changes', flagKey) after committing each mutation. Subscribers call CachingFlagStore.forceRefresh() on receipt. This uses zero new infrastructure and delivers sub-second propagation on the same Postgres connection pool already open in each service.
  • Implement bucketing as fnv1a32(userId + ":" + flagSalt) % 10000. A user is "in" if their bucket value is less than rolloutPercentage × 100. FNV-1a 32-bit requires no external library and can be written in ~8 lines in any language.
  • Define a canonical EvaluationContext with required fields userId, orgId, environment and an optional attributes map<string, string> for custom rule conditions. Keep the struct small to minimize per-call allocation pressure.
  • Emit telemetry at a configurable 1-in-N sampling rate (env var FLAG_TELEMETRY_SAMPLE_RATE, default 100 = 1%). Each event includes: flagKey, variant, context hash (not the raw context), evaluation reason, and a monotonic timestamp. Use a non-blocking async write to avoid any chance of the telemetry path adding latency to the evaluation call.

Open Questions

Does the deployment's connection pool support Postgres LISTEN/NOTIFY?

PgBouncer in transaction-pooling mode (the most common configuration) silently drops LISTEN/NOTIFY messages. If the deployment uses PgBouncer in transaction mode, the push-invalidation path will silently fail and the system will fall back to TTL polling without the operator realizing the kill-switch has a 30 s delay. We need to confirm the connection-pool configuration and, if PgBouncer transaction mode is in use, establish a separate session-mode connection for the LISTEN subscription (acceptable but requires a deliberate connection-budget decision). Needs infrastructure-team input before t2.3 is started.

What is the agreed telemetry destination for evaluation events?

The brief says every evaluation "emits a sampled event for later analysis" but does not name the destination. The choice affects the SDK interface and event schema: a Postgres flag_evaluation_events table (simplest, queryable by SQL), a Kafka topic (better for high-volume, downstream consumers), a metrics counter (StatsD/Prometheus — aggregated only, no per-user data), or an existing internal analytics pipeline. Needs platform-team input. Decision must be made before t2.4 and t2.5 are started, since both SDKs must emit to the same destination.

Core evaluation logic and rule-matching engine reversibility: high blast: low

Implement the evaluate(flagKey, context) → Variant function with the following precedence order: (1) if the flag is archived, return the default value immediately; (2) iterate targeting rules in priority order (ascending priority integer), returning the first rule's variant when all its conditions match; (3) for percentage-type flags with no matching rule, apply the bucketing function — return the rollout variant if the user is in-bucket, else the default; (4) for all other cases, return the flag's default value. Include a structured EvaluationReason field in the return value (ARCHIVED, RULE_MATCH, BUCKETED_IN, BUCKETED_OUT, DEFAULT). Write unit tests covering every branch including rule-priority edge cases, archived-flag short-circuit, and multivariate variant selection.

Deterministic bucketing algorithm and cross-language fixture reversibility: high blast: low

Implement bucket(userId, flagSalt) → int [0, 9999] using FNV-1a 32-bit hash of userId + ":" + flagSalt (UTF-8 encoded), result modulo 10000. Implement the function independently in both backend languages. Generate a canonical fixture: a CSV of 1 000 rows with columns userId, flagSalt, expectedBucket produced by a reference Python script included in the repo. Both SDKs must pass the fixture as a CI-required test. Any bucketing divergence between languages must block the merge. Document the algorithm and the normalization invariants (string encoding, integer overflow handling) in a short inline comment so future porters can implement it correctly.

Push-or-poll cache invalidation via Postgres NOTIFY reversibility: medium blast: low

Wire the flag-mutation write path to call SELECT pg_notify('flag_changes', flag_key) after every committed mutation. In each service process, maintain a dedicated Postgres connection subscribing to flag_changes via LISTEN; on receipt call CachingFlagStore.forceRefresh() for the affected key. If the LISTEN connection drops, reconnect with exponential backoff and fall back transparently to TTL polling at 30 s intervals. Expose a health-check field pushInvalidationConnected: bool in the service's existing health endpoint. Write an integration test that: seeds a flag at value A, starts a subscriber, mutates the flag to value B in a separate transaction, and asserts the subscriber's cache reflects value B within 500 ms.

SDK for backend language 1 reversibility: high blast: low

Package the evaluation engine and CachingFlagStore as an importable module in backend language 1. Public API: FlagClient.evaluate(flagKey, context) → Variant, FlagClient.evaluateBool(flagKey, context, defaultValue) → bool, FlagClient.evaluateString(flagKey, context, defaultValue) → string, and FlagClient.evaluateJSON(flagKey, context, defaultValue) → map. Include a middleware helper that automatically extracts userId, orgId, and environment from the request context and builds an EvaluationContext. Write integration tests that spin up a real test database, seed flags, and verify evaluation outcomes for all flag types. Implement the telemetry emission path using the destination agreed in oq2.2.

SDK for backend language 2 reversibility: high blast: low

Port the identical FlagClient interface to backend language 2. Share the cross-language bucketing fixture from t2.2 as the primary cross-SDK correctness test — it must run in this SDK's CI step as well. Implement the same middleware helper for request-context extraction. Implement telemetry emission to the same destination as SDK 1. Document initialization (how to wire the client into the dependency graph) and the expected startup behavior (eager cache load, time to first evaluation). Provide a code example in the shared developer documentation showing side-by-side SDK 1 and SDK 2 usage to make cross-language consistency obvious to reviewers.

JSON-over-HTTP evaluation endpoint and telemetry emission reversibility: high blast: low

Add POST /internal/flags/evaluate behind the existing auth middleware. Request: { "flagKey": "...", "context": { "userId": "...", "orgId": "...", "environment": "...", "attributes": {} } }. Response: { "variant": <value>, "reason": "..." }. This endpoint calls the same in-process evaluation library — no separate evaluation code path. Rate-limit at 1 000 req/s per authenticated caller (return 429 with a Retry-After header above the limit). Emit a sampled telemetry event on each evaluation (same rate and destination as SDK events). Write a load test asserting p99 latency is under 5 ms including network round-trip at 500 req/s sustained load.

Phase 3 — Admin UI

Build the internal dashboard that lets product managers, engineers, and support staff create, edit, search, and archive flags; configure per-environment overrides; preview bucketing in real time; and review the full audit history — all with role-based access control enforced at both the API and UI layers.

Phase Goal

By the end of Phase 3, a non-engineer product manager can navigate to the flags dashboard, create a percentage-rollout flag, configure a 5% production override and a 25% staging override, drag the rollout slider to see which sample user IDs fall in-bucket, save the changes, and view the full audit trail of who changed what and when — all without writing code or filing a ticket. Admins and flag owners can edit production values; all other authenticated users have read-only access enforced server-side.

Alternatives Considered

Off-the-shelf internal admin panel generator (Retool, Appsmith, or internal CRUD framework)

Use a low-code tool to scaffold the UI automatically from the flag schema. Pros: extremely fast to build initial CRUD views. Cons: a hosted tool (Retool) would introduce a new external SaaS dependency, violating a hard constraint. A self-hosted tool (Appsmith) adds a new service to operate and is unlikely to support the bespoke bucketing-preview slider or deeply integrated RBAC without custom code anyway. Rejected.

CLI-only flag management, defer UI to a later quarter

Ship a command-line tool for flag management and skip the browser-based admin UI in this phase. Pros: faster to deliver, no frontend work in the team's critical path. Cons: the kill-switch use case requires on-call engineers or support to act quickly under incident pressure; a GUI is substantially safer and faster in that scenario than a CLI that requires terminal access. The brief explicitly includes the admin UI as in-scope. Rejected.

Recommendations

  • Build the admin UI as a new route inside the existing internal frontend application, re-using existing design-system components (table, form, modal, slider) to minimize bespoke styling work and keep the UI consistent with existing internal tooling.
  • Enforce RBAC server-side in the API layer independently of the UI — the UI hides or disables edit controls for unauthorized users but the API must reject unauthorized mutations with 403 regardless of what the UI shows.
  • Implement the bucketing preview entirely client-side using the FNV-1a algorithm re-implemented in JavaScript (or compiled to WebAssembly if the existing frontend build pipeline supports it), to avoid a server round-trip on every slider tick and keep the preview interactive at 60 fps.
  • Use keyset pagination on occurred_at for the audit history query — not offset pagination — to keep response times stable even for flags with thousands of historical entries.
  • The Phase 3 admin API contract (route shapes and request/response schemas) should be agreed and documented before Phase 2 is complete so that frontend development can begin with mock responses and overlap with Phase 2 backend work, keeping the six-week timeline achievable.

Open Questions

How do we prevent flag key namespace collisions across teams?

Multiple teams creating flags independently will eventually collide on short, generic key names (e.g., enable_dark_mode, new_checkout). Options: (a) enforce a namespacing convention at the schema level via a check constraint on key format (team-name.feature-name); (b) document a convention and rely on the unique-key constraint to surface collisions at insert time; (c) introduce a team or namespace entity as a first-class FK on the flag row. Option (a) is simple and automatically enforced but imposes a format change on all existing flag key strings. Needs cross-team input before the create-flag form validation is finalized.

How do existing RBAC roles map to "flag owner" and "flag admin"?

The brief says "only flag owners and admins can edit production values." We need concrete mappings to the existing auth system. Specifically: (a) Is "admin" the existing ROLE_ADMIN, or do we introduce a new ROLE_FLAG_ADMIN? (b) Does "owner" mean the user recorded in the owner_id column at creation, or is it a separate editable field (allowing ownership transfer)? (c) Can a flag have multiple owners? The answers determine the RBAC check implementation in t3.6 and the ownership field design in t3.2. Needs platform-team and product input before t3.6 is started.

Role-based access control enforcement reversibility: medium blast: medium

Implement RBAC at two independent layers. Server-side: all mutation endpoints (POST, PATCH, PUT, DELETE on /api/admin/flags/*) check that the authenticated user is either (a) the flag's owner_id or (b) holds the admin role (mapping defined once oq3.2 is resolved); return 403 Forbidden with a machine-readable error code for unauthorized callers. Postgres + in-process cache chosen as the flag storage and read path

Three storage approaches were evaluated: (a) a YAML/JSON config file committed to the repository, (b) a self-hosted open-source flag service (Unleash, Flagsmith), and (c) a feature_flags table in the existing Postgres database with an in-process read-through cache. Option (c) was selected.

The config-file approach cannot support runtime kill-switches without a code deploy. The self-hosted service approach adds a new stateful dependency to the infrastructure and — without a carefully engineered local SDK cache — adds a network hop to every flag evaluation, violating a hard constraint. Postgres already has the reliability guarantees, backup tooling, and operational familiarity the team needs. The in-process cache keeps evaluation latency well below 1 ms. No new infrastructure is required.

The Postgres approach requires the team to implement cache invalidation logic that an off-the-shelf service SDK would provide for free. This is the highest-risk task in Phase 2 (t2.3) and must be monitored carefully in production. If the deployment's connection pooler is incompatible with LISTEN/NOTIFY, an alternative invalidation mechanism must be designed before Phase 2 ships.

In-process library chosen over sidecar service for the evaluation path

A sidecar evaluation service (gRPC or HTTP loopback) was seriously considered as it would allow a single implementation of all evaluation logic regardless of backend language. However, the brief states explicitly that "the evaluation path must not add a network hop to request handling." Even a Unix-socket loopback call adds measurable p99 tail latency under load, and the round-trip for serialization/deserialization pushes the total comfortably past the 1 ms budget. The chosen approach embeds the evaluation engine as a library in each backend language. A JSON-over-HTTP endpoint (t2.6) is provided as a fallback for scripts and non-primary languages, but it is explicitly not on the hot request path.

Maintaining the bucketing algorithm and rule-evaluation logic in two languages increases the risk of behavioral divergence. The cross-language bucketing fixture test (t2.2) mitigates this by requiring bit-identical output for 1 000 test cases in CI, but any future algorithm change must be landed in both languages simultaneously.

FNV-1a 32-bit selected as the bucketing hash function

Hash functions evaluated: MD5 (cryptographic, universally available, but slower than needed and overkill for non-security use), SipHash (fast, good distribution, designed for hash-table use, but less trivially portable across languages), MurmurHash3 (excellent distribution, fast, popular in flag systems, but requires a library dependency in some languages), and FNV-1a 32-bit (trivially portable — ~8 lines in any language, no library dependency, sufficient distribution quality for percentage-rollout bucketing at any realistic user ID scale). FNV-1a 32-bit was selected primarily because it eliminates the risk of library version mismatches causing bucketing divergence between SDKs. Any engineer can read and verify the implementation from the specification without trusting a dependency. Distribution uniformity has been empirically validated for use cases with random-looking string inputs such as UUID-based user IDs.

Stale cache makes the kill-switch slow or ineffective

Likelihood: Medium. Impact: High. If the push-invalidation path (Postgres LISTEN/NOTIFY) is unavailable or silently dropped by a connection pooler, pods will continue serving stale flag values for up to the full TTL (30 s) after an operator issues a kill. In a security or stability incident, 30 seconds of continued exposure to a misbehaving feature can be significant.

Mitigations:

  • Detect LISTEN/NOTIFY availability at startup and expose a health-check field (pushInvalidationConnected); alert via the existing alerting stack if the push channel drops in production.
  • Make the fallback TTL configurable (env var FLAG_CACHE_TTL_SECONDS, default 30). Document that lowering it during incidents is a safe lever.
  • Add a privileged admin API endpoint (POST /internal/flags/flush-cache) that triggers an immediate cache refresh on the receiving pod. Usable during incident response to force near-instant propagation if needed. Gate it behind the existing admin role.

Bucketing algorithm divergence between SDK implementations

Likelihood: Low. Impact: High. If the two backend-language SDKs produce different bucket values for the same (userId, flagSalt) pair, users will see inconsistent behavior — a feature enabled in one service but disabled in another for the same request. This is particularly hard to detect because automated tests typically run one SDK at a time, and the divergence would only manifest in integrated production scenarios.

Mitigations:

  • The cross-language bucketing fixture test (1 000 rows, generated by a canonical Python reference script) must pass in both SDKs' CI steps. Any divergence blocks the merge.
  • The fixture test must be re-run any time the bucketing algorithm or string normalization code changes in either SDK — enforced by a CI path-filter rule.
  • Document the normalization invariants (UTF-8 encoding, 32-bit unsigned integer arithmetic, wrapping overflow semantics) inline in both implementations so future maintainers cannot accidentally break them.

Phase dependencies compress the timeline if Phase 1 slips

Likelihood: Medium. Impact: Medium. Phase 2 cannot start evaluation-engine work until the FlagStore interface (t1.4) is stable, and Phase 3's API work depends on Phase 2's evaluation semantics being settled. If Phase 1 undergoes schema iteration after cross-team review (a likely scenario), the dependency chain compresses the remaining phases into fewer than four weeks for a three-engineer team.

Mitigations:

  • Agree the Phase 3 admin API contract (routes, request/response schemas) before Phase 2 is complete and provide mock responses; frontend development can begin against mocks and overlap with Phase 2 backend work.
  • Treat t3.6 (RBAC enforcement) as the explicit cut item if time runs short — the UI can ship read-only for admins only as a safe interim state while RBAC is completed in a follow-up.
  • Front-load Phase 1 schema review by sharing the migration PR with senior engineers in the first week rather than at the end of the phase.

Audit log write contention under heavy admin UI usage

Likelihood: Low. Impact: Low. Writing an audit row in the same transaction as every flag mutation adds a second insert to the critical path of each flag save. Flag mutations are low-frequency operations (not on the hot request path), so this is unlikely to cause problems. However, during a large coordinated rollout where many operators are simultaneously adjusting flag percentages, write contention on the flag_audit_log table is theoretically possible.

Mitigations:

  • Accept this risk for the initial launch given the low likelihood at current scale. Monitor pg_stat_user_tables for flag_audit_log write latency after launch.
  • If contention surfaces, move the audit write to an after-commit async job, accepting the small risk of a missing audit entry if the process crashes between commit and async write. Document this trade-off before making the change.

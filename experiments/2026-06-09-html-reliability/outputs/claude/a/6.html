Feature Flag System

A three-phase plan to build a first-party feature-flag platform on top of existing infrastructure — enabling engineering to ship code dark, product to run gradual rollouts, and support to disable misbehaving features without a deploy. Three engineers, roughly six weeks.

Success Criteria

  • Engineers can merge code behind a flag and enable or disable it in any environment without a deploy.
  • Flag evaluation resolves at p99 under 1 ms with no network hop added to request handling.
  • Product and support can toggle flags, configure percentage rollouts, and read audit history through the admin UI without database access.
  • Every flag mutation is captured in an immutable audit log (actor, timestamp, before/after state).
  • Percentage rollouts are deterministic: the same user always receives the same variant for a given flag, across all service instances and restarts.
  • The system supports at least 500 active flags and 10 000 evaluations per second without degradation.
  • All three phases are shipped and in production within six weeks.
  • Both backend languages in the monorepo have idiomatic typed SDK wrappers around the evaluation engine.

Scope

In scope

  • Flag model: key, description, owner, flag type (boolean / percentage rollout / multivariate), targeting rules (by user ID, org ID, environment), default value, lifecycle state (active / archived).
  • Storage: feature_flags table in primary Postgres; read-through in-process cache backed by Redis pub/sub invalidation.
  • Migrations and seed data for local, CI, and staging environments.
  • Typed accessor library wrapping the schema for both backend languages.
  • Audit history for all flag changes (append-only log table).
  • Evaluation engine library: deterministic bucketing, rule ordering, environment inheritance, local in-memory cache with push/poll invalidation.
  • SDK surface for both backend languages plus a JSON-over-HTTP endpoint for all other clients.
  • Sampled evaluation telemetry events routed to the existing analytics pipeline.
  • Admin UI: flag list/search, create/edit/archive, per-environment overrides, rollout slider with live bucketing preview, audit history timeline.
  • RBAC: only flag owners and admins can edit production values; all authenticated users can read.

Out of scope

  • A/B-test statistics and experiment analysis.
  • Scheduled (time-triggered) rollouts.
  • Mobile SDKs (iOS, Android).
  • Full change-approval workflow (reviewers, required sign-offs).
  • External SaaS integrations (LaunchDarkly, Flagsmith, etc.).

Constraints

  • No new external SaaS dependencies. The entire flag platform must run on existing self-hosted infrastructure.
  • No added network hop on the evaluation path. Flag decisions must resolve from an in-process cache; no remote call may block request handling.
  • All endpoints behind existing auth middleware. No new authentication surface; flag admin and the HTTP evaluation endpoint must reuse current session/token auth.
  • Postgres is the only new persistent store. A new Redis channel may be used for pub/sub, but Redis must already be in the infrastructure (no new Redis provisioning).
  • Team size and timeline: three engineers, approximately six weeks total (two weeks per phase).
  • Evaluation p99 budget: <1 ms. Cache must be in-process; even a local Unix-socket sidecar call is too expensive for the hot path.

Assumptions

a1 — Redis is already available in production infrastructure.

The Phase 2 cache invalidation story relies on Redis pub/sub. If Redis is absent, the fallback is TTL-based polling (configurable, default 30 s), which is acceptable but increases the staleness window. Confirm Redis availability before Phase 2 begins.

a2 — The monorepo uses exactly two backend languages that need native SDKs.

SDK work in Phase 2 is scoped for two languages. A third active language would either require scope expansion or fall back to the HTTP endpoint. Verify the language inventory before Phase 2 planning.

a3 — The existing auth middleware already injects user ID and org ID into request context.

The evaluation engine's targeting rules require a populated context struct (userId, orgId, environment). If this context must be assembled separately, a context-propagation task must be added to Phase 2 and the timeline may need adjustment.

a4 — The existing internal admin frontend can be extended with new routes without major rework.

Phase 3 estimates assume an existing React (or equivalent) app with routing, form components, an API client, and a user/role model already in place. If a new frontend app must be bootstrapped from scratch, Phase 3 must be re-estimated.

Phase 1 — Flag Schema and Storage

Establish the data model, migration pipeline, typed accessor library, and audit trail that every subsequent phase builds on. Target completion: end of week 2.

Phase Goal

By the end of this phase, flag definitions can be created, read, updated, and archived through the accessor library; the schema is deployed to all environments via versioned migrations; every mutation is durably recorded in the audit log; and seed data is available for local development and CI. The evaluation engine and admin UI are not started yet — this phase is purely storage and access.

Alternatives Considered

  • Config-file-in-repo (YAML/JSON checked in to version control): Zero infrastructure overhead; changes go through PR review. Rejected because non-engineers (product, support) cannot make changes without developer involvement, and any flag change requires a deploy — directly contradicting the stated purpose.
  • External SaaS (LaunchDarkly, Flagsmith, Unleash-cloud): Mature SDKs, admin UIs, and analytics out of the box. Rejected by the explicit constraint prohibiting new external SaaS dependencies.
  • Redis as primary store (no Postgres): Lowest read latency, trivial cache warming. Rejected because Redis is not durable by default, lacks relational integrity for the audit log and flag/environment relationship, and does not support the ad-hoc queries the admin UI needs.
  • Normalised targeting-rules table instead of JSONB: Allows relational querying (which flags target a given org?) and FK integrity. Deferred — JSONB is sufficient for Phase 1 and keeps reads simple (single row per flag); can be normalised later if query patterns demand it. See decision d3.

Recommendations

Use Postgres as the sole authoritative store with a feature_flags table and a companion flag_environments table for per-environment overrides. Store targeting rules as a JSONB column validated at the application layer (see task t1.5 for the schema contract). Write migrations with the existing tool (Flyway, Alembic, golang-migrate — whatever is already in the monorepo) so the schema is version-controlled and reversible. Record all mutations in a flag_audit_log table via a database trigger or application-level hook. The Redis invalidation channel is introduced in Phase 2 once the schema is stable — Phase 1 does not touch the cache layer.

Open Questions

q1.1 — What is the expected maximum number of flags at steady state?

Affects index strategy and seed-data volume for performance benchmarks. A 200-flag system and a 20 000-flag system have different lookup characteristics. Establish a capacity estimate before finalising the schema.

q1.2 — Should the audit log be tamper-evident at the database level (separate role with no DELETE privilege)?

If there is a compliance requirement for an immutable audit trail, the audit table needs a Postgres role restriction or row-level security policy preventing DELETE. Clarify with the security or legal team before the schema migration is deployed to production.

Write the feature_flags and flag_environments schema migrations

Reversibility: High Blast: Low

Create the feature_flags table: id (UUID PK), key (unique slugified text), description (text), owner_id (FK → users), flag_type (enum: boolean | percentage | multivariate), default_value (JSONB), targeting_rules (JSONB array), salt (UUID, auto-generated, immutable — used for bucketing), lifecycle_state (enum: active | archived), created_at, updated_at. Add a unique index on key and a partial index on (lifecycle_state = 'active'). Create the companion flag_environments table: id, flag_id (FK), environment (text), default_value (JSONB nullable), targeting_rules (JSONB nullable), unique on (flag_id, environment). Write both up and down migrations.

Create the flag_audit_log table and mutation hooks

Reversibility: High Blast: Low

Add a flag_audit_log table: id (UUID), flag_id (FK), environment (nullable — null means the base flag row), actor_id (FK → users), action (enum: created | updated | archived), before_state (JSONB), after_state (JSONB), changed_at (timestamptz, default now()). Index on (flag_id, changed_at DESC) for fast timeline queries. Implement the mutation hook: either a Postgres trigger on INSERT/UPDATE to feature_flags and flag_environments, or an explicit write in the accessor library — choose whichever is consistent with the monorepo's existing pattern. The trigger approach is preferred for tamper-resistance.

Build the typed accessor library for both backend languages

Reversibility: High Blast: Low

Implement a thin repository/DAO layer for both backend languages in the monorepo. Expose: createFlag(attrs), getFlag(key), listFlags(filter), updateFlag(id, attrs), archiveFlag(id), upsertEnvironmentOverride(flagId, env, attrs), getAuditHistory(flagId, pagination). Types and structs must validate flag_type, targeting_rules shape (see t1.5), and lifecycle state at the library boundary so callers never handle raw JSONB. Include unit tests using a test-database fixture that can be set up and torn down per suite. This library is the only sanctioned way to read or write flags — no ad-hoc SQL elsewhere.

Write seed data and development fixtures

Reversibility: High Blast: Low

Create an idempotent seed script (safe to re-run on any environment) that inserts representative flags covering all three flag types and several targeting-rule combinations: a boolean flag with no rules, a percentage rollout at 25 %, a multivariate flag with a user-ID targeting rule, and an org-scoped flag. Include a staging-environment override on one flag to exercise the override path. Add a separate lightweight fixture set for integration tests (a handful of well-known flags with known expected evaluation outcomes) that can be loaded and torn down per test run. Update the local setup docs to reference the seed command.

Define and publish the targeting-rule JSON Schema contract

Reversibility: High Blast: Low

Specify the canonical JSON shape for targeting rules and publish it as a checked-in JSON Schema file (e.g. libs/feature-flags/targeting-rule.schema.json). Each rule object: type (user_id | org_id | environment), operator (in | not_in), values (string array), variant (the return value if the rule matches). Rules are evaluated in declared array order; first match wins — document this ordering contract explicitly, as the evaluation engine (Phase 2) and admin UI drag-and-drop (Phase 3) must both honour it. Reference the schema file from both language accessor libraries' validation code. Any future rule type extension goes through a schema version bump.

Phase 2 — Evaluation Engine

Build the library (and thin HTTP convenience endpoint) that resolves evaluate(flagKey, context) → variant in under 1 ms at p99, with deterministic bucketing, in-process cache, and sampled telemetry. Target completion: end of week 4.

Phase Goal

By the end of this phase, all service instances in both backend languages can evaluate any flag against a user/org/environment context without issuing a database query at evaluation time. The in-process cache is warm on startup and stays current via Redis pub/sub (with a TTL-polling fallback). A JSON-over-HTTP endpoint is available for non-native clients. Sampled telemetry events are flowing to the analytics pipeline. Benchmarks confirm p99 evaluation latency under 1 ms.

Alternatives Considered

  • Shared sidecar service for all evaluation: Centralises cache management, one invalidation subscriber per host. Rejected as the primary path because even a local Unix-socket call adds 50–200 µs latency and is a single point of failure; violates the no-network-hop constraint. Retained as the implementation backing the HTTP convenience endpoint only.
  • Database query on every evaluation (no cache): Always consistent, trivial to implement. Rejected — cannot meet the p99 < 1 ms target at any meaningful request volume; would add significant database load.
  • Poll-only invalidation (no Redis pub/sub): Simpler operationally if Redis pub/sub proves unreliable. Kept as the explicit fallback: when the subscribe channel is unavailable, each cache entry expires via TTL (default 60 s). The two approaches are complementary and both are implemented.
  • murmur3 hash for bucketing: Faster than SHA-256. Rejected in favour of SHA-256 for well-studied uniform distribution properties and availability as a standard library in all target languages without a new dependency.

Recommendations

Implement the evaluation engine as an in-process library in each backend language. On initialization, bulk-load all lifecycle_state = 'active' flags from the database into a hash map keyed by flag key, then subscribe to the Redis channel feature_flags:invalidate for targeted invalidation. Bucketing: bucket(flagKey, salt, userId) = SHA-256(flagKey + ":" + salt + ":" + userId)[0:4] as uint32 % 100 — the salt is the immutable UUID stored on the flag row from Phase 1, ensuring independence between flags. Rule evaluation: iterate rules in declared order, return the first matching variant; fall back to the percentage bucket for percentage-type flags; fall back to default_value otherwise. Environment inheritance: if no flag_environments override row exists for the requested environment, use the base flag row values. Emit a flag_evaluated event at a configurable sample rate (default 1 %) to the existing analytics pipeline via a non-blocking queue.

Open Questions

q2.1 — What is the acceptable cache staleness window?

Redis pub/sub is at-most-once delivery. A process that restarts or misses a message will serve stale values until TTL expiry. What is the maximum tolerable lag: 5 s, 30 s, 60 s? The answer sets the default TTL and whether high-impact flags need a per-flag TTL override. Resolve with the product and on-call teams before finalising cache configuration.

q2.2 — Where should evaluation telemetry events be routed?

At full traffic, evaluation events could number in the tens of millions per day. If routed to the shared analytics event bus, the data team must agree on a sampling rate and topic. If written to a dedicated table, a retention and aggregation policy is needed. Resolve with the data team before t2.5 begins so the telemetry schema is agreed upfront.

Implement and validate deterministic bucketing

Reversibility: High Blast: Low

Write a pure function bucket(flagKey, salt, userId) → int [0,99] using SHA-256(flagKey + ":" + salt + ":" + userId), interpreting the first 4 bytes as a big-endian uint32 and returning value % 100. Implement in both backend languages using their standard-library SHA-256. Write property-based tests that verify: (a) identical inputs always produce identical output across restarts; (b) distribution is uniform over 10 000 distinct user IDs (chi-squared p-value check); (c) changing the salt produces a different but still uniform distribution, confirming flag independence. Cross-language parity test: assert that the two implementations produce the same bucket for a fixed set of 50 test vectors.

Build the rule evaluation engine with full ordering and inheritance semantics

Reversibility: High Blast: Low

Implement evaluate(resolvedFlag, context) → {variant, reason}: (1) if lifecycle_state == archived, return {variant: defaultValue, reason: "archived"}; (2) iterate targeting rules in order — for each rule, check that all conditions match the context (in / not_in against the relevant context field); return the rule's variant on first match with reason "rule_match"; (3) for percentage flags, call the bucketing function and compare against the configured threshold — return "on" or "off" with reason "bucketing"; (4) return default_value with reason "default". Context struct: {userId, orgId, environment, custom: map} — userId may be null for unauthenticated requests (rules targeting user_id never match a null userId). Environment resolution: merge base flag row with the environment-specific override row (override values win); pass the resolved single object to the evaluator. Cover all edge cases in unit tests including null userId, empty rules array, archived flag, unknown environment.

Implement in-process cache with Redis pub/sub invalidation and TTL fallback

Reversibility: Medium Blast: Medium

On library init, execute a single bulk SELECT of all active flags (base rows + all environment overrides) and populate an in-process hash map keyed by (flagKey, environment). Subscribe to feature_flags:invalidate on Redis; messages carry a flag key (or * for full refresh). On receiving a targeted message, re-fetch only the affected flag from the database and update the map. On reconnect after a Redis disconnect, perform a full reload. TTL fallback: tag each cached entry with a load timestamp; lazily check expiry on access and reload if stale. Use a read-write lock (or copy-on-write snapshot) to allow concurrent reads without blocking during updates. Implement a graceful degradation mode: if the database is unreachable, return the last cached value and log a warning (never fail hard). Write integration tests simulating a Redis disconnect and verifying TTL-driven refresh.

Expose SDK surface and JSON-over-HTTP evaluation endpoint

Reversibility: High Blast: Low

For each backend language, expose a package-level function Evaluate(ctx, flagKey, defaultValue) → T that wraps the evaluation engine and cache from t2.2/t2.3, extracts user/org/environment from the request context (using the injected values from the auth middleware — see assumption a3), and returns a typed value (bool, string, or float). Add a thin HTTP handler at POST /internal/flags/evaluate behind existing auth middleware, accepting {"flagKey": "...", "context": {"userId": "...", "orgId": "...", "environment": "..."}} and returning {"variant": ..., "reason": "...", "flagType": "..."}. This endpoint is the escape hatch for non-native languages and is used by the admin UI's live rollout preview. Apply a per-IP rate limit (e.g. 500 req/s) to prevent abuse from misconfigured callers.

Add sampled evaluation telemetry

Reversibility: High Blast: Low

After every Evaluate call, enqueue (non-blocking) a flag_evaluated event: flagKey, variant, reason (rule_match / bucketing / default / archived), userIdHash (first 8 hex chars of SHA-256(userId) — no raw IDs), orgId, environment, evaluatedAt. Default sample rate: 1 % configurable per flag via a telemetry_sample_rate field added to the flag model. Route events to the destination agreed in q2.2 via the existing async emission pattern. Implement a circuit breaker: if the telemetry sink is unavailable, events are dropped (not buffered indefinitely) and a counter is incremented. Telemetry failures must never block or degrade evaluation. Publish the event schema to the data team.

Phase 3 — Admin UI

Build the internal dashboard that lets engineering, product, and support manage flags without touching the database. Target completion: end of week 6.

Phase Goal

By the end of this phase, any authenticated user can browse flags and their current state across environments; flag owners and admins can create, edit, configure rollouts, and archive flags through a web UI; the percentage-rollout slider shows a live bucketing preview before saving; per-environment overrides are manageable independently; the full audit history is readable per flag; and RBAC prevents non-owners from modifying production values.

Alternatives Considered

  • CLI-only admin tooling (no browser UI): Faster to ship; lower maintenance burden. Rejected because the brief requires product and support to manage flags independently — a CLI is too high a barrier for non-engineers and violates the self-service goal.
  • Off-the-shelf low-code admin panel (Retool, Forest Admin): Minimal frontend build cost, admin views are auto-generated from the schema. Rejected by the no-new-external-SaaS constraint.
  • Embed flag management into the existing product settings UI rather than a separate admin section: Reduces context-switching for product owners. Rejected because this is an internal engineering tool and mixing it into the customer-facing settings surface creates RBAC complexity and user confusion.

Recommendations

Add a /admin/flags route group to the existing internal frontend. Build four views sharing a common flag-context layout: (1) list/search — sortable table with filter chips; (2) detail/edit — tabbed form for base config and per-environment overrides; (3) rollout preview — slider + live bucketing distribution panel; (4) audit history — chronological timeline per flag. Gate all write API endpoints with a server-side RBAC check: only the flag's owner_id user or any user with the admin role may mutate production-environment values; all authenticated users may edit non-production overrides and read everything. Apply the same check client-side to disable fields for a faster feedback loop, but never rely on the client-side check alone for security.

Open Questions

q3.1 — Should production writes require step-up (re-)authentication?

Accidental or malicious production flag changes could have significant user-facing impact. Some teams require re-entering a password or completing an MFA challenge for production writes. Clarify with the security team whether the existing session token is sufficient or whether a step-up flow must be implemented, before the edit form is built.

q3.2 — How should the rollout slider handle multivariate flags with more than two variants?

A boolean or two-variant rollout maps cleanly to a single 0–100 % slider. For multivariate flags the 0–100 range must be partitioned into N segments. Decide whether to support multi-segment sliders in Phase 3 (higher complexity) or defer multivariate rollout UI to a follow-up and render a simpler form for that flag type instead.

Build the flag list and search dashboard

Reversibility: High Blast: Low

Create the /admin/flags index page backed by a new API endpoint GET /api/admin/flags?q=&type=&state=&owner=&page=. Display flags in a sortable table: key (monospace, links to detail view), description, owner name, flag type badge, lifecycle state badge, and last-modified timestamp. Add filter controls: free-text search (matches key and description), flag type multi-select, lifecycle state toggle (active/archived/all), and owner dropdown. Include a primary "New Flag" button and per-row "Archive" quick-action (with confirmation prompt). Paginate results server-side; support keyboard navigation. The list view is read-only and accessible to all authenticated users.

Implement flag creation and editing forms with RBAC enforcement

Reversibility: High Blast: Low

Build a shared form component used for both "create new flag" and "edit existing flag". Fields: key (slug-validated, read-only after initial save), description, owner (searchable user picker backed by GET /api/users), flag_type (radio group — changing type after creation shows a warning about existing evaluations), default_value (type-appropriate input), targeting rules (dynamic ordered list with add/remove/drag-to-reorder — each row exposes type, operator, values, variant fields). Submit via POST /api/admin/flags or PATCH /api/admin/flags/:id. Server enforces RBAC: reject production mutations from non-owners/non-admins with a 403. Build per-environment override management tab

Reversibility: High Blast: Low

Add an "Environments" tab to the flag detail view. Display a row for each known environment (production, staging, development). Each row shows: whether values are inherited from production or overridden locally (visual indicator), the effective default value, and the effective targeting rules. An "Set Override" button opens an inline form to enter environment-specific values; a "Remove Override" button deletes the flag_environments row and reverts to inheritance. Add percentage-rollout slider with live bucketing preview

Reversibility: High Blast: Low

For flags of type percentage, render a 0–100 % slider adjacent to a "Preview" panel. As the slider moves (debounced 250 ms), client calls POST /internal/flags/evaluate with 100 synthetic context objects (user IDs sampled from a recent-user list fetched at page load, or deterministically generated if unavailable) and counts how many receive the "on" variant. Display: "At N %, K of 100 sampled users receive 'on'." Render a small bar chart showing the split. The preview is strictly read-only and does not persist anything; it helps operators verify the slider value before saving. If the HTTP endpoint is slow, show a spinner and disable save until the preview resolves.

Implement the audit history timeline view

Reversibility: High Blast: Low

Add an "Audit History" tab on the flag detail page. Fetch from GET /api/admin/flags/:id/audit?page=&environment= (paginated, newest first; filterable by environment). Render as a vertical timeline: each entry shows the actor's avatar and name, a relative and absolute timestamp, the action type label (created / updated / archived), and a human-readable diff of changed fields — e.g. "targeting_rules: added rule [user_id in {u123}]" rather than a raw JSON dump. Implement the diff by comparing before_state and after_state JSONB keys. The audit endpoint is read-only and accessible to all authenticated users (no RBAC restriction on reads). Load older entries with a "Load more" button, not infinite scroll, to keep the page performant for flags with long histories.

d1 — Postgres + in-process cache as the architecture (not config-files or SaaS)

Flags live in a feature_flags Postgres table (source of truth) and are evaluated from an in-process hash map (loaded at startup, invalidated via Redis pub/sub). This satisfies the no-network-hop constraint, keeps the authoritative state in a durable relational database that already supports audit logging and RBAC, and requires no new infrastructure beyond a Redis pub/sub channel.

A config-file-in-repo approach would require no new infrastructure and all changes would be reviewed via PRs. However, it forces non-engineers to go through a deploy pipeline for every flag change and cannot support real-time rollouts — directly contradicting the stated goals. An external SaaS such as LaunchDarkly was excluded by the no-new-SaaS constraint.

d2 — In-process library (not a shared sidecar) for the evaluation hot path

The evaluation engine is packaged as an in-process library for each backend language. Every service instance holds its own cache and makes zero network calls at evaluation time. The JSON-over-HTTP endpoint introduced in Phase 2 is a convenience layer for non-native clients only; it is not on the critical request path for any service that has the native SDK.

A shared sidecar would centralise cache management (one Redis subscriber per host instead of one per process) and simplify multi-language support. However, even a Unix-domain-socket call adds ~100 µs of latency, which violates the <1 ms p99 budget when combined with other middleware costs. For a team of three, maintaining one library per language is also operationally simpler than a separate long-running sidecar with its own deployment and health-check surface.

d3 — JSONB for targeting rules (deferred normalisation)

Targeting rules are stored as a JSONB column on feature_flags (and on flag_environments overrides) rather than in a separate normalised flag_rules table. This keeps reads to a single-row fetch per flag with no JOINs, allows the rule schema to evolve without additional migrations, and is sufficient for the query patterns required by Phase 1 and the evaluation engine.

A normalised rules table would enable relational queries such as "which flags target org X?" and would enforce referential integrity on rule values. If cross-flag rule analysis becomes a common operational need (e.g. for a "who is impacted by this rule change" view in the admin UI), this decision should be revisited and a migration written to extract rules into a dedicated table.

r1 — Cache staleness: a service instance serves wrong flag values after a missed invalidation

Likelihood: Medium. Impact: Medium–High (unexpected feature state for users; potential data integrity issues for flags gating writes).

Redis pub/sub is at-most-once. A process that restarts, reconnects, or experiences a brief network partition will not receive the invalidation message and will serve stale values until its TTL-based fallback expires. For a flag controlling a high-value feature (payments, permissions), even 30 s of stale state could be significant.

Mitigations: (1) Perform a full cache reload on process startup and on every Redis reconnect; (2) configure a short default TTL (60 s, tunable per flag); (3) provide a flag-level max_staleness_seconds override for high-impact flags that need aggressive TTLs; (4) document the staleness contract in the flag ownership guide so owners factor it into their rollout plan.

r2 — In-process cache memory pressure if flag count grows unexpectedly

Likelihood: Low near-term, Medium over 12 months. Impact: Medium (GC pressure or OOM in high-throughput services that have tight memory budgets).

Loading all active flags into every service process is efficient for hundreds of flags but can become problematic if thousands accumulate — especially if large JSONB rule arrays are common. The problem is proportional to flags × rule size × number of service instances.

Mitigations: (1) Only cache lifecycle_state = 'active' flags; (2) instrument cache size (entry count and byte estimate) as a Prometheus metric with an alert threshold; (3) if memory becomes a concern, switch to a lazy-load LRU cache that evicts cold flags; (4) set an organisational norm to archive flags once their rollout is complete to keep the active set small.

r3 — Existing env-var / hardcoded feature gates are never migrated, creating a dual-system problem

Likelihood: High. Impact: Medium (engineers confused about which system governs a given feature; support unable to disable things that are actually gated by environment variables rather than the new system).

Most codebases accumulate ad-hoc feature gating over time (if process.env.ENABLE_X, static constants, config YAML booleans). If these are not catalogued and migrated, the new flag system will govern only new code, and the product value of the admin UI will be partial.

Mitigations: (1) After Phase 1 ships, run a codebase grep audit to inventory all existing feature-gate patterns and produce a migration backlog; (2) schedule migration of the top-10 highest-value gates as a follow-up work item; (3) establish and communicate a team norm: all new feature gates use the new system from Phase 1 ship date forward; (4) add a linting rule flagging new uses of the old pattern.

r4 — Six-week timeline is tight for a team of three across all three phases

Likelihood: Medium. Impact: Medium (Phase 3 admin UI, being the most visible deliverable, may ship with reduced polish or deferred features).

Two weeks per phase is achievable but leaves no buffer for unforeseen complexity (e.g., a tricky multi-language SDK parity issue, or frontend infrastructure groundwork needed for Phase 3). Oncall rotations and any unplanned incident response will compress the available time further.

Mitigations: (1) Identify one engineer as the lead per phase to reduce coordination overhead; (2) treat the HTTP evaluation endpoint and the admin UI rollout-slider as Phase 2/3 stretch goals — the core evaluation library and basic CRUD admin views are the hard requirements; (3) review phase completion at the end of weeks 2 and 4 with explicit scope-cut options ready.

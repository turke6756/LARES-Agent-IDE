Feature Flag System

A three-phase, six-week initiative to add a first-party feature-flag system to the product — covering flag storage and schema, an in-process evaluation engine with per-language SDKs, and an admin dashboard with RBAC — enabling dark launches, gradual rollouts, and kill-switch capability with no new external SaaS dependencies and no added network hop on the hot evaluation path.

Success Criteria

  • An engineer can create, enable, and disable a feature flag without a production deploy, completing the action in under two minutes from the admin UI.
  • The evaluation engine answers evaluate(flagKey, context) at p99 < 1 ms measured in-process on representative production hardware, with no synchronous network hop on the hot request path.
  • Percentage rollouts are deterministic: the same userId + flagKey + salt triple always maps to the same variant across all SDKs and all application instances.
  • At least two backend languages in the monorepo have a typed SDK; all other callers can reach evaluation via the JSON-over-HTTP endpoint.
  • Every flag mutation is captured in an immutable audit log recording actor, timestamp, previous value, and new value.
  • Only the flag's designated owner and users with the admin role can edit production flag values; all other attempts are rejected with a 403.
  • A misbehaving feature can be killed via the admin UI within 30 seconds of operator intent, with cache propagation completing within one TTL cycle (target ≤ 60 s).
  • The system runs entirely on existing infrastructure — no new SaaS vendor relationships, no new database engine, no new identity system.

Scope

In Scope

  • Flag data model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (by user ID, by org ID, by environment), default value, lifecycle state (active / archived).
  • Postgres feature_flags and flag_targeting_rules tables, forward and rollback migrations, and seed data.
  • Append-only flag_audit_log table recording every flag mutation.
  • Read-through in-process cache backed by a shared store, with push-invalidation via pub/sub and TTL-based polling fallback.
  • Typed accessor library (one module per backend language) wrapping the cache and providing safe getters with fallback defaults.
  • Core evaluation algorithm: deterministic percentage bucketing (MurmurHash3), targeting-rule ordering (first-match-wins by priority), environment-inheritance chain.
  • Per-language SDKs for both backend languages currently in the monorepo.
  • JSON-over-HTTP evaluation endpoint for non-SDK callers, behind existing auth middleware.
  • Sampled telemetry event per evaluation, flushed asynchronously to the analytics pipeline.
  • Admin dashboard: flag list with search/filter, create/edit/archive forms, per-environment override UI, percentage-rollout slider with live bucketing preview, audit-history tab, RBAC enforcement.

Out of Scope

  • A/B-test statistical analysis or experiment significance reporting.
  • Scheduled (time-based) flag activation or deactivation.
  • Mobile SDKs (iOS, Android, React Native).
  • Four-eyes approval workflow before production flag changes.
  • External SaaS feature-flag vendors (LaunchDarkly, Statsig, Split, etc.).

Constraints

  • No new external SaaS dependencies. Every component must run on infrastructure the team already operates.
  • Zero network hop on the evaluation path. Flag evaluation inside application servers must resolve from an in-process or loopback-local cache — never via a synchronous RPC to another host.
  • Behind existing auth middleware. The admin dashboard, admin API routes, and HTTP evaluation endpoint must all sit behind the existing session and authentication middleware; no new identity stack.
  • Postgres as the system of record. The flag schema must live in the existing primary Postgres instance; no additional database engine is permitted.
  • Team size and timeline. Three engineers, approximately six weeks, yielding roughly 18 engineer-weeks of capacity.

Assumptions

A1 — Postgres is the team's primary relational database and migrations are run from the monorepo.

The Phase 1 design creates two new tables and an audit table in the existing Postgres instance, using the repo's existing migration toolchain. If the primary database is a different engine, column types and migration syntax will need adjustment.

A2 — A shared Redis (or equivalent) instance is available for cache-invalidation pub/sub.

The push-invalidation design publishes a message to a Redis channel after every flag write, allowing all application instances to drain their local caches promptly. Without this, only polling-based invalidation is available, widening the worst-case propagation window beyond the 60 s target.

A3 — Exactly two backend languages in the monorepo require typed evaluation SDKs.

Phase 2 budgets for two SDK implementations against the golden bucketing fixture. If a third actively-used language is discovered during Phase 2, approximately 3–4 engineer-days should be added to the estimate before committing to the six-week timeline.

A4 — The existing RBAC system supports per-resource ownership sufficient to model "flag owner" and "admin" roles.

Phase 3 RBAC enforcement relies on the session layer being able to tell whether the requesting user owns a specific flag or holds a global admin role. If the current permission model is too coarse (binary admin/non-admin only), a supplemental flag_permissions table will be required, adding scope to Phase 3.

Phase 1 — Flag Schema & Storage

Establish the canonical data model, persistence layer, cache infrastructure, typed accessor library, and audit trail that all subsequent phases depend on. This phase produces no user-visible product features but is the critical foundation — Phase 2 and Phase 3 work can begin in parallel once t1.3 and t1.4 are merged.

Phase Goal

By the end of Phase 1, any application code in the monorepo can retrieve a typed flag value via the accessor library, all flag mutations are durably recorded in an append-only audit log, and the data model fully supports boolean, percentage-rollout, and multivariate flag types with per-user, per-org, and per-environment targeting rules.

Alternatives Considered

Config-file-in-repo (YAML/JSON committed to source control)
Flags are stored as a checked-in config file, evaluated at deploy time. Pro: git history is the audit log for free; no runtime database dependency. Con: every flag change — including an emergency kill-switch — requires a commit, a CI run, and a deploy, which defeats the primary stated use cases. Rejected.
Dedicated flag-service with its own Postgres instance
A separate microservice owns its own isolated database. Pro: schema changes are blast-radius-isolated from the primary DB. Con: introduces a new RDS instance, credentials rotation, backup policy, and a network hop from application servers to the flag service — violating the no-network-hop constraint. Rejected in favor of a new table in the existing primary database.
Schema-per-flag-type (separate tables for boolean, percentage, multivariate)
Each flag type gets its own table to avoid nullable columns. Pro: type safety at the database layer. Con: adds JOIN complexity to every read path and makes it harder to query across flag types in the admin list view. Rejected in favor of a single table with a JSONB default_value column and a separate flag_targeting_rules child table.

Recommendations

  • Keep the feature_flags table narrow: key, description, owner_user_id, type enum, default_value (JSONB), lifecycle_state, salt (used for bucketing), created_at, updated_at. Push per-rule complexity into the flag_targeting_rules child table.
  • Store variant definitions and default values as JSONB. This accommodates multivariate flags without a rigid schema and remains queryable with Postgres JSON operators.
  • The in-process cache should load all active flags eagerly on startup into a hash map keyed by flag key. Evaluate to a hash-map lookup plus lightweight rule matching — not a database query per evaluation.
  • Implement the audit log as an append-only table with no UPDATE/DELETE granted to the application database user, making tamper evidence a database-level guarantee rather than an application-level convention.
  • Enforce a max of 20 targeting rules per flag at the write layer (accessor library + API validation) to bound worst-case evaluation time.

Open Questions

OQ1.1 — Acceptable cache staleness window and cold-start behavior

What maximum staleness is acceptable if a push-invalidation signal is lost? Should the TTL fallback be 30 s, 60 s, or something else? Also: on cold start, should the application block accepting requests until the cache is fully warm, or serve flag defaults immediately while warming in the background? The answer affects the cache module design in t1.3.

OQ1.2 — Multivariate variant value format constraint

Should multivariate variant values be constrained to strings, or can they be arbitrary JSON objects? Arbitrary JSON is more expressive but forces callers to deserialize and manage schema drift across flag variants. A decision is needed before the accessor library's typed API (t1.4) is finalized.

Write both forward and rollback migrations using the repo's existing migration toolchain.

Create seed data and fixture scripts rev: high blast: low

Write an idempotent seed script (upsert on key) that populates at least one flag of each type: a simple boolean kill-switch, a percentage-rollout flag at 20%, and a multivariate flag with three named variants. Implement read-through in-process cache with push/poll invalidation rev: medium blast: medium

Build a cache module that: (1) on initialization, queries all active flags and their targeting rules from Postgres and loads them into a thread-safe in-process hash map keyed by flag key; (2) subscribes to a Redis pub/sub channel (e.g., feature_flags:invalidate) and on receiving a message for a given flag key, re-fetches that flag's record from Postgres and atomically replaces the map entry; (3) runs a background polling loop as a fallback that does a full cache refresh every configurable TTL (default 60 s) in case any invalidation messages were missed. Expose a get(key) method returning the full flag record including targeting rules, or null if not found. Latency for get must be <0.1 ms (hash-map lookup only — no I/O on the hot path).

Build typed accessor library for both backend languages rev: high blast: low

Create a thin, idiomatic module per backend language that wraps the cache layer and exposes safe typed getters: getBooleanFlag(key, ctx, default) → bool, getStringVariant(key, ctx, default) → string, getNumberVariant(key, ctx, default) → number. Accessors must never throw — they fall back silently to default if the flag is missing, the cache is not yet warm, or the returned variant cannot be coerced to the expected type. The context parameter (ctx) carries userId, orgId, and environment and is threaded through to the evaluation engine in Phase 2. Write unit tests covering: missing key → default, cold-cache fallback, type coercion edge cases, archived flag → default.

Wire audit logging into all flag mutation paths rev: high blast: low

Ensure every INSERT or UPDATE to feature_flags or flag_targeting_rules is wrapped in a database transaction that also appends a row to flag_audit_log with the full before-state and after-state captured as JSONB. Implement this as a Postgres trigger (simpler, harder to bypass) rather than an application-layer hook, so that any future out-of-band changes are also captured. Verify via integration test that the application database user does not hold UPDATE or DELETE privileges on flag_audit_log. Also publish an invalidation message to the Redis channel from within the same transaction commit hook.

Write integration tests for the storage and cache layers rev: high blast: low

Using a transactional test harness against a real Postgres instance (not mocks), write integration tests covering: flag create/read/update/archive roundtrip; targeting rule insert and delete with correct priority ordering; audit log immutability (attempt DELETE and expect error); cache invalidation triggering a map refresh within the TTL window after a flag update; cold-start fallback serving the accessor library's supplied default; and archived flags returning defaults via the accessor. These tests must pass before Phase 2 begins, as they gate the evaluation engine work.

Phase 2 — Evaluation Engine

Build the algorithm that maps a (flagKey, evaluationContext) pair to a variant string in sub-millisecond time. The engine runs in-process inside every application server and is also exposed as an HTTP endpoint for callers that cannot embed the SDK. Deterministic bucketing, rule ordering, environment inheritance, and sampled telemetry are all in scope.

Phase Goal

By the end of Phase 2, any service in the monorepo can call evaluate(flagKey, context) and receive the correct variant in accordance with targeting rules and percentage bucketing, at p99 < 1 ms in-process. The JSON-over-HTTP endpoint is live, documented, and behind the existing auth middleware. Sampled telemetry events are flowing to the analytics pipeline. Both SDK implementations pass the golden bucketing fixture.

Alternatives Considered

Sidecar process per application host (Unix socket)
Run the evaluation engine as a sidecar, communicating over a loopback Unix socket. Pro: language-agnostic; engine can be updated independently of application servers. Con: a Unix-socket round trip costs 0.2–0.5 ms under contention and would frequently breach the <1 ms p99 target. Also adds a per-host process lifecycle concern. Rejected for the primary hot path; the HTTP endpoint serves the long-tail of callers where latency is not critical.
Centralized evaluation service (remote fleet)
All evaluations route to a dedicated fleet behind a load balancer. Con: adds a mandatory network hop to every flag evaluation. This directly contradicts the stated constraint. Rejected outright.
SHA-256 for percentage bucketing
Use SHA-256 instead of MurmurHash3 for bucketing. Pro: already available in every language's standard library; no extra dependency. Con: SHA-256 is a cryptographic hash — roughly 10× slower than MurmurHash3 for this input size — and does not improve distribution quality for this use case. Rejected in favor of MurmurHash3 (or the repo's existing non-cryptographic hash if one is present).

Recommendations

  • Bucketing formula: murmurhash3_32(userId + ":" + flagKey + ":" + flagSalt) mod 10000 → bucket ∈ [0, 9999]. A rollout of X% includes buckets 0 through floor(X × 100) − 1. The per-flag salt (stored in feature_flags.salt) ensures independent bucketing across flags for the same user.
  • Rule ordering: evaluate targeting rules in ascending priority integer order; first match wins; fall through to percentage bucketing if no rule matches; fall through to the flag's global default if the flag type is boolean or multivariate with no rollout configured.
  • Environment chain: build the inheritance list from a config value at startup (e.g., FEATURE_FLAG_ENV_CHAIN=dev,staging,production). On evaluation, walk left-to-right stopping at the first environment that has an override for the flag.
  • Telemetry: enqueue events into a per-goroutine/per-thread ring buffer; drain asynchronously. Never block the evaluation caller for telemetry. Drop events silently when the analytics pipeline is backpressured — evaluation correctness takes priority over telemetry completeness.

Open Questions

OQ2.1 — Push vs. poll invalidation: runtime switch or single mode?

The Phase 1 cache supports both Redis pub/sub push and TTL polling as a fallback. Should the evaluation engine expose a configuration switch to disable push invalidation entirely (for environments where Redis is unavailable), or should push always be attempted and polling always run in parallel as a safety net? The answer determines whether ops needs to configure two separate deployment profiles.

OQ2.2 — Telemetry sampling strategy and pipeline capacity

At high QPS, a 1% sample rate could still produce millions of events per day. Does the analytics pipeline (Kafka topic or equivalent) have a known ingestion limit that should cap the absolute rate? Should the sampling rate be flag-specific (100% for flags in early rollout <10%, 0.1% for stable flags >90%), or uniform across all evaluations?

Implement and validate deterministic bucketing algorithm rev: high blast: low

Write the pure function bucket(userId, flagKey, salt) → int [0, 9999] using MurmurHash3 (32-bit variant, seed 0) over the UTF-8 string userId + ":" + flagKey + ":" + salt, result mod 10000. Implement in both backend languages. Produce a golden fixture file — a CSV of 1000 rows: (userId, flagKey, salt, expectedBucket) — generated from a reference implementation. Both SDK test suites must pass this fixture as a required CI check. Also validate empirically that bucket distribution is uniform to within 1% over 100 000 synthetic user IDs to catch hash-quality issues.

Implement core evaluation function with rule ordering and fallback chain rev: high blast: low

Build evaluate(flagKey, context) → {variant: string, reason: string}. The context struct carries userId, orgId, and environment. Evaluation order: (1) look up flag from the in-process cache — if absent, return caller-supplied default with reason "flag_not_found" and emit a warn log (once per key per process lifetime via a seen-set); (2) if flag is archived, return default with reason "archived"; (3) iterate targeting rules in ascending priority order — return the first matching rule's variant with reason "rule_match"; (4) for percentage-rollout flags, compute bucket and compare to rollout threshold — return "on" or "off" with reason "percentage"; (5) return default_value with reason "default". Include a benchmark that must run under 0.5 ms p99 with 20 targeting rules on representative hardware.

Implement environment inheritance chain resolution rev: high blast: low

Add environment resolution to the evaluation path. On module initialization, read the FEATURE_FLAG_ENV_CHAIN config value (e.g., "dev,staging,production") and build an ordered list. During evaluation, the context's environment field selects the starting point in the chain; the engine walks toward production until it finds an environment-specific targeting-rule set or default-value override for the flag. If the entire chain is exhausted without finding an override, fall through to the flag's global default. Unit tests must cover: full chain (all three environments have overrides, correct one is selected), partial override (staging and production have overrides, dev inherits from staging), and chain exhaustion (no environment has an override, returns global default).

Build typed SDK wrappers for both monorepo languages rev: high blast: low

Wrap the core evaluation library in idiomatic typed clients for each backend language. Each SDK exposes three typed helpers — evaluateBoolean(flagKey, ctx, default), evaluateString(flagKey, ctx, default), evaluateNumber(flagKey, ctx, default) — which call the core evaluate function and coerce the variant to the requested type or return the default if coercion fails. Both SDKs must pass the golden bucketing fixture from t2.1. Include a README with initialization snippet, the three call shapes, and guidance on where to construct the context struct in a request handler.

Expose JSON-over-HTTP evaluation endpoint rev: medium blast: medium

Add POST /internal/flags/evaluate behind the existing auth middleware. Request body: {"flagKey": "...", "context": {"userId": "...", "orgId": "...", "environment": "..."}}. Response: {"variant": "...", "reason": "rule_match|percentage|default|archived|flag_not_found"}. The endpoint calls the same in-process evaluation library — no separate code path, no database queries. Apply a per-caller rate limit (e.g., 500 req/s per auth token) to prevent accidental hot-spot usage patterns from services that should be embedding the SDK. Register the endpoint in the internal API catalog with a note recommending SDK use for latency-sensitive callers.

Instrument evaluation telemetry and metrics rev: high blast: low

After each evaluation, enqueue a telemetry event — {flagKey, variant, reason, userId, orgId, environment, sampledAt} — into a ring buffer local to the current goroutine/thread. A single background worker drains all ring buffers and batches events to the analytics pipeline (Kafka topic feature_flag_evaluations or equivalent). Default sampling: 100% for flags with rollout < 10%, 1% for all others. The ring buffer drops events silently when full — never block the evaluation caller. Add two metrics via the existing metrics library: flag_evaluations_total{flag_key, variant, reason} (counter) and flag_evaluation_latency_seconds{flag_key} (histogram, p50/p95/p99 reported). Verify in load tests that evaluation latency does not increase when the telemetry pipeline is artificially stalled.

Phase 3 — Admin UI

Deliver a self-service dashboard inside the existing web application where engineers and product managers can create, configure, and archive flags without touching the database. Enforces RBAC so that only flag owners and admins can edit production values. Surfaces the full audit history and a live rollout preview.

Phase Goal

By the end of Phase 3, non-engineering stakeholders can create, modify, and archive feature flags via the web UI without any database or CLI access. The UI enforces role-based access at both the UI and API layer, shows a live bucketing preview for percentage rollouts, displays the full cursor-paginated audit history for any flag, and allows any authorized user to activate a kill-switch within 30 seconds.

Alternatives Considered

Standalone single-page application at a separate origin
Build the admin UI as a separate React/Vue SPA with its own deployment pipeline. Pro: clean isolation; can be locked to an internal network range independently of the main app. Con: requires cross-origin auth plumbing (separate CORS policy, token sharing), a second CI/CD artifact, and a second deployment runbook — none of which are budgeted in 18 engineer-weeks. Rejected in favor of a new section within the existing admin area of the monorepo web app, which reuses the existing component library, auth middleware, and deployment pipeline.
CLI-only flag management (no web UI)
Provide only a CLI tool and skip the web dashboard. Pro: eliminates all frontend work, saving roughly 4–5 engineer-weeks. Con: product managers and support teams cannot self-serve; every flag change requires an engineer with production database credentials and CLI access, which undermines the stated goals of enabling product-led gradual rollouts and support-led kill-switches. Rejected.
Third-party embedded admin component (e.g., Retool, internal tools platform)
Use an internal tooling platform to generate the CRUD UI automatically against the Postgres schema. Pro: near-zero frontend development time. Con: contradicts the no-new-SaaS-dependencies constraint, and internal tooling platforms typically lack support for custom widgets like the bucketing-preview slider. Rejected.

Recommendations

  • Build inside the existing admin section (/admin/flags) to inherit navigation chrome, auth session, and the established component library. Avoid introducing a second frontend framework or build system.
  • The percentage-rollout slider preview should compute the approximate affected-user count client-side using the bucketing formula and a cached total-user-count fetched once on page load. Label it clearly as an approximation — it is not a live cohort query.
  • Audit-history should paginate server-side with a cursor (not offset) to remain performant as logs grow. Load 50 entries per page; provide a "Load more" button rather than infinite scroll.
  • RBAC must be enforced server-side on every mutating API call — not just in the UI by disabling buttons. The check is: caller.userId === flag.ownerUserId || caller.hasRole('admin'). UI state is informational only.
  • Minimum viable Phase 3 (if timeline is tight): tasks t3.1 and t3.2 (list + create/edit/archive) constitute the essential self-service surface. Tasks t3.3–t3.6 are high-value polish that can slip to a follow-up if needed.

D1 — Store flags in Postgres (not config-file-in-repo)

We will store the flag schema in a new feature_flags table in the existing primary Postgres instance rather than as a YAML or JSON file committed to the monorepo.

Rationale: The core use cases — emergency kill-switches, support-driven interventions, gradual rollouts managed by product — all require runtime changes without triggering a CI pipeline and deploy. A config-file approach ties every flag mutation to a commit, CI run, and rollout, which defeats these use cases entirely. Postgres also provides relational integrity for ownership and org references, JSONB for flexible variant schemas, and transactional guarantees needed for the audit log. The operational cost of one new table in an existing instance is negligible.

The config-file approach has a genuine advantage: git history is the audit log for free, diffs are human-readable without tooling, and the schema is reviewable in pull requests. We mitigate these gaps by building an explicit append-only audit table and a human-readable diff view in the Phase 3 admin UI.

D2 — In-process evaluation library (not sidecar or centralized service)

The evaluation engine will be implemented as an in-process library embedded directly in each application server, not as a sidecar process or a centralized evaluation fleet.

Rationale: The explicit constraint is that the evaluation path must not add a network hop to request handling. An in-process library with a pre-loaded in-memory flag cache reduces evaluation to a hash-map lookup plus lightweight rule matching, trivially satisfying the <1 ms p99 target. A sidecar adds a minimum 0.2–0.5 ms Unix-socket round trip; a centralized service adds a full network hop. The in-process design also has no single point of failure — if the flag backend (Postgres + Redis) becomes unavailable, the in-process cache continues serving the last known state for up to the TTL window.

The primary downside is deployment coupling: a bug in the evaluation engine requires rolling out new application server versions rather than redeploying a single sidecar binary. We accept this trade-off given the latency constraint and the fact that the evaluation engine is a small, well-tested pure function unlikely to require frequent hotfixes.

D3 — MurmurHash3 with per-flag salt for deterministic percentage bucketing

Percentage rollout bucketing uses MurmurHash3 (32-bit, seed 0) over the UTF-8 string userId:flagKey:flagSalt modulo 10000, producing a bucket in [0, 9999]. A flag with X% rollout includes users whose bucket falls in [0, floor(X × 100) − 1].

Rationale: MurmurHash3 is a non-cryptographic hash that is fast (<10 ns for short strings), produces a uniform distribution, and has well-tested portable implementations in both monorepo languages. The 10000-bucket granularity gives 0.01% rollout precision. The per-flag salt (a random string stored in feature_flags.salt) ensures that a user landing in the first 20% for flag A does not automatically land in the first 20% for flag B — preventing correlated exposure across simultaneous rollouts and experiments.

MurmurHash3 is not in every standard library; it may need to be vendored for one of the backend languages. We mitigate this by checking the repo's existing dependency tree first and using SHA-256 as a fallback only if MurmurHash3 is truly unavailable, with an explicit note in the golden fixture about which hash function is in use.

R1 — Cache invalidation failures cause stale flag evaluations after kill-switch

Likelihood: Medium. Redis pub/sub delivers messages on a best-effort basis; network partitions, Redis restarts, or subscriber backpressure can cause dropped messages.

Impact: High. A stale "on" value persisting after an operator activates a kill-switch is the worst-case failure mode for the entire system — the feature continues misbehaving for up to the TTL window despite the operator's action.

Mitigation: (1) TTL-based full-refresh (target 60 s) runs unconditionally in the background even when push invalidation is configured — it is a safety net, not just a fallback. (2) After a flag write commits, the admin API also issues direct HTTP invalidation calls to all known application instances via the service-discovery registry, providing a second parallel invalidation path. (3) Add an alerting rule that fires if any application instance's flag-cache age exceeds 90 s. (4) Document the expected worst-case propagation window in the ops runbook so support teams know what to communicate during an incident.

R2 — Evaluation overhead degrades hot request-path performance at high QPS

Likelihood: Low for simple flags; Medium for flags with many targeting rules or for services calling evaluate in tight loops.

Impact: Medium. A 0.5 ms p99 regression on a latency-sensitive endpoint running at 10k QPS can surface in SLA dashboards and trigger pager alerts.

Mitigation: (1) Cap targeting rules at 20 per flag, validated on write. (2) The benchmark in t2.2 must pass before the evaluation engine is merged: <0.5 ms p99 for a flag with 20 rules on representative CI hardware. (3) Monitor flag_evaluation_latency_seconds p99 in the production metrics dashboard from day one of the Phase 2 rollout. (4) If a latency regression is observed, the first remediation is caching the compiled rule set as a pre-sorted slice rather than re-sorting on every evaluation.

R3 — Team capacity shortfall causes Phase 3 to slip past the six-week window

Likelihood: Medium. Three engineers over six weeks is ~18 engineer-weeks for a full-stack feature spanning schema design, two SDKs, an HTTP endpoint, telemetry, and a web UI. Any Phase 1 or Phase 2 scope creep directly compresses Phase 3.

Impact: Medium. Phase 3 delivers the self-service surface; without it, engineers must make flag changes via the database or CLI, reverting to the pre-system workflow for non-engineering stakeholders.

Mitigation: Define the minimum viable Phase 3 explicitly: tasks t3.1 (list page) and t3.2 (create/edit/archive) are required; t3.3 (slider preview), t3.4 (env overrides), t3.5 (audit history), and t3.6 (RBAC tests) are high-value polish. At the end of week 4, assess Phase 1 and 2 completion. If the team is behind by more than 2 engineer-days, defer t3.3–t3.5 to a documented follow-up sprint and ship the MVP admin surface on schedule.

R4 — Cross-language bucketing divergence between the two SDKs

Likelihood: Low-Medium. Subtle differences in string encoding (BOM, trailing bytes), integer overflow behavior, or hash-library version can produce divergent outputs for identical inputs.

Impact: High. If the two SDKs bucket differently, a user will see different variants depending on which service handles their request, breaking the determinism guarantee and potentially exposing a user to both sides of a gradual rollout simultaneously.

Mitigation: The golden fixture file (t2.1) is the contractual specification. Every SDK CI pipeline runs the 1000-row fixture as a required, non-skippable test. Any divergence is a hard CI failure, not a warning. The fixture header documents the exact input encoding (UTF-8, no BOM, colon delimiter, no trailing whitespace) and the hash algorithm (MurmurHash3, 32-bit, seed 0) to eliminate ambiguity across languages.

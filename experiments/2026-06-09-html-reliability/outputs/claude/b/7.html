Feature Flag System

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases: flag schema and storage, evaluation engine, and admin UI. Three engineers, roughly six weeks. No new external SaaS dependencies; evaluation must not add a network hop to the request path.

Success criteria

  • Any boolean, percentage-rollout, or multivariate flag can be created, edited, and archived through the admin UI without a code change or deploy.
  • The evaluation engine answers evaluate(flagKey, context) in under 1 ms at p99 in production load tests, measured in-process with no extra network hop.
  • Deterministic bucketing: given the same user ID and flag key, the same variant is returned across all service instances and restarts.
  • Flag changes propagate to all service instances within 30 seconds of being saved (push or poll invalidation).
  • Every flag evaluation emits a sampled telemetry event consumable by the analytics pipeline.
  • Audit history records every flag mutation (who changed what, when, and to what value) and is visible in the admin UI.
  • Role-based access prevents non-owners and non-admins from editing production flag values.
  • Zero new external SaaS dependencies introduced; everything operates behind the existing auth middleware.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state (active / archived).
  • Postgres feature_flags table with migrations and seed data.
  • Read-through in-memory cache with push-or-poll invalidation.
  • Audit history table recording all flag mutations.
  • Typed accessor library (flag-store client).
  • Evaluation engine: in-process library for the two backend languages in the monorepo.
  • JSON-over-HTTP evaluation endpoint for languages not covered by a native SDK.
  • Deterministic percentage-rollout bucketing (hash of user ID + flag salt).
  • Rule ordering semantics and environment inheritance (staging defaults from production).
  • Sampled evaluation telemetry events.
  • Admin UI: create, edit, search, archive flags; per-environment overrides; percentage slider with live bucketing preview; audit-history view.
  • Role-based access: flag owners and admins may edit production values; others read-only.

Out of scope

  • A/B-test statistics and experiment analysis.
  • Scheduled (time-based) rollouts.
  • Mobile SDKs.
  • Full approval / change-request workflow (audit history only).
  • External SaaS flag vendors (LaunchDarkly, Unleash, etc.).

Constraints

  • No new external SaaS dependencies. The entire system runs on existing infrastructure (Postgres, internal cache layer, monorepo services).
  • No added network hop on the evaluation path. The evaluation engine must run in-process; the HTTP endpoint is available only as a fallback for non-native callers, not on the hot path.
  • Existing auth middleware. The admin UI and HTTP endpoint are gated behind the same auth as the rest of the product — no new auth surface.
  • Team size: three engineers. Phases are sequenced to avoid blocking dependencies; Phase 1 storage layer must be stable before Phase 2 engine work completes, and Phase 2 evaluation library must be usable before Phase 3 UI preview features land.
  • Six-week total timeline. Roughly two weeks per phase, with overlap where possible.
  • Backwards compatibility. Flag evaluation must degrade gracefully (return default value) if the cache or database is unavailable — never throw into the application request path.

Assumptions

The monorepo has exactly two backend languages. Native SDKs will be written for both; all other callers use the JSON-over-HTTP endpoint. If a third language is in active use, SDK scope expands and timeline may slip.

The primary Postgres instance and the existing in-process/shared cache layer can sustain flag-data read load without dedicated read replicas or a separate cache tier. Flag data is small and infrequently written; cache hit rates will be high.

No formal change-approval workflow is required. Audit history (who changed what, when) is sufficient for compliance and security purposes within this product's current posture.

The existing frontend stack and admin UI framework can render a range-input slider and a small deterministic-bucketing preview without significant new dependencies or a separate frontend build pipeline.

Phase 1 — Flag Schema and Storage

Define the canonical flag model, create the Postgres schema, write migrations and seed data, implement the read-through cache layer, build the typed accessor library, and record audit history on every mutation. This phase produces the stable data contract that Phases 2 and 3 build on.

Phase goal

Deliver a production-ready storage layer for feature flags: a versioned Postgres schema, a migration pipeline, a typed accessor library in each backend language, and a read-through cache that serves flag data in-process. By the end of Phase 1, any service can read flag definitions reliably, changes are recorded in an audit log, and the data model is locked enough that Phase 2 can begin evaluation-engine development in parallel.

Alternatives considered

  • Config-file-in-repo approach — store flags as YAML/JSON committed to the monorepo. Simple to bootstrap, no new database table. Rejected because it requires a deploy to change a flag value, which defeats the "kill a misbehaving feature without a deploy" requirement, and audit history becomes a git-blame exercise that support cannot easily read.
  • Separate flags microservice with its own database — isolates flag data fully. Rejected because it introduces a network hop on the evaluation path (violating a hard constraint) and adds operational overhead for a three-person team.
  • Piggyback on existing settings/config table — reuse a generic key-value store already in Postgres. Rejected because the flag model (targeting rules, lifecycle states, multivariate variants, audit log) is complex enough to warrant its own tables with proper indexes and foreign keys rather than serialised blobs in a generic store.

Recommendations

Use two new Postgres tables: feature_flags (one row per flag, with a rules JSONB column for targeting rules and a variants JSONB column for multivariate payloads) and feature_flag_audit_log (append-only, records actor, timestamp, before/after snapshot as JSONB). The accessor library wraps these tables and populates an in-process LRU or time-bounded cache on first read, refreshed by a lightweight poll (or push notification via Postgres LISTEN/NOTIFY if the platform supports it). Keep the flag model's JSONB columns schema-validated at the application layer with a typed struct, not at the Postgres level, so the schema can evolve without migrations for minor field additions.

Open questions

Does the existing Postgres setup support LISTEN/NOTIFY reliably enough to drive cache invalidation, or do we fall back to polling on a fixed interval (e.g. 10 s)? Answer affects the invalidation story in Phase 2.

Should percentage-rollout salt be stored per-flag (generated at flag creation) or derived from the flag key? Per-flag salt allows re-randomising a rollout without changing the key; key-derived salt is simpler but locks the bucketing population to the key forever.

Define the flag data model and write Postgres migrations

Create the feature_flags table with columns: id (UUID), key (unique text), description, owner (user/team reference), flag_type (enum: boolean, percentage, multivariate), rules (JSONB), variants (JSONB), default_value (JSONB), environment (text), state (enum: active, archived), salt (text, generated UUID at creation time), created_at, updated_at. Write the up/down migrations. Add indexes on key and state.

Create the audit-log table and trigger-or-application-level recording

Create feature_flag_audit_log: id, flag_id (FK), actor_id, action (created/updated/archived), before_snapshot (JSONB), after_snapshot (JSONB), created_at. Decide between a Postgres trigger and application-level writes; prefer application-level so the audit record and flag mutation share the same transaction without a DDL-level trigger. Add a migration and an index on flag_id, created_at for the history view query.

Write seed data and a flag-definition validator

Provide a seed script that inserts a small set of well-known flags (e.g. new-dashboard-ui boolean, checkout-v2 percentage rollout at 0 %) useful for local development and CI smoke tests. Write a validator that checks a flag struct against the schema rules (key format, valid variant shapes, rule field types) before any write — used by both the accessor library and the admin UI API.

Implement the typed accessor library (both backend languages)

Write a FlagStore class/module in each of the two backend languages. Exposes: getFlag(key), listFlags(filter), createFlag(def), updateFlag(key, patch), archiveFlag(key). All mutating methods write the audit log entry in the same transaction. Return typed structs, not raw rows. This library is the only sanctioned way to read or write flag data — the evaluation engine and admin API both depend on it.

Build the in-process read-through cache with invalidation

Wrap FlagStore.getFlag with an in-process LRU cache (bounded by flag count, not memory, since total flag data is small). On cache miss, load from Postgres and populate. Implement invalidation: attempt LISTEN/NOTIFY on a flag_changes channel (answer to open question q1.1); fall back to a configurable poll interval (default 10 s). Expose a forceRefresh() method for tests. Document the worst-case staleness bound.

Phase 2 — Evaluation Engine

Build the in-process evaluation library (and HTTP fallback endpoint) that answers evaluate(flagKey, context) → variant in under 1 ms at p99. Covers deterministic bucketing, rule ordering, environment inheritance, telemetry emission, and the JSON-over-HTTP endpoint for non-native callers.

Phase goal

Ship a battle-tested evaluation engine that any service in the monorepo can import and call synchronously with no added latency budget. The engine reads from the Phase 1 cache, never from Postgres directly. Both native SDKs pass a shared compliance test suite covering boolean, percentage, and multivariate evaluation, targeting rule ordering, and graceful degradation on missing flags. The HTTP endpoint is deployed and documented for edge callers.

Alternatives considered

  • Sidecar proxy (separate process, local socket) — evaluation runs in a language-agnostic sidecar; callers hit a local Unix socket. Eliminates per-language SDK maintenance. Rejected because even a local socket adds latency variance, requires process lifecycle management, and the constraint explicitly forbids adding a network hop to the evaluation path. The HTTP fallback endpoint already covers the multi-language need for non-hot-path callers.
  • Server-side evaluated at API gateway / edge — evaluate flags in the gateway before the request reaches services, inject results as headers. Rejected because it couples flag logic to infrastructure, makes context (user ID, org) harder to pass, and still results in a network hop from the service's perspective.
  • WebAssembly evaluation module shared across languages — single rule evaluator compiled to Wasm, called from each SDK. Interesting for consistency but adds a Wasm runtime dependency to every service and increases cold-start time. Deferred; the shared compliance test suite achieves consistency without runtime coupling.

Recommendations

Implement the evaluator as a pure function over a flag definition and an evaluation context struct. Rule evaluation order: (1) check if flag is active; (2) evaluate targeting rules top-to-bottom, return first match; (3) if flag type is percentage rollout, hash SHA-256(userId + ":" + flagSalt), take the first 32 bits modulo 10 000 as a basis-point value, compare to the rollout threshold; (4) fall back to defaultValue. Environment inheritance: if a flag definition for staging environment is absent, the evaluator transparently looks up the production definition. Telemetry: emit a sampled (configurable rate, default 10 %) evaluation event to the existing analytics event bus with fields flagKey, variant, context.userId, context.env, latencyUs.

Open questions

What is the canonical evaluation context schema? At minimum: userId, orgId, environment. Do we need email, plan, or custom attributes for existing targeting use cases? Expanding the context struct after SDKs are released is a breaking change in strictly typed languages.

What is the acceptable telemetry sampling rate? 10 % is a starting proposal. At high QPS the full 100 % rate may be undesirable; at very low QPS 10 % produces sparse data. Should the rate be flag-level configurable or system-wide?

Define the evaluation context struct and SDK contract

Specify the EvaluationContext type (userId, orgId, environment, plus an extensible attributes map for custom targeting). Define the SDK surface: evaluate(flagKey, context) → variant (synchronous), evaluateBool(flagKey, context) → bool (convenience wrapper), evaluateString(flagKey, context) → string. Write the shared compliance test suite as a language-agnostic JSON fixture file: input flag definitions + contexts, expected output variants. Both native SDKs must pass this suite.

Implement the core evaluation logic (rule engine + deterministic bucketing)

Write the evaluator in Language A. Implement: active-state check, top-to-bottom targeting rule evaluation (operators: equals, in-set, starts-with, regex for string fields; lt/lte/gt/gte for numeric fields), percentage-rollout bucketing via SHA-256(userId + ":" + salt) mod 10 000, multivariate variant selection, environment inheritance fallback, and default-value return on any error or missing flag. All branches must be covered by unit tests. Port to Language B; both must pass the shared compliance fixture suite.

Integrate telemetry emission

After each evaluation, enqueue a sampled event to the existing analytics event bus (do not block the return path — fire-and-forget into a buffered channel or queue). Event schema: { flagKey, variant, userId, orgId, environment, latencyMicros, sampledAt }. Implement configurable sampling rate (system-wide default, overridable per flag via a telemetrySampleRate field). Write a test that verifies events are emitted at approximately the configured rate over a large sample.

Build the JSON-over-HTTP evaluation endpoint

Add a route (e.g. POST /internal/flags/evaluate) behind the existing auth middleware. Request body: { flagKey, context }. Response: { variant, flagType, evaluated_at }. The handler calls the same in-process evaluator used by the native SDKs — no separate evaluation logic. Rate-limit per caller. Document the endpoint in the internal API spec. This endpoint is for non-hot-path callers (scripts, edge workers, mobile backend-for-frontend); services with a native SDK should not use it.

Load test the evaluation path and validate the p99 < 1 ms SLO

Write a benchmark (in-process, not via HTTP) that evaluates 10 000 flags in rapid succession covering all flag types and targeting rule combinations. Measure p50, p95, p99 latency with a warm and cold cache. Confirm p99 remains under 1 ms on the CI benchmark runner. Document the worst-case flag-count and rule-depth at which the SLO holds. This is a gate criterion for Phase 2 completion.

Phase 3 — Admin UI

Build the web dashboard for creating, editing, searching, and archiving flags; per-environment overrides; a percentage-rollout slider with live bucketing preview; an audit-history view; and role-based access control. The UI consumes the accessor library via an admin API layer.

Phase goal

Deliver a self-service admin interface that lets product managers and support staff manage flags without engineering involvement. Flag owners and admins can create and modify production values; other authenticated users get a read-only view. The percentage-rollout slider gives instant visual feedback on which user IDs would be bucketed into the rollout at the current threshold. Audit history is visible per flag with actor, timestamp, and a diff of what changed.

Alternatives considered

  • Embed flag management into existing settings pages — no new top-level nav entry, flags live under "Advanced Settings." Rejected because the flag list, per-environment overrides, and audit log need enough screen real estate and specialised interactions (slider, live preview, diff view) that shoehorning them into a settings panel would produce a poor UX and complicate the existing settings codebase.
  • Read-only UI with all writes via CLI/API only — simpler to build, avoids RBAC UI complexity. Rejected because the brief explicitly requires product and support to be self-sufficient; a CLI-only write path does not meet that bar.

Recommendations

Implement the admin UI as a new page in the existing admin section, backed by a thin REST API layer that delegates to the Phase 1 accessor library. RBAC: derive the caller's role from the existing auth session; expose a canEdit(flagKey, callerId) helper on the API that checks whether the caller is the flag owner or has the flags:admin permission. The percentage-rollout slider runs the deterministic bucketing function client-side (compiled or reimplemented in JS) against a fixed sample of user IDs from a test set to render the live preview — no round-trip needed. Audit-history diff view: store and display before/after JSON snapshots side by side with highlighted changes.

Open questions

Where does flags:admin permission come from? Is it an existing role in the auth system, or do we need to add it? If it must be added, is there a self-service role-assignment UI or does it require a database change per user?

For the live bucketing preview, what sample of user IDs should be used? A static fixture set (consistent, privacy-safe) or a sample from real production user IDs (more representative but raises privacy questions)?

Build the admin API layer (CRUD + RBAC enforcement)

Add REST endpoints: GET /admin/flags (list with search/filter), GET /admin/flags/:key, POST /admin/flags, PATCH /admin/flags/:key, POST /admin/flags/:key/archive, GET /admin/flags/:key/history. All routes are behind existing auth middleware. Mutating routes check canEdit(flagKey, callerId) and return 403 if the caller is not the flag owner or an admin. Delegate all reads and writes to the Phase 1 accessor library. Write integration tests covering the RBAC rules.

Implement the flag list and search UI

New admin page with a paginated, searchable table of flags. Columns: key, description, type, owner, state, last-modified. Filter bar: by state (active/archived), by type, by owner, by environment. Clicking a row opens the flag detail/edit view. Non-owners see flag details read-only; owners and admins see edit controls. Implement with the existing UI component library — no new frontend framework dependencies.

Build the flag create/edit form with per-environment overrides

Form fields: key (immutable after creation), description, owner, flag type, default value, targeting rules (add/remove rule rows, field/operator/value per rule), per-environment override section (add an override for a named environment that inherits from production unless explicitly set). Include the percentage-rollout slider (see t3.4) inline when flag type is percentage. Validate on submit using the Phase 1 flag-definition validator. Show server-side validation errors inline.

Implement the percentage-rollout slider with live bucketing preview

A range input (0–100 %) that, as it is dragged, runs the deterministic bucketing algorithm in the browser against a fixed sample of 1 000 synthetic user IDs (generated deterministically from a seed, not real user data) and displays: the count and percentage that would receive the treatment variant at the current threshold, and a small visual bar. The bucketing JS implementation must produce identical results to the server-side evaluator for the same inputs (verified by a cross-language test using the shared compliance fixture from t2.1).

Build the audit-history view

Per-flag history tab listing all mutations in reverse-chronological order. Each entry shows: actor name, action (created/updated/archived), timestamp, and a collapsible diff of changed fields (highlight added/removed/changed values between before_snapshot and after_snapshot). Paginate if flag history exceeds 50 entries. History is read-only for all users including admins.

End-to-end testing and staged rollout of the admin UI

Write end-to-end tests covering the critical paths: create a boolean flag, toggle it in staging, verify evaluation returns the expected variant, archive the flag, verify audit log entry. Run tests in CI against a staging environment populated with seed data. Deploy the admin UI behind a feature flag (dogfooding the system on itself) at 0 % rollout, increase to 100 % for internal users before general availability. Document the kill-switch procedure in the runbook.

Store flags in Postgres (new table) rather than a config file in the repo

The core requirement is the ability to change a flag's value without a code deploy. A config-file-in-repo approach violates this directly: every flag change requires a commit, CI run, and deploy. The Postgres table approach satisfies the requirement, integrates with the existing audit-log pattern, and is queryable by the admin UI and accessor library without special tooling.

Config-in-repo is simpler to bootstrap (no migration, no cache), makes flag history a natural git log, and has zero runtime database dependency. It remains a viable choice for projects where "no deploy" is not a hard requirement — but it is one here.

In-process evaluation library over a sidecar service

The evaluation path must not add a network hop to request handling. An in-process library reading from an in-memory cache satisfies the sub-millisecond p99 requirement and has no additional failure mode. A sidecar on a local socket is appealing for language-agnostic deployment but adds latency variance, per-host process management, and a new failure mode even on localhost. The JSON-over-HTTP endpoint covers non-hot-path, non-native callers without putting them on the critical path.

A sidecar eliminates per-language SDK maintenance and lets the evaluation logic evolve in one place. For a monorepo with more than two backend languages this trade-off would likely tip the other way.

Audit history via application-level writes, not Postgres triggers

Writing audit log entries in the same application transaction as the flag mutation gives full control over what is recorded, keeps the audit schema aligned with the application's domain model, and avoids DDL-level trigger coupling that makes schema evolution harder. Triggers are harder to test, less visible to application developers, and can be accidentally disabled during migrations.

Postgres triggers guarantee the audit entry is written even if the application code path is buggy or bypassed (e.g. a direct SQL update during an incident). For compliance-critical systems this guarantee is worth the coupling cost.

Cache staleness causes a flag change to take longer than 30 s to propagate

If LISTEN/NOTIFY is unavailable or misconfigured, the system falls back to polling. At a 10 s poll interval, worst-case propagation is 10 s; but if the polling thread is delayed under load, or if multiple cache instances have skewed clocks, staleness could exceed the 30 s SLO. Mitigation: implement an explicit maximum TTL cap on cached entries (30 s) regardless of invalidation path; add a monitoring alert if the flag-refresh heartbeat misses two consecutive windows. Document the propagation SLO in the runbook.

Evaluation engine language-B port diverges from language-A for edge cases

Porting the evaluator to a second language introduces the risk of subtle behavioural differences in edge cases (e.g. hash function output for Unicode user IDs, floating-point percentage comparisons, rule operator semantics). A user could receive different variants from two services evaluating the same flag. Mitigation: the shared JSON compliance fixture suite (task t2.1) must cover Unicode inputs, boundary percentages (0 %, 100 %, 50.001 %), and all targeting operators. Both SDKs must pass the full suite in CI before Phase 2 is considered complete.

RBAC gap allows non-owners to modify production flags via direct API calls

If the canEdit check is missing from any admin API route, a non-owner could modify production flag values by calling the API directly (bypassing the UI). This is especially risky for kill-switch flags. Mitigation: RBAC enforcement lives in the API layer, not only in the UI; integration tests explicitly assert that a non-owner receives 403 on all mutating routes for flags they do not own; a security review pass is scheduled before Phase 3 ships to production.

Telemetry emission at high QPS adds unexpected load to the analytics bus

At a high flag-evaluation rate (e.g. thousands per second per instance), even 10 % sampling produces a high event volume. If the analytics event bus is not sized for this, back-pressure could slow down the buffered telemetry channel and — if the buffer is bounded — start dropping events silently. Mitigation: telemetry emission is fire-and-forget with a bounded buffer and explicit drop-on-full semantics (never block the evaluation path); sampling rate is configurable at runtime; load-test the telemetry path as part of the Phase 2 benchmark task (t2.5).

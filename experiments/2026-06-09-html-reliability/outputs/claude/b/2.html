Feature Flag System

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases: flag schema and storage, an evaluation engine with sub-millisecond p99, and an admin UI. Six-week timeline, team of three engineers, no new external SaaS dependencies.

Success criteria

  • Any engineer can define a boolean, percentage-rollout, or multivariate flag and have it evaluated in production within one deploy cycle, with no additional deploy needed to change its value.
  • Flag evaluation at p99 adds fewer than 1 ms of latency to any request path (measured end-to-end including cache lookup).
  • Support can disable a flag for all users within 30 seconds of toggling it in the admin UI, with no code change or deploy.
  • All flag-value changes are captured in an immutable audit log with actor, timestamp, before-value, and after-value.
  • Percentage rollouts produce deterministic, stable bucketing: the same user always gets the same variant for a given flag, and the bucket does not change unless the rollout percentage or salt is explicitly edited.
  • The typed accessor library compiles without errors against the existing TypeScript and Go codebases in the monorepo.
  • Role-based access prevents non-owners and non-admins from changing production flag values; the restriction is enforced server-side.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state (active / archived).
  • feature_flags table in the primary Postgres database, plus schema migrations and seed data.
  • Read-through in-process cache with push-or-poll invalidation.
  • Typed accessor library for the two backend languages in the monorepo (TypeScript and Go).
  • JSON-over-HTTP evaluation endpoint for all other callers.
  • Evaluation engine: deterministic bucketing, rule ordering, environment inheritance.
  • Sampled telemetry event per evaluation for later analysis.
  • Admin UI: create, edit, search, archive, per-environment overrides, percentage-rollout slider with live bucketing preview, audit-history view, RBAC.
  • Audit history of flag changes (who changed what, when, from what value to what value).

Out of scope

  • Full approval workflow for flag changes.
  • A/B-test statistical analysis.
  • Scheduled rollouts (time-based flag activation).
  • Mobile SDKs.
  • Any new external SaaS dependency (no LaunchDarkly, Unleash, etc.).

Constraints

  • No new external SaaS. The entire system must run on existing infrastructure — Postgres, the monorepo app servers, and any internal cache layer already in use.
  • No network hop on evaluation. The evaluation path must resolve flags from an in-process or in-host cache; it must not make a synchronous network call to an external service during request handling.
  • Auth middleware. All flag management and evaluation HTTP endpoints must sit behind the existing auth middleware — no unauthenticated surface.
  • Team size. Three engineers available full-time for approximately six weeks (~18 engineer-weeks total).
  • Latency budget. p99 evaluation ≤ 1 ms.
  • Backwards compatibility. Introducing the flag system must not require changes to existing request-handling code paths until an engineer explicitly opts a call site in.

Assumptions

The two backend languages in the monorepo are TypeScript (Node.js) and Go. The typed accessor library will be built for those two targets only.

The team has write access to the primary Postgres instance and can land schema migrations through the existing migration toolchain (e.g., Flyway or similar) without a separate DBA approval gate.

An in-process memory cache (e.g., a simple TTL map) is acceptable for the initial evaluation path. A more sophisticated shared cache (Redis or similar) is already available in the stack if push invalidation is required.

The existing admin frontend can render a percentage-rollout slider and a live bucketing preview using libraries already in the frontend dependency tree — no new UI framework is required.

Phase 1 — Flag schema and storage

Phase 1 establishes the canonical data model for feature flags and makes it reliably readable at low latency. By the end of this phase every other component in the system has a stable, typed contract to program against, migrations are applied to all environments, and a thin accessor library allows existing application code to read flag values without raw SQL.

Phase goal

Deliver a production-ready feature_flags schema in Postgres — including the flags table, a targeting-rules table, a flag-values-per-environment table, and an audit-log table — along with seed data covering a representative set of bootstrap flags, a migration pipeline that runs cleanly in all environments, and a typed read/write accessor library for TypeScript and Go that the evaluation engine (Phase 2) can import directly.

Alternatives considered

Config-file-in-repo approach. Storing flag definitions as YAML or JSON files committed to the monorepo was considered because it gives full git history for free and requires no new database tables. It was rejected because it cannot support runtime value changes (support cannot kill a flag without a commit + deploy), cannot store per-environment overrides cleanly, and makes the RBAC story much harder (file permissions ≠ role-based UI access).

Single denormalized flags table. Embedding targeting rules as a JSONB column rather than a separate flag_targeting_rules table was considered for simplicity. Rejected because JSONB targeting rules are opaque to SQL queries and make the audit log harder to produce meaningfully; a normalized rules table lets the evaluation engine load rules with a single indexed join and lets the audit log record which rule changed.

Recommendations

Use a normalized Postgres schema: feature_flags (one row per flag), flag_environment_values (per-environment enabled state and default variant), flag_targeting_rules (ordered rules with a condition type, condition value, and target variant), and flag_audit_log (append-only, one row per change event). The accessor library should be a thin wrapper — no ORM — with a clear interface boundary so the evaluation engine can swap in a cache-backed implementation without touching callers.

Open questions

Should multivariate flag variants store their weights (for future weighted random) in the schema now, or defer that column until it is needed? Adding it now costs nothing but might confuse the first implementation if it is never read.

What is the expected cardinality of targeting rules per flag? If the answer is "typically 1–5 rules," a simple ordered list is fine; if some flags will have hundreds of org-level rules, the rule-loading query needs an index strategy from day one.

Design and document the flag data model

Write a short design doc (can live as a comment in the migration file) covering: table shapes, column types, nullability, primary keys, foreign keys, and index strategy. Include the flag_type enum (boolean, percentage_rollout, multivariate), the lifecycle_state enum (active, archived), and the condition_type enum for targeting rules (user_id, org_id, environment). Get sign-off from the team before writing migrations.

Write and land database migrations

Produce four migration files in the existing migration toolchain: (1) feature_flags core table, (2) flag_environment_values, (3) flag_targeting_rules with an order column and composite index on (flag_id, environment, order), (4) flag_audit_log append-only table with a CHECK constraint preventing UPDATE/DELETE. Run against the dev database, confirm schema matches the design doc, then apply to staging.

Write seed data and bootstrap flags

Provide a seed script (idempotent — safe to re-run) that inserts a small set of well-known flags used by the evaluation engine itself (e.g., feature-flags.sampling-rate to control telemetry volume) and at least two example flags covering each flag type. Seed data doubles as functional documentation and as fixtures for integration tests.

Build the typed accessor library — TypeScript

Implement a FlagStore interface in TypeScript with methods: getFlag(key): Promise<Flag | null>, listFlags(filter?): Promise<Flag[]>, getFlagRules(flagId, env): Promise<TargetingRule[]>, writeAuditEvent(event): Promise<void>. Backed by parameterized SQL (no ORM). Export generated types from the schema so the evaluation engine imports them rather than redefining its own.

Build the typed accessor library — Go

Mirror the TypeScript FlagStore interface as a Go FlagStore interface in a new internal/flagstore package. Implement a PostgresFlagStore struct using database/sql with prepared statements. Include the same four operations as the TypeScript version. Add a FlagStoreTestSuite using testcontainers-go so CI exercises the real schema.

Integration tests for schema and accessor libraries

Write end-to-end integration tests that spin up a Postgres container, apply all migrations, run the seed script, and assert correct round-trip behavior for all flag types and targeting rule variants. Test the audit log's append-only constraint by attempting an UPDATE and verifying it is rejected. These tests must run in CI on every pull request that touches the schema or accessor code.

Phase 2 — Evaluation engine

Phase 2 delivers the hot path: the code that, given a flag key and a caller context (user ID, org ID, environment), returns the correct variant in under a millisecond at p99. This phase owns the in-memory cache, the invalidation strategy, the bucketing algorithm, rule-ordering semantics, environment inheritance, the HTTP endpoint for non-SDK callers, and the sampled telemetry event pipeline.

Phase goal

Ship a production-ready evaluation library for both TypeScript and Go that resolves flag variants from an in-process cache (populated from the Phase 1 accessor library), exposes a evaluate(flagKey, context) → variant API, and keeps p99 latency under 1 ms. Additionally, expose a POST /internal/flags/evaluate JSON-over-HTTP endpoint (behind existing auth middleware) for callers that cannot use an in-process SDK. Every evaluation emits a sampled structured event to the existing telemetry pipeline.

Alternatives considered

Sidecar process instead of in-process library. Running a local sidecar (Unix socket or loopback HTTP) that owns the cache and answers evaluation requests was considered because it isolates the cache from application memory and makes cache invalidation a single point. Rejected because it adds operational complexity (sidecar lifecycle, health checks, deployment coupling) and still adds a socket round-trip to every evaluation — violating the no-network-hop constraint on the hot path. An in-process library with a background refresh goroutine/timer achieves the same cache-isolation property at zero latency cost.

Poll-only invalidation vs. push + poll. A pure poll (e.g., reload flag table every 10 seconds) is simpler to implement and requires no additional infrastructure. A push model (Postgres LISTEN/NOTIFY or an internal webhook) lets changes propagate in under a second. The recommendation is a hybrid: push via Postgres LISTEN/NOTIFY for fast invalidation when the app is connected, with a 30-second TTL poll as a fallback for cold starts and reconnects.

Recommendations

Implement the evaluation engine as a shared library (one for TypeScript, one for Go) that wraps the Phase 1 accessor and adds: an in-memory flag map refreshed via Postgres LISTEN/NOTIFY plus a 30-second TTL poll, a deterministic bucket function (murmurhash3(userID + "|" + flagSalt) mod 100), and a rule evaluator that walks rules in ascending order and returns the first matching variant (fall through to default). Telemetry events should be fire-and-forget on a buffered channel/queue with a 1 % default sample rate (overridable via the bootstrap flag added in Phase 1).

Open questions

Should environment inheritance (staging defaults from production) be evaluated at read time (the cache merges production + staging values on load) or at evaluation time (the evaluator falls back to the production row when no staging override exists)? The read-time merge is simpler but means a staging cache entry becomes stale if the production default changes.

What telemetry sink does the sampled evaluation event write to — the existing structured-log pipeline, an internal analytics queue, or both? This affects the event schema and whether the evaluation library needs a new dependency.

Implement the in-memory cache with invalidation

Build a FlagCache that loads all active flags and their targeting rules into a read-optimized in-memory map on startup. Subscribe to Postgres LISTEN/NOTIFY on a flag_changes channel (the audit log trigger populates this). Fall back to a 30-second full-reload poll when the LISTEN connection is not available. The cache must be goroutine-safe (Go) / concurrency-safe (TypeScript async) and expose a synchronous getFlag(key) accessor for zero-await hot-path calls.

Implement deterministic bucketing for percentage rollouts

Implement the bucket function: murmurhash3(userID + "|" + flagSalt) mod 100. The salt is stored per-flag in the schema (column added if not already present). Write a property-based test that asserts: (a) the same inputs always produce the same bucket, (b) the distribution across 10,000 random user IDs is within ±2 % of uniform for all bucket boundaries, and (c) changing the salt produces a different distribution. The TypeScript and Go implementations must produce identical bucket values for the same inputs — add a cross-language golden-value test.

Implement rule evaluation and environment inheritance

Implement the rule evaluator: walk targeting rules in ascending order, evaluate each condition against the caller context (user ID match, org ID match, environment match, percentage bucket), and return the first matching variant. If no rule matches, fall back to the environment default; if no environment-specific default exists, inherit from production. Write unit tests covering: rule ordering, environment fallback, percentage boundary conditions (exactly 0 % and 100 %), and archived flags (must always return the default, never a rule variant).

Add sampled telemetry event emission

After each evaluation, enqueue a structured event { flagKey, variant, context, sampledAt, evaluationMs } to a buffered channel. A background worker drains the channel and writes to the existing telemetry sink (determined by resolving open question q2.2). The sample rate defaults to 1 % and is controlled by the feature-flags.sampling-rate bootstrap flag from Phase 1. The telemetry path must never block the evaluation return path.

Expose JSON-over-HTTP evaluation endpoint

Add POST /internal/flags/evaluate to the existing API server. Request body: { flagKey: string, context: EvaluationContext }. Response: { variant: string | boolean | number, reason: string }. The endpoint calls the same in-process evaluation library (no separate codepath). Wire it behind the existing auth middleware. Document the contract in the internal API reference. Add a rate-limit guard (configurable, default 1,000 rps) to prevent accidental hammering from misconfigured clients.

Latency benchmark and p99 verification

Write a microbenchmark (Go benchmark + Node.js autocannon or similar) that exercises the hot path: cache hit, two targeting rules, percentage rollout. Run against a machine representative of production hardware. The benchmark must confirm p99 < 1 ms for the in-process path and p99 < 10 ms for the HTTP endpoint (network excluded). Commit the benchmark results as a checked-in artifact so regressions are visible in future PRs.

Phase 3 — Admin UI

Phase 3 delivers the human-facing control plane: a dashboard where product and engineering can create and edit flags, support can archive or disable a flag immediately, and anyone can inspect the full audit history. All UI actions call new admin API endpoints that enforce RBAC server-side; the UI never bypasses the auth middleware.

Phase goal

Ship a flags dashboard page integrated into the existing admin frontend, with full CRUD for flags and targeting rules, per-environment override controls, a percentage-rollout slider with live bucketing preview, an audit-history view per flag, and server-side RBAC ensuring only flag owners and admins can edit production values. Support can archive any flag from the UI within two clicks.

Alternatives considered

Separate admin microservice. Building a standalone admin service (its own port, its own auth) was considered for isolation. Rejected because it adds deployment overhead and makes it harder to reuse the existing auth middleware and admin UI shell. Embedding the flags admin into the existing admin app is lower risk and faster to ship.

Full approval workflow before production changes. Requiring a second-approval step (like a PR review) before any production flag change takes effect was considered because it reduces accidental rollouts. Deferred out of scope per the brief; RBAC (owner + admin only) provides a meaningful safety gate without the full workflow cost. The audit log makes accidental changes recoverable.

Recommendations

Build the admin UI as a new route in the existing admin frontend (e.g., /admin/flags). Use the existing component library for tables, modals, and forms. Implement the percentage slider as a controlled input that re-runs the bucketing hash client-side against a sample of recent user IDs (pulled from a lightweight GET /internal/flags/sample-users endpoint) to render a live preview of who would be in/out of the rollout. All write operations (create, update, archive, rule change) must call server-side endpoints that re-check RBAC before writing; the UI should treat the server response as authoritative and re-fetch after any mutation.

Open questions

Where is the "owner" field sourced from — is it a free-text email, a user ID from the auth system, or a team identifier? This affects how the RBAC check is implemented (lookup by user ID vs. by team membership) and whether the UI can show a human-readable owner name.

Should the live bucketing preview sample real user IDs from the database, or use a synthetic set of representative IDs? Using real IDs is more meaningful but requires a new read endpoint with privacy implications; synthetic IDs are safe but less illustrative.

Build admin API endpoints (CRUD + RBAC)

Add the following REST endpoints to the existing admin API server, all behind the auth middleware: GET /admin/flags (list with search/filter), POST /admin/flags (create), GET /admin/flags/:key (detail + rules + audit), PATCH /admin/flags/:key (update metadata), POST /admin/flags/:key/rules (add targeting rule), DELETE /admin/flags/:key/rules/:ruleId, POST /admin/flags/:key/archive, PUT /admin/flags/:key/environments/:env (set per-environment override). Every write endpoint checks that the authenticated user is either the flag owner or has the flags:admin role before allowing production-environment writes. Non-owners can read all flags and write to non-production environments.

Build the flags list and search page

Implement the /admin/flags page: a searchable, filterable table of all flags showing key, description, owner, type, lifecycle state, and last-modified date. Include filter controls for flag type and lifecycle state. Each row links to the flag detail page. The "Archive" action is available inline for owners and admins and triggers a confirmation modal before calling POST /admin/flags/:key/archive.

Build the flag detail and edit page

Implement the /admin/flags/:key page with: flag metadata editor (description, owner, type), a targeting-rules editor (add/remove/reorder rules with condition type + value + variant inputs), and per-environment override toggles (enabled/disabled + default variant per environment). Edits are staged locally and submitted as a batch on "Save." The UI re-fetches and re-renders from the server response after save to confirm the written state.

Build the percentage-rollout slider with live preview

For flags of type percentage_rollout, render a slider (0–100 %) on the detail page. As the user drags the slider, run the bucketing hash client-side against the sample user set (resolved from open question q3.2) and display: current percentage, estimated number of affected users, and a sample list of up to 10 user IDs that would be included/excluded at the current percentage. The preview is purely client-side (no server call on slider drag); only the final "Save" triggers a write.

Build the audit-history view

Add an "Audit history" tab on the flag detail page that fetches GET /admin/flags/:key/audit (paginated, newest first) and renders a timeline of changes: timestamp, actor, field changed, before value, after value. The server endpoint reads from flag_audit_log and returns structured diff objects. Implement server-side pagination (cursor-based, 50 events per page) so flags with long histories do not cause large payloads.

End-to-end tests and access-control verification

Write Playwright (or equivalent) end-to-end tests covering: create a boolean flag, add a targeting rule, set a per-environment override, archive the flag, and verify it appears in audit history. Add a separate test suite that verifies RBAC: a non-owner user cannot write to production (receives 403), can write to staging, and can read all flags. Run these tests in CI against a staging environment seeded with the Phase 1 seed data.

Store flags in Postgres, not in a config file in the repository

A database-backed store allows runtime changes without a code commit or deploy, supports per-environment overrides as first-class rows, enables RBAC at the write path, and makes the audit log a natural append to the same schema. It also allows the evaluation engine to receive push-invalidation signals via Postgres LISTEN/NOTIFY.

A config-file approach would give git history for free, require no new migrations, and be trivially diffable in pull requests. It was rejected because changes require a deploy (blocking support's kill-switch requirement) and per-environment overrides would need awkward file conventions.

In-process library (not sidecar) for the evaluation hot path

Embedding the evaluation engine as an in-process library satisfies the hard constraint that the evaluation path must not add a network hop to request handling. The library loads flags into a process-local cache on startup and refreshes it in the background; the evaluate() call is a pure in-memory operation. A JSON-over-HTTP endpoint is also provided for non-SDK callers, but it is not on the critical request path.

A sidecar would centralize cache management and make invalidation simpler to reason about, but every evaluation would require a loopback socket call — adding latency and a new operational dependency that must be deployed, healthchecked, and restarted alongside every app instance.

Use MurmurHash3 for deterministic percentage bucketing

MurmurHash3 is fast (sub-microsecond for short strings), produces a well-distributed output suitable for uniform bucketing, has stable cross-platform implementations in both Go and TypeScript, and is not a cryptographic hash (no overhead from entropy hardening). Bucketing as hash(userID + "|" + flagSalt) mod 100 ensures the same user always lands in the same bucket for a given flag, and changing the salt re-randomizes assignments without requiring a schema change.

FNV-1a was considered as a simpler alternative; it is slightly faster but produces less uniform distributions for short numeric user ID strings, which could cause visible clustering at low rollout percentages.

Cache staleness causes stale flag values after a flag change

If the Postgres LISTEN/NOTIFY connection drops and the poll interval is 30 seconds, flag changes may not propagate to all app instances for up to 30 seconds. For a support kill-switch scenario this could mean a misbehaving feature continues serving affected users for half a minute after the flag is disabled.

Mitigation: Monitor the LISTEN connection health and alert on disconnect. Expose a POST /internal/flags/refresh endpoint that forces an immediate cache reload on a specific instance; support runbook documents this as the fast-path option if 30 seconds is too slow. Consider reducing the poll interval to 5 seconds for the first release.

Schema migration causes downtime or data loss on the primary Postgres

The Phase 1 migrations add new tables to the primary database. If the migration toolchain runs a full table lock or if a future migration inadvertently alters a high-traffic table, it could cause downtime. The flag_audit_log append-only constraint is also enforced by a trigger; trigger creation on a busy database can stall writes briefly.

Mitigation: All Phase 1 migrations only create new tables (no ALTER on existing tables), so lock risk is minimal. The trigger is on the new flag_audit_log table, not on any existing table. Run migrations during a low-traffic window and verify on staging first.

TypeScript and Go bucketing implementations diverge

If the MurmurHash3 implementations in TypeScript and Go produce different outputs for the same input (due to endianness, integer overflow, or string encoding differences), users would be assigned different buckets depending on which language evaluates the flag. This could cause a user to see different variants across services.

Mitigation: Task t2.2 explicitly requires a cross-language golden-value test: a fixed set of (userID, flagSalt) pairs with known expected bucket outputs, verified by both the TypeScript and Go test suites against the same hardcoded expected values.

Six-week timeline is tight for three engineers across three phases

18 engineer-weeks covering schema design, two accessor libraries, a cache with invalidation, a bucketing engine, an HTTP endpoint, telemetry, an admin API, and a full admin UI is ambitious. If Phase 1 integration tests surface schema design issues late, Phases 2 and 3 compress.

Mitigation: Phase 1 tasks are front-loaded specifically so the schema is locked before Phase 2 begins. The admin UI (Phase 3) can ship without the live bucketing preview if necessary — that feature is the most deferrable deliverable. Identify the cut line early: a Phase 3 without the slider still satisfies the core support kill-switch and RBAC requirements.

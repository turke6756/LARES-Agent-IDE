Feature-flag system

Add a first-party feature-flag platform so engineering can ship code dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Delivered in three phases over six weeks: flag schema and storage, evaluation engine, and admin UI. No new external SaaS dependencies; evaluation must stay in-process.

Success criteria

  • Evaluation latency: evaluate(flagKey, context) returns a variant in under 1 ms at p99 on any backend service, measured by integration benchmark.
  • Rollout accuracy: Percentage-rollout bucketing is deterministic — the same user + flag salt always lands in the same bucket, verified by unit test over 10 000 synthetic IDs.
  • Kill-switch round-trip: An operator can disable a flag in the admin UI and all running instances stop serving the variant within 30 seconds (push invalidation) or 60 seconds (poll fallback).
  • Audit completeness: Every flag mutation (create, edit, archive, override) produces an audit record with actor, timestamp, before/after diff, and environment.
  • RBAC enforcement: A non-owner, non-admin user cannot save changes to production flag values; this is verified by an automated test against the API.
  • No new SaaS dependency: The system passes a dependency audit — zero new external paid services introduced.
  • Coverage: Both backend languages in the monorepo have a typed SDK; everything else can evaluate flags via the JSON-over-HTTP endpoint.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state (active / archived).
  • Storage: feature_flags table in primary Postgres plus read-through in-memory cache.
  • Audit history of every flag change (who, when, what changed, which environment).
  • Typed accessor library for both backend languages in the monorepo.
  • JSON-over-HTTP evaluation endpoint for other callers.
  • Admin UI: create, edit, search, archive flags; per-environment overrides; percentage slider with live bucketing preview; audit history view.
  • Role-based access: flag owners and admins may edit production values; others get read-only.
  • Telemetry: sampled evaluation events emitted for later analysis.
  • Migrations and seed data for local development and CI.

Out of scope

  • A/B-test statistics or experiment analysis.
  • Scheduled (time-based) rollouts.
  • Mobile SDKs (client-side JS / native).
  • Full approval workflow for flag changes (audit only, not approval gates).
  • External SaaS feature-flag services (LaunchDarkly, Flagsmith, etc.).

Constraints

  • Team: Three engineers; roughly six calendar weeks.
  • No new SaaS: All components must run on existing infrastructure.
  • No network hop in the hot path: Flag evaluation must be in-process (local cache); no synchronous RPC call per request.
  • Auth: Admin UI and HTTP endpoint must sit behind the existing auth middleware — no separate auth implementation.
  • Database: Postgres is the system of record; no new databases or caches (e.g. dedicated Redis) unless already provisioned.
  • Reversibility window: Phase 1 schema changes must be backward-compatible for at least one release cycle so rollback does not require data loss.

Assumptions

The existing primary Postgres instance has sufficient read capacity to serve flag-config polling (expected low QPS — flags change infrequently). A read replica or separate store is not required.

There are exactly two backend languages in the monorepo that require a typed SDK. All other callers (scripts, data pipelines, edge workers) can use the JSON-over-HTTP endpoint without blocking any team.

The infrastructure already exposes a lightweight pub/sub or webhook mechanism (e.g. Postgres LISTEN/NOTIFY or an internal event bus) that can carry flag-change notifications to running instances for push invalidation.

A 30-second push-invalidation SLA (60-second poll fallback) is acceptable to the product and support teams for kill-switch scenarios.

Phase 1 — Flag schema and storage

Lay the data foundation: define the flag model in Postgres, write migrations, build an audit-history mechanism, stand up the read-through cache layer, and ship a typed accessor library for both backend languages. This phase ends when flags can be created and read programmatically with full audit trails and the cache layer is exercised by a benchmark.

Phase goal

Deliver a durable, auditable flag store backed by Postgres, accessible through a typed library in both backend languages, with a read-through cache that will be the in-process hot path for Phase 2's evaluation engine. At the end of Phase 1, an engineer can create a flag via a migration or seed script, read it via the accessor library, and see every mutation in the audit log.

Alternatives considered

Config-file-in-repo approach: Flags live as YAML/JSON in the repository; changes go through code review; the evaluation engine reads the file at startup. Advantages: free audit trail via git history, zero new infrastructure, instantly reversible. Rejected because it requires a deploy to change any flag value, which defeats the kill-switch requirement and makes gradual rollouts operationally painful for product and support teams.

Dedicated key-value store (Redis): Flags stored in Redis with a custom schema. Advantages: sub-millisecond reads, built-in pub/sub. Rejected because it introduces a new stateful dependency not already provisioned, violating the no-new-infrastructure constraint. If Redis is already present it can serve as a caching tier in a future iteration.

Chosen approach — Postgres + in-process cache: Postgres provides ACID guarantees, easy audit-history joins, and runs on existing infrastructure. An in-process cache (populated at startup, refreshed via LISTEN/NOTIFY or poll) keeps evaluations off the database hot path.

Recommendations

  • Use a single feature_flags table with a JSONB targeting_rules column for flexibility; add a separate feature_flag_audit table written by a trigger.
  • Version the flag schema with a schema_version integer column so the accessor library can detect schema drift without a deploy.
  • Ship seed data with at least one flag of each type (boolean, percentage, multivariate) so Phase 2 can develop against realistic data from day one.
  • Define the accessor library interface (types + function signatures) before writing implementations so both language SDKs stay in sync.

Open questions

Should the targeting_rules column use JSONB with a versioned schema, or should rules be first-class rows in a child table? JSONB is faster to ship but harder to query in ad-hoc SQL; child rows are more normalized but require schema migrations every time we add a rule type.

Do we need multi-environment rows in the same table (one row per flag per environment) or a single row with a JSONB env_overrides field? The former is easier to query and audit; the latter reduces row count.

Write and apply the initial Postgres migration

Create the feature_flags table with columns: id (UUID), key (text, unique), description, owner, flag_type (enum: boolean / percentage_rollout / multivariate), targeting_rules (JSONB), default_value (JSONB), lifecycle_state (enum: active / archived), created_at, updated_at, schema_version. Add appropriate indexes on key and lifecycle_state. Migration must be backward-compatible (no dropped columns, no NOT NULL without defaults).

Build the audit-history table and trigger

Create feature_flag_audit with columns: id, flag_id (FK), actor (user/service identity from session), action (created / updated / archived), environment, before_value (JSONB snapshot), after_value (JSONB snapshot), changed_at. Implement as a Postgres trigger on INSERT/UPDATE/DELETE on feature_flags. Write tests asserting that every mutation produces exactly one audit row.

Implement the in-process read-through cache

Build a cache module that loads all active flags from Postgres at process startup into a thread-safe in-memory map. Implement a refresh path via Postgres LISTEN/NOTIFY on a flag_changes channel (push) with a configurable poll interval (default 30 s) as fallback. Expose getAll(), getByKey(key), and invalidate(key?). The cache must never block the caller: reads are lock-free (copy-on-write swap). Write a benchmark asserting getByKey at under 50 µs with 1 000 flags loaded.

Build the typed accessor library (both backend languages)

Define a shared interface spec (as a language-agnostic JSON Schema or internal doc): FlagConfig type, FlagStore interface with get(key), list(), upsert(config), archive(key). Implement in both backend languages, each wrapping the in-process cache from t1.3 for reads and Postgres directly for writes. Include typed enums for FlagType and LifecycleState.

Write seed data and CI fixture scripts

Create seed scripts (runnable in local dev and CI) that insert at least one flag of each type: a boolean kill-switch, a 10 % percentage rollout, and a multivariate flag with three variants. Include a test fixture helper that creates and tears down flags within a transaction so unit tests do not leak state. Document the seed command in the repo's dev-setup README section.

Phase 2 — Evaluation engine

Build the library and endpoint that answer evaluate(flagKey, context) → variant in under 1 ms at p99. Deterministic bucketing, rule-ordering semantics, environment inheritance, in-memory cache from Phase 1, SDK surfaces for both backend languages, a JSON-over-HTTP endpoint, and sampled telemetry events.

Phase goal

Ship a production-ready evaluation engine that any backend service can import to resolve a flag variant from local memory — no network call in the hot path. The engine handles all flag types, respects rule ordering, inherits staging defaults from production when no override exists, and emits a sampled event for every evaluation. A JSON-over-HTTP endpoint wraps the same logic for non-monorepo callers. The phase is done when a benchmark proves sub-millisecond p99 under realistic load and at least one integration test exercises each flag type end-to-end.

Alternatives considered

Sidecar service (separate process per host): A small daemon holds flag state and answers evaluation RPCs over a Unix socket. Advantages: language-agnostic, single cache owner, easier to update independently. Rejected because it adds a mandatory network hop (even over a socket) and a new operational dependency that must be colocated with every service, which violates the "no network hop in request handling" constraint and complicates deployment.

Shared evaluation service (remote RPC): A central microservice answers all evaluation calls. Completely rejected — adds network latency to every flag check and introduces a hard availability dependency.

Chosen approach — in-process library: Each service links the evaluation library and holds its own in-memory copy of flag state (populated by the Phase 1 cache). This maximises isolation and latency at the cost of each process having its own cache (acceptable given the push/poll invalidation story).

Recommendations

  • Use MurmurHash3 (or FNV-1a) of userId + ":" + flagSalt modulo 10 000 for bucketing — fast, dependency-free, and well-understood.
  • Define rule evaluation order as: (1) environment-specific targeting rules in declared order, (2) environment default, (3) global default. Document this contract in code comments and the SDK README.
  • Implement environment inheritance as a fallback read: if no rule matches in the current environment and the environment has a parent_env pointer (e.g. staging → production), recurse once to the parent's default value only (not its targeting rules, to avoid leaking user-ID rules across env boundaries).
  • Sample evaluation telemetry at 1 % by default, configurable per flag to 100 % (for new flags under observation) or 0 % (for extremely high-volume flags).

Open questions

What hash algorithm guarantees the best distribution uniformity with the fewest external dependencies across both backend languages? We need identical output from the same inputs; FNV-1a has no external deps but MurmurHash3 has better avalanche properties. Need to confirm both language standard libraries or acceptable small dependencies.

Where should sampled evaluation events be written? Options: an existing internal analytics event bus, a flag_evaluations Postgres table (simple but noisy at scale), or a fire-and-forget UDP sink. Decision affects the telemetry implementation in t2.6.

Implement the core evaluation logic

Write the evaluate(flagKey, context) → variant function. Context carries: userId, orgId, environment, and an arbitrary attributes map for future rule types. Evaluation order: iterate targeting rules in declared index order; first match wins; fall back to environment default, then global default. Return a typed EvaluationResult with the variant, the matched rule index (or "default"), and the flag schema version. All code paths must be covered by unit tests.

Implement deterministic percentage bucketing

Implement bucket(userId, flagSalt) → int [0, 9999] using the agreed hash algorithm (see open question q2.1). Wrap in a isInRollout(userId, flagSalt, percentage) → bool helper. Write a property-based test over 100 000 synthetic user IDs asserting that the actual percentage in-bucket is within 0.5 % of the configured value and that the function is pure (same inputs → same output always).

Wire evaluation engine to Phase 1 cache and environment inheritance

Connect the evaluation function to the in-process cache from t1.3. Add environment-inheritance logic: when context.environment has no matching rule and the environment record has a parent_env, fall back to the parent's default value (one level only). Write integration tests covering: (a) cache hit, (b) cache miss triggers a Postgres reload, (c) environment inheritance resolves correctly, (d) archived flags always return the default value.

Publish SDK wrappers for both backend languages

Wrap the evaluation engine in ergonomic SDK modules for both languages. Each SDK exposes: FlagClient (singleton, initialised with env and optional overrides for testing), getBool(key, default), getVariant(key, default), getNumber(key, default). Provide a FakeClient / test helper that accepts a map of overrides so application tests can control flag values without Postgres. Write usage examples in each language's internal docs site.

Build the JSON-over-HTTP evaluation endpoint

Expose POST /internal/flags/evaluate accepting {"flagKey": "...", "context": {...}} and returning {"variant": ..., "matchedRule": ..., "schemaVersion": ...}. The handler must run behind the existing auth middleware. The endpoint uses the same in-process evaluation library (not a separate code path). Add rate limiting at 1 000 req/s with a configurable override. Document the contract in the internal API catalogue.

Implement sampled evaluation telemetry

After each evaluation, emit a sampled event to the destination resolved in open question q2.2. Event payload: flagKey, variant, userId (hashed), environment, matchedRule, timestamp. Default sample rate: 1 %; configurable per flag via a telemetry_sample_rate field added to the flag schema (migration required). Telemetry emission must be fire-and-forget — a failure to emit must never throw or degrade evaluation latency. Add a benchmark asserting p99 evaluation latency stays under 1 ms with telemetry enabled at 100 % sample rate.

Phase 3 — Admin UI

Build the operator-facing dashboard: flag list with search and filtering, create/edit form, per-environment overrides panel, percentage-rollout slider with live bucketing preview, audit-history view, and RBAC enforcement for production edits.

Phase goal

Deliver a functional admin dashboard that lets product, engineering, and support staff manage flags without touching the database or deploying code. At phase end: a product manager can create a boolean flag, enable it for 10 % of users in production using the percentage slider, watch the live bucketing preview update, and verify their change in the audit history — all without engineering involvement. Support can kill a feature in under two minutes. RBAC prevents non-owners from changing production values.

Alternatives considered

Expose a raw REST API and let engineers use curl/Postman: No UI investment; flag changes require engineering. Rejected — violates the product requirement that non-engineers (support, PM) can operate flags independently, especially for kill switches.

Embed flag management into an existing internal tools platform (e.g. Retool, internal admin panel): Faster to build a basic CRUD UI without frontend work. Rejected because it likely requires a new SaaS license (Retool) or significant customisation of the existing admin panel that takes as long as building the dedicated page. The percentage slider with live bucketing preview is domain-specific enough to warrant a custom component.

Chosen approach — dedicated dashboard page in the existing internal frontend: One new page in the existing admin/internal frontend; reuses existing auth, routing, and design system. Keeps everything behind existing auth middleware.

Recommendations

  • Reuse the existing design-system table and form components for flag list and edit form; build only the percentage slider and bucketing preview as bespoke components.
  • The bucketing preview should show a histogram of the first N (e.g. 200) known user IDs bucketed at the current slider value — computed client-side using the same hash algorithm as the evaluation engine (ported to JS).
  • RBAC check: the API layer enforces it; the UI shows a read-only view to non-owners/non-admins rather than hiding fields entirely, to aid observability.
  • Environment tabs (production / staging / development) should be the primary navigation within a flag detail page, making per-environment overrides the natural workflow.

Open questions

Should RBAC roles (flag owner, admin, read-only) be derived from the existing user/role table in the product, or does the flag system need its own role assignments per flag? Per-flag ownership is more granular but requires new data modelling; deriving from existing roles is simpler but less precise.

What is the user-ID population used for the bucketing preview? Using live production user IDs raises privacy concerns; using synthetic IDs (sequential integers) may not reflect real distribution. Need alignment with security/privacy stakeholders before implementing the preview feature.

Build the flag list and search page

Create the main /admin/flags page with a searchable, filterable table of all flags. Columns: key, description, owner, type, lifecycle state, last updated. Support free-text search on key and description, filter by type and lifecycle state, and sort by last-updated descending by default. Add a "New flag" button (opens create form) and an "Archive" action per row (owner/admin only, confirmation dialog required). Page must load in under 2 s for up to 1 000 flags.

Build the flag create/edit form

Form fields: key (create-only, slugified, validated unique), description, owner (user picker), flag type (selector — changes available fields), default value, and per-environment override panel (see t3.3). Validate on submit; show inline errors. On save, call the flag write API, which enforces RBAC server-side. Show a success toast with a link to the audit entry. Key must be immutable after creation (display as read-only text on edit).

Implement per-environment overrides panel

Within the flag detail/edit page, render a tab strip for each known environment (production, staging, development, and any custom environments from the DB). Each environment tab shows: the resolved value for that environment (including inherited value if no override), targeting rules list (add/remove/reorder), and for percentage rollouts, the slider (see t3.4). Changes to production overrides are subject to RBAC: non-owners see the panel read-only with a "Request edit access" prompt. Saving an environment-specific override calls a PUT /admin/flags/:key/environments/:env endpoint that writes a new audit record.

Build the percentage-rollout slider with live bucketing preview

For percentage-rollout flags, render a range slider (0–100 %) in the environment override panel. As the user drags, a live preview histogram appears below the slider showing how a sample population (resolved from q3.2) distributes into "in rollout" vs "out of rollout" buckets using a client-side port of the hash function from t2.2. The preview updates on every slider tick without a server round-trip. Display the exact count and percentage in/out. Include a "Copy bucket list" action for debugging.

Implement the audit-history view

Add an "Audit history" tab on the flag detail page. Fetch from GET /admin/flags/:key/audit (paginated, newest first). Each entry displays: timestamp, actor (name + email), action, environment, and a before/after diff rendered as a two-column JSON diff. Support filtering by environment and actor. The global /admin/flags/audit page shows all flag mutations across all flags, useful for compliance and incident investigation.

Enforce RBAC in the API layer and surface in the UI

Add server-side RBAC middleware to all flag write endpoints (POST /admin/flags, PUT /admin/flags/:key, PUT /admin/flags/:key/environments/production, DELETE /admin/flags/:key): check that the calling user is either the flag's owner or has the flags:admin role. Return HTTP 403 with a descriptive error message otherwise. In the UI, derive the user's effective permissions from the API's GET /admin/flags/:key/permissions response and render production fields as read-only for non-owners. Write automated tests for both the 403 path and the happy path for each role.

Postgres table as system of record, not config-file-in-repo

Flags live in a feature_flags Postgres table, not in a YAML/JSON file committed to the repository. This satisfies the kill-switch requirement (operators change flag state without a deploy), supports non-engineer operators via the admin UI, and enables audit history via a database trigger. Git history would have provided audit trail for free, but it requires a deploy for every flag change and cannot support a UI-driven workflow.

Config-in-repo ships faster initially, is trivially reversible, and gives free audit history via git blame. It is the right choice if the team never needs non-engineer operators and is willing to accept deploy-time flag changes.

In-process evaluation library, not a sidecar service

The evaluation engine is a library linked into each service, not a sidecar process or remote service. Each instance holds its own in-memory copy of flag state and refreshes it via LISTEN/NOTIFY or periodic poll. This satisfies the hard constraint that evaluation must not add a network hop to request handling, and eliminates a new operational dependency (sidecar lifecycle, health checks, colocated deployment). The tradeoff is that each process has its own cache, so flag propagation is not instantaneous — but the 30 s push / 60 s poll SLA is acceptable.

A sidecar service would be the single cache owner (no stale-read divergence between processes on the same host), would be language-agnostic, and would be independently deployable. It is the better choice if strict consistency across processes on a host matters more than the zero-extra-hop constraint.

JSONB targeting rules column rather than normalised child table

Targeting rules are stored as a JSONB array in feature_flags.targeting_rules rather than as rows in a separate flag_targeting_rules table. JSONB allows adding new rule types (e.g. geo-based, attribute-based) without schema migrations, and the entire flag config is readable in a single row fetch. Rule ordering is preserved by array index. The accessor library validates the JSONB against a versioned JSON Schema at read time to catch drift early.

A normalised child table makes individual rule rows queryable in SQL (useful for analytics: "how many flags use org-based targeting?"), enforces foreign-key integrity on rule types, and avoids unbounded column width. Prefer it if cross-flag rule analytics become a requirement.

Cache invalidation lag causes stale flag state during incident response

If the LISTEN/NOTIFY channel drops (e.g. Postgres failover, network partition) and the poll interval is the only fallback, a kill-switch change could take up to 60 seconds to propagate to all instances. In an active incident this may be too slow.

Mitigation: (1) Implement LISTEN/NOTIFY as primary with poll as fallback and monitor the channel health. (2) Provide an emergency POST /internal/flags/flush-cache endpoint that any instance can call to force an immediate reload from Postgres, invocable from the admin UI's "Force sync" button. (3) Document the worst-case propagation time in the runbook so on-call knows what to expect.

Evaluation latency regression in high-frequency code paths

If a service calls evaluate() on every request in a hot loop (e.g. per-item in a feed rendering pipeline), even sub-millisecond overhead accumulates. A poorly written targeting rule (e.g. O(n) list scan over a large user-ID set) could spike latency significantly.

Mitigation: (1) Add a p99 latency benchmark to CI that fails if evaluation exceeds 1 ms under load. (2) Validate targeting rules at write time (reject rules with more than N user IDs in a direct-match list; recommend org-based rules instead). (3) Document the performance contract in the SDK README.

Flag sprawl degrades cache performance and operational clarity

Without governance, teams may create hundreds of flags and never archive them. A large number of active flags increases cache memory footprint, slows the startup load, and makes the admin UI harder to navigate.

Mitigation: (1) Add a last_evaluated_at timestamp updated (asynchronously, sampled) by the evaluation engine; surface flags not evaluated in 90 days as "stale" in the admin UI. (2) Emit a weekly digest (Slack or email) of stale flags to their owners. (3) Consider a hard limit (e.g. 500 active flags) enforced at create time with an admin override, to force explicit governance decisions.

RBAC bypass via direct database access

If engineers have direct Postgres access in production (common in small teams), they can modify flag state and targeting rules without going through the API, bypassing RBAC and the audit trigger. This is both a security risk and an audit integrity risk.

Mitigation: (1) The audit trigger fires on ALL writes to the feature_flags table regardless of source, so direct DB edits are still recorded. (2) Document in the team runbook that direct DB edits are prohibited for flags and will be flagged in compliance reviews. (3) Consider a DB-level role that revokes UPDATE/DELETE on feature_flags from the application user and routes all writes through a stored procedure that enforces the audit insert.

Feature Flag System

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases: flag schema and storage, evaluation engine, and admin UI. Team of three engineers, roughly six weeks.

Success criteria

  • Any engineer can create a boolean, percentage-rollout, or multivariate flag and target it by user ID, org, or environment without a code deploy.
  • Flag evaluation p99 latency is under 1 ms measured in a production load test with the evaluation library running in-process (no network hop).
  • Support can toggle (enable/disable) any flag in production via the admin UI within 30 seconds of identifying a misbehaving feature, with no engineering involvement.
  • Every flag change is captured in an immutable audit log with actor, timestamp, previous value, and new value.
  • Both backend languages in the monorepo have a typed SDK; everything else can evaluate via the JSON-over-HTTP endpoint.
  • All evaluation traffic and admin actions pass through the existing auth middleware — no new auth surface introduced.
  • The system is self-contained: no new external SaaS dependencies.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state (active / archived).
  • Postgres feature_flags table plus a read-through in-process cache.
  • Database migrations and seed data for the flag schema.
  • Typed accessor library wrapping flag reads and writes.
  • Audit history table recording every flag change (actor, diff, timestamp).
  • Evaluation engine: deterministic bucketing, rule ordering, environment inheritance (staging inherits production defaults), in-memory cache with invalidation.
  • SDK for the two backend languages in the monorepo.
  • JSON-over-HTTP evaluation endpoint for non-native callers.
  • Sampled evaluation telemetry events for later analysis.
  • Admin dashboard: create, edit, search, archive flags; per-environment overrides; percentage-rollout slider with live bucketing preview; audit-history view.
  • Role-based access: only flag owners and admins can edit production values.

Out of scope

  • A/B-test statistics or experiment analysis.
  • Scheduled (time-based) rollouts.
  • Mobile SDKs.
  • Full approval / change-request workflow for flag edits.
  • External SaaS flag services (LaunchDarkly, Unleash, etc.).

Constraints

  • No external SaaS dependencies. The entire system must run within the existing infrastructure.
  • No network hop on evaluation. The evaluation library must run in-process; the HTTP endpoint is only for non-native callers that are not on the hot path.
  • Auth middleware. All admin UI endpoints and the HTTP evaluation endpoint must sit behind the existing auth middleware without modification.
  • Team size and timeline. Three engineers, approximately six weeks (Phases 1–3 must be sequenced to unblock each other but can overlap at the margins).
  • Postgres primary. Flag storage must use the existing primary Postgres instance; no new database technology.
  • Audit immutability. Audit records must be append-only; no update or delete path exposed in the application layer.

Assumptions

The monorepo has exactly two backend languages (assumed Go and Python). Native SDKs will be written for those two; any other runtime consumes the HTTP endpoint.

Flag cardinality is moderate (hundreds to low thousands of flags). The full flag ruleset can fit comfortably in a per-process in-memory cache without special sharding.

A cache TTL of 30 seconds (or a lightweight poll/push via Postgres LISTEN/NOTIFY) is acceptable propagation latency for flag changes in production.

The admin UI can be built as a new page within the existing frontend application using the existing component library and build pipeline.

Phase 1: Flag Schema and Storage

Establish the data model, migration strategy, and typed accessor library that all subsequent phases depend on. Nothing about evaluation logic or UI lives here — just a clean, well-typed, auditable storage layer. Phase 1 is the critical-path unblock: Phases 2 and 3 cannot start meaningfully until the schema and library are stable.

Phase goal

Deliver a production-ready feature_flags table (with audit history), the Postgres migration files, seed data for common flag shapes, and a typed accessor library in both backend languages. At the end of Phase 1, an engineer can create and read a flag record programmatically and every write is captured in the audit log.

Alternatives considered

  • Config file in repo (YAML/JSON flags file, checked in). Simple, version-controlled, no new infra. Rejected because it requires a deploy for every flag change, which defeats the core "ship dark / kill without deploy" requirement.
  • Separate flags microservice with its own database. Better isolation, independent scaling. Rejected for Phase 1 scope: three engineers in six weeks cannot absorb the infra overhead, and keeping flags in the primary Postgres avoids a new network dependency on the evaluation hot path.
  • Redis as primary store. Fast reads, TTL-based expiry. Rejected because Redis alone offers no durable audit log, no transactional writes, and no SQL querying for the admin UI without a parallel SQL store anyway.

Recommendations

  • Use a single feature_flags table with a JSONB rules column for targeting rules; this avoids a complex EAV schema while keeping rules queryable. Add a separate flag_audit_log table (append-only, foreign-keyed to feature_flags) triggered by application-layer writes rather than a Postgres trigger, so the audit actor (user ID) is always present.
  • Version the flag schema with a schema_version integer on each flag row to handle future rule-shape evolution without a full migration.
  • The typed accessor library should expose only five operations: GetFlag, ListFlags, CreateFlag, UpdateFlag, ArchiveFlag. Keep the surface minimal so the evaluation engine can depend on it without pulling in admin logic.

Open questions

Should rules be a JSONB column or a normalized flag_rules table? JSONB is simpler to evolve but harder to query across rules for analytics. Decision needed before the migration is written.

What is the retention policy for flag_audit_log? Indefinite retention is the safest default but may require a partition or archival job at scale. Needs sign-off from the DBA or infra team.

Write and review the flag data model

Define the full schema in a design doc (or RFC comment in the migration PR): feature_flags columns (id, key, description, owner, flag_type, rules JSONB, default_value, state, salt, schema_version, created_at, updated_at) and flag_audit_log columns (id, flag_id, actor_id, action, previous_value, new_value, created_at). Get team sign-off before writing migrations.

Write Postgres migrations

Create feature_flags and flag_audit_log tables with appropriate indexes (key unique index, state index, flag_id + created_at composite index on audit log). Include a down-migration. Follow the project's existing migration tool conventions (e.g., Flyway, golang-migrate, Alembic — confirm which is used). Do not add foreign keys to application tables; flags are referenced by key string, not FK, to avoid coupling.

Write and publish typed accessor library (both languages)

Implement GetFlag, ListFlags, CreateFlag, UpdateFlag, and ArchiveFlag in both Go and Python packages within the monorepo. Each write operation must append a corresponding row to flag_audit_log within the same transaction. Include typed structs/dataclasses for Flag and AuditEntry. Publish as internal packages following existing monorepo conventions.

Add seed data and local-dev fixtures

Provide a seed script that inserts one flag of each type (boolean, percentage rollout, multivariate) with representative targeting rules. Seed should be idempotent (ON CONFLICT DO NOTHING or equivalent). Include fixtures for the test suite so unit and integration tests have a known baseline state without hitting production.

Write unit and integration tests for the accessor library

Unit tests cover all five operations, including error paths (duplicate key, archiving an already-archived flag). Integration tests run against the real migration-applied schema (not mocks) to catch schema/query drift. Aim for >90% line coverage on the accessor library. Wire into the existing CI pipeline.

Phase 2: Evaluation Engine

Build the library and HTTP endpoint that answer evaluate(flagKey, context) → variant. This phase depends on a stable Phase 1 schema. The evaluation engine must be correct (deterministic bucketing, correct rule ordering), fast (sub-millisecond p99 in-process), and observable (sampled telemetry events).

Phase goal

Deliver an in-process evaluation library (Go and Python) with a local in-memory cache, deterministic percentage bucketing via hash(userID + flagSalt), ordered targeting-rule evaluation, environment inheritance, and a sampled evaluation event emitter. Also deliver a JSON-over-HTTP endpoint for non-native callers. At the end of Phase 2, any service in the monorepo can evaluate a flag in under 1 ms p99 without a network hop, and every evaluation is optionally sampled to the telemetry pipeline.

Alternatives considered

  • Sidecar service for evaluation (all callers use HTTP). Centralizes evaluation logic, single deployment unit. Rejected because it adds a network hop to every flag evaluation, violating the core latency constraint. The HTTP endpoint is still provided for non-hot-path callers.
  • Push-only invalidation via Postgres LISTEN/NOTIFY. Lower latency than polling; flags propagate in milliseconds. Considered as the primary invalidation mechanism. However, LISTEN/NOTIFY connections hold open Postgres connections per process and can be unreliable at high connection counts. Recommended approach: use Postgres LISTEN/NOTIFY as the primary push mechanism with a 30-second TTL poll as a fallback safety net.
  • MurmurHash vs. FNV vs. SHA-256 for bucketing. SHA-256 is cryptographically strong but slower. FNV-1a is fast and has good distribution for this use case. MurmurHash is similar. Recommendation: FNV-1a for performance; document the exact hash function and salt concatenation format in the spec so all SDKs produce identical bucketing.

Recommendations

  • Define a canonical rule-evaluation order spec (most-specific rule wins; within same specificity, rules are evaluated in insertion order) and encode it in a shared test fixture that both SDKs must pass — this prevents subtle divergence between Go and Python evaluation.
  • Environment inheritance: staging reads from the staging overrides table first, then falls back to the production default value. Do not copy production rules into staging on write; compute inheritance at evaluation time to avoid stale copies.
  • Telemetry: emit a sampled evaluation event (1-in-N, configurable) to the existing internal event bus. Fields: flag_key, variant, context_hash (not the raw user ID), rule_matched, timestamp. Hashing the context protects PII in the analytics pipeline.

Open questions

What is the canonical hash function and input format for percentage bucketing? Must be documented and agreed before SDKs are written to prevent Go/Python evaluation divergence. Candidate: FNV-1a(flagSalt + ":" + userID) mod 10000, expressed as a basis-point percentage.

Does the existing internal event bus support the sampled telemetry volume? Need an estimate of peak evaluation rate × sample rate to confirm the pipeline can absorb it without backpressure.

Write the evaluation engine spec

Document the exact rule-evaluation algorithm: input context shape, rule-matching priority (user ID > org > environment > default), percentage bucketing formula, environment inheritance semantics, and the multivariate variant-selection logic. Include cross-SDK test vectors (a table of flag configs + contexts + expected variants) that will drive the conformance test suite in both languages.

Implement in-memory cache with invalidation

Build a cache module (shared between Go and Python implementations) that loads all active flags on startup, subscribes to Postgres LISTEN/NOTIFY on a flag_changed channel for push invalidation, and falls back to a 30-second TTL poll if the LISTEN connection drops. The cache must be safe for concurrent reads. Expose a ForceRefresh() method for tests and for the admin UI to call after a write.

Implement evaluation library in Go and Python

Each library exposes a single public function: Evaluate(flagKey string, ctx EvalContext) (Variant, error) (Go) and evaluate(flag_key: str, ctx: EvalContext) -> Variant (Python). Internally: look up flag from cache, walk rules in order, apply bucketing for percentage flags, return variant. Must pass all cross-SDK test vectors from t2.1. Zero external dependencies beyond the standard library and the accessor library from Phase 1.

Build JSON-over-HTTP evaluation endpoint

Add a POST /internal/flags/evaluate endpoint to the existing API gateway (behind auth middleware). Request body: {"flag_key": "...", "context": {...}}. Response: {"variant": "...", "reason": "..."}. This endpoint calls the Go evaluation library in-process — it is not a separate service. Rate-limit at the API gateway level using the existing rate-limiter. Document the endpoint in the internal API reference.

Add sampled evaluation telemetry

After each evaluation, probabilistically emit an event to the internal event bus at a configurable sample rate (default: 1-in-100). Event schema: flag_key, variant, rule_matched, context_hash (FNV-1a of serialized context, not raw PII), evaluated_at. Sample rate must be a flag-level config field (so high-value flags can be sampled at 100%). Wire into the existing analytics pipeline.

Performance benchmark and latency validation

Write a benchmark suite (Go benchmark + Python timeit) that measures p50/p95/p99 evaluation latency under a realistic flag set (100 flags, mix of types and rule counts) with a warm cache. Target: p99 < 1 ms in-process. Run the benchmark in CI as a non-blocking advisory check; flag regressions of >20% as a warning. Document baseline numbers in the PR.

Phase 3: Admin UI

Build the dashboard that product, support, and engineering use to manage flags day-to-day. Depends on Phases 1 and 2 being stable (schema locked, HTTP endpoint available). The UI must be functional and safe — role-based access prevents support from accidentally editing production values they don't own, and the audit-history view provides accountability.

Phase goal

Deliver a dashboard page integrated into the existing admin application where users can create, edit, search, and archive feature flags; set per-environment overrides; use a percentage-rollout slider with a live bucketing preview; view the full audit history for any flag; and where role enforcement (owner + admin only for production edits) is applied at the API layer (not just the UI). At the end of Phase 3, support can disable a misbehaving feature in under 30 seconds without engineering involvement.

Alternatives considered

  • Admin UI as a standalone single-page app. Full design freedom, no coupling to existing frontend. Rejected: separate SPA requires its own auth integration, deployment pipeline, and domain — too much overhead for three engineers in the remaining timeline.
  • Role enforcement in the UI only (no API-layer check). Simpler to implement. Rejected: API-layer enforcement is required by the security model — the UI check is a UX nicety, not a security boundary. Both must exist.
  • Percentage-rollout slider without live bucketing preview. Simpler. Accepted as a stretch goal: the live preview (showing how many of a sample of test user IDs would be included at a given percentage) is high-value for product confidence but can be deferred if time is short. Marked as P1 feature, not P0 blocker.

Recommendations

  • Implement role enforcement as middleware on the admin API routes: check that the requesting user is either the flag's owner field or has the flags_admin role before allowing any write to a production-environment flag. Return 403 otherwise.
  • The audit-history view should be paginated (cursor-based) and filterable by actor and date range. Do not try to diff JSONB in the UI on the first pass — showing previous and new raw JSON side-by-side is sufficient.
  • The percentage-rollout slider's live preview should call POST /internal/flags/evaluate with a set of 20 deterministic test user IDs (hardcoded in the frontend) and display the count that would receive the treatment. This gives product a fast sanity check without any server-side computation beyond the existing evaluation endpoint.

Open questions

What is the existing role/permission model? Does a flags_admin role need to be defined in the auth system, or can we reuse an existing admin role? Needs answer from the auth team before the API middleware can be wired up.

Should non-owner editors be able to edit staging/dev environments freely, or does the same owner+admin restriction apply to all environments? Product and security need to align on this before the RBAC logic is written.

Add admin API routes for flag CRUD

Expose REST endpoints: GET /admin/flags (list + search), POST /admin/flags (create), GET /admin/flags/:key (read), PATCH /admin/flags/:key (update), DELETE /admin/flags/:key (archive), GET /admin/flags/:key/audit (paginated audit history). All routes behind existing auth middleware. Apply role-enforcement middleware on write routes for production-environment flags. Input validation: reject unknown flag_type values, enforce key format (lowercase alphanumeric + hyphens), validate percentage is 0–100.

Build flag list and search page

Dashboard page listing all flags with columns: key, type, owner, state, last-modified. Client-side filtering by name substring; server-side filtering by state (active / archived) and environment. Each row links to the flag detail page. Pagination with 50 items per page. Use the existing data-table component from the component library.

Build flag create and edit form

Form fields: key (create only, immutable after creation), description, owner (autocomplete from user directory), flag type (select), default value, targeting rules (dynamic rule builder: add/remove/reorder rules with fields for dimension, operator, and value), per-environment overrides. For percentage-rollout flags, replace the default-value field with a percentage slider (0–100) and a live bucketing preview panel that calls the evaluation endpoint with 20 fixed test user IDs. Confirm destructive actions (archiving, removing targeting rules) with a modal.

Build audit history view

Per-flag audit-history tab showing a reverse-chronological list of changes: actor name, timestamp, action type (created / updated / archived), and a before/after diff of the changed fields. Use a simple two-column JSON diff display (previous left, new right) with changed keys highlighted. Cursor-based pagination (load older entries on scroll or button). Filterable by actor and date range using the existing date-range picker component.

Wire role-based access controls in API and UI

API layer: middleware checks that the authenticated user is the flag's owner or has the flags_admin role for any PATCH/DELETE on a production-environment flag; returns 403 with a descriptive error message otherwise. UI layer: disable edit controls and show a tooltip explaining the restriction if the current user lacks permission. Test with at least two roles (owner, non-owner non-admin) in integration tests. Coordinate with the auth team on the flags_admin role definition (see open question q3.1).

End-to-end testing and rollout

Write end-to-end tests covering the golden paths: create a boolean flag, enable it in staging, verify evaluation returns the expected variant via the HTTP endpoint, archive the flag, verify it no longer evaluates. Also test the RBAC path: non-owner cannot edit production. Run E2E tests in the staging environment before production rollout. Prepare a runbook for support: how to find a flag, how to disable it, what to do if the UI is unavailable (direct API call). Roll out the admin UI to internal users first for two days before opening to support.

Postgres + in-process cache over a dedicated flag service or external SaaS

Flags are stored in the existing primary Postgres instance and evaluated by an in-process library with a local in-memory cache. This satisfies the sub-millisecond p99 latency requirement without adding a network hop, keeps the system entirely within existing infrastructure (no new SaaS), and avoids the operational burden of a new microservice for a team of three. The trade-off is that cache invalidation requires a Postgres LISTEN/NOTIFY mechanism, and very high flag cardinality (>10 000 flags) may require revisiting the in-memory approach.

A dedicated sidecar or microservice would give cleaner separation of concerns and independent scaling, but at the cost of a network hop on every evaluation and additional infra ownership — both incompatible with the constraints.

JSONB column for targeting rules over a normalized rules table

Targeting rules are stored as a JSONB column on the feature_flags row rather than in a separate normalized flag_rules table. This allows the rule schema to evolve without additional migrations, simplifies the read path (one row fetch loads the complete flag definition), and is sufficient for the expected rule complexity (a few conditions per flag). A schema_version field on each flag enables future migration of individual flag records to a new rule shape without a big-bang migration.

A normalized rules table would be more queryable for analytics ("how many flags target org X?") and would enforce rule-shape constraints at the database layer. This can be revisited if analytics requirements emerge.

Cache invalidation lag causes stale flag values after a kill-switch action

If support disables a misbehaving feature but cache TTL is 30 seconds, the feature may remain active for up to 30 seconds across all running processes. For a truly misbehaving feature, 30 seconds of continued exposure could be significant.

Mitigation: Use Postgres LISTEN/NOTIFY to push invalidation events to all processes immediately on write. The 30-second TTL poll is a fallback, not the primary mechanism. Document the expected propagation SLA (seconds, not minutes) in the runbook so support sets expectations correctly. If near-instant propagation is required, evaluate a Redis pub/sub layer in a future phase.

Go/Python evaluation divergence causes split-brain rollouts

If the Go and Python SDKs implement bucketing or rule ordering slightly differently, a user may see different variants depending on which backend service handles their request. This is especially harmful for percentage rollouts where consistency per user is expected.

Mitigation: The canonical evaluation spec (t2.1) includes cross-SDK test vectors. Both SDKs must pass the same vector suite in CI. Any deviation is a blocking CI failure. The hash function, salt format, and rule-ordering semantics are specified to the byte level in the spec.

Postgres LISTEN/NOTIFY connection exhaustion at high process count

Each process holds an open Postgres connection for LISTEN/NOTIFY. At high horizontal scale (many instances of many services), this could exhaust the Postgres connection pool.

Mitigation: The design includes a 30-second TTL poll fallback specifically for this case. If LISTEN/NOTIFY connections are disabled (e.g., via a feature flag — meta), processes fall back to polling gracefully. Monitor connection counts as part of rollout; if connection pressure appears, disable LISTEN/NOTIFY and rely solely on polling or introduce a shared pub/sub intermediary.

Timeline pressure leads to skipping cross-SDK conformance tests

Three engineers, six weeks, three phases is a tight schedule. Under pressure, the conformance test suite (t2.1) may be deferred, leaving evaluation divergence undetected until production.

Mitigation: The conformance test vectors are authored in Phase 2, task t2.1, before any SDK code is written. They are a prerequisite for t2.3, not an afterthought. If timeline pressure forces cuts, cut UI polish (Phase 3 stretch goals) before cutting correctness infrastructure.

Feature Flag System

Add a first-party feature-flag system so engineering can ship dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases over six weeks with a team of three: flag schema and storage, evaluation engine, and admin UI.

Success criteria

  • Flag evaluation p99 latency under 1 ms measured in a load test against the in-process cache.
  • Engineers can create a boolean flag, target it to a specific user ID or org, and enable it in staging without writing or deploying code.
  • Support can set a flag to disabled via the admin UI and the change propagates to all running instances within 30 seconds.
  • Percentage rollouts are deterministic: the same user always lands in the same bucket for a given flag.
  • Every flag change (create, edit, archive, override) appears in the audit-history view with actor, timestamp, and diff.
  • Role-based access is enforced: non-owners cannot edit production flag values.
  • All evaluation paths run behind the existing auth middleware — no net-new auth surface.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state (active / archived).
  • feature_flags Postgres table, migration files, and seed data for standard infrastructure flags.
  • Read-through in-memory cache with push-or-poll invalidation.
  • Typed accessor libraries for the two backend languages in the monorepo.
  • JSON-over-HTTP evaluation endpoint for all other consumers.
  • Audit-history table and view.
  • Admin dashboard: create, edit, search, archive, per-environment overrides, percentage-rollout slider, audit history, RBAC.
  • Sampled evaluation telemetry events.

Out of scope

  • A/B-test statistics or experiment analysis.
  • Scheduled or time-gated rollouts.
  • Mobile SDKs.
  • Full approval workflow (four-eyes review before flag changes take effect).
  • External SaaS flag providers (LaunchDarkly, Statsig, etc.).

Constraints

  • No new external SaaS dependencies. Everything runs on existing infrastructure.
  • Evaluation must not add a network hop to request handling. The evaluation library runs in-process; the HTTP endpoint is for non-backend consumers only.
  • Behind existing auth middleware. Admin UI and evaluation endpoint both authenticate through the current session/token system.
  • Team size: three engineers.
  • Timeline: roughly six weeks total across three phases.
  • Postgres only for durable storage — no Redis or other new infrastructure required at launch (cache is in-process).

Assumptions

The existing primary Postgres instance has sufficient headroom to serve flag reads and audit writes without requiring a read replica dedicated to flag traffic.

Both backend languages in the monorepo support a long-lived in-process singleton suitable for holding the in-memory flag cache across requests.

The number of active flags will remain well under 10 000 for the foreseeable future, keeping the full in-memory snapshot small enough for p99 < 1 ms evaluation.

Audit logging of flag changes (who changed what and when) satisfies compliance requirements without a blocking approval workflow.

Phase 1: Flag schema and storage

Establish the canonical data model for flags, get it into Postgres, provide seed data for infrastructure flags, stand up the audit trail, and ship a typed accessor library that the rest of the system will build on. All subsequent phases depend on this foundation being stable before they begin.

Phase goal

By the end of Phase 1, the team can create, read, update, and archive a feature flag through the database layer. The schema handles all flag types (boolean, percentage rollout, multivariate) and all targeting dimensions (user ID, org, environment). Migrations are idempotent and checked in. The typed accessor library passes its test suite in both backend languages. The audit log records every mutation with actor and diff. Nothing yet evaluates flags or shows UI — that comes in phases 2 and 3.

Alternatives considered

Config files in the repo (JSON/YAML checked in to git). Attractive because git history is the audit log and there is no new DB surface. Rejected because it makes programmatic flag creation from the admin UI impossible without auto-committing to the repo, and it serialises all flag changes through the CI pipeline — too slow for incident response.

Separate flags microservice with its own database. Maximises isolation but introduces a network hop on every evaluation, violating the stated constraint. Adds operational overhead a team of three cannot absorb in six weeks.

Chosen: feature_flags table in the primary Postgres database plus an in-process read-through cache. Leverages existing infrastructure, keeps evaluation in-process (no network hop), and gives us transactions, foreign keys, and row-level audit via a flag_audit_log table.

Recommendations

  • Store targeting rules as a jsonb column with a well-documented JSON Schema — this avoids premature normalisation while keeping rules queryable. Validate the schema at the application layer on write.
  • Use a BIGSERIAL primary key and a separate immutable flag_key text column with a unique index. Keys are the stable public identifier; the integer PK is the internal join key.
  • The audit log should store the full before/after JSON snapshot (not just a diff string) so the admin UI can reconstruct any historical state without custom diff logic.
  • Ship seed migrations with a small set of real infrastructure flags (e.g. enable_new_login_flow, maintenance_mode) so developers have examples to work from on day one.

Open questions

Should multivariate flag variants be stored as a jsonb array on the flag row, or in a child flag_variants table? The child table is more relational but adds a join; the array is simpler but makes variant-level querying harder. Decision needed before the migration is written.

Which column(s) identify the "actor" in the audit log — the internal user ID, their email, or both? We want something stable for the long-term audit trail that survives user email changes.

Write and review the flag data model

Document the full schema for feature_flags and flag_audit_log — column names, types, constraints, indexes, and the JSON Schema for the targeting_rules and variants jsonb columns. Get sign-off from the team before writing any migration. This is a design artifact, not code, and is the single most-leveraged deliverable in Phase 1.

Write Postgres migrations

Create up and down migration files for feature_flags and flag_audit_log. Follow the existing migration naming convention in the repo. Migrations must be idempotent (use IF NOT EXISTS guards). Include a separate seed migration that inserts a handful of example flags for local development.

Implement the typed accessor library — Backend Language A

CRUD operations for flags, a helper to record audit-log entries (called automatically on every write), and query helpers for "list flags by environment" and "get flag by key". Include unit tests with a real test database (no mocks). Expose a clean public interface that hides the SQL; Phase 2's evaluation engine will depend on this.

Implement the typed accessor library — Backend Language B

Port the same accessor surface from t1.3 to the second backend language. Re-use the same test database fixture strategy. The public interfaces should be idiomatically consistent with each language's conventions even if they are not syntactically identical.

Write schema validation for targeting rules

Implement a validator (usable from both accessor libraries) that accepts a targeting_rules payload and returns typed errors if it violates the JSON Schema. This runs at write time — the evaluation engine will trust that stored rules are valid. Include tests covering the full set of rule types: user-ID list, org-ID list, environment name, and compound AND/OR rules.

Run migration in staging; verify audit log end-to-end

Apply the migration to the staging database. Manually create, edit, and archive a flag using the accessor library (via a one-off script) and confirm that every mutation produces a correct audit-log row. Fix any issues found before Phase 2 begins. Document the rollback procedure for the migration.

Phase 2: Evaluation engine

Build the in-process library that answers evaluate(flagKey, context) → variant at p99 under 1 ms, plus the HTTP endpoint for non-backend consumers. This phase also covers cache management, cache invalidation, deterministic bucketing, rule evaluation order, environment inheritance, and sampled telemetry.

Phase goal

By the end of Phase 2, any backend service in the monorepo can import the flag evaluation library and call evaluate(flagKey, context) without a network round-trip. The result is deterministic (same inputs always produce the same variant), the cache refreshes within 30 seconds of a flag change, and evaluation events are emitted at a configurable sample rate to the internal analytics pipeline. The JSON-over-HTTP endpoint is deployed and documented for non-backend consumers.

Alternatives considered

Sidecar process per application instance. Isolates flag evaluation memory from the application, allows language-agnostic implementation in one place, and can be restarted independently. Rejected because it requires a local network hop on every evaluation request, violating the stated constraint, and adds a new process lifecycle to manage.

Polling only (no push invalidation). Simpler to implement — each instance polls Postgres every N seconds. The downside is a worst-case propagation delay of N seconds for every flag change. Acceptable for many use cases but fails the "support can kill a feature instantly" story unless N is very small (which increases DB load).

Chosen: in-process library with a short-poll fallback and a Postgres LISTEN/NOTIFY push channel. LISTEN/NOTIFY is built into Postgres, requires no new infrastructure, and gives near-instant invalidation. The short-poll fallback (every 30 s) handles cases where the NOTIFY connection is lost and ensures eventual consistency without manual intervention.

Recommendations

  • Use FNV-1a or MurmurHash3 for the bucketing hash — both are fast, have good distribution, and are easy to implement identically in multiple languages. Hash flagKey + ":" + userId (with a per-flag salt stored in the flag row) so changing the salt re-buckets users without touching the flag key.
  • Define rule evaluation order explicitly in the schema documentation: more-specific rules win; within the same specificity level, rules are evaluated in the order they appear in the targeting_rules array. Document this as a contract so that future rule types can be added without breaking existing behaviour.
  • Environment inheritance: if a flag has no override for the current environment, fall back to the production flag value. This means staging automatically tracks production unless explicitly overridden, which is the safe default.
  • Telemetry: emit evaluation events to the existing internal event bus (not a new pipeline). Sampling rate should be configurable per-flag, defaulting to 1 %. Include flag key, variant returned, context dimensions (user ID hash, org ID, environment), and evaluation latency.

Open questions

Should the cache hold the full flag snapshot (all flags at once) or be keyed per flag? Full snapshot is simpler to invalidate atomically but uses more memory. Per-flag LRU is more memory-efficient but complicates invalidation when a rule change affects multiple flags (e.g. a shared segment). Need to decide before implementing the cache layer.

Is the existing internal event bus appropriate for evaluation telemetry, or does the sample volume (potentially millions of events per day) require a dedicated sink? Need input from the data-platform team before wiring up telemetry.

Implement core evaluation logic (rule engine)

Write the function that, given a flag row and an evaluation context, returns the correct variant. Cover: boolean flags (on/off by default, override by targeting rule), percentage-rollout bucketing (hash-based, deterministic), multivariate flag variant selection, rule ordering semantics, and environment inheritance fallback. Heavily unit-tested with property-based tests for bucketing distribution.

Implement in-memory cache with LISTEN/NOTIFY invalidation

On startup, load all active flags from Postgres into a thread-safe in-memory map. Subscribe to a Postgres NOTIFY channel (e.g. flag_changed). On notification, reload only the affected flag. Fall back to a full reload every 30 seconds in case the NOTIFY connection is lost. Expose a health-check method that reports cache age and last-invalidation time.

Wire evaluation library into both backend languages

Wrap the core evaluation logic and cache in idiomatic SDKs for both backend languages. Provide a top-level evaluate(flagKey, context) function and a evaluateAll(context) bulk variant. Ensure the cache singleton is initialised once per process, not once per request. Write integration tests that start a real Postgres instance, insert a flag, and assert correct evaluation output.

Build JSON-over-HTTP evaluation endpoint

Add a POST /internal/flags/evaluate endpoint behind the existing auth middleware. Request body: { flagKey, context }. Response: { variant, flagType, evaluatedAt }. Bulk variant: POST /internal/flags/evaluate-all with context only. This endpoint uses the same in-process cache as the SDKs — it is a thin HTTP wrapper, not a separate service. Document the API contract.

Integrate sampled telemetry

After each evaluation, emit a sampled event to the internal event bus with the fields described in the recommendations. Make sample rate configurable via an environment variable, defaulting to 0.01 (1 %). Instrument both the SDK evaluation path and the HTTP endpoint. Verify event delivery in a staging environment by inspecting the event stream for a flag under 100 % sampling.

Load test and validate p99 latency

Write a load test that calls evaluate() in a tight loop from multiple goroutines / threads, simulating realistic flag counts (200 flags, 5 targeting rules each). Assert p99 latency is under 1 ms with the cache warm. Run the test in CI as a non-blocking benchmark (fail only if p99 exceeds 5 ms, to catch catastrophic regressions). Document the results for the team.

Phase 3: Admin UI

Build the dashboard that engineers, product managers, and support use to manage flags day-to-day. This phase makes the system self-service and removes the need for direct database access. It builds on the accessor library from Phase 1 and exposes the audit history written by Phase 2's evaluation engine.

Phase goal

By the end of Phase 3, any engineer or authorised product manager can log into the admin UI (authenticated through the existing auth middleware), create a flag, target it to specific users or orgs, set a percentage rollout with a visual bucketing preview, and archive it when done — all without writing code. Support staff can flip a flag off in under 10 seconds. Admins can view the full audit history of any flag. Non-owners cannot edit production flag values. The UI is integrated into the existing admin application, not a standalone app.

Alternatives considered

Standalone React SPA served from a new origin. Maximum frontend flexibility, no coupling to the existing admin app. Rejected because it requires new auth integration, a new deployment target, and adds operational overhead the team cannot absorb. The existing admin app already has auth, routing, and a component library.

No dedicated UI — CLI tooling only. Fastest to build, zero frontend work. Rejected because support staff (non-engineers) need to be able to kill a flag during an incident, and a CLI is not accessible to them. An incident is the wrong time to teach a new CLI.

Chosen: new pages within the existing admin application. Reuses auth, routing, component library, and deployment pipeline. Engineering cost is proportional to the number of pages, not the total infrastructure setup.

Recommendations

  • The percentage-rollout slider should show a live preview of how many users in a given org or cohort would be bucketed into the treatment variant at the current percentage. This makes the rollout concrete and reduces support escalations from confused users.
  • RBAC enforcement should happen at the API layer (not just in the UI) so that direct API calls also respect ownership. The UI should additionally grey out controls the current user cannot use, but never rely solely on the UI for access control.
  • Search should be client-side filtered from a cached full-list response for flag counts under ~5 000; add server-side pagination only if cardinality exceeds that threshold. Optimise for simplicity now.
  • Archive (soft delete) rather than hard delete. Archived flags remain visible in the audit history and can be un-archived if needed. Hard deletion should require an explicit admin action and a confirmation prompt.

Open questions

How is flag ownership determined — is it a free-text email field on the flag row, or a foreign key to the existing users table? The latter is more correct but requires the UI to resolve user IDs to display names, and adds a dependency on the users service. Need to align with the auth team before building the RBAC UI.

Should per-environment overrides be a separate tab within the flag detail page, or a column-based view showing all environments side by side? The side-by-side view is more informative but harder to build; the tab view is simpler. Needs a UX decision before implementation starts.

Build REST API layer for admin operations

Add authenticated REST endpoints for all admin operations: list flags (with filter/search params), get flag detail, create flag, update flag, set per-environment override, and archive flag. These endpoints wrap the Phase 1 accessor library. RBAC is enforced here: PATCH /flags/:id on production values requires the caller to be the flag owner or an admin role. Return 403 otherwise. Write contract tests covering the permission boundaries.

Flag list and search page

A paginated table of all flags showing key, description, owner, type, lifecycle state, and last-modified date. Client-side text search across key and description. Filter controls for environment, type, and state. Each row links to the flag detail page. Archived flags are hidden by default with a toggle to show them. Matches the visual design of other admin list pages.

Flag create / edit form

Form for creating a new flag and editing an existing one. Fields: key (create only, immutable after creation), description, owner, flag type, default value, targeting rules (dynamic form sections per rule type: user-ID list, org-ID list, environment). Validates the targeting-rule JSON Schema client-side before submit. Displays validation errors inline. On save, calls the REST API and shows a success toast; on error, surfaces the API error message.

Percentage-rollout slider with bucketing preview

Within the flag create/edit form, when flag type is percentage_rollout, show a slider (0–100 %) alongside a read-only preview panel. The preview panel shows: the hash salt in use, an example of three user IDs and which bucket they fall into at the current percentage, and the effective count if applied to a user cohort (entered as a number field). The bucketing preview runs the same deterministic hash logic as the evaluation engine, implemented in JavaScript, so the preview is always accurate.

Per-environment overrides panel

Within the flag detail page, a panel listing all environments (staging, production, and any others registered in the system). For each environment, show the effective value (inherited from production or overridden) and an edit button. Clicking edit opens an inline form to set the override value for that environment. Saving calls POST /flags/:id/overrides/:env. Deleting an override reverts to inheritance. Non-owners see this panel as read-only.

Audit history view

A chronological list of all changes to a flag, displayed at the bottom of the flag detail page and also accessible from the flag list as a dedicated route. Each entry shows: timestamp, actor (name + email), change type (created / updated / archived / override-set), and a human-readable diff of what changed (old value → new value). Sourced from the flag_audit_log table via a dedicated GET /flags/:id/audit endpoint. Paginated, newest-first.

Store flags in Postgres, not in a config file in the repo

Rationale: config-in-repo makes programmatic flag creation from the admin UI impossible without auto-committing to the repo. It also serialises all flag changes through CI, which is unacceptably slow for incident response (killing a misbehaving flag must happen in seconds, not minutes). Postgres gives us transactions, foreign keys, audit via triggers, and LISTEN/NOTIFY for cache invalidation at no additional infrastructure cost.

Config-in-repo gives git history as a free audit log and eliminates a database dependency. It is a valid approach for teams where flag changes are always developer-initiated and latency is not a concern.

In-process evaluation library, not a sidecar service

Rationale: the brief requires that the evaluation path not add a network hop to request handling. A sidecar process, even on localhost, introduces a network call and a process lifecycle dependency. The in-process library shares the application's memory space and can answer in microseconds once the cache is warm. The operational downside (flag-library bugs can crash the application) is mitigated by thorough testing and the fact that the library is read-only at evaluation time.

A sidecar isolates flag-evaluation memory leaks and CPU usage from the application process, and allows the cache to be shared across multiple application instances on the same host — which an in-process cache cannot do.

Use Postgres LISTEN/NOTIFY for cache invalidation with a polling fallback

Rationale: near-instant flag propagation is a hard requirement for the "kill switch" use case. LISTEN/NOTIFY is already available in Postgres with no new infrastructure. A polling-only approach with a 30-second interval is too slow for incidents; a 1-second interval creates unacceptable DB load at scale. LISTEN/NOTIFY gives sub-second propagation at near-zero cost, with a 30-second polling fallback for resilience.

LISTEN/NOTIFY adds a persistent connection per application instance. At very high instance counts this could exhaust Postgres connection limits. PgBouncer in session mode or a dedicated notification relay can mitigate this if it becomes a problem.

Postgres LISTEN/NOTIFY connection exhaustion at scale

If the number of application instances grows large (hundreds of pods), each holding a persistent LISTEN connection, Postgres connection limits could be exhausted. Mitigation: monitor connection count from day one; if it becomes a concern, route LISTEN/NOTIFY through a single relay process per node (or use PgBouncer in session mode for the notification connection only). The polling fallback ensures correctness even if NOTIFY connections are dropped.

Evaluation library bug causes application-wide crash or incorrect variant

Because the evaluation library runs in-process, a null-pointer dereference or infinite loop in the rule engine could crash the application or return wrong variants at scale before anyone notices. Mitigation: wrap the top-level evaluate() call in a recover/catch; on panic or exception, log the error and return the flag's default value. This degrades gracefully (all users get the default) rather than crashing. Property-based tests covering the full rule grammar reduce the probability of such bugs reaching production.

Schema migration takes too long on the primary Postgres instance

Adding a new table to a busy primary can acquire locks that block writes temporarily. Mitigation: migrations should be additive (no ALTER TABLE on existing tables in Phase 1). Use CREATE TABLE IF NOT EXISTS. Test migration duration in a staging environment that mirrors production data volume before running in production. Schedule the migration during a low-traffic window.

Six-week timeline is tight for three engineers across three phases

Phase 1 is foundational — slippage here cascades into Phase 2 and 3. Mitigation: Phase 1 tasks are the most parallelisable (schema design, migration, two accessor libraries can be done by three people in parallel). Phase 3's admin UI tasks are also largely independent once the REST API (t3.1) is done. The riskiest serial dependency is t1.x → t2.x; plan Phase 1 to complete by end of week 2 so Phase 2 starts no later than week 3.

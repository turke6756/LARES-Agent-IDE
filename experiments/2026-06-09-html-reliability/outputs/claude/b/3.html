Feature Flag System

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill misbehaving features without a deploy. Three phases over six weeks: flag schema and storage, evaluation engine, and admin UI. No new external SaaS dependencies; evaluation must not add a network hop.

Success criteria

  • Any engineer can create, target, and archive a flag without a deploy or database migration.
  • evaluate(flagKey, context) returns the correct variant in under 1 ms at p99 under production load (no extra network hop).
  • Percentage rollouts produce deterministic bucketing: the same user always gets the same variant for a given flag.
  • A support engineer can disable any flag in production within 30 seconds via the admin UI without touching code.
  • Every flag change (create, edit, archive, override) appears in the audit history with actor, timestamp, and diff.
  • Role-based access prevents non-owner, non-admin users from editing production flag values.
  • Both backend languages in the monorepo have typed SDK access; all other callers can use the JSON-over-HTTP endpoint.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage rollout / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state (active / archived).
  • Storage: new feature_flags table in the primary Postgres instance plus a read-through in-process cache.
  • Database migrations and seed data for a set of bootstrap flags.
  • Typed accessor library for both backend languages.
  • Audit history table logging all flag mutations.
  • Evaluation engine as an in-process library (not a sidecar) with local in-memory cache and push/poll invalidation.
  • JSON-over-HTTP evaluation endpoint for non-native callers, protected by existing auth middleware.
  • Sampled telemetry event emitted on every evaluation.
  • Admin dashboard: create, edit, search, archive flags; per-environment overrides; percentage-rollout slider with live bucketing preview; audit history view; role-based access control.

Out of scope

  • A/B-test statistical analysis.
  • Scheduled (time-based) rollouts.
  • Mobile SDKs.
  • Full approval/change-request workflow for flag edits.
  • Any new external SaaS (no LaunchDarkly, Split, Flagsmith, etc.).

Constraints

  • No new external SaaS. All components must run in the existing infrastructure.
  • No extra network hop in the evaluation path. The evaluation library must be in-process; the HTTP endpoint is a secondary path for non-native callers only.
  • Behind existing auth middleware. All API and UI routes must reuse the current auth layer; no new auth surface.
  • Team size: three engineers, approximately six weeks.
  • Evaluation latency: p99 under 1 ms including cache lookup.
  • Audit history is required; approval workflow is not.

Assumptions

The monorepo has exactly two backend languages that need native SDK support. A third would require an additional SDK implementation not currently scoped.

The primary Postgres instance has sufficient headroom to serve flag reads at the polling interval without degrading application query latency. A dedicated read replica is not required.

The existing auth middleware and role model can be extended to express the "flag owner" and "flag admin" roles needed for production edit gating, without a separate identity service change.

At launch, environment inheritance (staging defaults from production) is a read-time fallback, not a promotion workflow. Manual per-environment overrides in the UI are sufficient.

Phase 1: Flag schema and storage (weeks 1–2)

Establish the canonical data model, persistence layer, migration story, seed data, and typed accessor libraries. All downstream phases depend on this foundation. Phase 1 ends when both backend SDKs can read flags from Postgres through the cache and the audit log records every write.

Phase goal

Deliver a stable, versioned flag schema in Postgres with a read-through in-process cache, a migration and seed-data workflow, a typed accessor library for each backend language, and an append-only audit history table. After Phase 1, engineers can define flags in the database and read them from application code; the evaluation logic itself comes in Phase 2.

Alternatives considered

Config files in the repository. Flags as YAML/JSON committed to the repo avoids a new database table and gives a natural audit trail via git. Rejected because it requires a deploy to change any flag value, which defeats the core "kill without a deploy" requirement.

Separate dedicated flags database. A second Postgres instance (or a Redis-primary model) would isolate flag traffic. Rejected at this stage because it introduces a new infrastructure dependency, adds operational complexity for a three-engineer team, and the primary Postgres has headroom (see assumption a2). Can be revisited if load warrants it.

Chosen approach: feature_flags table in primary Postgres + in-process read-through cache. Keeps infrastructure minimal, leverages existing backup/monitoring/auth, and the in-process cache ensures the evaluation path never hits the database on the hot path.

Recommendations

  • Use ULID or UUID primary keys on feature_flags and flag_audit_log to avoid exposing sequential IDs in the admin UI.
  • Store targeting rules as a JSONB column with a well-documented JSON Schema so the evaluation engine can evolve rule types without table migrations.
  • Version the cache invalidation protocol from day one (a simple monotonic updated_at + polling is sufficient; add push/WebSocket later in Phase 2).
  • Write the accessor library as a thin wrapper over the cache so Phase 2 can swap the backing store without changing call sites.

Open questions

What is the expected maximum number of flags at steady state? This affects index design and whether the entire flag table can be loaded into the in-process cache on startup.

Does the audit log need to store the full before/after JSONB diff, or is a human-readable summary sufficient? Full diff enables programmatic rollback; summary is cheaper to store and display.

Define and migrate the feature_flags schema

Write the migration creating the feature_flags table with columns: id (ULID), key (unique, slug-format), description, owner (user or team slug), flag_type (enum: boolean | percentage | multivariate), targeting_rules (JSONB), default_value (JSONB), state (enum: active | archived), created_at, updated_at. Add a unique index on key and a partial index on state = 'active'. Migration must be backward-compatible (no column drops).

Create the flag_audit_log table and write trigger

Add a flag_audit_log table: id, flag_id (FK), actor, action (enum: created | updated | archived), before_snapshot (JSONB), after_snapshot (JSONB), created_at. Wire a Postgres trigger on INSERT/UPDATE/DELETE of feature_flags to append a row. The trigger must capture the actor from a session-local variable set by the application before each write.

Seed data and bootstrap flags

Write a seed script (idempotent, safe to re-run) that inserts a small set of system flags used by the platform itself (e.g., admin_ui_enabled, evaluation_telemetry_enabled). Seed runs in CI and in local dev setup. Each seed flag documents its owner and default value in a comment block.

In-process read-through cache with polling invalidation

Implement a cache module (shared by both language SDKs) that loads all active flags on first access and refreshes on a configurable interval (default 10 s). The cache stores flags keyed by flag_key. Expose a forceRefresh() method for tests and a hook for push invalidation to be wired in Phase 2. Thread-safety is required; use a read-write lock or copy-on-write snapshot pattern.

Typed accessor libraries for both backend languages

Wrap the cache in a typed accessor for Language A and Language B. Each accessor exposes at minimum: getFlag(key): FlagDefinition | null and listActiveFlags(): FlagDefinition[]. Generate types from the JSONB schema so callers get autocomplete on flag type, targeting rule shape, and allowed variant values. Ship unit tests covering cache miss, cache hit, and stale-cache-with-refresh.

Phase 2: Evaluation engine (weeks 3–4)

Build the logic layer that answers evaluate(flagKey, context) → variant. This is entirely in-process; no new service is introduced. The HTTP endpoint is a thin wrapper for non-native callers. Phase 2 ends when both SDKs pass a shared evaluation test suite and telemetry events are flowing.

Phase goal

Deliver a correct, fast, and deterministic evaluation engine embedded in the Phase 1 accessor library. The engine must handle all three flag types, evaluate targeting rules in declared order, implement deterministic hash-based bucketing for percentage rollouts, respect environment inheritance, and emit a sampled telemetry event on every evaluation. A JSON-over-HTTP endpoint wraps the engine for non-native callers. p99 evaluation latency (cache warm) must be under 1 ms.

Alternatives considered

Sidecar evaluation service. A separate process (e.g., a small Go binary) that all application processes query over a Unix socket or loopback. Avoids duplicating evaluation logic across languages. Rejected because it adds a mandatory network hop (even loopback) and a new process lifecycle dependency, violating the constraint that evaluation must not add latency to the request path.

Shared evaluation logic via gRPC in-process plugin. Compile the engine once and call via gRPC-over-Unix-socket. Rejected for the same latency reason and added build complexity.

Chosen: in-process library duplicated per language, sharing a test suite via a JSON fixture file. Both language implementations are validated against the same golden-file test cases so behavioral divergence is caught in CI. Implementation cost is two smaller libraries rather than one complex service.

Recommendations

  • Use murmurhash3(userId + ":" + flagSalt) mod 100 for percentage bucketing. Document the exact algorithm in a spec file so future SDKs (including the HTTP endpoint) can match it exactly.
  • Rule ordering: rules evaluate top-to-bottom; first match wins; default value is the fallback. Store rule order as an integer priority field on each rule object in the JSONB array.
  • Environment inheritance: if no override exists for the current environment, fall back to the production environment's rules. Make the fallback chain configurable but default to production → default.
  • Telemetry: emit a structured event with fields flag_key, variant, context_hash (not raw user ID), rule_matched, latency_us. Sample at 10% by default; make the rate configurable via a system flag.

Open questions

What telemetry sink should evaluation events flow into — the existing event bus, a direct database write, or a fire-and-forget HTTP POST to the internal analytics service? The choice affects backpressure behavior when the sink is slow.

Should the HTTP evaluation endpoint support batch evaluation (multiple flag keys per request) to reduce round trips for non-native callers, or is single-flag evaluation sufficient at launch?

Write the evaluation spec and golden-file test suite

Before any code, write a language-agnostic spec document (Markdown + JSON fixture files) that defines: boolean evaluation, percentage bucketing (with known input/output pairs for the chosen hash function), rule ordering, multivariate selection, environment inheritance fallback, and default-value fallback. Both language implementations will run against the same fixture files; CI fails if either diverges.

Implement evaluation engine in Language A

Build evaluate(flagKey, context): variant in Language A. Context shape: { userId, orgId, environment, customAttributes }. Engine reads from the Phase 1 cache (no Postgres calls on hot path). Passes all golden-file fixtures. Includes benchmark test asserting p99 < 1 ms on a warm cache with 1 000 active flags.

Implement evaluation engine in Language B

Mirror of t2.2 for Language B. Both implementations share the same golden-file fixtures. A CI job runs both test suites on every pull request touching either implementation or the spec.

Wire push-invalidation from the database to the in-process cache

When any flag row is written, the application server that performed the write should notify all in-process caches to refresh immediately (rather than waiting for the poll interval). Implement via a lightweight in-process pub/sub or a Postgres LISTEN/NOTIFY channel. Falls back gracefully to poll-interval refresh if the notification channel is unavailable.

JSON-over-HTTP evaluation endpoint

Add POST /internal/flags/evaluate and (optionally) POST /internal/flags/evaluate-batch behind the existing auth middleware. Request body: { flagKey, context }. Response: { variant, ruleMatched, flagType }. The handler calls the Language A engine directly; no separate evaluation service. Document the endpoint in the internal API reference.

Telemetry event emission

In both language engines, after each evaluation, emit a sampled structured event to the agreed sink (see open question q3). Event schema: flag_key, variant, context_hash, rule_matched, latency_us, environment, timestamp. Sampling rate is read from the evaluation_telemetry_sample_rate system flag so it can be adjusted without a deploy. Emission must be non-blocking (fire-and-forget from the caller's perspective).

Phase 3: Admin UI (weeks 5–6)

Build the dashboard page that product, support, and engineering use to manage flags day-to-day. The UI is the operational surface; correctness of the evaluation engine is already established. Phase 3 ends when all RBAC rules are enforced, the audit history view is live, and a support engineer can disable a production flag without developer assistance.

Phase goal

Deliver a dashboard (integrated into the existing admin application) that allows authorized users to create, edit, search, and archive flags; set per-environment overrides; use a percentage-rollout slider with live bucketing preview showing how many of a sample user set would receive each variant; view the full audit history for any flag; and enforce role-based access so only flag owners and admins can modify production values.

Alternatives considered

Separate standalone admin app. A dedicated single-page app with its own auth. Rejected because it duplicates the existing admin application's auth and navigation shell, and adds a new deployment unit for a three-engineer team already constrained on time.

CLI-only management (no UI). Flags managed via a command-line tool; no dashboard. Rejected because support engineers need a no-code path to disable a flag quickly, and product managers need the rollout slider to set percentages without engineering involvement.

Chosen: page within the existing admin application. Inherits auth, navigation, and deployment; ships faster; lower ongoing maintenance surface.

Recommendations

  • The percentage-rollout slider should show a live deterministic preview: given the current slider value, display how many of a synthetic 1 000-user sample would receive each variant. This uses the same bucketing hash as the engine so the preview is exact, not approximate.
  • Scope RBAC at the API layer, not just the UI layer. The backend must reject write requests from non-owners/non-admins even if the UI hides the controls, so that API clients respect the same rules.
  • The audit history view should be paginated and filterable by actor, action, and date range. Deep-link each audit entry to the flag detail page at the state it was in at that point in time (read-only snapshot view).
  • Use optimistic UI updates on toggle/slider changes with a visible rollback if the server returns an error, to keep the support "kill switch" flow snappy.

Open questions

Should the percentage-rollout slider show a preview based on a synthetic random sample or based on actual user IDs from the database? The latter is more accurate but requires a user-count query and raises privacy considerations for the audit log preview.

Who can grant and revoke the "flag admin" role — only superadmins, or can team leads self-serve? This determines how onerous the RBAC model is in practice and whether a separate admin-management UI is needed at launch.

Flag list and search page

Add a /admin/flags route to the existing admin application. The page renders a searchable, filterable table of all flags (key, type, state, owner, last-modified). Search is client-side for up to ~500 flags; falls back to a debounced server query beyond that. Columns are sortable. Archived flags are hidden by default behind a toggle. Each row links to the flag detail page.

Flag create and edit form with RBAC enforcement

Build the create/edit form for a flag: fields for key (slug-validated, immutable after creation), description, owner, type, default value, and targeting rules (dynamic rule builder for user ID list, org list, and environment). On submit, the backend sets the session-local actor variable before writing so the audit trigger records the correct user. The backend rejects edits to production values from non-owners and non-admins with a 403 and a human-readable error. The UI disables the production override fields and shows a tooltip explaining the restriction.

Per-environment override panel and percentage-rollout slider

On the flag detail page, add a per-environment section showing the effective rules for each environment (production, staging, development). Each environment has an override toggle; enabling it reveals an editor for that environment's rules. For percentage-rollout flags, render a slider (0–100%) with a live bucketing preview panel that shows the variant distribution across a 1 000-user synthetic sample using the same hash algorithm as the evaluation engine. Changes are saved per-environment and recorded in the audit log.

Audit history view

Add an audit history tab on the flag detail page. Fetches from GET /admin/flags/:key/audit (paginated, newest-first). Each entry shows: timestamp, actor, action, and a before/after diff rendered as a two-column JSON diff. Filterable by actor and date range. Deep-links are shareable (query params preserve filter state). Read-only; no actions available from this view.

Archive and kill-switch flow

Add an "Archive flag" action (requires owner or admin role) that sets state = 'archived' and records the audit entry. Archived flags are immediately excluded from the active cache on next refresh (or on push-invalidation). Also add a prominent "Disable in production" shortcut button on the flag detail page that sets the production override to the flag's off/false/0% variant in one click, with a confirmation modal. This is the support kill-switch flow; it must complete in under two UI interactions and under 30 seconds end-to-end.

Store flags in primary Postgres, not a config file or external service

Config files in the repo require a deploy to change any value, which breaks the "kill without a deploy" requirement. External SaaS (LaunchDarkly, Split) is explicitly prohibited. A dedicated second database adds operational overhead. Primary Postgres with a read-through in-process cache satisfies all requirements with minimal new infrastructure.

Config-in-repo provides a free git-based audit trail and is trivially reversible (revert the commit). Postgres requires explicit audit infrastructure and a migration story. If the team later needs multi-region low-latency flag reads, a separate store would have been the right foundation.

Evaluation engine as in-process library, not sidecar service

The brief explicitly prohibits adding a network hop to the evaluation path. An in-process library is the only architecture that satisfies this constraint. Both backend languages get their own implementation validated against a shared golden-file test suite to prevent behavioral divergence. The JSON-over-HTTP endpoint is a secondary path for non-native callers and is not on the hot path.

A sidecar service would centralize evaluation logic (one implementation instead of two) and make it easier to update the algorithm without touching application code. The network latency cost (even loopback) is the sole reason this was rejected; revisit if the monorepo acquires a third language.

Use murmurhash3(userId + ":" + flagSalt) mod 100 for percentage bucketing

Deterministic bucketing requires a stable, fast, well-distributed hash. MurmurHash3 is non-cryptographic (fast), has excellent distribution for short string keys, and has implementations in every major language. Including a per-flag salt ensures that a user who falls in the bottom 10% of one flag does not automatically fall in the bottom 10% of all flags (which would create correlated exposure across experiments). The algorithm is documented in a spec file so any future SDK (including the HTTP endpoint) produces identical bucketing.

FNV-1a or xxHash would also work. SHA-256 mod 100 is cryptographically stronger but ~10× slower and overkill for feature-flag bucketing.

Evaluation engine behavioral divergence between the two language implementations

If Language A and Language B produce different results for the same input (e.g., different hash output, different rule-ordering semantics), users will receive inconsistent variants depending on which service handles their request. This is particularly dangerous for percentage rollouts where inconsistency breaks the determinism guarantee.

Mitigation: Golden-file test suite (task t2.1) shared between both implementations and run in CI on every relevant PR. Any divergence is a CI failure. The spec document pins the exact hash algorithm, inputs, and expected outputs for a set of known test vectors.

Stale cache serves wrong variant during flag changes

The in-process cache has a poll interval (default 10 s). During the window between a flag change and cache refresh, different application instances may serve different variants. For a "kill switch" scenario, up to 10 seconds of continued wrong behavior is acceptable but must be documented and understood.

Mitigation: Push-invalidation via Postgres LISTEN/NOTIFY (task t2.4) reduces the window to milliseconds for the instance that performed the write. Other instances still rely on polling, but the poll interval is configurable and can be lowered for critical flags. The support kill-switch UI (task t3.5) documents the expected propagation delay.

Telemetry emission adds latency to the evaluation hot path

If telemetry events are emitted synchronously on the evaluation path, slow sinks (database write, HTTP POST) will inflate evaluation latency and potentially breach the <1 ms p99 target.

Mitigation: Task t2.6 explicitly requires non-blocking (fire-and-forget) emission. The telemetry sink is chosen to support backpressure (see open question q3). A benchmark test in t2.2 validates that warm-cache evaluation including telemetry stays under 1 ms p99.

RBAC bypass via direct API calls to the evaluation or write endpoints

If role checks are only enforced in the UI layer, a user with a valid session token could call the write API directly and modify production flags they do not own.

Mitigation: Task t3.2 explicitly requires backend enforcement of RBAC (403 rejection independent of UI state). Security review should include a test of direct API write calls from a non-owner session.

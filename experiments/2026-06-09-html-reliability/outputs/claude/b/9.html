Feature-flag system

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases over roughly six weeks with a team of three engineers: flag schema and storage, evaluation engine, and admin UI.

Success criteria

  • Any engineer can create a flag, target it to a subset of users or orgs, and have it evaluated within one minute of saving — no deploy required.
  • The evaluation path adds zero extra network hops to request handling: evaluate() resolves entirely from a local in-memory cache, with p99 latency under 1 ms.
  • Percentage-rollout bucketing is deterministic: the same user always gets the same variant for the same flag, across all services and restarts.
  • Every flag change is recorded in an immutable audit log showing who changed what and when.
  • The admin UI lets a non-engineer (support, product) toggle or kill a flag in production without engineering involvement.
  • All three flag types (boolean, percentage rollout, multivariate) are usable from both backend languages in the monorepo and from any HTTP client.
  • Evaluation events are sampled and stored, enabling downstream analysis of flag exposure.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state.
  • feature_flags Postgres table, migrations, and seed data.
  • Read-through in-process cache with push-or-poll invalidation.
  • Audit history table for flag changes.
  • Typed accessor library for the two monorepo backend languages.
  • JSON-over-HTTP evaluation endpoint for other callers.
  • Deterministic bucketing (HMAC/hash of user ID + flag salt).
  • Environment inheritance (staging defaults from production).
  • Admin dashboard: create, edit, search, archive flags; per-environment overrides; percentage slider with live bucketing preview; audit-history view.
  • Role-based access: only flag owners and admins may edit production values.
  • Sampled evaluation telemetry events.

Out of scope

  • A/B-test statistical analysis.
  • Scheduled or time-based rollouts.
  • Mobile SDKs.
  • Full approval / change-request workflow (audit log is in scope; approval gates are not).
  • New external SaaS flag services (LaunchDarkly, Statsig, etc.).

Constraints

  • No new external SaaS dependencies. The entire system must be self-hosted within existing infrastructure.
  • No extra network hop on the evaluation hot path. The SDK must resolve flags from an in-process cache; remote reads are only for cache refreshes.
  • Everything behind the existing auth middleware. No new auth surface; admin UI and HTTP endpoint both use existing session/token checks.
  • Team size: 3 engineers; timeline: ~6 weeks. Scope decisions must account for this.
  • Postgres is the system of record. The primary DB already exists; no new databases are to be introduced.
  • Backward compatibility. Adding the flag system must not require changes to existing callers before they are ready to adopt it.

Assumptions

The existing primary Postgres instance has sufficient read capacity to serve flag data. A read-through cache means the DB is only hit on cache misses and on background refresh intervals, so the incremental load is low.

Both monorepo backend languages support a common HMAC-SHA256 (or equivalent) hashing primitive, enabling the same deterministic bucketing algorithm to be implemented identically in each SDK without third-party libraries.

A cache TTL of 30 seconds (with an optional server-sent-event or webhook push channel for faster invalidation) is acceptable propagation latency for flag changes. Near-real-time is desirable but hard <1 s is not required.

The admin UI can be added as a new route in the existing monorepo frontend without standing up a separate application, keeping the delivery within the six-week window.

Phase 1: Flag schema and storage

Define the canonical flag model, create the Postgres tables, write the migrations and seed data, build the read-through cache layer, and deliver the typed accessor library for both backend languages. Audit history is part of this phase. At the end of Phase 1, engineers can persist flags and read them programmatically; no evaluation logic or UI is required yet.

Phase goal

Deliver a durable, well-typed, cache-backed storage layer for feature flags. Any service in the monorepo can call getFlag(key) and receive the raw flag record (not yet evaluated against a context). Migrations are reviewed and merged; the audit table records every write; seed data covers the three flag types so the rest of the team can begin developing against real records.

Alternatives considered

Config file in repo (YAML/JSON checked in to git). Pros: zero infra, trivially auditable via git log, no migration complexity. Cons: changing a flag requires a commit and deploy; cannot support runtime targeting rules or percentage rollouts without a deploy; no support for per-environment overrides without branching strategy hacks. Rejected because the primary use case is runtime control without a deploy.

Separate key-value store (Redis as primary). Pros: very fast reads. Cons: Redis is not a system of record and lacks relational integrity, audit-log FK constraints, and structured querying. Rejected; Redis is retained only as a potential secondary cache layer, not the primary store.

Postgres (chosen). The primary DB already exists, supports JSONB for flexible targeting rules, has FK constraints for audit history, and is already backed up and monitored. A read-through in-process cache eliminates hot-path latency.

Recommendations

Use Postgres as the sole system of record with a feature_flags table and a feature_flag_audit_log table. Store targeting rules as a JSONB column with a versioned schema (v1) so rule types can be extended without a migration. Use a monotonically incrementing version integer on the flags table to drive cache invalidation efficiently (poll for max(version) rather than fetching all rows).

Open questions

Should environment be a first-class column on the flags table, or should it be modelled as a targeting rule? First-class is simpler to query; a targeting rule is more flexible. Decision affects schema before migrations are written.

What is the appropriate cache TTL and refresh strategy — pure TTL polling, long-poll, or server-sent events? The answer affects what infrastructure components are needed in Phase 1 vs Phase 2.

Design and write the flag schema migration

Create the feature_flags table with columns: id (UUID PK), key (unique text), description, owner (FK to users), flag_type (enum: boolean / percentage / multivariate), default_value (JSONB), targeting_rules (JSONB, versioned), lifecycle_state (enum: active / archived), version (integer, incremented on every update), created_at, updated_at. Write a reversible migration. Peer-review schema before applying to any shared environment.

Write the audit-log migration

Create feature_flag_audit_log with columns: id, flag_id (FK), changed_by (FK to users), changed_at, old_value (JSONB snapshot of the full row), new_value (JSONB snapshot), change_type (enum: created / updated / archived). All writes to feature_flags must go through a service layer that also appends a row here; direct DB writes bypass the log.

Write seed data covering all three flag types

Provide at least one seed flag for each type (boolean, percentage rollout at 20%, and multivariate with three variants). Seed data should cover both active and archived lifecycle states. Seeds are only loaded in development and CI, never in production.

Implement the flag repository / service layer

A thin service layer that wraps all DB reads and writes. Writes: createFlag, updateFlag, archiveFlag — each must append an audit row in the same transaction. Reads: getFlag(key), listFlags(filters). This layer is the only place allowed to touch the feature_flags table directly.

Build the read-through in-process cache

Implement an in-process cache (simple map + TTL) that is populated on first read and refreshed in the background. The cache polls SELECT max(version) FROM feature_flags every 30 s; if the version advanced, it re-fetches all active flags. Expose a forceRefresh() method for tests. The cache must be safe for concurrent reads from multiple goroutines/threads.

Deliver typed accessor libraries for both backend languages

Wrap the cache + service layer in a thin, idiomatic library for each backend language in the monorepo. Expose at minimum: getFlag(key) -> FlagRecord | null and listActiveFlags() -> FlagRecord[]. Include unit tests using the seed data. Document the public API surface with inline doc-comments.

Phase 2: Evaluation engine

Build the evaluation library that answers evaluate(flagKey, context) -> variant using the cache populated in Phase 1. Covers deterministic bucketing, rule-ordering semantics, environment inheritance, and sampled telemetry. Also delivers the JSON-over-HTTP endpoint for callers that cannot embed the native SDK.

Phase goal

Any service in the monorepo can call evaluate(flagKey, {userId, orgId, environment}) and receive the correct variant in under 1 ms at p99, with no network call on the hot path. Percentage rollouts are deterministic across restarts and services. Evaluation events are sampled (1-in-N, configurable) and emitted to the telemetry pipeline. An HTTP endpoint at /internal/flags/evaluate lets other languages use the same logic over the network.

Alternatives considered

Sidecar microservice for evaluation. Each app makes a local socket call to a sidecar. Pros: language-agnostic, single implementation. Cons: adds an IPC hop to every flag evaluation, complicates deployment (every pod needs a sidecar), and raises operational complexity. Rejected as violating the no-extra-network-hop constraint on the hot path.

Native SDK per language (chosen). Implement the evaluator once in a shared algorithm spec (documented), then implement it in each backend language. The shared spec and a cross-language test suite (golden files) ensure consistency. The HTTP endpoint is a thin wrapper around the primary-language SDK for callers that cannot link a native library.

Re-evaluate from DB on every call. Simplest code path; no cache needed. Rejected because a DB round-trip on every flag check would add 5–50 ms per call and collapse under load.

Recommendations

Specify the bucketing algorithm in a language-neutral document first (HMAC-SHA256 of userId + ":" + flagSalt, modulo 10 000, compared against the rollout threshold expressed as basis points). Use this spec to drive cross-language golden-file tests before writing production SDK code. Rule ordering: targeting rules are evaluated top-to-bottom; first match wins; if no rule matches, the default value is returned. Environment inheritance: if a flag has no explicit rule for the current environment, look up the parent environment chain (staging → production) before falling back to the global default.

Open questions

What is the telemetry sampling rate and destination? A fixed 1-in-100 ratio written to an existing events table, or a configurable rate sent to the streaming pipeline? The answer affects how telemetry is implemented and whether additional infra is needed.

Should the HTTP evaluation endpoint support batch evaluation (evaluate N flags in one request) for client-heavy callers, or is single-flag-per-request sufficient for v1?

Write the evaluation algorithm spec and golden-file test suite

Before any SDK code, document the evaluation algorithm: rule ordering, bucketing formula (HMAC-SHA256, basis-point threshold), environment inheritance chain, and multivariate variant selection. Produce a JSON golden-file corpus (flag config + context input + expected variant output) covering edge cases: no matching rule, boundary percentages (0 %, 100 %, 50 % ± 1 bp), environment fallthrough, archived flag. Both SDK implementations must pass all golden-file tests.

Implement the evaluation engine in backend language A

Implement evaluate(flagKey, context) -> variant following the spec from t2.1. Reads from the in-process cache built in Phase 1. Must pass all golden-file tests. Expose the public API: evaluate, evaluateBool (convenience wrapper), and evaluateWithDetails (returns variant + matched-rule metadata for debugging).

Implement the evaluation engine in backend language B

Port the same algorithm to the second backend language. Must pass the same golden-file test suite. Where the languages have different HMAC libraries, verify byte-for-byte identical output on a shared test vector before merging.

Add sampled telemetry emission

After every successful evaluation, with probability 1/samplingRate (default 100, configurable), emit an evaluation event to the telemetry pipeline. Event payload: flag key, variant returned, context hash (no PII), timestamp, environment. Telemetry must be fire-and-forget (non-blocking) and must not affect the p99 latency of evaluate().

Build the JSON-over-HTTP evaluation endpoint

Expose POST /internal/flags/evaluate behind the existing auth middleware. Request body: {flagKey, context}. Response: {variant, details}. The handler calls the language-A SDK internally; it is not a re-implementation of the algorithm. Rate-limit the endpoint to prevent it being used as a cheap bulk-evaluation path (use the existing rate-limiter middleware).

Phase 3: Admin UI

Deliver the web dashboard that lets engineers, product managers, and support staff manage flags through a UI rather than direct DB or API calls. Covers flag CRUD, per-environment overrides, the percentage slider with live bucketing preview, audit-history view, and RBAC.

Phase goal

A non-engineer can open the admin dashboard, find a flag by name or owner, toggle its default value for a specific environment, set a percentage rollout, and see who last changed it — all without engineering help. Flag owners and admins can edit production; other authenticated users have read-only access. The UI is a route in the existing frontend, behind the existing auth middleware.

Alternatives considered

Standalone admin SPA (separate deploy). Clean separation of concerns. Rejected because it requires a new deploy target, a new auth surface, and additional operational overhead that exceeds the six-week budget.

CLI / direct DB tooling for admin operations. Fastest to build; no UI work needed. Rejected because support staff cannot safely use the DB CLI, and the brief explicitly calls for a UI that support can use to kill a feature without a deploy.

New route in existing frontend (chosen). Reuses auth, routing, component library, and deployment pipeline. Acceptable scope for the remaining time after Phases 1 and 2.

Recommendations

Build the admin UI as a single new route group (/admin/flags) in the existing frontend. Use the existing component library for forms, tables, and modals. The percentage-rollout slider should show a live preview by running the bucketing hash client-side (the algorithm is pure JS — no server round-trip needed for preview). RBAC enforcement happens in the API layer (Phase 1 service layer); the UI reflects permissions by disabling edit controls for users without the required role, but does not rely solely on UI gating.

Open questions

Which existing roles map to "flag owner" and "flag admin" in the RBAC model? Do we introduce new permission strings or reuse existing admin/superuser roles? Needs product and security sign-off before the UI gating is built.

Should the percentage-slider live preview show a sample of real user IDs from the DB (showing who would be bucketed in at the current percentage), or a synthetic random sample? Real user IDs are more useful but raise a privacy question about exposing user IDs in the admin UI.

Build the flag list and search page

A paginated table of all flags showing key, type, lifecycle state, owner, and last-modified date. Supports filter by owner, type, and lifecycle state; full-text search on key and description. Clicking a row opens the flag detail/edit view. Archived flags are hidden by default but can be shown via a toggle.

Build the flag create and edit form

Form fields: key (unique, immutable after creation), description, owner, flag type, default value, lifecycle state. Flag type selection dynamically shows the appropriate value input (boolean toggle, percentage slider, or multivariate variant list). Saving calls the service-layer API from Phase 1; the API enforces RBAC. Validation errors are shown inline.

Build per-environment override management

On the flag detail page, show a tab or accordion section listing each environment (production, staging, development) with its current effective value and whether it is overriding the default. Allow flag owners and admins to set or clear an override for any environment. Environment inheritance (staging falls through to production if no override is set) should be visible in the UI ("inheriting from production").

Build the percentage-rollout slider with live bucketing preview

For percentage-rollout flags, replace the default-value input with a slider (0–100 %). As the slider moves, show a live preview: the client-side bucketing algorithm (ported to JS) computes which of a fixed set of synthetic user IDs would be in the treatment group at the current percentage, and renders this as a simple count ("~20 of 100 sample users"). This runs entirely in the browser with no extra API call.

Build the audit-history view

On the flag detail page, a chronological list of all changes to that flag, sourced from the feature_flag_audit_log table. Each entry shows: who made the change, when, and a diff of the old vs new value (rendered as a side-by-side JSONB diff or human-readable field-level summary). Paginated; most recent first.

Enforce RBAC: production-edit gating

Gate all production-value edits (including production environment overrides) to flag owners and users with the admin role. In the UI, show edit controls as disabled with a tooltip ("you are not the owner or an admin") for users without permission. Enforcement is also in the API layer (the service layer checks the calling user's role before applying any write). Add integration tests covering the unauthorized-edit rejection path.

Postgres as the system of record; no new external SaaS

The feature-flag data will live in the existing primary Postgres instance rather than in a dedicated SaaS (LaunchDarkly, Statsig, etc.) or a separate data store. An in-process read-through cache eliminates the hot-path read cost. This keeps the system entirely within existing infrastructure, satisfies the no-new-external-SaaS constraint, and keeps operational complexity inside the team's existing skill set.

A managed SaaS flag service would reduce engineering effort for the evaluation engine and admin UI, but introduces an external dependency that violates the stated constraint and creates a potential outage vector outside our control.

Native SDK per backend language + HTTP endpoint for others; no sidecar

The evaluation engine is implemented as a native library for each of the two monorepo backend languages, backed by an in-process cache. A JSON-over-HTTP endpoint serves callers that cannot link a native library. A sidecar service was considered and rejected: it would add an IPC hop to every flag evaluation, violating the no-extra-network-hop constraint, and would increase deployment complexity for all services that need flag evaluation.

A sidecar provides a single implementation of the algorithm and is language-agnostic, reducing the risk of cross-language divergence. That risk is mitigated instead by the golden-file test suite.

Deterministic bucketing via HMAC-SHA256 of userId + flagSalt

Percentage rollouts use HMAC-SHA256(userId + ":" + flagSalt) modulo 10 000 as the bucketing value, compared against the rollout threshold expressed in basis points. Using a per-flag salt ensures that a user in the 20 % bucket for flag A is not automatically in the 20 % bucket for flag B, reducing correlation artifacts in multi-flag analysis. HMAC-SHA256 is available natively in all target languages.

A simpler CRC32 or FNV hash would be faster and easier to implement, but HMAC provides better distribution properties and the performance difference is negligible for this use case.

Cache staleness causes a misbehaving feature to stay live after an emergency kill

If the in-process cache has a 30-second TTL and an operator toggles a flag off in the admin UI, the flag may continue evaluating as "on" for up to 30 seconds across all running instances. Mitigation: provide a forceRefresh() API that can be called via the HTTP admin endpoint (POST /internal/flags/refresh) to immediately invalidate the cache on a specific host, or implement a lightweight pub/sub push channel (e.g., Postgres LISTEN/NOTIFY) to push invalidations within <1 s. If a faster kill is required before the push channel is built, document the procedure (rolling restart flushes all caches).

Cross-language SDK divergence produces different variants for the same user

If the two backend SDKs implement the bucketing algorithm slightly differently (e.g., different byte encodings for the HMAC input, different integer overflow behavior), the same user could receive different variants from different services, causing inconsistent experiences. Mitigation: the golden-file test suite (task t2.1) must include test vectors covering boundary conditions and must be run in CI for both SDKs. Any divergence fails the build before merge.

Postgres read load spike if cache warm-up is not staggered at deploy

If all instances restart simultaneously (e.g., a rolling deploy that briefly redeploys all pods), they may all attempt to re-populate their caches at the same time, producing a thundering-herd read spike against Postgres. Mitigation: add jitter (±5 s) to the initial cache-load delay, and ensure the Postgres connection pool is sized for this scenario. Monitor query latency during the first post-Phase-1 deploy.

Six-week timeline is tight for three phases with a three-engineer team

Phase 1 (schema + cache) is roughly 2 weeks; Phase 2 (evaluation engine with two SDKs) is roughly 2 weeks; Phase 3 (admin UI) is roughly 2 weeks. Any scope creep, blocking dependency, or unplanned incident could push Phase 3 out. Mitigation: scope Phase 3 to the minimum viable dashboard (list, edit, audit log, RBAC). The percentage-slider live preview (t3.4) is the first task to cut if time is short, since a numeric input field is a valid fallback.

Feature-flag system

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can disable a misbehaving feature without a deploy. Three phases over six weeks: flag schema and storage, a sub-millisecond evaluation engine, and an admin dashboard with RBAC. No new external SaaS dependencies; evaluation must stay in-process.

Success criteria

  • Any engineer can create a flag, target it by user ID / org / environment, and toggle it without a deploy.
  • Flag evaluation at p99 < 1 ms measured in-process (no extra network hop on the hot request path).
  • The evaluation engine SDK ships for both backend languages in the monorepo; a JSON-over-HTTP fallback exists for other callers.
  • Every flag change is captured in an immutable audit log with actor, timestamp, before-state, and after-state.
  • The admin UI enforces RBAC: only the flag owner and admins can edit production values.
  • A percentage-rollout flag correctly buckets the same user ID to the same variant on repeated calls (deterministic hashing).
  • All three phases delivered within six weeks by a team of three engineers, with no new external SaaS services introduced.

Scope

In scope

  • Flag model: key, description, owner, type (boolean / percentage-rollout / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state (active / archived).
  • Postgres feature_flags table + migrations + seed data.
  • Read-through in-memory cache with push-or-poll invalidation.
  • Typed accessor library for both monorepo backend languages.
  • Audit history table for all flag mutations.
  • Evaluation engine: deterministic bucketing, rule ordering, environment inheritance (staging defaults from production).
  • Sampled evaluation telemetry events.
  • JSON-over-HTTP evaluation endpoint for non-native callers.
  • Admin dashboard: create / edit / search / archive flags, per-environment overrides, percentage-rollout slider with live bucketing preview, audit-history view, RBAC.

Out of scope

  • A/B-test statistical analysis.
  • Scheduled / time-gated rollouts.
  • Mobile SDKs.
  • Full approval workflow (approvals, change-request gates).
  • Any new external SaaS flag service (e.g. LaunchDarkly, Unleash cloud).

Constraints

  • No new external SaaS dependencies. All components must run inside the existing infrastructure.
  • Evaluation must not add a network hop. The evaluation library runs in-process; the HTTP endpoint is a convenience wrapper for non-native callers, not the primary path.
  • Everything behind existing auth middleware. No new auth surface; admin UI and HTTP endpoint reuse the current session/JWT stack.
  • Team size: three engineers, approximately six weeks calendar time.
  • p99 evaluation latency target: under 1 ms (served from in-memory cache).
  • Audit log is append-only. Flag changes may never silently overwrite history.

Assumptions

The monorepo has exactly two backend languages requiring a native typed accessor; all other callers are comfortable with the JSON-over-HTTP endpoint.

Postgres is an acceptable source-of-truth for flag definitions. Read volume to the database is low because the evaluation engine caches the full flag set in memory and only polls/receives push invalidations.

A simple audit log (who changed what and when) satisfies compliance requirements for this feature. A full approval workflow with mandatory sign-offs is explicitly deferred.

The existing auth middleware already makes user ID, org ID, and environment available on the request context, so the evaluation engine can consume them without additional middleware work.

Phase 1: Flag schema and storage

Establish the canonical data model for feature flags, the Postgres tables that store them, the audit trail, and the typed accessor library that the rest of the system will build on. This phase produces no user-visible UI but delivers the foundation every later phase depends on.

Phase goal

Deliver a stable, migrated database schema for feature flags and flag change history; a seed script with representative flag fixtures; and a typed accessor library (one module per backend language) that reads, writes, and validates flag records. At the end of Phase 1 an engineer can create, update, and archive a flag programmatically with a full audit trail, but there is no evaluation logic or UI yet.

Alternatives considered

Config-file-in-repo approach (YAML/JSON checked in to git): Low ops cost and easy to review via PRs, but cannot support runtime changes without a deploy, cannot store per-environment overrides that differ between prod and staging at runtime, and makes percentage-rollout targeting awkward. Rejected because the brief explicitly requires "kill a feature without a deploy."

Separate dedicated flag database (e.g. Redis as primary store): Lower read latency for raw lookups, but introduces a new persistence dependency, complicates migrations, and makes audit history harder to query relationally. Rejected in favour of Postgres + in-memory cache (cache handles the latency requirement; Postgres gives us SQL for audits and targeting rules).

Single flat flags table with JSON blob for rules: Simpler migration, but makes querying and indexing targeting rules difficult and breaks strong typing in the accessor library. Chosen approach uses a normalised schema with a flag_rules child table instead.

Recommendations

  • Use a feature_flags table for flag metadata and a flag_rules table for targeting rules (one row per rule, ordered by priority integer). This keeps the core record small and makes rule management straightforward.
  • Use a separate flag_audit_log table (append-only, no deletes) with a JSONB column for before/after snapshots. A Postgres trigger is the simplest enforcement mechanism.
  • The accessor library should expose a thin repository interface (getFlag, listFlags, upsertFlag, archiveFlag) so Phase 2 and Phase 3 never touch SQL directly.

Open questions

Should multivariate flag variants be stored as an ordered JSON array in the flags row, or in a separate flag_variants table? The latter is more relational but adds a join on every flag read.

What is the maximum expected number of flags in production at steady state? This affects whether we can safely load all active flags into memory on startup or need a partial/lazy load strategy.

Design and write the database migration

Create migration files for feature_flags, flag_rules, and flag_audit_log. The feature_flags table includes: id (UUID PK), key (unique text), description, owner (FK to users), flag_type (enum: boolean / percentage_rollout / multivariate), default_value (JSONB), lifecycle_state (enum: active / archived), created_at, updated_at. The flag_rules table includes: id, flag_id (FK), priority (integer), dimension (user_id / org_id / environment), operator (in / not_in / eq), values (JSONB array), variant (JSONB). The flag_audit_log is append-only with actor, action, before/after JSONB snapshots, and a timestamp. Include down-migration scripts.

Add Postgres trigger for audit logging

Write a BEFORE UPDATE and BEFORE DELETE trigger on feature_flags and flag_rules that inserts a row into flag_audit_log capturing the actor from the session variable app.current_user_id. This enforces audit completeness even if application code bypasses the accessor library. Include a test that verifies audit rows are created on direct SQL mutations.

Write seed data and fixtures

Create a seed script with at least one flag of each type (boolean, percentage rollout, multivariate), covering multiple environments and targeting dimensions. Seed data should be idempotent (upsert on key) so it can be re-run in CI and local dev without duplicating rows. Include at least one archived flag to exercise that lifecycle state.

Implement typed accessor library (Language A)

Build the repository module for the first backend language. Expose getFlag(key), listFlags({lifecycle_state?, owner?}), upsertFlag(payload), and archiveFlag(key). All write operations must set the Postgres session variable app.current_user_id before executing so the audit trigger captures the actor. Include unit tests with a test-database fixture and integration tests that verify audit rows are written.

Implement typed accessor library (Language B)

Port the same repository interface to the second backend language in the monorepo. Share the same contract (method signatures, error types) as Language A's library so Phase 2 can implement a single evaluation engine design against a consistent API regardless of language. Tests mirror those for Language A.

Phase 2: Evaluation engine

Build the sub-millisecond evaluation core: in-memory cache, rule matching, deterministic bucketing for percentage rollouts, environment inheritance, and the telemetry pipeline. Also deliver the JSON-over-HTTP endpoint for non-native callers.

Phase goal

Deliver an evaluation library (in both monorepo languages) that answers evaluate(flagKey, context) → variant entirely from an in-memory snapshot, with p99 latency under 1 ms. The snapshot refreshes from Postgres via a configurable poll interval and optionally via push invalidation. Every evaluation emits a sampled telemetry event. A thin HTTP handler wraps the same logic for non-native callers. At the end of Phase 2, application code can gate features behind flags in production.

Alternatives considered

Sidecar service (separate process) for evaluation: Isolates the flag engine from application processes and allows independent scaling. However, it adds a network hop on the hot path, which violates the stated constraint. Ruled out for the primary evaluation path; the JSON-over-HTTP endpoint fulfils the sidecar-like need for non-native callers without penalising the main path.

Push-only invalidation (Postgres LISTEN/NOTIFY): Lower staleness than polling, but LISTEN connections add connection-pool pressure and the feature is not available in all Postgres-compatible managed services. Chosen approach supports both: push via LISTEN/NOTIFY when available, with a poll fallback (configurable interval, default 30 s) so the system degrades gracefully.

Consistent hashing for percentage rollout bucketing: Provides smooth re-distribution when flag salt changes, but adds complexity. A simple murmurhash(userId + flagSalt) % 100 approach is deterministic, fast, and well-understood. Chosen over consistent hashing for simplicity; the salt can be rotated to re-bucket deliberately.

Recommendations

  • Load the full active flag set into an immutable in-memory map on startup. Refreshes replace the whole map atomically (swap pointer) so readers never observe a partial state.
  • Rule evaluation order: iterate flag_rules by ascending priority; return the variant of the first matching rule. If no rule matches, return the flag's default_value.
  • Environment inheritance: if a flag has no rule for the requested environment, fall back to the production environment rules. Make this behaviour opt-in per flag via a inherit_from_env field so teams can opt out.
  • Telemetry: emit a sampled event (1-in-N, configurable) to the existing internal event bus with flag key, variant returned, targeting context (hashed), and latency. Do not emit PII.

Open questions

What is the acceptable staleness window for flag changes to propagate to all running instances? This determines the default poll interval and whether push invalidation via LISTEN/NOTIFY is required for launch or can be a fast-follow.

Should the HTTP evaluation endpoint authenticate via the existing session middleware (cookie/JWT) or via a service-to-service API key? The latter is safer for machine callers but requires key management.

Implement in-memory flag cache with poll refresh

Write a FlagCache class/struct that loads all active flags (with their rules) from the accessor library on startup and refreshes on a configurable interval (default 30 s). The snapshot is stored as an immutable map; refreshes replace the reference atomically. Expose a get(key) method that returns null for unknown keys (so callers can fall back to the default value). Include a manual forceRefresh() method for testing and for the push path.

Implement rule evaluator and deterministic bucketing

Write the core evaluate(flagKey, context) function. Steps: (1) look up the flag in the cache; (2) iterate rules by priority, testing each dimension (user_id in list, org_id in list, environment equals); (3) for percentage-rollout flags, compute murmurhash(context.userId + flag.salt) % 100 and compare against the rule threshold; (4) return the matching variant or the flag's default value. Environment inheritance: if no rules match for context.env and flag.inherit_from_env is true, re-evaluate with context.env = "production". All paths must be covered by unit tests with known hash values pinned in test fixtures.

Add LISTEN/NOTIFY push invalidation (optional fast-follow)

Subscribe to a Postgres channel (e.g. flag_changed) notified by the audit trigger. On receiving a notification, call forceRefresh() immediately rather than waiting for the poll interval. Wrap in a feature flag (bootstrapped boolean, config file) so it can be disabled if LISTEN/NOTIFY is unavailable in the deployment environment. Graceful degradation: if the LISTEN connection drops, log a warning and rely on poll-only mode.

Wire telemetry: sampled evaluation events

After every evaluate() call, sample at a 1-in-N rate (configurable, default 1-in-100) and emit an event to the internal event bus with fields: flag_key, variant, env, latency_us, rule_matched (index or "default"), and a hashed (non-reversible) user identifier. The emit must be non-blocking (fire-and-forget to a channel/queue); evaluation latency must not increase if the event bus is slow.

Expose JSON-over-HTTP evaluation endpoint

Add a route (e.g. POST /internal/flags/evaluate) behind the existing auth middleware. Request body: {"flagKey": "...", "context": {"userId": "...", "orgId": "...", "env": "..."}}. Response: {"variant": ..., "flagType": "..."}. Reuses the same in-process evaluator — no separate code path. Rate-limit to prevent abuse; document the endpoint in the internal API catalogue. Include integration tests.

Phase 3: Admin UI

Build the dashboard that product managers, engineers, and support use to manage flags day-to-day. Includes RBAC enforcement, per-environment overrides, a percentage-rollout slider with live bucketing preview, and an audit-history view.

Phase goal

Deliver a web dashboard (integrated into the existing admin area, behind existing auth) where users can create, edit, search, and archive flags; set per-environment overrides; visualise percentage-rollout bucketing interactively; and browse the full audit history of any flag. Only flag owners and admins can write production values; others can read and can write non-production values. At the end of Phase 3 the system is fully operational without any direct database access.

Alternatives considered

Separate standalone admin app (new frontend service): Full control over stack and deployment, but adds infra overhead and means a new auth integration. Rejected in favour of embedding the dashboard in the existing admin area so it inherits auth, navigation, and deployment for free.

Read-only audit log view only (no full history UI): Faster to ship, but support engineers need to diagnose "who turned this off at 2 am" quickly. A full history view with actor, timestamp, and diff is required to make the system trustworthy for on-call use. Retained in scope.

No RBAC — trust all admin users equally: Simpler, but production flag changes are high-blast-radius; an accidental edit during an outage investigation could make things worse. Role differentiation (owner + admin vs. read-only + staging-write) is a hard requirement from the brief.

Recommendations

  • Build the flag list as a server-rendered page with client-side search/filter to avoid a separate search API. For the scale of flags expected, loading all active flags and filtering in the browser is fast enough.
  • The percentage-rollout slider preview should compute bucket membership client-side using the same murmurhash function compiled to WASM or re-implemented in JS, applied against a sample of representative user IDs shown as a bar chart.
  • Per-environment overrides should be presented as tabs per environment on the flag edit page; each tab shows the default value and rules for that environment, editable independently.
  • The audit-history view should be paginated (server-side) and filterable by actor and date range. Show a human-readable diff (before → after) for each change.

Open questions

Should non-admin users be able to create new flags (and become the owner), or is flag creation restricted to admins? This affects the self-service story for product teams.

Which environments are predefined (e.g. development / staging / production) and are they hard-coded in the UI or configurable per deployment? Affects how per-environment override tabs are rendered.

Flag list and search page

Add a /admin/flags route that lists all flags with columns: key, description, type, owner, lifecycle state, last-modified. Client-side filtering by key substring and owner. Status badge (active / archived) with colour coding. Link each row to the flag detail/edit page. Pagination or virtual scroll for large lists. Accessible table markup; no JS framework dependency beyond what the existing admin area already uses.

Flag create and edit form with RBAC enforcement

Form at /admin/flags/new and /admin/flags/:key/edit for all flag fields. Per-environment tabs for overrides. Server-side RBAC check on save: if the target environment is production, the authenticated user must be the flag owner or have the admin role; otherwise return 403. Display a clear in-form message when edit is blocked. Flag type changes are allowed only when the flag is not active (to prevent silent type coercion in the evaluator).

Percentage-rollout slider with live bucketing preview

On the edit form for a percentage-rollout flag, render a slider (0–100%) alongside a bar chart showing the projected distribution across a sample of 1 000 representative anonymised user IDs stored in the admin frontend (no real user data sent). The bucketing preview recomputes on every slider movement using the same hash algorithm as the server-side evaluator (implement in JS, cross-tested against a known set of server-side fixture values). Show "~N users affected" estimated from the current active user count stored in a periodically-refreshed cache.

Audit-history view

Add a tab on the flag detail page showing the full change history from flag_audit_log. Paginated, server-side, 20 per page. Each entry shows: actor name (resolved from user ID), action (created / updated / archived), timestamp, and a key-by-key diff (before → after) rendered as a two-column table highlighting changed fields. Filterable by actor and by date range (date picker). Export to CSV for audit purposes (streaming response, no buffering full result in memory).

Archive and lifecycle management actions

Add an "Archive flag" action (confirmation modal required) that sets lifecycle_state = 'archived' and disables evaluation (archived flags always return their default value). Add an "Restore" action to move archived flags back to active. Both actions are restricted to flag owners and admins for production flags. Archived flags are hidden from the default list view but accessible via the "Show archived" filter toggle. Ensures the flag namespace stays clean without hard-deleting audit history.

Postgres as primary store with in-memory cache (not a dedicated flag SaaS)

Rationale: the brief prohibits new external SaaS dependencies. Postgres is already in the stack, provides strong consistency, relational querying for audit history, and transactional writes. An in-memory cache (refreshed via poll + optional LISTEN/NOTIFY push) meets the sub-millisecond evaluation latency requirement without any network hop. This trades operational simplicity for the need to maintain the cache invalidation story ourselves, which is acceptable given the small flag set expected.

A dedicated flag service (open-source Unleash self-hosted, Flipt, etc.) would give us SDKs, a UI, and evaluation semantics out of the box, reducing build time. Ruled out because any self-hosted service still constitutes a new infrastructure dependency, and the brief explicitly excludes it.

In-process library for primary evaluation path (not sidecar)

Rationale: the constraint "evaluation must not add a network hop to request handling" rules out a sidecar or remote service for the hot path. The evaluation library runs in the application process, reads from its own in-memory snapshot, and never touches the network during evaluation. The JSON-over-HTTP endpoint is a convenience wrapper for non-native callers (scripts, services in other languages) and is not on the critical path.

A sidecar would allow independent deployment and scaling of the flag engine, and a single cache per host instead of one per process. Rejected because the latency constraint is non-negotiable and the flag dataset is small enough that per-process memory cost is negligible.

Append-only audit log enforced by Postgres trigger

Rationale: audit completeness must be guaranteed even if application code has a bug or someone executes SQL directly. A trigger fires at the database level regardless of the caller, providing a tamper-evident log. Storing before/after snapshots as JSONB makes the log self-contained without joining other tables to reconstruct history.

Application-level audit logging (write the audit row in the accessor library) is simpler to implement and easier to test, but can be bypassed by direct SQL access or a future code path that forgets to call the audit helper. The trigger approach is marginally harder to test but strictly safer.

Cache staleness causes inconsistent flag state across instances

If LISTEN/NOTIFY push invalidation is not implemented for launch and only poll-based refresh is used, a flag change could take up to 30 s to propagate to all running instances. During that window some requests get the old value and some get the new value. Mitigation: (1) make the poll interval configurable and set it low (10 s) for production at launch; (2) prioritise LISTEN/NOTIFY as a fast-follow in Phase 2 task t2.3; (3) document the expected staleness window in the runbook so on-call engineers know to wait before assuming a flag change took effect.

Percentage-rollout hash function divergence between server and UI preview

The admin UI's live bucketing preview (Phase 3, task t3.3) re-implements the hash function in JavaScript. If the JS and server-side implementations diverge (different seed, endianness, or string encoding), the preview will show incorrect bucketing percentages, eroding trust in the tool. Mitigation: write a shared fixture file of (userId, salt, expectedBucket) test vectors and run it against both implementations in CI. Any divergence fails the build before it reaches production.

Flag proliferation without lifecycle hygiene degrades cache performance over time

If flags are never archived, the in-memory snapshot grows indefinitely. With hundreds of stale flags the memory footprint and refresh time increase. Mitigation: (1) the Phase 3 archive action makes it easy to retire flags; (2) add a dashboard metric showing the count of active vs. archived flags; (3) add a CI lint rule that flags (pun intended) any flag key present in code that has been archived for more than 90 days, prompting engineers to clean up the call site.

Six-week timeline is tight for three phases with a team of three

Phase 1 must be complete before Phase 2 can start, and Phase 2 must deliver a stable API before Phase 3 can build on it. Any slip in Phase 1 (e.g. schema design churn, migration issues in staging) cascades. Mitigation: Phase 1 is scoped conservatively (no UI, no evaluation logic) and targeted for completion by end of week 2. Phase 2 runs weeks 3–4. Phase 3 weeks 4–6, with UI work able to begin against a mock evaluator while Phase 2 finalises. If time is short, the LISTEN/NOTIFY push invalidation (t2.3) and the audit CSV export are the first candidates for deferral.

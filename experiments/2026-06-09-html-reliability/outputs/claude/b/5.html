Feature-flag system

Add a first-party feature-flag system so engineering can ship dark, product can run gradual rollouts, and support can kill a misbehaving feature without a deploy. Three phases: flag schema and storage, evaluation engine, and admin UI. Targeted at a team of three over six weeks; no new external SaaS dependencies.

Success criteria

  • Any engineer can create a boolean, percentage-rollout, or multivariate flag, enable it in staging, and promote it to production without a code deploy.
  • Flag evaluation at p99 stays under 1 ms for all flag types, measured from within the same process (no added network hop on the hot path).
  • Percentage rollouts are deterministic: a given user ID always lands in the same bucket for the lifetime of a flag.
  • Disabling a flag via the admin UI takes effect within 30 seconds across all running instances.
  • Every flag mutation is captured in an immutable audit log with actor, timestamp, and before/after diff.
  • The admin UI enforces RBAC: only a flag's owner or a member of the flag-admin role may edit production values.
  • Both backend languages in the monorepo have typed SDK clients; all other callers can use the JSON-over-HTTP fallback endpoint.

Scope

In scope

  • Flag schema: key, description, owner, type (boolean / percentage / multivariate), targeting rules (user ID, org, environment), default value, lifecycle state.
  • Postgres-backed storage with a read-through cache.
  • Database migrations and seed data for standard bootstrap flags.
  • A typed accessor library exposing the flag model to application code.
  • Audit history of all flag changes (who changed what, when, and what it was before).
  • Evaluation engine as an in-process library with a local in-memory cache and push-or-poll invalidation.
  • Deterministic percentage bucketing via hash(userID + flagSalt).
  • Environment inheritance: staging inherits from production defaults unless explicitly overridden.
  • Sampled evaluation telemetry events for later analysis.
  • SDK for the two monorepo backend languages.
  • JSON-over-HTTP evaluation endpoint for non-monorepo callers.
  • Admin dashboard: create, edit, search, archive flags; per-environment overrides; percentage-rollout slider with live bucketing preview; audit-history view; RBAC enforcement.

Out of scope

  • Full approval workflow (draft → review → approve) for flag changes.
  • A/B-test statistical analysis.
  • Scheduled rollouts (time-based flag transitions).
  • Mobile SDKs.
  • Any new external SaaS dependencies (no LaunchDarkly, Split, etc.).

Constraints

  • No new SaaS: the entire system must run on existing infrastructure.
  • No added network hop on the evaluation path: the evaluation engine must run in-process; the HTTP endpoint is a convenience for external callers, not for the monorepo services themselves.
  • Auth middleware: all admin UI and HTTP evaluation endpoints must be gated by the existing auth middleware — no new authn surface.
  • Team size and timeline: three engineers, roughly six weeks; scope must be achievable within that envelope.
  • Evaluation latency: p99 under 1 ms in-process, measured with realistic flag counts (~500 flags).
  • Postgres as primary store: no new databases; the read-through cache must be an existing caching layer (e.g., the app's Redis instance or an in-process LRU).

Assumptions

The monorepo contains exactly two backend languages that need native SDK support. All other callers (scripts, external services) can tolerate the HTTP endpoint's slightly higher latency.

An existing Redis (or equivalent) instance is available in the infrastructure and can serve as the shared read-through cache for flag state, avoiding the need to provision new infrastructure.

A lightweight RBAC model (owner + admin role) is sufficient for production flag changes. A full change-approval workflow is not required now.

The in-memory cache can hold the full flag ruleset (~500 flags at launch, growing to a few thousand) without material memory pressure on application pods.

Phase 1 — Flag schema and storage

Stand up the data model, migrations, and accessor library that everything else builds on. By the end of this phase a developer can define a flag in the database and read it back through a typed API. No evaluation logic yet — just the canonical source of truth.

Phase goal

Deliver a production-ready feature_flags schema in Postgres (plus audit tables), a zero-downtime migration path, seed data covering the initial flag set, and a typed accessor library in both monorepo languages that abstracts all direct DB access. RBAC roles and ownership metadata must be stored but need not be enforced yet — that comes in Phase 3.

Alternatives considered

Config-file-in-repo approach: store flags as YAML/JSON in the repository, evaluated at build or boot time. Simple to audit via git history, zero new infrastructure. Rejected because it requires a deploy to change any flag value, which defeats the primary use-case (kill a misbehaving feature without a deploy).

Dedicated flags microservice with its own database: cleanly isolated, independently deployable. Rejected for the six-week timeline — adds network hop, new service SLO, and new database provisioning. The monolith's Postgres + cache is sufficient and keeps the evaluation path in-process.

Chosen: new table in primary Postgres with a read-through cache. Leverages existing backup, replication, and monitoring. Keeps the schema change reviewable in the standard migration workflow. Cache layer prevents flag reads from adding DB load on the hot path.

Recommendations

Model the flag ruleset as JSONB inside the feature_flags row (targeting rules, variants, rollout percentages) rather than normalizing into child tables. This keeps rule evaluation simple and allows schema evolution without additional migrations. Index on (key, environment) for fast lookups. Store audit rows in a separate append-only feature_flag_audit table populated by a Postgres trigger or application-layer hook — triggers are simpler but application-layer gives richer context (actor identity, request ID).

Open questions

Should audit rows be written by a Postgres trigger (guaranteed, but no actor context beyond DB user) or by the application layer (richer context, but can be skipped on direct DB access)? Decision affects the audit completeness guarantee.

What is the canonical format for the targeting_rules JSONB field? Define a versioned JSON Schema now so the evaluation engine and admin UI parse the same structure, rather than discovering incompatibilities later.

Write and review the flag data model

Produce an RFC-style doc (or ADR) capturing the full column set for feature_flags: id, key (unique), description, owner, flag_type (enum: boolean / percentage / multivariate), environments (JSONB map of environment → config), targeting_rules (JSONB array), default_value, lifecycle_state (enum: active / archived), salt (random string for bucketing), created_at, updated_at. Also define the feature_flag_audit table schema. Get sign-off from at least one other engineer before writing the migration.

Author and run database migrations

Write forward-only migrations (using the project's existing migration tool) to create feature_flags, feature_flag_audit, and any required indexes. Migrations must be backward-compatible so a rollback of application code does not require a schema rollback. Include a down migration that drops the new tables for development convenience, but document that production rollbacks are data-destructive and require a separate runbook.

Write seed data for bootstrap flags

Create a seed script that inserts the initial set of flags needed to test the system end-to-end (e.g., feature-flags-admin-ui boolean flag to gate the admin UI itself). Seeds must be idempotent (upsert on key) so they are safe to re-run in CI and staging.

Build typed accessor library (both monorepo languages)

Implement a thin repository/DAO layer exposing: getFlag(key), listFlags(filters), createFlag(dto), updateFlag(key, patch), archiveFlag(key). All writes must append a row to feature_flag_audit with actor identity. Types/interfaces must be generated from or co-located with the schema definition so they stay in sync. No business logic here — pure storage access.

Write unit and integration tests for the accessor library

Cover: round-trip create/read/update/archive, audit row creation on every mutation, idempotency of seed script, and rejection of invalid flag keys (empty string, duplicate). Integration tests must run against a real Postgres instance (not mocked) to catch constraint violations early.

Phase 2 — Evaluation engine

Build the library that answers evaluate(flagKey, context) → variant at sub-millisecond latency, ships with an in-process cache, and exposes a JSON-over-HTTP fallback endpoint. This phase delivers the runtime path that all product code will ultimately call.

Phase goal

Ship a production-hardened evaluation library in both monorepo languages that: loads the full flag ruleset into memory at startup, refreshes it via push invalidation (or polling fallback) within 30 seconds of any change, evaluates any flag type deterministically in under 1 ms at p99, and emits a sampled telemetry event per evaluation for downstream analysis. Also ship the HTTP endpoint so non-monorepo callers can evaluate flags without embedding SDK logic.

Alternatives considered

Sidecar service (separate process, same host): evaluation runs as a sidecar; application calls it over a Unix socket. Isolates the cache and evaluation logic from the application process. Rejected — adds operational complexity (sidecar lifecycle, socket management), and Unix-socket latency, while not meaningfully reducing blast radius compared to an in-process library.

Evaluate directly from Postgres on every call: simplest possible implementation, no cache. Rejected immediately — a DB round-trip on every flag evaluation on the hot path would add 1–10 ms of latency and create a new DB bottleneck.

Chosen: in-process library with in-memory cache. Zero network hops on the evaluation path. Cache invalidation via a lightweight pub/sub channel (e.g., Postgres LISTEN/NOTIFY or Redis pub/sub) with a polling fallback for reliability. Evaluation logic is a pure function over the cached ruleset — easy to test and benchmark.

Recommendations

Use Postgres LISTEN/NOTIFY on a flag_changes channel as the primary invalidation mechanism — no new infrastructure, and it fires on every committed write. The application re-fetches the entire flag table (not just the changed row) on each notification to avoid partial-update races. Keep a polling fallback at 30-second intervals as a safety net for missed notifications. For the deterministic bucketing: bucket = murmur3(userID + ":" + flagSalt) mod 100; document the exact algorithm and seed so it can be reimplemented identically in any language.

Open questions

What sampling rate should evaluation telemetry use by default? 100% sampling gives complete data but adds write load. A configurable rate (defaulting to 1–10%) seems right — but who owns the configuration, and should it be a flag itself?

How should environment inheritance work at evaluation time when a flag has no explicit staging override? Inherit from production default silently, or require an explicit "inherit" sentinel value that makes the relationship visible in the UI?

Implement the core evaluation algorithm

Write a pure function evaluate(flag, context) → variant that handles all three flag types. Boolean: return the variant for the first matching targeting rule, else the default. Percentage rollout: compute murmur3(context.userID + ":" + flag.salt) mod 100 and compare to the rollout threshold. Multivariate: same bucketing, but map bucket ranges to named variants. Rules are evaluated in declaration order; first match wins. Document the bucketing algorithm in a language-agnostic spec so both SDK implementations are byte-for-byte equivalent.

Build in-memory cache with invalidation

On startup, load the full flag table into a thread-safe in-memory map. Register a Postgres LISTEN handler on the flag_changes channel; on notification, re-fetch and hot-swap the cache atomically. Add a background polling loop (30 s interval) as a fallback. Expose a warmCache() method for use in tests and a cacheAge() metric for observability. Ensure cache reads require no locking (copy-on-write or read-write lock with short critical section).

Wire up Postgres NOTIFY on flag writes

Modify the accessor library from Phase 1 to execute NOTIFY flag_changes, '{"key": "..."}' inside the same transaction as each flag write. This ensures no notification is sent for a rolled-back change. Add a test that creates a flag, verifies the notification fires, and confirms the cache is updated within 1 second.

Implement SDK surface for both monorepo languages

Expose a clean public API: FlagClient.evaluate(flagKey: string, context: EvalContext): Variant and typed helpers for boolean (isEnabled) and string variant (getVariant) cases. EvalContext carries userID, orgID, environment, and an arbitrary attributes map for future targeting dimensions. SDK must fail closed (return default value) if the cache is uninitialized or the flag key is unknown — never throw on the evaluation path.

Build JSON-over-HTTP evaluation endpoint

Add a POST /internal/flags/evaluate endpoint behind the existing auth middleware. Request body: {"flagKey": "...", "context": {...}}. Response: {"variant": "...", "reason": "rule-match|default|error"}. Accepts bulk requests (array of {flagKey, context}) for callers that need multiple flags. Must share the same in-process cache as the SDK — no second DB read path. Document the endpoint in the internal API reference.

Add evaluation telemetry

On each evaluation, if a random draw is below the configured sample rate, emit an event to the existing telemetry pipeline (structured log, metrics sink, or event bus — use whatever the monorepo already has). Event payload: flagKey, variant, reason, environment, userID (hashed), evalDurationUs. Make the sample rate configurable via an environment variable defaulting to 5%.

Phase 3 — Admin UI

Deliver the dashboard that product, support, and engineering use to manage flags day-to-day. Builds on Phases 1 and 2; no new backend concepts, mostly UI surface and RBAC enforcement.

Phase goal

Ship a polished, production-ready admin dashboard (gated behind the feature-flags-admin-ui flag from Phase 1) covering: flag list with search and filter, flag create/edit form, per-environment override editor, percentage-rollout slider with live bucketing preview, audit history view, and archive/restore actions. RBAC is fully enforced: only flag owners and flag-admin role members can edit production values. All actions go through the existing auth middleware.

Alternatives considered

Standalone admin app (separate origin): isolates the admin UI from the main product bundle. Rejected — adds a second deployment target, a second auth integration, and more CORS surface for a six-week timeline.

CLI-only admin tooling: flag management via a command-line tool. Fast to build; zero UI work. Rejected — product and support teams need a graphical tool; a CLI is useful as a complement but not a replacement.

Chosen: a route inside the existing web application, using the same component library and auth session as the rest of the product. Minimizes new surface, keeps RBAC in one place.

Recommendations

Build the live bucketing preview as a client-side simulation: given the current rollout percentage and salt, render a deterministic sample of 100 fictional user IDs and show which bucket each falls into. This requires no server round-trip and gives product managers an immediate intuition for how the rollout will spread. For the audit history view, paginate server-side (the audit table can grow large) and show a human-readable diff of the JSONB changes rather than raw JSON.

Open questions

Should non-owner engineers be able to edit staging overrides without restriction, or should the same owner+admin gate apply to all environments? Locking staging is safer but may slow down development workflows.

Is there an existing role/permission system in the product we should integrate with for flag-admin membership, or do we need to build a simple group table?

Build flag list page with search and filter

Render a paginated table of all flags showing key, description, owner, type, lifecycle state, and per-environment active status. Support free-text search on key and description, filter by environment, type, and lifecycle state. Each row links to the flag detail/edit page. Flags the current user owns or can administer are visually distinguished. Archived flags are hidden by default with a toggle to show them.

Build flag create and edit form

Form covers all schema fields: key (immutable after creation), description, owner, type selector, default value, and per-environment config panels. Changing the flag type resets the environment configs with a confirmation prompt. Validation is client-side first, then server-side; server returns typed error objects the form can map to specific fields. Writes go through the accessor library (Phase 1) which records audit rows. On save, the page optimistically updates and shows a success/error toast.

Build percentage-rollout slider with live bucketing preview

Within the flag edit form, when flag type is percentage, show a slider (0–100%). Below the slider, render a 10×10 grid of 100 cells, each representing one percentage point. Cells in the "enabled" bucket are filled; cells in the "disabled" bucket are empty. Compute the grid client-side using the same murmur3 algorithm as the evaluation engine (port or import the same implementation). Update the grid in real time as the slider moves so product managers see the exact cohort before saving.

Build audit history view

On each flag's detail page, show a paginated chronological list of all changes from feature_flag_audit. Each row shows: timestamp, actor (name + email), change type (created / updated / archived / restored), and a human-readable summary of what changed (e.g., "rollout percentage: 10% → 25%"). For JSONB diffs, compute a field-level diff server-side and return structured change objects rather than raw before/after blobs. Older entries are loaded on demand (infinite scroll or "load more").

Enforce RBAC for production flag edits

On every write API endpoint (PUT /flags/:key, PATCH /flags/:key/environments/production, DELETE /flags/:key), check that the authenticated user is either the flag's owner or a member of the flag-admin role. Return 403 Forbidden with a clear message if not. In the UI, disable editing controls and show a tooltip explaining the permission requirement. Ensure the RBAC check happens server-side regardless of what the UI renders — the UI gate is a UX improvement, not a security boundary.

Write end-to-end tests for critical admin flows

Cover: create a flag and verify it appears in the list; edit a flag's rollout percentage and verify the cache invalidation fires and the new percentage is returned by evaluate(); attempt to edit a production flag as a non-owner and verify 403; archive a flag and verify evaluate() returns the default value. Use the project's existing e2e test framework against a test database seeded with known flags and users.

Store flags in Postgres (not a config file in the repo)

Flags live in a feature_flags table in the primary Postgres database, with a read-through in-memory cache in each application process. This allows flag values to be changed at runtime without a code deploy, which is the core requirement (kill a misbehaving feature without a deploy). The trade-off is added operational surface (migrations, cache invalidation) compared to a flat config file, but the config-file approach fails the primary use-case entirely.

A config file in the repo is simpler to audit (git log) and requires zero new infrastructure, but any change requires a deploy — which is exactly what this system is designed to avoid.

In-process library (not a sidecar) for the evaluation path

The evaluation engine runs as an in-process library sharing the application's memory, not as a separate sidecar process. This is the only way to guarantee no added network hop on the request-handling path, which is a hard constraint. The trade-off is that cache state is per-process (each pod has its own copy) rather than shared, but this is acceptable: the cost of a slightly stale cache (up to 30 seconds) is lower than the cost of a network call on every evaluated flag.

A sidecar process over a Unix socket could share cache across threads within a pod and isolate the evaluation logic from application crashes, but adds sidecar lifecycle management and measurable latency even over a local socket.

Use Postgres LISTEN/NOTIFY for cache invalidation (with polling fallback)

When a flag is written, the application issues NOTIFY flag_changes in the same transaction. All running application instances subscribe to this channel and reload the flag cache on receipt. A 30-second polling loop acts as a safety net for missed notifications (e.g., during reconnects). This requires no new infrastructure and delivers sub-second propagation in normal operation.

Redis pub/sub would decouple the notification channel from the database and work across multiple database replicas, but adds a dependency on Redis being available for correctness (not just performance), and LISTEN/NOTIFY is sufficient for the expected flag-change frequency.

Cache invalidation failure → stale flag values served indefinitely

If the Postgres LISTEN connection drops and the polling fallback also fails (e.g., DB overload), application instances will serve stale flag values until the connection is restored. For a kill-switch use-case, this could mean a misbehaving feature stays enabled longer than expected.

Mitigation: The 30-second polling loop is the primary fallback. Additionally, expose a /internal/flags/reload endpoint (admin-only) that forces an immediate cache reload on a single pod — useful for emergency use. Log a warning metric whenever the NOTIFY connection has been down for more than 60 seconds so on-call is alerted.

Bucketing algorithm divergence across SDK implementations

If the two monorepo SDK implementations of the murmur3 bucketing algorithm differ by even one bit, the same user may get different variants from different services in the same request, creating incoherent user experiences (e.g., the API enables a feature but the rendering service disables it).

Mitigation: Publish a canonical test vector suite (100 known inputs and expected bucket outputs) as a shared test fixture. Both SDK implementations must pass the same test vectors before merging. The vectors are checked into the repo as a language-agnostic JSON file.

Flag proliferation without lifecycle governance

Without a forcing function, flags accumulate over time and never get archived. A large number of stale flags increases cache size, clutters the admin UI, and creates dead code paths that make the codebase harder to reason about.

Mitigation: Add a last_evaluated_at timestamp to the flag cache (updated on each cache reload from telemetry data). Surface flags not evaluated in the past 30 days as "stale" in the admin UI. Consider a weekly automated report to flag owners listing their unevaluated flags. Full enforcement (auto-archiving) is deferred.

RBAC bypass via direct database access

The RBAC checks live in the application layer. Anyone with direct Postgres access (e.g., via a DB console, migration script, or a bug in the accessor library) can modify flag values without the audit trail or RBAC enforcement.

Mitigation: Use a Postgres trigger as a belt-and-suspenders audit fallback — even if the application layer is bypassed, the trigger writes a row to feature_flag_audit with the DB session user. Restrict direct DB write access to feature_flags to a minimal set of DB roles. Document the out-of-band change procedure in the runbook.

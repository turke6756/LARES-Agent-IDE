Feature Flag System Plan

Build a first-party feature-flag system across schema, evaluation, and administration so engineering can ship dark, product can run gradual rollouts, and support can disable faulty behavior without a deploy.

Success Criteria

  • Backend teams can define and read typed flags without direct SQL access or ad hoc configuration parsing.
  • Flag evaluation returns the correct variant in under one millisecond at p99 from local process memory on the request path.
  • Product and support users can create, search, edit, and archive flags from an authenticated admin UI.
  • Production edits are limited to flag owners and admins, and all flag changes are captured in audit history.
  • Percentage rollouts are deterministic, stable across deploys, and explainable through preview tooling.
  • The system supports boolean, percentage rollout, and multivariate flags with user, organization, and environment targeting.

Scope

In scope: a durable flag schema, Postgres storage, read-through caching, migrations, seed data, typed accessors, audit history, an embedded evaluation library for the two backend languages in the monorepo, a JSON-over-HTTP endpoint for non-native consumers, sampled evaluation telemetry, and an authenticated admin dashboard.

Out of scope: full approval workflows, A/B-test statistics, scheduled rollouts, mobile SDKs, external SaaS flag providers, and using the HTTP endpoint from latency-sensitive request handling where an in-process SDK can be used.

Constraints

  • No new external SaaS dependencies.
  • The hot evaluation path must not add a network hop to request handling.
  • All admin and API surfaces must sit behind existing authentication middleware.
  • The team is three engineers with roughly six weeks of implementation time.
  • Storage, cache, and UI decisions should fit the existing monorepo and deployment model.

Assumptions

Primary Postgres can be the source of truth

The plan assumes the existing primary Postgres is appropriate for flag definitions and audit history because flags are operational product metadata, not high-volume event data.

A practical invalidation path exists

The evaluation libraries need local in-memory snapshots. This plan assumes we can either use an existing internal push mechanism or implement short-interval polling with version checks without violating performance or load constraints.

The required backend SDK targets are known

The plan assumes the two backend languages in the monorepo are stable enough to define matching SDK behavior, tests, and release gates during the six-week window.

Phase 1: Flag Schema and Storage

Establish the durable model, database structures, audit trail, and typed access patterns that later phases rely on.

Phase Goal

Create a reliable source of truth for feature flags with enough structure to support targeting, lifecycle management, evaluation snapshots, and auditability without introducing an approval workflow.

Alternatives Considered

A config-file-in-repo approach was considered because it is simple, reviewable, and deployment-friendly. It is not recommended for this launch because support and product need runtime changes, kill switches, and audit history without deploys. The recommended path is a new feature_flags table in primary Postgres, backed by a read-through cache and versioned snapshots for SDK consumers.

Recommendations

Use Postgres as the canonical store, with normalized metadata columns for ownership and lifecycle plus JSONB columns for targeting rules and variants. Keep audit history append-only. Build typed accessors around the model immediately so product code never reads raw rows directly.

Open Questions

Where should valid flag owners come from?

Decide whether owners are users, teams, service groups, or a combination, and how that maps to production edit permissions in the admin UI.

Define the Flag Data Model

Specify fields for key, description, owner, type, default value, lifecycle state, environments, targeting rules, variants, salt, version, timestamps, and archival metadata. Include validation rules for key format, unique keys, valid variant weights, and supported targeting dimensions.

Create Postgres Migrations

Add feature_flags, feature_flag_environment_overrides, and feature_flag_audit_events tables. Add indexes for key lookup, active flags, owner search, environment overrides, and audit history retrieval by flag key.

Add Seed Flags

Create representative seed data for one boolean flag, one percentage rollout, and one multivariate flag in non-production environments. Use these to validate migrations, accessors, admin forms, and evaluation fixtures.

Build Typed Accessors

Expose repository-level functions for loading flags by key, listing active flags, writing environment overrides, archiving flags, and appending audit events. Enforce model validation in the accessor layer so callers cannot persist invalid rollout weights or malformed targeting rules.

Implement Read-Through Cache

Add a cache keyed by flag key and environment-aware snapshot version. The cache should reduce database reads for admin and service startup paths while preserving Postgres as the source of truth.

Capture Audit History

Record create, update, archive, and environment override changes with actor, timestamp, previous value, next value, source surface, and reason when supplied. Keep the structure queryable for the admin audit-history view.

Phase 2: Evaluation Engine

Deliver deterministic, low-latency evaluation for request handling and a compatible HTTP endpoint for consumers that cannot embed a native SDK.

Phase Goal

Provide evaluate(flagKey, context) -> variant with deterministic results, clear rule semantics, local in-memory snapshots, sampled telemetry, and matching behavior across supported runtimes.

Alternatives Considered

A centralized sidecar-only service was considered for implementation simplicity. It is not recommended as the primary request-path mechanism because it would add a network hop. The preferred design is an embedded SDK backed by local snapshots, plus an optional JSON-over-HTTP endpoint for tools, jobs, and services that do not run on latency-sensitive request paths.

Recommendations

Define one language-neutral evaluation specification and conformance test suite, then implement SDKs for both backend languages against that spec. Use a stable hash of user identifier, flag key, and flag salt for percentage rollouts. Make rule ordering explicit: environment override, targeted allow or variant rules in configured order, percentage allocation, then default value.

Open Questions

Should cache invalidation be push-first or poll-first?

Choose whether the initial release uses existing internal pub/sub or a short polling loop with snapshot versions. Push gives faster propagation; polling is usually simpler to operate.

Write the Evaluation Specification

Define context shape, required and optional attributes, rule ordering, environment inheritance, missing-context behavior, default fallback behavior, variant return shape, and error handling. Treat malformed flags as disabled with telemetry and operational alerts rather than request failures.

Implement Deterministic Bucketing

Use a stable non-cryptographic hash over user ID, flag key, and per-flag salt to map identities into a fixed bucket range. Preserve bucket assignments when rollout percentages increase so users do not churn between variants unexpectedly.

Build Local In-Memory Snapshots

Load active flag snapshots into each process and refresh them through versioned invalidation. Ensure evaluation never blocks on Postgres or the HTTP endpoint during normal request handling. Include stale snapshot metrics and a bounded startup fallback policy.

Ship Backend SDKs

Implement the native SDK surface for the two backend languages in the monorepo. Provide typed calls for boolean, string or variant, and percentage-backed flags, while retaining a generic evaluate API for shared infrastructure.

Add JSON-over-HTTP Evaluation Endpoint

Expose an authenticated endpoint that evaluates using the same local engine and conformance tests as the SDKs. Document that latency-sensitive request handlers should use native SDKs rather than making a network call.

Emit Sampled Evaluation Telemetry

Emit sampled events with flag key, variant, environment, rule matched, SDK language, snapshot version, and coarse context identifiers. Avoid logging raw sensitive context values. Add counters for evaluation latency, misses, malformed flags, and stale snapshots.

Phase 3: Admin UI

Build the authenticated operational surface for managing flags, editing environment-specific values, previewing rollouts, reviewing audit history, and enforcing role-based production edits.

Phase Goal

Give engineering, product, and support a safe interface to create, edit, search, preview, and archive flags while preserving ownership boundaries and auditability.

Alternatives Considered

A minimal internal CRUD page was considered. It would be faster, but it would miss key safety requirements around production permissions, rollout preview, and audit visibility. The recommended UI is still modest, but includes the workflows needed to operate flags safely from day one.

Recommendations

Place the dashboard inside the existing admin shell and reuse current authentication, authorization, form, table, and audit display patterns where available. Make production edits visibly distinct, require ownership or admin permission, and show the effective value per environment before saving.

Open Questions

Can support edit production kill switches directly?

Clarify whether support users can disable production flags when they are not the owner, or whether they need an admin role or a dedicated emergency permission.

Create Dashboard List and Search

Build a flag index page with search by key, description, owner, type, environment, and lifecycle state. Show current production state, active rollout percentage or variant summary, owner, last updated time, and archive status.

Build Create and Edit Forms

Support boolean, percentage rollout, and multivariate flag creation with validation matching the backend model. Include description, owner, default value, targeting rules, environment overrides, and lifecycle actions.

Add Per-Environment Overrides

Show inherited values and explicit overrides for production, staging, and other supported environments. Implement staging defaults from production while allowing explicit staging overrides when needed.

Add Rollout Slider and Bucketing Preview

Provide a percentage slider with a live preview that shows sample user IDs, bucket assignments, and variant outcomes. Use the same bucketing implementation or shared test fixtures as the evaluation engine to prevent UI drift.

Expose Audit History

Add an audit-history view on each flag detail page showing actor, timestamp, changed fields, previous value, next value, and source. Provide enough context for support and engineering to understand when a rollout changed.

Enforce Role-Based Access

Restrict production edits to flag owners and admins. Allow broader read access behind the existing auth middleware. Ensure authorization is enforced server-side and reflected in disabled or hidden UI actions.

Use Postgres plus cache instead of config files

Feature flags will live in primary Postgres with read-through caching and local evaluation snapshots. This supports runtime changes, audit history, ownership metadata, environment overrides, and support-operated kill switches without deploys.

A repo-backed config file would be easier to review and roll back through Git, but it would make gradual rollout changes and emergency disables dependent on deployment machinery.

Make embedded SDK evaluation the primary request-path integration

The evaluation path must not add a network hop to request handling, so services on the hot path should use local in-memory SDK snapshots. The HTTP endpoint remains available for consumers that cannot embed an SDK or are outside latency-sensitive paths.

Stale local snapshots delay kill switches

If invalidation is slow or broken, a production kill switch may not take effect quickly across all service processes. Mitigation: version snapshots, emit stale-cache metrics, set a strict refresh interval, and add operational alerts for processes behind the latest version.

SDKs disagree on evaluation results

Different language implementations could diverge on hashing, rule order, missing context, or environment inheritance. Mitigation: create a language-neutral specification and shared conformance fixtures that every SDK and the HTTP endpoint must pass.

Incorrect production edit permissions create operational risk

A UI-only permission check could allow unauthorized production changes through direct API calls. Mitigation: enforce authorization server-side, include permission tests, and audit all denied and accepted production edits.

The six-week window may pressure UI and telemetry scope

The core schema and evaluation path are higher priority than polish. Mitigation: keep A/B stats, scheduled rollouts, and mobile SDKs out of scope, and treat the first launch as operational flagging rather than experimentation infrastructure.

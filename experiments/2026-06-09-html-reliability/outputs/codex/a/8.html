Feature Flag System Implementation Plan

Plan for delivering an internal feature-flag system in three phases: durable flag schema and storage, sub-millisecond local evaluation, and an authenticated admin UI for controlled operations.

Success Criteria

  • Engineering can merge and deploy code paths guarded by flags without exposing them to all users.
  • Product can run deterministic gradual rollouts by percentage, user, organization, and environment.
  • Support and authorized operators can disable a misbehaving feature without a deploy.
  • Backend request handling can evaluate flags without adding a network hop and with p99 evaluation latency under one millisecond from local process state.
  • Every flag mutation is auditable, including actor, timestamp, environment, previous value, and new value.
  • The system ships within roughly six weeks with a team of three engineers.

Scope

In scope: a typed flag model, Postgres-backed storage, migrations, seed data, audit history, read-through and local caches, deterministic rollout evaluation, backend SDKs for the two monorepo languages, a JSON-over-HTTP endpoint for non-SDK consumers, sampled evaluation telemetry, and an authenticated admin dashboard for creating, editing, searching, previewing, and archiving flags.

Out of scope: external feature-management SaaS, full approval workflows, A/B-test statistics, scheduled rollouts, mobile SDKs, and any evaluation path that requires a per-request network call.

Constraints

  • No new external SaaS dependencies.
  • The critical evaluation path must use in-process state and must not add a network hop to normal request handling.
  • All admin and API surfaces must sit behind existing authentication middleware.
  • Production edits must be restricted to flag owners and admins.
  • The implementation must fit a three-engineer, six-week delivery window.

Assumptions

Primary Postgres Can Host Flag State

The existing primary Postgres is available for low-write, high-read configuration state and can support a new feature flag table plus append-only audit table.

Two Backend SDKs Are Sufficient For Launch

The monorepo has two backend languages that cover the latency-sensitive services. Other consumers can use the HTTP endpoint or defer adoption.

Existing Auth Can Enforce Roles

The current authentication and authorization layer can identify admins, flag owners, and environment-level edit permissions without a separate identity system.

Phase 1: Flag Schema And Storage

Build the durable source of truth for flags, auditability, and typed access. This phase should leave the product able to define flags safely even before all runtime evaluation surfaces are complete.

Phase Goal

Create a Postgres-backed feature flag model with migrations, seed data, audit history, lifecycle state, and a typed accessor library used by later evaluation and UI work.

Alternatives Considered

A config-file-in-repo approach was considered because it is simple, reviewable, and deploy-aligned. It is not the preferred launch path because support needs immediate kill-switch behavior without deploys, product needs gradual rollout edits, and audit history should capture operational changes made through the admin surface.

Recommendations

Use primary Postgres as the source of truth with a read-through cache for admin and synchronization reads. Store flag definitions separately from environment-specific values and targeting rules so production edits can be permissioned independently from global metadata.

Open Questions

Where Should Flag Ownership Come From?

Confirm whether owners should be stored as individual users, teams, service owners, or a combination mapped from the existing authorization system.

Define The Flag Data Model

Specify tables and typed fields for key, description, owner, type, default value, lifecycle state, salt, variants, targeting rules, and environment overrides. Enforce globally unique keys, stable salts, valid lifecycle transitions, and type-compatible defaults.

Add Postgres Migrations

Create migrations for feature_flags, feature_flag_environments, feature_flag_rules, and feature_flag_audit_events. Include indexes for flag key lookups, environment lookups, lifecycle filtering, and audit history retrieval.

Create Audit History Writes

Implement append-only audit recording for create, update, archive, and environment override changes. Each event should include actor, timestamp, operation, flag key, environment, previous serialized state, new serialized state, and request metadata available from existing middleware.

Build Typed Accessor Library

Expose internal APIs to read active flags by key, list flags by lifecycle state, fetch environment-specific configuration, and write changes through validation paths that always emit audit records. Keep this library independent from the admin UI so the evaluation engine can reuse it.

Seed Initial Flags

Add seed data for a small set of non-critical internal flags that exercise boolean, percentage, and multivariate types. Use these seeds for SDK integration tests, UI smoke testing, and rollout preview validation.

Phase 2: Evaluation Engine

Implement deterministic, low-latency runtime evaluation with local process caches and a compatibility endpoint for services that cannot adopt an SDK immediately.

Phase Goal

Deliver evaluate(flagKey, context) -> variant with deterministic rule semantics, p99 latency under one millisecond from in-memory state, backend SDKs for both monorepo languages, cache invalidation, and sampled telemetry.

Alternatives Considered

A sidecar-only evaluator was considered for language neutrality. It is not preferred for latency-sensitive request paths because it would add a local network hop and operational surface. The recommended shape is shared SDK evaluation logic where practical, with an HTTP endpoint reserved for non-critical or non-SDK consumers.

Recommendations

Represent loaded flags as immutable in-memory snapshots. Refresh snapshots by polling a version endpoint at short intervals for launch, with the schema leaving room for push invalidation later. Use deterministic hashing over flagKey, stable flag salt, environment, and bucketing identifier to avoid cross-flag correlation.

Open Questions

What Initial Sampling Rate Should Evaluation Telemetry Use?

Choose default sampling rates for high-volume and low-volume services so telemetry is useful for rollout analysis without materially increasing logging or analytics cost.

Define Rule Ordering And Evaluation Semantics

Document and implement precedence: archived flags return their default or a hard disabled value, explicit user targets override org targets, environment overrides apply before inherited defaults, ordered targeting rules short-circuit on first match, and percentage rollout applies only after higher-priority matches fail.

Implement Deterministic Bucketing

Use a stable hash of user ID or configured bucket key plus flag salt to assign percentage rollout buckets. Validate that distribution is acceptably uniform, sticky across deploys, independent across flags, and consistent across the two SDK implementations.

Build Local Cache And Invalidation

Load an immutable snapshot of active flags into each process. Add read-through warmup, periodic polling by version, stale-cache metrics, last-known-good fallback, and a bounded startup path that prevents request handling from depending on live database reads.

Ship Backend SDKs

Implement equivalent SDK surfaces for both backend languages in the monorepo. Each SDK should expose typed helpers for boolean, percentage, and multivariate flags, default-value fallbacks, context validation, and integration hooks for service metrics.

Add JSON-Over-HTTP Evaluation Endpoint

Provide an authenticated endpoint for non-SDK consumers that evaluates against the same engine and cache snapshot. Mark it unsuitable for latency-critical request paths unless the caller already has an acceptable network boundary.

Emit Sampled Evaluation Telemetry

Emit sampled events containing flag key, selected variant, environment, rule identifier, context shape, SDK version, and evaluation latency. Avoid raw personally identifiable information by hashing or omitting sensitive identifiers according to existing telemetry standards.

Phase 3: Admin UI

Build the operational surface that lets product, engineering, and support manage flags without direct database access while preserving auditability and production safeguards.

Phase Goal

Deliver an authenticated dashboard for creating, editing, searching, archiving, previewing, and auditing feature flags with role-based production edit controls.

Alternatives Considered

A minimal internal CLI was considered as the first management surface. It would be faster to build but weaker for product rollouts, support kill switches, audit review, and percentage preview. The dashboard should be the primary interface, with CLI support deferred unless operations demand it.

Recommendations

Reuse the existing authenticated app shell and design system. Keep editing flows explicit and environment-scoped, with production changes requiring owner or admin authorization. Show audit history next to editable configuration so operators understand recent changes before modifying a flag.

Open Questions

Which Identifiers Should The Rollout Preview Accept?

Decide whether live bucketing preview should accept arbitrary user IDs, organization IDs, synthetic examples, or only identifiers the current operator is authorized to inspect.

Build Flag Dashboard And Search

Create a dashboard that lists flags with key, description, owner, type, lifecycle state, environments, and last modified timestamp. Add search by key and description plus filters for owner, type, lifecycle state, and environment.

Build Create And Edit Flows

Implement forms for flag metadata, default values, variants, targeting rules, and lifecycle state. Use type-specific validation so boolean, percentage, and multivariate flags cannot save incompatible values.

Add Per-Environment Overrides

Expose environment-specific values and targeting rules, including staging inheritance from production defaults. Make inherited values visually distinct from explicit overrides and require deliberate action to clear an override.

Add Percentage Rollout Slider And Preview

Provide a rollout slider for percentage flags with live preview of bucket assignments for representative or entered identifiers. The preview must use the same deterministic bucketing implementation as the runtime SDKs.

Add Audit History View

Show chronological audit events for each flag with actor, timestamp, operation, environment, and before-and-after summaries. Include enough detail for incident review without exposing sensitive context values unnecessarily.

Enforce Role-Based Access

Gate all admin UI routes behind existing auth middleware. Allow owners and admins to edit production values, allow broader internal roles to view and edit non-production values if policy permits, and enforce the same checks on server-side mutation endpoints.

Use Postgres As The Source Of Truth

Feature flags will live in primary Postgres with a read-through cache and process-local evaluation snapshots. This satisfies auditability, immediate operational edits, and no-SaaS constraints while avoiding deploy-gated configuration changes.

A config-file-in-repo approach is simpler and strongly reviewable, but it cannot support support-driven kill switches or product rollout changes without a deploy.

Prefer SDK-Local Evaluation For Request Paths

The primary runtime path will evaluate flags in-process from local snapshots. The HTTP endpoint exists for compatibility, not as the default mechanism for latency-sensitive service code.

Stale Local Caches Delay Kill Switches

If invalidation or polling is too slow, support may disable a flag but services may continue serving the old value for longer than acceptable. Mitigation: define a launch stale-time objective, expose cache age metrics, use short polling intervals initially, and consider push invalidation after the first release.

SDKs Return Different Variants

Independent implementations in two backend languages can diverge on hashing, rule ordering, or environment inheritance. Mitigation: create shared conformance fixtures and require both SDKs and the HTTP endpoint to pass the same test vectors.

Production Edit Permissions Are Enforced Only In UI

If server-side mutation endpoints do not enforce ownership and admin checks, users could bypass UI restrictions. Mitigation: centralize authorization in the write API and treat UI checks as usability hints only.

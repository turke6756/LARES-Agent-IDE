Feature Flag System Rollout Plan

Build an internal feature-flag platform in three phases so engineering can ship dark code, product can manage gradual rollouts, and support can disable misbehaving features without a deploy while keeping request-time evaluation local and fast.

Success Criteria

  • Backend callers can evaluate a flag with evaluate(flagKey, context) -> variant locally with p99 latency under 1 millisecond after warmup.
  • Boolean, percentage rollout, and multivariate flags support targeting by user ID, organization, and environment with deterministic results.
  • Production flag edits are restricted to flag owners and admins, and every change is captured in audit history.
  • Flags can be created, edited, searched, archived, and overridden per environment from an authenticated admin dashboard.
  • The system launches within roughly six weeks for the two backend languages in the monorepo plus a JSON-over-HTTP fallback endpoint.

Scope

In scope: Postgres-backed flag schema, audit history, seed data, migrations, typed accessor libraries, local evaluation SDKs for the two backend languages, cache invalidation, sampled telemetry events, HTTP evaluation endpoint, and an authenticated admin UI.

Out of scope: A/B-test statistical analysis, scheduled rollouts, mobile SDKs, full approval workflow, and external SaaS dependencies.

Constraints

  • No new external SaaS dependency is allowed.
  • The hot evaluation path must not add a network hop to normal request handling.
  • All dashboard and endpoint access must sit behind existing authentication middleware.
  • The plan assumes three engineers and a six-week delivery window, so implementation must favor a compact internal platform over a broad experimentation suite.

Assumptions

Primary Postgres Is The Source Of Truth

The product already operates a primary Postgres database suitable for storing low-volume flag configuration, environment overrides, and audit records.

Existing Auth Can Support Flag Permissions

The admin UI can reuse existing authentication and authorization primitives to distinguish admins, flag owners, and read-only users.

Backend SDK Surface Is Limited

The monorepo has exactly two backend languages that need first-class typed SDK support for initial release; other runtimes can use the JSON-over-HTTP endpoint.

Phase 1: Flag Schema And Storage

Establish the durable source of truth, lifecycle model, migrations, seed data, audit trail, and typed access layer before building runtime evaluation.

Phase Goal

Deliver a versioned Postgres-backed flag model that can represent boolean, percentage, and multivariate flags, including targeting dimensions, defaults, lifecycle state, environment overrides, and complete change history.

Alternatives Considered

A config-file-in-repo approach would make review and deployment behavior simple, but it would not let support kill a feature without a deploy and would slow product-managed rollouts. A Postgres source of truth with read-through caching better matches the operational requirements while staying within the no-SaaS constraint.

Recommendations

Use Postgres as the source of truth with normalized metadata tables and JSONB rule payloads for extensibility. Keep the evaluation snapshot format explicit and versioned so SDKs can cache a compact read model without understanding every storage detail.

Open Questions

Where Should Flag Ownership Come From?

Decide whether owner values are free-form team identifiers, user IDs, group IDs from the auth system, or a combination of team and accountable user.

Define Flag Domain Model

Specify fields for key, description, owner, type, default value, lifecycle state, salt, variants, targeting rules, environment overrides, and timestamps. Include validation rules for key format, variant weights, archived flag behavior, and required owner metadata.

Create Postgres Migrations

Add feature_flags, feature_flag_environments, and feature_flag_audit_events tables. Include indexes for key lookup, active flags, owner search, lifecycle state, and recent audit events.

Implement Audit History Writes

Record before and after values, actor identity, timestamp, environment, change reason when available, and request correlation ID. Keep the audit trail append-only and separate from the current flag read model.

Add Seed Data And Fixtures

Create representative boolean, percentage, and multivariate flags for local development and tests. Include examples for user targeting, organization targeting, environment override, active state, and archived state.

Build Typed Storage Accessor Library

Expose repository methods for loading active flag snapshots, fetching by key, writing updates with audit events, searching flags, and archiving flags. Return typed objects instead of raw database rows so later phases can share one contract.

Phase 2: Evaluation Engine

Build the low-latency evaluator and SDK surface that services can use without adding a request-time network dependency.

Phase Goal

Deliver deterministic local evaluation for all supported flag types, backed by an in-memory cache and invalidation mechanism, with SDKs for the two backend languages and an authenticated HTTP endpoint for non-SDK consumers.

Alternatives Considered

A centralized sidecar-only evaluator would simplify implementation consistency but risks adding operational complexity and accidental network hops. The recommended shape is a shared evaluation spec with language-native SDKs, plus an optional internal endpoint for batch or non-critical consumers.

Recommendations

Represent runtime data as a compact immutable snapshot. SDKs should refresh the snapshot out of band, evaluate synchronously in process, and fail closed to default values when a flag is missing or malformed. Use a stable hash of user ID and flag salt for percentage bucketing.

Open Questions

Push Or Poll Invalidation For Initial Launch?

Decide whether the first version uses periodic polling only, an existing pub/sub channel, or a hybrid where push invalidates quickly and polling repairs missed messages.

Write Evaluation Semantics Spec

Define rule ordering, targeting precedence, environment inheritance, missing context behavior, default fallback, archived flag handling, variant selection, and percentage allocation boundaries. Treat this as the contract shared by both SDK implementations and the HTTP endpoint.

Implement Deterministic Bucketing

Use a stable non-cryptographic hash over user ID and flag salt to map users into a fixed bucket range. Add golden tests so both backend language SDKs produce identical variants for the same inputs.

Build Local Cache And Refresh Path

Load the active flag snapshot into memory at process start, refresh it out of band, and expose health metrics for snapshot age and refresh failures. Keep request handling on the last known good snapshot when refresh fails.

Ship Backend SDKs

Provide idiomatic SDK APIs for both backend languages, including typed context objects, default value helpers, variant return types, cache lifecycle hooks, and test utilities for overriding flags in unit and integration tests.

Add JSON-Over-HTTP Evaluation Endpoint

Expose authenticated endpoints for consumers that cannot use an SDK. Clearly document that this endpoint is not for hot request paths unless callers can tolerate the added network hop.

Emit Sampled Evaluation Telemetry

Record sampled events with flag key, variant, environment, reason code, SDK language, snapshot version, and coarse context identifiers suitable for later analysis. Avoid logging raw sensitive user attributes.

Phase 3: Admin UI

Provide the authenticated operational interface for creating, editing, searching, archiving, auditing, and safely rolling out flags.

Phase Goal

Deliver an admin dashboard that lets authorized users manage flags and per-environment values, preview rollout bucketing, inspect audit history, and enforce production edit permissions for owners and admins.

Alternatives Considered

A minimal internal CRUD form would be faster, but it would increase production risk by hiding rollout previews, audit context, and environment differences. A focused dashboard with purpose-built controls is the better fit for support and product workflows.

Recommendations

Build the UI inside the existing admin shell and reuse existing auth middleware, forms, tables, and role checks. Keep creation and edit flows explicit, with production changes requiring a reason field that is stored in the audit event.

Open Questions

What Guardrail Copy Is Required For Production Changes?

Decide whether production edits need a confirmation dialog, required change reason, warning text for broad rollouts, or all three.

Build Searchable Flag Dashboard

Create a list page with search by key, description, owner, lifecycle state, type, and environment. Show current production value, staging override status, owner, last updated time, and archived state.

Implement Create And Edit Flows

Add forms for flag metadata, default values, variants, targeting rules, lifecycle state, and per-environment overrides. Validate rule syntax and variant weights client-side and server-side.

Add Percentage Rollout Slider And Preview

Provide a slider for rollout percentage and a live preview showing sample users or generated IDs mapped into included and excluded buckets. Use the same bucketing library as the evaluator to avoid UI/runtime drift.

Build Audit History View

Show chronological flag changes with actor, timestamp, environment, before and after values, reason, and correlation ID. Include filters for environment and change type.

Enforce Role-Based Production Editing

Allow admins and flag owners to edit production values. Allow broader read access where appropriate. Enforce authorization on the server and reflect disabled controls in the UI for users without edit rights.

Use Postgres As Source Of Truth With Read-Through Runtime Cache

The system needs support-driven kill switches and product-managed rollout changes without deploys, which makes config files in the repository a poor operational fit. Postgres provides transactional writes, auditability, and easy integration with existing auth and admin tooling, while SDK-local caches keep evaluation off the request-time network path.

This introduces database schema and cache invalidation work that a config-file approach would avoid.

Make Local SDK Evaluation The Primary Runtime Path

The p99 latency requirement and no-network-hop constraint require request handlers to evaluate flags from an in-process snapshot. The HTTP endpoint exists for compatibility, not as the primary request-path integration.

Stale SDK Caches Delay Kill Switches

If invalidation is slow or broken, support may not be able to disable a bad feature quickly enough. Mitigation: track snapshot age, use short polling intervals or existing push infrastructure, and alert on refresh failures.

SDK Implementations Drift Across Languages

Different language implementations could disagree on rule ordering or bucketing. Mitigation: maintain a shared semantics spec, golden fixtures, cross-language conformance tests, and shared generated test cases.

Production Permissions Are Too Broad Or Too Narrow

Incorrect role mapping could block urgent support action or allow unauthorized production edits. Mitigation: enforce server-side checks, add audit visibility, and test owner/admin/read-only paths explicitly.

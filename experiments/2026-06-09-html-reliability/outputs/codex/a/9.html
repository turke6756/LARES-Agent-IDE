Feature Flag System Implementation Plan

Plan a three-phase feature-flag system that supports dark launches, gradual rollouts, emergency kill switches, typed backend access, audited changes, and an authenticated admin experience within roughly six weeks for a team of three engineers.

Success Criteria

  • Engineering can merge and deploy code paths guarded by typed feature flags without exposing unfinished behavior by default.
  • Product can configure percentage and multivariate rollouts by environment, user, and organization without a deploy.
  • Support and admins can disable a misbehaving production feature within minutes through the existing authenticated product surface.
  • Backend request handling does not add a network hop for flag evaluation, and cached evaluations meet a p99 latency target under one millisecond.
  • Every flag change is persisted with actor, timestamp, before and after values, and target environment for auditability.
  • The first release includes SDK support for both backend languages in the monorepo and a JSON-over-HTTP endpoint for remaining consumers.

Scope

In scope: persistent flag schema, migrations, seed data, audit history, typed accessor libraries, deterministic rollout evaluation, local in-memory caching, cache invalidation, telemetry sampling, backend SDKs, authenticated HTTP evaluation endpoint, and an admin UI for creating, editing, searching, previewing, and archiving flags.

Out of scope: full approval workflows, A/B-test statistics, scheduled rollout automation, mobile SDKs, external SaaS flag providers, and request-path evaluation that depends on a remote service call.

Constraints

  • No new external SaaS dependencies are allowed.
  • The evaluation path must not add a network hop to normal request handling.
  • All admin and API surfaces must sit behind the existing authentication middleware.
  • The plan assumes three engineers and approximately six calendar weeks.
  • Production edits require role-based access: only flag owners and admins may edit production values.
  • Audit history is required, but approval workflows are deliberately deferred.

Assumptions

Primary Postgres Can Store Flag State

The product already has a reliable primary Postgres deployment, migration workflow, and operational backup story suitable for feature flag metadata and audit events.

Existing Authorization Can Express Flag Roles

The current authorization model can be extended or reused to distinguish admins, flag owners, and read-only users without introducing a separate identity system.

Backend SDK Targets Are Known

The two backend languages in the monorepo have stable package patterns and test harnesses that allow SDK work to be delivered inside the same release plan.

Phase 1: Flag Schema and Storage

Build the durable source of truth for flags before any runtime behavior depends on them. This phase establishes the data model, audit trail, migrations, seed data, and typed access primitives needed by later phases.

Phase Goal

Create a reliable, auditable feature flag storage layer in primary Postgres with a read-through cache and typed accessors that can represent boolean, percentage rollout, and multivariate flags across users, organizations, and environments.

Alternatives Considered

Config files in repository: simple review flow and versioning, but too slow for support kill switches and product-controlled rollouts because each change requires a deploy.

External SaaS provider: mature functionality, but rejected because the constraints disallow new external SaaS dependencies.

Primary Postgres with cache: selected because it supports authenticated admin writes, durable audit history, transactional migrations, and local cached reads without adding a request-path network hop.

Recommendations

Use a normalized Postgres-backed design with a compact JSONB rule document for targeting logic, explicit environment override rows, and an append-only audit table. Keep the storage model strict enough for validation while allowing rule shapes to evolve without a migration for every targeting enhancement.

Open Questions

How Should Flag Ownership Be Sourced?

Decide whether the owner field references individual users, teams, service ownership metadata, or a combination. This affects production edit authorization and search filters in the admin UI.

Define the Flag Data Model

Create the canonical schema for flag key, description, owner, type, lifecycle state, default value, salt, targeting rules, variants, environment overrides, timestamps, and actor metadata. Include validation rules for unique keys, valid variant weights, valid percentage ranges, and archived flag immutability expectations.

Add Postgres Migrations

Add migrations for feature_flags, feature_flag_environment_values, and feature_flag_audit_events. Index lookups by key, environment, lifecycle state, owner, and updated timestamp. Ensure audit rows are append-only and include enough before and after data to reconstruct a change.

Introduce the Read-Through Cache Contract

Define the cache abstraction that later evaluation code will use: fetch all active flags for an environment, fetch a single flag by key, expose version or updated-at metadata, and tolerate stale reads within an explicitly documented window. The first implementation may be process-local with clear extension points for push or poll invalidation.

Create Seed Flags and Fixtures

Add representative seed data for a boolean kill switch, a ten-percent rollout, and a multivariate flag. Include staging and production values so migrations, accessors, evaluation tests, and the UI can share realistic fixtures.

Build Typed Accessor Library

Create typed accessors for loading, validating, and serializing flags in the backend language that owns persistence. Expose clear domain types for flag definitions, targeting rules, variants, environments, lifecycle states, and audit event creation.

Implement Audit Event Recording

Wrap create, update, archive, and environment override changes so every mutation writes an audit event in the same transaction. Capture actor, reason if provided, request source, previous value, new value, and affected environment.

Phase 2: Evaluation Engine

Build the runtime path that turns stored flag definitions into deterministic variants. This phase prioritizes latency, determinism, cache correctness, telemetry, and SDK ergonomics.

Phase Goal

Deliver a local evaluation library with deterministic bucketing, well-defined rule precedence, environment inheritance, sampled telemetry, backend SDKs for both monorepo languages, and a JSON-over-HTTP endpoint for consumers that cannot embed an SDK.

Alternatives Considered

Central sidecar-only evaluation: rejected for normal request handling because it risks adding a network hop, even if local to the host.

Database lookup per evaluation: rejected because it cannot reliably meet the p99 target and couples request latency to database health.

Embedded SDK with in-memory cache: selected for request-path evaluation because it keeps reads local, allows deterministic behavior across languages, and still supports an HTTP endpoint for non-critical or non-embedded consumers.

Recommendations

Implement one conformance-test suite shared by both SDKs. Treat the evaluator as pure logic over an immutable snapshot of flag definitions and context, then layer cache refresh, invalidation, and telemetry around it.

Open Questions

Should Cache Invalidation Start With Push or Poll?

Choose whether the first release uses Postgres notifications, an internal pub-sub mechanism, periodic polling, or a hybrid. The decision should balance freshness, operational complexity, and compatibility with existing infrastructure.

Implement Core Evaluation Semantics

Build evaluate(flagKey, context) -> variant as a pure function over a flag snapshot. Define missing flag behavior, archived flag behavior, default fallback behavior, rule ordering, first-match semantics, and explicit handling for user ID, organization, and environment targeting.

Add Deterministic Bucketing

Use a stable hash of user ID plus flag salt to assign percentage rollout buckets. Ensure bucket assignments are stable across SDK languages, insensitive to process restarts, and validated by golden test vectors for boolean, percentage, and multivariate flags.

Implement Environment Inheritance

Define production as the base environment and allow staging to inherit production defaults unless an explicit staging override exists. Make inheritance visible in returned evaluation metadata so the UI and logs can distinguish direct values from inherited values.

Build Local Snapshot Cache and Invalidation

Load active flags into an immutable in-memory snapshot per process. Add polling or push invalidation, version checks, stale snapshot metrics, and a safe fallback policy if refresh fails. The request path should read only from the local snapshot.

Ship Backend SDKs and HTTP Endpoint

Expose idiomatic SDK functions for both backend languages, including typed helpers for booleans and variants. Add a JSON-over-HTTP endpoint for other consumers behind existing auth, with clear documentation that normal latency-sensitive request paths should prefer embedded SDK evaluation.

Emit Sampled Evaluation Telemetry

Emit sampled events containing flag key, variant, environment, match reason, SDK language, service name, and non-sensitive context identifiers. Avoid logging raw targeting payloads that could contain personal data. Add counters for cache age, evaluation errors, and unknown flags.

Phase 3: Admin UI

Build the authenticated operational surface for product, engineering, and support. This phase turns the storage and evaluation foundations into controlled workflows for managing flags safely.

Phase Goal

Deliver an authenticated dashboard where users can create, edit, search, preview, audit, and archive flags, with per-environment overrides and production edit restrictions for owners and admins.

Alternatives Considered

CLI-only management: useful for engineers but insufficient for product and support workflows.

Admin UI generated directly from database forms: quick to build but too easy to bypass domain validation, preview behavior, and permission rules.

Purpose-built dashboard: selected because it can present lifecycle state, environment inheritance, rollout previews, audit history, and role-based controls in one coherent workflow.

Recommendations

Use existing product layout, auth middleware, API patterns, and role primitives. Keep creation and editing forms schema-driven from the same validation rules used by backend persistence to reduce drift.

Open Questions

Should Production Edits Require a Reason Field?

Audit history can store an optional reason, but the team should decide whether production changes require a reason to improve later incident review without creating a formal approval workflow.

Build Flag Dashboard and Search

Create a dashboard page listing flag key, description, owner, type, lifecycle state, updated timestamp, and environment summary. Add search and filters for key, owner, type, state, and environment so support can quickly find kill switches.

Create Flag Editor Workflows

Implement create and edit screens for boolean, percentage rollout, and multivariate flags. Validate keys, defaults, targeting rules, variant weights, lifecycle state transitions, and environment overrides before submitting changes.

Add Rollout Slider and Bucketing Preview

Add a percentage rollout slider with live preview showing sample users, bucket boundaries, and expected inclusion changes before save. Use the same deterministic bucketing implementation or shared test vectors as the evaluation engine.

Enforce Role-Based Access

Apply existing auth middleware and authorization checks so all authenticated users can view permitted flag data, but only flag owners and admins can edit production values. Ensure server-side checks mirror UI affordances and are covered by tests.

Expose Audit History

Display audit events for each flag with actor, timestamp, environment, change type, before and after values, and reason if available. Keep the view readable for incident review and support handoff.

Implement Archive Flow

Add an archive action that removes flags from active editing and evaluation lists while preserving historical records. Require confirmation when archiving active production flags and write an audit event for the transition.

Use Primary Postgres With a Read-Through Cache for Flag Storage

Flags should live in a new Postgres-backed storage model with a process-local read-through cache. This satisfies no-SaaS constraints, supports audited admin writes, allows support-driven emergency changes without deploys, and keeps request-path evaluation local once snapshots are loaded.

A config-file-in-repo approach gives strong code review and simple history, but it fails the kill-switch and product rollout requirements because changes would depend on pull requests and deployments.

Cache Staleness Could Delay Emergency Kill Switches

If cache invalidation is too slow or unreliable, support may believe a feature is disabled while some processes continue serving the old snapshot. Mitigation: define a freshness SLO, expose cache age metrics, include manual refresh hooks, and test invalidation failure modes before launch.

SDKs Could Evaluate the Same Flag Differently

Different hash implementations, JSON parsing behavior, or rule ordering bugs across backend languages could split traffic incorrectly. Mitigation: maintain shared golden test vectors and run conformance tests in both SDK packages.

Production Edit Permissions Could Be Too Broad

Incorrect role checks could let non-owners change production behavior. Mitigation: enforce authorization server-side, add explicit tests for owner, admin, and read-only users, and make audit history visible from the first release.

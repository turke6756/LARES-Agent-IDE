Feature Flag System Plan

Build an internal feature-flag system across schema, evaluation engine, and admin UI so engineering can ship dark, product can roll out gradually, and support can disable broken features without a deploy.

Success Criteria

  • Engineers can define typed flags with defaults, lifecycle state, owners, and targeting metadata through migrations and seed data.
  • Backend services can evaluate flags locally with p99 latency below one millisecond, without adding a network hop to normal request handling.
  • Product and support users can search, create, edit, archive, and inspect flags through an authenticated admin dashboard.
  • Production edits are restricted to flag owners and admins, and every flag mutation is captured in audit history.
  • Percentage and multivariate rollouts are deterministic for a stable context and can be previewed before rollout changes are saved.

Scope

The plan covers persistent flag storage, schema migrations, seed data, a typed accessor library, a fast local evaluation engine, SDKs for the two backend languages in the monorepo, a JSON-over-HTTP evaluation endpoint for non-core callers, telemetry emission, cache invalidation, and an authenticated admin UI.

Out of scope are A/B-test statistics, scheduled rollouts, mobile SDKs, a full approval workflow, and any external SaaS dependency.

Constraints

  • No new external SaaS dependencies are allowed.
  • The evaluation path used during request handling must be local and must not perform remote I/O.
  • All admin and API surfaces must sit behind the existing authentication middleware.
  • The team is three engineers with roughly six weeks available.
  • Production edits require role-based access control that permits only flag owners and admins.

Assumptions

Existing authorization can support flag ownership checks

The plan assumes the current auth middleware can provide user identity, admin status, and enough role data to enforce production-edit permissions without introducing a separate authorization platform.

Backend SDKs can be packaged as shared monorepo libraries

The plan assumes both backend languages already have internal package distribution conventions, allowing the evaluation SDKs to be consumed by services without special deployment work.

Primary Postgres has enough capacity for control-plane traffic

Flag reads are expected to be cache-backed and low volume relative to request traffic, while writes and audit entries should be small enough for the primary database.

Phase 1: Flag Schema and Storage

Create the durable control plane for flags: normalized storage, audit history, migration path, seed data, and typed accessors used by the rest of the system.

Phase Goal

Establish a reliable source of truth for feature flags in primary Postgres with cache-friendly read models, typed definitions, and immutable audit records for every create, edit, archive, and environment override mutation.

Alternatives Considered

A config-file-in-repo approach would give excellent code review and rollback mechanics, but it would not let support kill a feature without a deploy and would make gradual rollout changes too slow. The recommended path is a new Postgres-backed flag store plus read-through cache because the feature needs operational edits and auditability.

Recommendations

Use Postgres as the source of truth and store flag definitions, environment-specific values, targeting rules, variants, salts, ownership, lifecycle state, and audit entries in explicit tables. Generate a compact read model for evaluation caches so the engine does not need to assemble complex relational state during request handling.

Open Questions

What value types must multivariate flags support initially?

Confirm whether variants are limited to strings and booleans for launch, or whether JSON payload variants are required from day one.

Define Flag Domain Model

Specify the canonical model for flag key, description, owner, type, default value, lifecycle state, salt, environment values, targeting rules, and variants. Include validation rules for key format, unique ownership, percentage bounds, variant weights, and active versus archived behavior.

Create Postgres Migrations

Add tables for feature_flags, feature_flag_environments, feature_flag_rules, feature_flag_variants, and feature_flag_audit_events. Include indexes for key lookup, active flags, owner search, environment lookup, and audit history by flag.

Build Cache Read Model

Define a serialized flag bundle format consumed by the evaluation engine. The bundle should include all active flags, version metadata, environment inheritance data, salts, ordered rules, and defaults so services can refresh in memory without extra database joins.

Add Seed Flags and Fixtures

Create representative seed data for boolean, percentage rollout, and multivariate flags across production and staging. Use the same fixtures for migration verification, SDK tests, and admin UI development.

Implement Typed Accessor Library

Expose repository functions for creating, updating, archiving, listing, and fetching flags, plus a typed read path for the evaluation bundle. The library should centralize validation and audit-event creation so the admin API cannot bypass consistency checks.

Phase 2: Evaluation Engine

Build the local runtime path that evaluates flags deterministically and quickly for services, with cache invalidation, telemetry, and compatibility for callers outside the two main backend languages.

Phase Goal

Deliver a local in-memory evaluator that supports ordered rules, environment inheritance, deterministic percentage bucketing, multivariate variants, sampled telemetry, SDKs for both backend languages, and a JSON-over-HTTP endpoint for non-core systems.

Alternatives Considered

A central sidecar or service-only evaluator would simplify consistency, but it would violate the no-network-hop constraint for request handling. The recommended approach is a shared evaluator library embedded in services, with an optional HTTP endpoint for tooling and lower-throughput callers.

Recommendations

Implement the evaluator as a pure function over an immutable in-memory flag bundle. Use a stable hash of userId, flag salt, and variant namespace for percentage decisions. Refresh bundles by push where existing infrastructure supports it and fall back to short-interval polling with version checks.

Open Questions

Which existing channel should drive cache invalidation?

Confirm whether the platform already has pub/sub, message bus, or deploy-time config refresh hooks suitable for pushing flag bundle version changes to services.

Implement Core Evaluation Semantics

Define and code evaluate(flagKey, context) -> variant with missing-flag behavior, default fallback, rule ordering, user ID targeting, organization targeting, environment targeting, and environment inheritance where staging can inherit production defaults unless explicitly overridden.

Add Deterministic Bucketing

Use a stable non-cryptographic hash over user identifier and per-flag salt to assign percentage rollouts and multivariate variants. Include tests proving assignment stability, approximate distribution, salt isolation, and behavior when rollout percentages change.

Build Local Cache and Invalidation

Load a complete active-flag bundle into process memory at startup, refresh it atomically, and expose current version metadata. Prefer push invalidation when an existing internal channel is available; otherwise poll a lightweight version endpoint and fetch the bundle only when the version changes.

Ship Backend SDKs

Create SDK packages for both backend languages in the monorepo with the same conceptual API, typed context object, typed variant result, safe default helpers, cache status diagnostics, and integration examples for request handlers.

Add JSON-over-HTTP Evaluation Endpoint

Expose an authenticated endpoint for lower-throughput callers that cannot use the native SDKs. Document that request-path services must use local SDK evaluation and that the endpoint is not the primary hot path.

Emit Sampled Evaluation Telemetry

Record sampled events containing flag key, environment, variant, rule match type, service name, and anonymized context identifiers where allowed. Ensure telemetry emission is non-blocking and cannot push evaluation over the latency target.

Phase 3: Admin UI

Provide the authenticated operational interface for product, engineering, and support to manage flags safely across environments.

Phase Goal

Deliver a dashboard for creating, editing, searching, archiving, previewing, and auditing feature flags, with per-environment overrides and production edit permissions enforced for owners and admins.

Alternatives Considered

A database-only internal tool would be faster to build but would make permission checks, validation, rollout preview, and audit visibility fragile. A purpose-built admin page is recommended because the tool will be used during incidents and rollout decisions.

Recommendations

Build the UI on the existing authenticated admin shell, reuse standard form components, and keep the first release focused on reliable flag operations. Use server-side validation from the typed accessor library so UI and API behavior stay consistent.

Open Questions

How explicit should production-change confirmation be?

Decide whether production value changes require a typed confirmation, a modal summary, or only a standard save confirmation given that a full approval workflow is out of scope.

Build Flag Dashboard and Search

Create a dashboard showing active and archived flags with search by key, description, owner, type, environment, and lifecycle state. Include clear indicators for production overrides and recently changed flags.

Create Flag Editor

Implement forms for boolean, percentage rollout, and multivariate flags. Support owner assignment, descriptions, defaults, per-environment values, ordered targeting rules, and archive actions using the same validation rules as the storage layer.

Add Percentage Rollout Slider and Preview

Provide a rollout slider with a live preview of sample user bucketing. The preview should use the same hashing algorithm as the evaluator so users can see whether selected identifiers would receive the feature before saving.

Implement Audit History View

Show chronological changes for each flag, including actor, timestamp, environment, changed fields, previous values, and new values. Make audit history accessible from the flag detail page and searchable enough for incident review.

Enforce Role-Based Production Editing

Gate production edits in both UI and API so only flag owners and admins can change production values. Non-authorized users may view flags and edit non-production environments only if their existing role permits it.

Use Postgres as the source of truth with a read-through evaluation cache

The feature needs operational edits, audit history, and no-deploy kill switches. A Postgres-backed control plane supports those needs while the local in-memory evaluator protects request latency.

A config-file-in-repo design would improve reviewability but would make support and product dependent on deploy cadence for urgent or gradual changes.

Use embedded SDK evaluation for request-path services

The evaluation path must not add a network hop. Native SDKs using an in-memory bundle satisfy the latency constraint, while an HTTP endpoint remains available for systems that are not on latency-sensitive paths.

Stale caches delay kill-switch effectiveness

If services poll too slowly or miss push invalidations, a disabled feature may continue serving for longer than support expects. Mitigation: versioned bundles, visible cache age diagnostics, short fallback polling intervals, and an operational target for maximum propagation delay.

Evaluation misses the sub-millisecond p99 target

Complex rule evaluation, telemetry overhead, or lock contention could push latency above target. Mitigation: immutable bundles, lock-free read paths, precompiled rule structures, benchmark coverage, and asynchronous telemetry.

Production edit permissions are enforced inconsistently

If the UI hides controls but the API does not enforce the same checks, unauthorized production edits are possible. Mitigation: centralize authorization in the admin API and treat UI checks as presentation only.

Six-week schedule leaves little room for polish

Three phases across storage, SDKs, telemetry, and UI may exceed the team capacity. Mitigation: prioritize boolean and percentage flags first, keep A/B analytics out of scope, and timebox multivariate UI complexity.

Feature Flag System Plan

Build an internal feature-flag system in three phases so engineering can ship dark code, product can run gradual rollouts, and support can disable misbehaving features without a deploy, while keeping request-path evaluation local and fast.

Success Criteria

  • Backend services can call a typed evaluate(flagKey, context) API and receive a boolean or variant value with p99 evaluation time under 1 millisecond after local cache warmup.
  • Engineering can define, seed, and read flags with stable keys, typed defaults, targeting rules, lifecycle state, ownership, and audit history.
  • Product and support users can create, search, edit, override, and archive flags through an authenticated admin UI.
  • Production edits are restricted to flag owners and admins, with all changes captured in audit history.
  • Evaluation works without adding a network hop to normal request handling.
  • The first production-ready version ships within roughly six weeks with a team of three engineers.

Scope

In scope: a Postgres-backed flag schema, migrations, seed data, audit history, read-through caching, a typed accessor library, deterministic percentage bucketing, rule ordering, environment inheritance, SDKs for the two backend languages in the monorepo, a JSON-over-HTTP evaluation endpoint for non-request-path consumers, sampled telemetry events, and an admin dashboard.

Out of scope: full approval workflows, external feature-management SaaS, A/B-test statistical analysis, scheduled rollouts, mobile SDKs, and any design that requires request handlers to call a remote service during flag evaluation.

Constraints

  • No new external SaaS dependencies are allowed.
  • The request-path evaluation flow must be local to the process or sidecar cache and must not require a network round trip.
  • All admin and HTTP surfaces must sit behind existing authentication middleware.
  • The rollout must fit a three-engineer team over about six weeks.
  • Audit history is required, but production approval gates are deferred.

Assumptions

Existing auth can support edit permissions

The plan assumes the current authentication and authorization stack can identify admins and can support owner-based write checks for production flag values.

Two backend SDKs cover request-path services

The first release targets the two backend languages currently used for request handling; other consumers use the HTTP endpoint or a later SDK.

A practical invalidation mechanism already exists

The plan assumes we can use an existing internal pub/sub mechanism or fall back to short-interval polling with version checks for local cache invalidation.

Phase 1: Flag Schema and Storage

Establish the durable model, migrations, audit trail, seed flags, and typed accessors that every later phase depends on.

Phase Goal

Ship a reliable Postgres-backed flag registry with typed values, explicit ownership, lifecycle state, targeting-rule storage, environment overrides, audit history, and a cacheable read API.

Alternatives Considered

A config-file-in-repo approach would be simple, reviewable, and easy to bootstrap, but it cannot satisfy support kill-switch edits without deploys and would put product rollouts behind engineering merge cadence. A dedicated external SaaS is ruled out by constraint. The recommended storage path is a new primary Postgres table plus audit table and read-through cache.

Recommendations

Use Postgres as source of truth, store rules and variants as validated structured JSON with typed columns for key metadata, and expose a typed library that hydrates validated flag definitions into immutable in-process snapshots.

Open Questions

Where should rule JSON validation live?

Decide whether rule-shape validation is enforced only in application code or also through database constraints and check functions.

Define the canonical flag model

Create the domain model for flag key, description, owner, type, variants, default value, targeting rules, supported environments, lifecycle state, salt, and timestamps. Include validation rules for key format, owner presence, default value compatibility, variant weights, and archived flag behavior.

Add Postgres migrations

Create feature_flags, environment override storage, and feature_flag_audit_events. Include uniqueness constraints on keys, indexes for search and active flag lookup, and a monotonically increasing version or updated-at field for cache invalidation.

Implement audit history writes

Capture create, update, archive, and environment override changes with actor, timestamp, old value summary, new value summary, reason when supplied, and request metadata available from existing middleware.

Add seed data and sample flags

Seed a small set of non-production example flags covering boolean, percentage rollout, and multivariate types. Use them in local development, smoke tests, and admin UI previews without affecting real product behavior.

Build the typed accessor library

Expose read APIs for loading flag snapshots by environment and key, parsing structured rules, enforcing type compatibility, and returning immutable objects suitable for engine consumption. Add unit tests for malformed flags and backwards-compatible schema evolution.

Phase 2: Evaluation Engine

Deliver the runtime evaluation path, cache invalidation, SDKs, HTTP endpoint, and telemetry needed for controlled rollout without adding request latency.

Phase Goal

Provide deterministic, local, sub-millisecond flag evaluation for request-path services, with consistent behavior across SDKs and a safe integration surface for secondary consumers.

Alternatives Considered

A central evaluation service would simplify consistency, but it violates the no-network-hop constraint for request handling. A sidecar-only design may help some services but adds deployment complexity. The recommended design is an embedded SDK evaluation engine with local snapshots, plus an HTTP endpoint for tools, jobs, and systems that are not in the synchronous request path.

Recommendations

Implement the engine once as a small shared core where practical, then wrap it in language-specific SDKs. Use a stable hash of flag salt and user or organization identifier for percentage bucketing, evaluate rules in explicit priority order, and emit sampled telemetry asynchronously.

Open Questions

What cache freshness target is required?

Choose a maximum propagation delay for production flag changes, especially support kill switches, so push-or-poll invalidation can be sized correctly.

Define rule ordering and inheritance semantics

Document and implement evaluation precedence: explicit user targeting, organization targeting, environment-specific overrides, percentage rollout, multivariate allocation, and default value. Define staging inheritance from production and how explicit staging overrides break inheritance.

Implement deterministic bucketing

Use a stable hash over flag key or salt plus the chosen bucketing identifier. Ensure percentage and multivariate rollouts remain stable across deploys, SDK languages, and cache refreshes. Add golden test vectors shared by both SDK implementations.

Add local in-memory cache and invalidation

Load a full environment snapshot into memory, serve evaluations from immutable snapshots, and refresh via push notification when available or polling by version when not. Preserve the last good snapshot if refresh fails.

Build backend SDKs

Provide idiomatic SDK APIs for the two backend languages, including typed evaluation helpers, context builders, default fallback behavior, metrics hooks, and startup warmup. Include integration tests against identical fixture snapshots.

Expose JSON-over-HTTP evaluation endpoint

Add an authenticated internal endpoint for non-request-path consumers. The endpoint should use the same engine and snapshots as SDKs, return variant metadata, and include rate limits or operational safeguards appropriate for internal callers.

Emit sampled evaluation telemetry

Emit asynchronous sampled events containing flag key, environment, returned variant, matched rule category, SDK version, and non-sensitive context identifiers. Avoid blocking request handling and exclude raw personally identifiable data.

Phase 3: Admin UI

Build the authenticated operational interface for creating, changing, searching, previewing, and auditing flags.

Phase Goal

Give engineering, product, and support a safe dashboard to manage feature flags with environment-aware editing, production write controls, rollout preview, archive support, and audit visibility.

Alternatives Considered

A CLI-only first release would be faster for engineering but would not meet product rollout or support kill-switch needs. A broad experimentation dashboard would exceed scope. The recommended UI is a focused internal admin page for flag lifecycle and rollout control only.

Recommendations

Integrate with the existing admin shell and auth middleware. Prioritize dense searchable tables, explicit environment tabs, clear production edit affordances, and preview tooling that explains which users or organizations fall into a rollout without exposing sensitive data unnecessarily.

Open Questions

Should production edits require a reason?

Decide whether the UI must require a short reason for production changes so audit history is more useful during incident review.

Create dashboard list and search

Build a dashboard page listing key, description, owner, type, lifecycle state, environments, and last updated time. Support search by key, owner, description, and active or archived state.

Build create, edit, and archive flows

Add forms for creating and editing flags with validation matching the schema model. Include archive behavior that prevents normal evaluation changes while preserving audit history and historical reads.

Add per-environment override controls

Expose production, staging, and other configured environments with clear inherited versus overridden values. Make staging inheritance from production visible and allow explicit overrides where permitted.

Implement rollout slider and bucketing preview

Add a percentage slider for rollout flags and a preview panel showing deterministic sample bucket assignments for representative user or organization IDs. Use the same hashing logic as the evaluation engine to avoid UI-runtime drift.

Display audit history

Show chronological audit events for each flag, including actor, timestamp, changed fields, environment, and reason when present. Provide enough detail for incident review without turning the UI into an approval workflow.

Enforce role-based production access

Restrict production edits to flag owners and admins in both UI and API layers. Non-authorized users may view flags and edit allowed non-production values only if existing product permissions allow it.

Use Postgres plus read-through caching as the source of truth

Flags should live in a new Postgres-backed model rather than config files in the repo. This supports support-driven kill switches, product-owned gradual rollout changes, audit history, search, and authenticated admin edits without deploys.

Config files are simpler and naturally reviewed, but they do not meet the operational requirement to change production flag values without a deploy.

Use embedded SDK evaluation for request handling

Request-path services should evaluate flags from local in-memory snapshots through language SDKs. A JSON-over-HTTP endpoint is still useful for secondary consumers, but normal request handling must not depend on a remote evaluation call.

A central service would be easier to operate consistently, but it adds latency and availability coupling to every request that evaluates a flag.

Kill-switch changes may propagate too slowly

If cache invalidation relies only on polling, a misbehaving production feature may continue evaluating as enabled until the next refresh. Mitigation: define a freshness SLO, prefer push invalidation where available, use short polling intervals for active services, and expose last-refresh health metrics.

SDKs may drift across languages

Different hash implementations, JSON parsing behavior, or fallback semantics could produce inconsistent variants. Mitigation: maintain shared fixtures, golden bucket vectors, and cross-language conformance tests as release blockers.

Production edit permissions may be incomplete

If ownership and admin checks are enforced only in the UI, direct API calls could bypass intended controls. Mitigation: enforce permissions server-side and treat UI affordances as convenience only.

Evaluation telemetry could create excessive event volume

High-traffic request paths may emit too many sampled events if defaults are too aggressive. Mitigation: centralize sample-rate configuration, emit asynchronously, and add per-service caps or adaptive sampling.

Feature Flag System Rollout Plan

Build a first-party feature-flag platform across schema, low-latency evaluation, and an authenticated admin UI so engineering can dark ship, product can run gradual rollouts, and support can disable problematic features without a deploy.

Success Criteria

  • Backend callers can evaluate boolean, percentage, and multivariate flags through typed accessors in both monorepo backend languages.
  • The hot evaluation path is local to request handling, avoids a network hop, and meets sub-millisecond p99 latency under expected production flag counts.
  • Product and support users can create, edit, search, archive, and audit flags through an admin UI protected by existing authentication and role checks.
  • Production edits are restricted to flag owners and admins, with audit history captured for every material flag change.
  • The system supports safe rollout and kill-switch workflows for at least the first set of migrated product features by the end of the six-week window.

Scope

In scope: persistent flag schema, migrations, seed data, typed accessor library, audit history, deterministic evaluation, local cache invalidation, SDKs for the two backend languages, JSON-over-HTTP evaluation for non-request-path consumers, sampled telemetry, and an admin dashboard with environment overrides.

Out of scope: A/B-test analysis, scheduled rollouts, mobile SDKs, full approval workflow, and any new external SaaS dependency.

Constraints

  • No new external SaaS dependencies; storage, cache, telemetry, and UI must use existing platform components.
  • The request-time evaluation path must not make a network call.
  • All admin surfaces and HTTP endpoints must sit behind the existing auth middleware.
  • Team size is three engineers, with roughly six calendar weeks available.
  • Evaluation should return evaluate(flagKey, context) -> variant in under one millisecond at p99.

Assumptions

Reusable Invalidation Path Exists

The plan assumes the product already has either a cache invalidation bus, internal event stream, or accepted polling pattern that services can use to refresh in-memory flag snapshots.

Backend SDK Packaging Is Straightforward

The plan assumes the two backend languages have established internal package distribution patterns and can consume generated or shared flag type definitions.

Existing Auth Can Carry Role Checks

The plan assumes current auth middleware can identify admins, support users, and flag owners without introducing a separate identity system.

Phase 1: Flag Schema and Storage

Establish the durable source of truth, typed domain model, migrations, seed data, and audit trail before wiring runtime evaluation or admin editing paths.

Phase Goal

Create a stable feature flag data model in primary Postgres with a read-through cache boundary, plus a typed accessor library that prevents ad hoc flag reads from spreading through the codebase.

Alternatives Considered

Config file in repo: simpler review and deployment mechanics, but it cannot support support-led kill switches without deploys and makes live audit/UI edits awkward.

Postgres source of truth: better fit for admin editing, audit history, environment overrides, and emergency changes. This is the recommended path, with local caches protecting runtime reads.

Recommendations

  • Use primary Postgres as the authoritative store and keep request-path evaluation on in-memory snapshots.
  • Model flag definitions separately from environment-specific values and targeting rules so production permission checks are precise.
  • Store audit events append-only with actor, timestamp, environment, changed fields, previous value, and new value.

Open Questions

How Strictly Should Targeting Rules Be Normalized?

Decide whether rules should be fully normalized relational rows or stored as validated JSON with a versioned schema. Validated JSON is faster to deliver; normalized rows are easier to query and inspect.

Define Flag Domain Model

Specify fields for key, description, owner, type, default value, lifecycle state, salt, environments, targeting rules, variants, and metadata. Include validation rules for unique keys, owner presence, allowed variant weights, archived behavior, and production edit restrictions.

Create Postgres Migrations

Add tables for feature_flags, environment overrides, targeting rules or validated rule JSON, variants, and append-only audit entries. Add indexes for key lookup, lifecycle filtering, owner filtering, and audit history by flag and timestamp.

Add Seed Flags

Seed representative boolean, percentage, and multivariate flags in non-production environments. Include at least one archived sample and one environment override so admin UI and evaluator tests have realistic fixtures.

Implement Audit History Writes

Create a shared mutation layer that records every create, edit, archive, and environment override change. Ensure audit entries include actor, source surface, before and after payloads, and a correlation ID when available.

Build Typed Accessor Library Skeleton

Expose typed flag keys and expected return types so callers do not hard-code raw strings or cast variants manually. Include compile-time or test-time checks that seeded and registered keys match known definitions.

Phase 2: Evaluation Engine

Build the runtime evaluator that can be embedded locally into services, backed by a refreshed in-memory snapshot and exposed through SDKs plus an internal HTTP endpoint for non-critical consumers.

Phase Goal

Deliver deterministic, sub-millisecond local evaluation for flag keys and caller context, with consistent semantics across backend SDKs and operational telemetry for later analysis.

Alternatives Considered

Central sidecar-only evaluation: simpler consistency story, but it risks adding a request-time network hop and violates the latency constraint unless every service embeds it locally.

Embedded library with optional HTTP endpoint: keeps request-time evaluation in process while still giving batch jobs, scripts, and secondary services a generic JSON interface.

Recommendations

  • Use a canonical evaluator core and thin language-specific wrappers to keep rule semantics aligned.
  • Use hash-based bucketing from user ID, flag salt, and variant key for deterministic percentage rollouts.
  • Prefer push invalidation if an internal bus is available; otherwise use short-interval polling with jitter and snapshot version checks.

Open Questions

Can Both Backend SDKs Share One Evaluator Core?

Confirm whether code generation, FFI, or a small duplicated implementation is the best fit for the two backend languages while preserving identical bucketing and rule ordering behavior.

Specify Evaluation Semantics

Define rule precedence for user ID, org, environment, percentage rollout, multivariate variants, defaults, archived flags, and missing context. Document environment inheritance, including staging defaulting from production unless explicitly overridden.

Implement Deterministic Bucketing

Use a stable hash of user ID plus flag salt to assign users into percentage buckets. Add golden test vectors so both backend SDKs and the HTTP endpoint return identical variants for the same inputs.

Build In-Memory Snapshot Cache

Load active flag definitions into immutable local snapshots keyed by version. Implement read-through startup behavior, refresh failure handling, stale snapshot limits, and push-or-poll invalidation without blocking request handling.

Ship Backend SDKs

Provide idiomatic evaluate(flagKey, context) APIs for both backend languages in the monorepo. Include typed return helpers for boolean and variant values, context builders, and safe fallback behavior for unknown flags.

Add JSON-over-HTTP Endpoint

Expose an authenticated internal endpoint for consumers that cannot use the backend SDKs. Mark it unsuitable for latency-sensitive request paths and enforce rate limits and structured error responses.

Emit Sampled Evaluation Telemetry

Emit sampled events containing flag key, environment, returned variant, rule match category, SDK language, snapshot version, and non-PII context identifiers where permitted. Ensure telemetry failure never changes evaluation results.

Phase 3: Admin UI

Build the authenticated operational surface for creating, editing, searching, archiving, previewing, and auditing feature flags across environments.

Phase Goal

Give engineering, product, and support a reliable dashboard for managing flags while protecting production changes with role-based access and clear audit visibility.

Alternatives Considered

Internal API only: faster for engineering, but insufficient for support kill switches and product-led gradual rollouts.

Full admin UI: more upfront work, but required for safe operational ownership and auditability across teams.

Recommendations

  • Start with a compact dashboard optimized for search, status scanning, and fast environment edits.
  • Use the same mutation APIs as seed and migration tooling so audit history stays consistent.
  • Make production changes visibly distinct and require owner/admin authorization at the API layer, not only in the UI.

Open Questions

Where Should Flag Ownership Be Sourced?

Decide whether owners are individual users, teams, code-owner groups, or a combination. This affects production edit authorization, filtering, and handoff when teams change.

Build Dashboard List and Search

Create a dashboard page showing flag key, description, owner, type, lifecycle state, environments, and recent update metadata. Add search and filters for owner, state, type, and environment.

Implement Create and Edit Workflows

Add forms for boolean, percentage, and multivariate flags with validation matching the schema layer. Support editing description, owner, defaults, variants, targeting rules, and lifecycle state.

Add Per-Environment Overrides

Expose environment-specific values and targeting rules with clear inheritance indicators. Show when staging inherits from production and when an explicit override is active.

Create Rollout Slider and Bucket Preview

Add a percentage slider for rollout flags and a live preview that shows sample users or entered identifiers mapping into enabled and disabled buckets using the same hashing logic as the evaluator.

Surface Audit History

Show chronological audit entries for each flag, including actor, timestamp, environment, changed fields, previous values, and new values. Link audit entries back to the relevant flag detail page.

Enforce Role-Based Access

Use existing auth middleware to restrict production edits to flag owners and admins. Allow broader read access where appropriate, and make archive and production override actions server-authorized and audited.

Use Postgres as Source of Truth with Local Cached Evaluation

The feature-flag system should store flag definitions, environment overrides, targeting rules, and audit history in primary Postgres. Runtime evaluators should read from local in-memory snapshots refreshed through cache invalidation or polling.

This supports admin edits, support kill switches, audit history, and environment-specific overrides while preserving the constraint that request-time evaluation cannot add a network hop.

A config-file-in-repo approach would be simpler to review but would make urgent support changes and product-operated gradual rollouts depend on deploys.

Stale Local Flag Snapshots

If invalidation fails or polling intervals are too long, services may continue evaluating old flag values after a kill switch or production rollback. Mitigation: snapshot versioning, bounded staleness alerts, refresh metrics, and manual refresh hooks for critical services.

SDK Evaluation Semantics Drift

Two backend SDKs may diverge in rule ordering, bucketing, or default handling. Mitigation: shared specification, golden fixtures, cross-language test vectors, and CI checks that compare evaluator outputs.

Unsafe Production Edits

A permissive UI or incomplete server-side authorization could allow accidental production changes. Mitigation: enforce owner/admin checks in API handlers, clearly separate environments in the UI, and audit every mutation.

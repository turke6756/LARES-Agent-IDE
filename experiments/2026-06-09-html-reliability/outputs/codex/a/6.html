Feature Flag System Rollout Plan

Plan a three-phase delivery of an internal feature-flag system covering durable schema and storage, a low-latency evaluation engine, and an authenticated admin UI for controlled rollout and emergency kill switches.

Success Criteria

  • Engineering can merge and deploy code paths guarded by typed feature-flag accessors without exposing them to users by default.
  • Product and support can update non-archived flags through an authenticated UI, with production edits restricted to flag owners and admins.
  • Backend request paths evaluate flags locally without adding a network hop and meet a p99 evaluation target below one millisecond under normal cache-warm conditions.
  • Percentage rollouts are deterministic, explainable, and stable for a given user, flag, and salt.
  • Every flag mutation is auditable, including who changed what, when, and for which environment.
  • Evaluation telemetry is sampled and emitted in a form that supports later analysis without creating unacceptable request latency or event volume.

Scope

The work covers a new flag data model, storage and migrations, seed data, audit history, typed backend accessors, a deterministic evaluation library, cache invalidation, SDK surfaces for the two backend languages in the monorepo, a JSON-over-HTTP endpoint for non-native consumers, and an admin dashboard for flag management.

The plan deliberately excludes a full approval workflow, A/B-test statistics, scheduled rollouts, mobile SDKs, and any external feature-management SaaS dependency.

Constraints

  • No new external SaaS dependencies are allowed.
  • The evaluation path must not add a network hop to ordinary request handling.
  • All admin and API surfaces must sit behind existing authentication middleware.
  • The team size is three engineers and the target delivery window is roughly six weeks.
  • The design must support boolean, percentage rollout, and multivariate flags from the first release.
  • Production edit authorization must distinguish admins, flag owners, and non-owner viewers or editors.

Assumptions

Primary Postgres Can Store Flag Definitions

The existing primary Postgres instance is suitable for authoritative feature-flag definitions and audit history, with application-side caching used to protect request latency.

Existing Auth Can Support Flag Permissions

The current authentication and authorization layer can be extended or reused to enforce owner and admin permissions for production flag changes.

Two Backend SDKs Cover Critical Services

The two backend languages mentioned in the brief cover the request paths that need local flag evaluation for the initial launch.

Phase 1: Flag Schema and Storage

Establish the authoritative data model, migration path, audit trail, seed data, and typed accessor foundation that later phases will consume.

Phase Goal

Create a durable, validated source of truth for feature flags that supports all required flag types, environment-specific configuration, targeting rules, lifecycle state, and audit history without relying on external services.

Alternatives Considered

A config-file-in-repo approach would provide strong code review and simple local development, but it would make support-driven kill switches and product-managed gradual rollouts depend on deploys. The recommended path is a Postgres-backed model with a read-through cache, plus seed data and typed accessors for developer ergonomics.

Recommendations

Use Postgres as the authoritative store with separate tables for flag definitions, per-environment values, targeting rules, variants, and audit events. Store rule configuration in structured JSON only where rule shape is intentionally extensible, and validate it at the application boundary with typed schemas.

Open Questions

Which existing cache should back read-through flag lookups?

Confirm whether the product already has Redis, an in-process shared cache abstraction, or another approved cache layer that can be reused without adding a new external dependency.

Define Flag and Environment Schema

Design migrations for feature flag keys, descriptions, owners, flag type, lifecycle state, salts, default variants, per-environment overrides, and rule definitions. Include database constraints for unique keys, valid lifecycle states, and referential integrity between flags, variants, rules, and environments.

Add Audit History Tables

Create append-only audit records for create, update, archive, and environment override changes. Capture actor, timestamp, flag key, environment, before and after values, and request metadata available from existing middleware.

Create Seed Flags

Add seed data for representative boolean, percentage, and multivariate flags in non-production environments. Include at least one disabled-by-default production flag to validate the dark-launch workflow.

Build Typed Accessor Library

Expose typed definitions for flag keys, context shape, variants, and default values. Make invalid flag keys and incompatible variant reads fail early in development where possible and return safe defaults in production runtime paths.

Create Internal CRUD API Foundation

Implement authenticated internal endpoints for listing, reading, creating, updating, and archiving flags. Keep production write authorization strict from the beginning so the admin UI does not need to compensate for weak server-side checks.

Phase 2: Evaluation Engine

Implement the low-latency runtime path that resolves a flag key and request context into a boolean or variant answer with deterministic rollout semantics.

Phase Goal

Deliver local, deterministic flag evaluation for backend services with cache-backed configuration loading, consistent rule ordering, environment inheritance, SDK coverage for the two backend languages, and sampled evaluation telemetry.

Alternatives Considered

A sidecar service would centralize evaluation logic but would risk adding operational complexity and could add a network hop if misused. The recommended default is an embedded library for request paths, with an HTTP endpoint only for clients that cannot adopt a native SDK.

Recommendations

Keep evaluation pure and data-driven: services periodically receive a compiled flag snapshot, then evaluate synchronously in memory. Use a shared test corpus across SDKs so boolean, percentage, multivariate, targeting, and inheritance semantics stay identical.

Open Questions

Should cache invalidation be push-first or poll-first?

Decide whether to start with short-interval polling for simplicity or use an existing pub/sub mechanism for faster propagation of kill-switch changes.

Implement Core Evaluation Semantics

Build the shared algorithm for rule matching, explicit user and organization targeting, environment-specific overrides, production-to-staging inheritance, default fallback, and inactive or archived flag behavior. Define rule ordering as first match wins, followed by percentage or default evaluation.

Add Deterministic Bucketing

Use a stable hash of user ID and flag salt to place users into rollout buckets. Preserve bucket stability across rollout percentage changes and support weighted multivariate allocation without reassigning unaffected users unnecessarily.

Build Local Snapshot Cache and Invalidation

Load compiled flag snapshots into process memory and refresh them through the chosen push-or-poll invalidation path. Define stale-cache behavior, startup behavior, refresh failure logging, and emergency fallback to stored defaults.

Ship SDKs for Both Backend Languages

Provide native SDKs with the same evaluate API, typed context fields, default handling, telemetry hooks, and shared conformance tests. Include integration examples for common request handlers in the monorepo.

Expose JSON-over-HTTP Evaluation Endpoint

Add an authenticated endpoint for non-request-path consumers and systems that cannot use the native SDKs. Document that latency-sensitive request handling must use local SDK evaluation rather than calling this endpoint inline.

Emit Sampled Evaluation Telemetry

Emit sampled events containing flag key, environment, matched rule metadata, variant, context classification, and SDK identity. Avoid raw sensitive identifiers where possible by hashing or redacting according to existing telemetry policy.

Phase 3: Admin UI

Provide a controlled operational interface for creating, editing, searching, archiving, and auditing flags across environments.

Phase Goal

Launch an authenticated dashboard that lets authorized users manage flags safely, preview rollout behavior, inspect audit history, and apply production restrictions consistently with backend authorization.

Alternatives Considered

A CLI-only management path would be faster to implement but would not serve product and support workflows well. A full workflow engine with approvals is out of scope, so the plan favors a focused dashboard with auditability and role-based production edits.

Recommendations

Design the UI around operational safety: clear environment labels, visible production warnings, diff previews before saving, archive instead of delete, and server-enforced permissions. Keep the first version dense and functional rather than building experiment analytics.

Open Questions

Where should flag ownership come from?

Confirm whether owners should be individual users, teams, service ownership metadata, or a combination, and how that maps to production edit rights.

Build Flag Dashboard and Search

Create a dashboard that lists flags by key, description, owner, type, lifecycle state, and environment status. Add search and filters for owner, type, environment, and archived state.

Create Flag Editor Forms

Implement create and edit flows for boolean, percentage, and multivariate flags. Include validation for keys, required owners, default values, targeting rules, variant weights, and lifecycle transitions.

Add Per-Environment Overrides

Show production, staging, and other environments side by side where useful. Make inherited values explicit and require users to intentionally override or clear environment-specific settings.

Build Percentage Rollout Slider and Preview

Add a rollout slider with a live preview that demonstrates deterministic bucketing for sample user IDs and organizations. Use the same bucketing logic or shared test vectors as the evaluation engine to avoid UI/runtime drift.

Display Audit History

Provide an audit-history view per flag with actor, timestamp, environment, changed fields, and before-and-after values. Include enough filtering to support incident review and support handoff.

Enforce Role-Based Production Access

Wire UI affordances to server-side permission checks so only admins and flag owners can edit production values. Non-authorized users may view flags according to existing product policy but cannot perform restricted mutations.

Use Postgres as Source of Truth with Read-Through and In-Memory Caches

The plan selects a new Postgres-backed feature-flag schema over a config-file-in-repo model because product and support need runtime changes and emergency kill switches without deploys. Request paths still evaluate locally from in-memory snapshots, preserving the no-network-hop constraint.

The main downside is operational complexity: schema migrations, cache invalidation, and admin authorization all become required for a safe first release.

Prefer Embedded SDK Evaluation Over a Required Sidecar

The evaluator should run as a local library in latency-sensitive backend request paths. A JSON-over-HTTP endpoint is still included for non-native consumers, but it must not be used as an inline dependency for ordinary request handling.

Cache Staleness Delays Emergency Kill Switches

If local SDK caches refresh too slowly or invalidation fails, support may believe a feature has been disabled while some services continue serving the old value. Mitigate with explicit maximum staleness, visible propagation status, refresh failure alerts, and a conservative fallback strategy.

SDKs Diverge Across Backend Languages

Separate implementations can drift on rule ordering, bucketing, inheritance, or default behavior. Mitigate with shared conformance fixtures, golden test vectors, and release checks that every SDK passes the same evaluation corpus.

Production Edits Bypass Intended Ownership Rules

If role checks live only in the frontend, unauthorized users could mutate production flags through APIs. Mitigate by enforcing owner and admin checks server-side and recording every denied and successful production mutation attempt where appropriate.

Feature Flag System Plan

Build an internal feature-flag system over three phases: durable flag schema and storage, a low-latency evaluation engine, and an authenticated admin UI for rollout and lifecycle management.

Success Criteria

  • Engineering can define typed flags, ship guarded code paths dark, and consume values through typed backend accessors.
  • Product can run deterministic percentage rollouts and multivariate releases by environment without code deploys.
  • Support or admins can disable a misbehaving production feature quickly through an authenticated internal interface.
  • Flag evaluation runs locally in request handling and meets under 1 ms p99 in steady state.
  • All flag changes have audit history, including actor, timestamp, target environment, old value, and new value.
  • The system ships in roughly six weeks with three engineers and no external SaaS dependency.

Scope

In scope: a Postgres-backed flag model, migrations, seed data, typed accessor library, audit history, deterministic evaluation, in-memory cache invalidation, backend SDKs for the two monorepo languages, a JSON-over-HTTP evaluation endpoint for non-request-path callers, sampled telemetry events, and an authenticated admin dashboard.

Out of scope: full approval workflows, A/B-test statistics, scheduled rollouts, mobile SDKs, third-party flag platforms, and any evaluation design that introduces a network hop into normal request handling.

Constraints

  • No new external SaaS dependencies.
  • The request-path evaluator must run locally from cached data.
  • All admin and HTTP surfaces must sit behind existing auth middleware.
  • Production edits are restricted to flag owners and admins.
  • Staging defaults inherit from production unless explicitly overridden.
  • The plan must fit a team of three engineers over about six weeks.

Assumptions

Primary Postgres Can Own Flag Configuration

The product already depends on primary Postgres for authenticated application state, so storing flag definitions there keeps operational ownership inside the existing platform.

Cache Invalidation Can Reuse Existing Infrastructure

The implementation assumes either an existing pub/sub channel, app event bus, or lightweight polling mechanism can propagate flag changes to application processes without introducing a new managed vendor.

Initial SDK Surface Covers Two Backend Languages

The first release targets the two backend languages already used by request-handling services; other consumers use the JSON-over-HTTP endpoint outside latency-sensitive paths.

Phase 1: Flag Schema and Storage

Establish the durable model, database ownership, audit history, seed data, and typed application access layer that later phases will evaluate and expose.

Phase Goal

Create a reliable source of truth for feature flags with typed definitions, environment-specific values, targeting rules, lifecycle state, audit history, and safe migration paths.

Alternatives Considered

A config-file-in-repo approach would keep changes reviewable through normal pull requests, but it would not let support kill production behavior without a deploy. A Postgres source of truth with read-through caching better matches the required operational workflow.

Recommendations

Use primary Postgres as the authoritative store, with normalized flag metadata, per-environment configuration records, JSONB targeting rules validated by application code, and append-only audit history. Use a read-through cache for non-request-path reads and feed the evaluation engine with process-local snapshots.

Open Questions

How Strict Should Rule Storage Validation Be?

Decide whether targeting rules should be validated only in application code or also constrained with a database-level JSON schema/check strategy.

Define Flag Data Model

Design tables for flag metadata, environment values, targeting rules, variant definitions, and lifecycle state. Include key, description, owner, type, default value, salt, active or archived state, created timestamps, and updated timestamps.

Create Migrations and Indexes

Add migrations for feature flag tables and audit tables. Index by flag key, lifecycle state, owner, environment, and updated timestamp so admin search and cache refreshes are efficient.

Implement Audit History

Record append-only audit rows for creates, edits, archive operations, environment overrides, and targeting-rule changes. Capture actor, action, previous payload, next payload, target environment, and request metadata available from existing auth context.

Add Seed Data

Create representative seed flags for boolean, percentage rollout, and multivariate cases across development, staging, and production. Use these seeds for SDK integration tests and admin UI development.

Build Typed Accessor Library

Provide typed read and write helpers for flag definitions and environment values. Enforce valid flag keys, allowed variants, default value compatibility, lifecycle restrictions, and audit emission at the accessor boundary.

Phase 2: Evaluation Engine

Build a deterministic, local, low-latency evaluator with cache refresh semantics, SDK coverage for backend services, a fallback HTTP endpoint, and telemetry emission.

Phase Goal

Provide evaluate(flagKey, context) -> variant in under 1 ms p99 from local process memory, with deterministic rollout behavior and consistent semantics across supported backend languages.

Alternatives Considered

A sidecar-only evaluator would centralize implementation but would add operational moving parts and risk an accidental network hop in request handling. A shared library with a non-request-path HTTP endpoint better satisfies the latency constraint.

Recommendations

Implement a language-native evaluator in each backend SDK using the same rule contract and shared test vectors. Use a periodically refreshed local snapshot with push invalidation where available and poll fallback. Keep HTTP evaluation available for jobs, tools, and unsupported languages, not for hot request paths.

Open Questions

Which Cache Invalidation Mechanism Ships First?

Choose between database notification, existing event bus publication, or short-interval polling with ETag-style version checks for the initial release.

Specify Evaluation Semantics

Document rule ordering, context fields, environment inheritance, default fallback behavior, archived-flag behavior, missing-context behavior, and how user, organization, and environment targeting combine.

Implement Deterministic Bucketing

Hash user ID plus flag salt into a stable bucket for percentage rollouts. Provide shared test vectors so both backend SDKs produce identical variants for the same inputs.

Build Local Snapshot Cache

Maintain an in-memory immutable snapshot of active flags and per-environment rules. Add startup load, refresh, invalidation, stale snapshot metrics, and safe fallback to defaults when the store is temporarily unavailable.

Ship Backend SDKs

Expose typed evaluate helpers for the two backend languages in the monorepo. Include initialization, context construction helpers, default-value handling, telemetry hooks, and conformance tests.

Add JSON-over-HTTP Evaluation Endpoint

Provide an authenticated endpoint for unsupported languages, internal tools, and batch jobs. Mark it as unsuitable for normal request-path use and instrument callers so accidental hot-path adoption can be detected.

Emit Sampled Evaluation Telemetry

Emit sampled events containing flag key, selected variant, environment, rule match metadata, SDK language, and coarse context identifiers appropriate for privacy constraints. Ensure telemetry does not block evaluation.

Phase 3: Admin UI

Create the authenticated operational surface for creating, editing, searching, previewing, and archiving feature flags across environments.

Phase Goal

Deliver an internal dashboard where authorized users can manage flag lifecycle, production values, environment overrides, rollout percentages, audit history, and archive operations without a deploy.

Alternatives Considered

A read-only dashboard plus database scripts would reduce UI scope but would not meet the support kill-switch requirement. A full approval workflow was considered but remains out of scope for the initial six-week delivery.

Recommendations

Build the UI inside the existing authenticated admin shell. Start with dense list and detail workflows, explicit production-edit affordances, owner/admin authorization checks on the server, and audit history visible from each flag detail page.

Open Questions

Where Should the Dashboard Live?

Confirm the route and navigation placement in the existing admin shell, including whether support users already have access to that area.

Build Flag List and Search

Create a dashboard list with search by key, description, owner, type, lifecycle state, and environment. Include clear archived-state filtering and quick links to flag detail pages.

Build Create and Edit Workflows

Add forms for flag metadata, type-specific defaults, variants, targeting rules, and lifecycle state. Validate on both client and server, and route all writes through the accessor layer so audit history is complete.

Add Environment Overrides

Show production, staging, and development values side by side. Make inherited staging values visually distinct from explicit overrides and require authorized writes for production changes.

Create Rollout Slider and Preview

Add a percentage-rollout slider with a live preview of representative user buckets. Use the same bucketing test vectors as the evaluator so the preview reflects production behavior.

Display Audit History

Provide a per-flag audit view showing actor, timestamp, environment, action, previous value, and next value. Include enough detail for support and engineering to understand recent production changes.

Enforce Role-Based Access

Use existing auth middleware and server-side authorization checks so only owners and admins can edit production values. Allow broader read access where existing internal policy permits it.

Use Primary Postgres as Source of Truth with Local Evaluation Cache

Primary Postgres supports fast operational edits, audit history, environment-specific overrides, and integration with existing auth and migration practices. The request path will not query Postgres directly; services evaluate from local in-memory snapshots refreshed by invalidation or polling.

A config-file-in-repo system would provide natural code review but fails the requirement that support can kill a feature without deploy. A third-party SaaS platform is excluded by constraint.

Use SDK Libraries for Request-Path Evaluation

The primary evaluator will be implemented as backend SDK libraries so request handling does not add a network hop. A JSON-over-HTTP endpoint remains available for lower-volume or unsupported consumers.

Stale Flag Snapshots

If invalidation is delayed, services may evaluate old flag values after an emergency kill switch. Mitigation: versioned snapshots, short poll fallback, freshness metrics, admin-visible propagation status, and alerting when evaluators exceed the accepted staleness window.

SDK Semantics Drift Across Languages

Two backend SDKs can diverge in rule ordering, bucketing, or default handling. Mitigation: shared evaluation spec, fixture-based conformance tests, deterministic bucketing test vectors, and CI checks for both SDKs.

Incorrect Production Edits

Direct production edits can cause broad behavior changes. Mitigation: server-side RBAC, explicit production edit confirmation, audit history, clear owner display, and safe default fallback when a malformed rule is rejected.

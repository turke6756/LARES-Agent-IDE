Feature Flag System Plan

Deliver a first-party feature-flag system that supports dark launches, gradual rollouts, fast operational kill switches, audited changes, and production-safe administration without adding a network hop to request handling.

Success Criteria

  • Engineering can merge feature code behind typed flags and keep it dark until explicitly enabled.
  • Product can run deterministic percentage rollouts and per-environment overrides without developer intervention.
  • Support and admins can disable a problematic production flag without a deploy.
  • Backend evaluations resolve locally from memory with p99 latency under one millisecond, excluding telemetry flushing.
  • Every flag mutation is captured in an immutable audit history with actor, timestamp, old value, and new value.
  • The system ships in roughly six weeks with a three-engineer team and no external SaaS dependency.

Scope

The feature includes a Postgres-backed flag model, migrations, seed data, typed accessors, an evaluation library for the two backend languages in the monorepo, a JSON-over-HTTP endpoint for non-core consumers, local cache invalidation, sampled evaluation telemetry, and an authenticated admin dashboard for flag lifecycle management.

Out of scope for this lift are A/B-test statistics, scheduled rollouts, mobile SDKs, and a full approval workflow. Auditability and role-restricted production edits are included, but multi-step approval gates are deferred.

Constraints

  • No new external SaaS dependencies; storage, telemetry, and administration must use existing platform primitives.
  • The request evaluation path must not introduce a remote call or sidecar dependency.
  • All admin and API surfaces must sit behind existing authentication middleware.
  • Production edits must be restricted to flag owners and admins.
  • The evaluation engine must support deterministic bucketing, rule ordering, environment inheritance, and sampled telemetry.
  • The plan assumes three engineers over approximately six calendar weeks.

Assumptions

Existing Auth Can Enforce Flag Roles

The admin UI and mutation APIs can reuse the current authentication and authorization stack, with modest additions for flag-owner checks.

Backend SDK Scope Is Bounded

The two backend languages mentioned in the brief cover all latency-sensitive request paths for the first release.

Primary Postgres Is Acceptable As Source Of Truth

Flag definitions and audit records are small, low-write-volume data, so primary Postgres is suitable as the source of truth when paired with local process caches.

Phase 1: Flag Schema And Storage

Establish the durable source of truth, typed model, audit log, and internal accessor library that later phases consume.

Phase Goal

Create a versioned, audited, strongly typed feature-flag data model in primary Postgres, backed by a read-through cache and seed data for initial operational flags.

Alternatives Considered

A config-file-in-repo approach would provide reviewability and simple rollback, but it blocks support-led kill switches and product-managed rollout changes because every production change requires a deploy. A Postgres-backed model better matches the operational requirements while still allowing auditability.

Recommendations

Use primary Postgres as the source of truth with separate tables for flags, environment-specific values, targeting rules, variants, and audit events. Keep the model normalized enough for validation and audit clarity, but expose a compiled flag document to the evaluator cache.

Open Questions

Where Should Flag Ownership Come From?

Decide whether owners are individual users, teams, service ownership records, or a combination. The answer affects RBAC checks, search filters, and escalation paths.

Define The Flag Domain Model

Specify fields for key, description, owner, type, default value, lifecycle state, salt, variants, percentage weights, and targeting rules by user ID, organization, and environment. Include validation rules for key format, variant weights, archived flags, and default-value compatibility with flag type.

Create Postgres Migrations

Add tables for feature flags, environment overrides, targeting rules, variant definitions, and audit events. Include indexes for key lookup, lifecycle filtering, owner search, environment lookup, and audit history retrieval by flag key.

Implement Audit History Writes

Record every create, edit, archive, and environment override change with actor, timestamp, action, previous value, new value, and request metadata. Store audit events append-only and make them queryable before the admin UI is built.

Add Seed Data And Fixtures

Seed representative boolean, percentage, and multivariate flags for local development and automated tests. Include at least one archived flag and one environment override to exercise lifecycle and inheritance behavior early.

Build Typed Accessor Library

Expose repository-level read and mutation APIs that validate flag shape before persistence, return typed flag documents, and hide table layout from callers. This library becomes the shared contract for the evaluator, HTTP endpoint, and admin UI backend.

Phase 2: Evaluation Engine

Build the low-latency runtime path that answers flag evaluations locally and consistently across backend languages.

Phase Goal

Deliver deterministic flag evaluation with local in-memory caching, predictable rule semantics, SDKs for the two backend languages, a JSON-over-HTTP fallback endpoint, and sampled telemetry.

Alternatives Considered

A central sidecar or service would simplify cross-language consistency, but it violates the no-network-hop constraint for request handling. The preferred approach is shared evaluation semantics implemented in each backend SDK, with the HTTP endpoint reserved for non-latency-sensitive or non-core consumers.

Recommendations

Compile database rows into a compact immutable flag snapshot per environment. SDKs should evaluate against the local snapshot, refresh through push if an internal event bus is already available, and fall back to short-interval polling with jitter if push is not ready.

Open Questions

Which Invalidation Channel Is Available?

Confirm whether the platform already has a reliable internal pub/sub or notification channel that can broadcast flag version changes to application processes.

Specify Evaluation Semantics

Define rule ordering, matching behavior, environment inheritance, default fallback, archived-flag behavior, and error handling. Document that explicit environment overrides win, staging inherits production defaults when unset, targeting rules are evaluated in stored priority order, and default value is returned when no rule matches.

Implement Deterministic Bucketing

Use a stable hash of user ID, flag key, and flag salt to map contexts into percentage rollout buckets. Keep the algorithm language-neutral and covered by shared golden test vectors so both backend SDKs return identical variants.

Build Local Snapshot Cache

Maintain an in-memory compiled flag snapshot in each process. Add version checks, startup warmup, stale-read metrics, and invalidation through push or jittered polling. Ensure request handlers never block on a flag storage read after warmup.

Ship Backend SDKs

Provide the `evaluate(flagKey, context) -> variant` API for both backend languages, including typed helpers for boolean and multivariate flags. Add tests for missing context, malformed flags, environment inheritance, ordered rules, and p99 latency budget.

Add JSON-Over-HTTP Evaluation Endpoint

Create an authenticated endpoint for consumers outside the two primary SDK languages. Mark it unsuitable for latency-sensitive request paths, enforce auth middleware, and reuse the same compiled evaluation package to avoid semantic drift.

Emit Sampled Evaluation Telemetry

Emit sampled events containing flag key, environment, returned variant, matched rule identifier, context classification, SDK language, and evaluation duration. Avoid storing raw sensitive targeting values unless explicitly approved by the existing telemetry policy.

Phase 3: Admin UI

Provide the authenticated operational interface for creating, changing, searching, previewing, and archiving flags.

Phase Goal

Launch an admin dashboard that lets authorized users manage flags safely across environments, inspect audit history, preview rollout buckets, and enforce production edit permissions.

Alternatives Considered

A developer-only internal CLI would be faster to build but would not satisfy product rollout management or support kill-switch needs. The UI is required for non-engineering operators, while CLI or script helpers can remain a later convenience.

Recommendations

Build the UI as an internal dashboard page behind existing auth, backed by server-side mutation endpoints that reuse the typed accessor library and audit writer. Treat production edits as privileged actions with clear permission checks and confirmation for high-impact changes.

Open Questions

What Context Should The Rollout Preview Use?

Decide whether the live bucketing preview accepts pasted user IDs, generated sample IDs, organization IDs, or all of the above.

Create Dashboard List And Search

Build a dashboard page that lists flags by key, description, owner, type, lifecycle state, and environment status. Add search and filters for owner, state, type, and environment so support and product can find flags quickly during incidents.

Build Create And Edit Flows

Support creating boolean, percentage rollout, and multivariate flags. Provide validation for keys, default values, variants, rule ordering, and targeting rules. Prevent unsafe edits to archived flags except explicit restoration or metadata-only changes if allowed.

Add Per-Environment Overrides

Expose production, staging, and other configured environments with visible inheritance behavior. Make it clear when staging inherits production defaults and when an override is active.

Add Percentage Slider And Bucket Preview

Provide a percentage rollout slider that previews how sample users or entered identities fall into buckets using the same deterministic bucketing algorithm as the SDKs. Show the projected variant outcome before saving.

Display Audit History

Add an audit-history view on each flag detail page showing actor, timestamp, action, environment, previous value, and new value. Include enough detail for incident review without exposing unnecessary sensitive context values.

Enforce Role-Based Access

Allow all authenticated internal users with dashboard access to view flags, but restrict production edits to flag owners and admins. Apply checks in backend mutation endpoints, not only in the UI, and include negative authorization tests.

Use Postgres As Source Of Truth With Local Evaluation Caches

The plan uses a new `feature_flags` storage model in primary Postgres, plus compiled in-memory snapshots in application processes. This satisfies operational edits, audit history, search, and support kill switches while preserving the requirement that request-time evaluation does not add a network hop.

A config-file-in-repo model is easier to review in code and can be deployed with existing workflows, but it is too slow and engineering-dependent for support-driven production disablement and product-managed gradual rollouts.

Flag Changes May Propagate Too Slowly

If cache invalidation is only poll-based or polling intervals are too long, emergency kill switches may not take effect quickly enough. Mitigation: define a freshness SLO, include version metrics, use push invalidation if existing infrastructure allows it, and keep jittered polling as a fallback.

SDKs May Diverge Across Languages

Separate backend SDK implementations can produce different variants for the same flag and context if hashing, rule ordering, or default behavior drifts. Mitigation: maintain shared semantic documentation and golden test vectors that every SDK must pass in CI.

Admin Users May Misconfigure Production Flags

A mistaken production edit could expose unfinished code or disable a critical path. Mitigation: enforce RBAC on mutation endpoints, show environment context clearly, preview rollout outcomes, audit all changes, and add confirmation for high-impact production edits.

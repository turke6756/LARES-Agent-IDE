Feature flag system

Add a first-party feature-flag platform so engineering can ship dark, product can run controlled rollouts, and support can disable misbehaving features without a deploy.

Success criteria

The system supports boolean, percentage, and multivariate flags with targeting by user ID, organization, and environment.

Backend request handling evaluates flags from local process memory without adding a network hop, and the hot-path evaluator meets a p99 latency target below one millisecond under representative production load.

Product and support can create, edit, search, and archive flags through an authenticated admin UI, with production edits restricted to flag owners and admins.

Every flag mutation is recorded in audit history, and every evaluation emits sampled telemetry suitable for later rollout analysis.

The feature is deliverable by three engineers in roughly six weeks without introducing external SaaS dependencies.

Scope

In scope: the persisted flag schema, Postgres migrations, seed data, audit history, typed accessors, evaluation libraries for the two backend languages in the monorepo, a JSON-over-HTTP endpoint for non-native consumers, local cache invalidation, sampled telemetry, and an authenticated admin UI.

Out of scope: a full approval workflow, A/B-test statistics, scheduled rollouts, external flag-management SaaS, mobile SDKs, and any request-path design that requires a remote service call during ordinary flag evaluation.

Constraints

The evaluation path must be local to the process that handles the request. Shared services may publish configuration changes, but application code must not synchronously call a flag service to answer ordinary evaluations.

All admin surfaces and HTTP endpoints must sit behind existing authentication middleware and reuse existing authorization primitives where possible.

No new external SaaS dependencies are allowed. New infrastructure should be limited to database tables, application libraries, existing cache infrastructure, and internal background workers or sidecars if needed.

The implementation should fit a six-week schedule for three engineers by sequencing storage first, then the evaluator, then the UI, while allowing early backend integration before the full dashboard is complete.

Assumptions

The initial flag set is small enough to keep an environment-scoped snapshot in each backend process, with cache refreshes replacing the whole snapshot or a compact changed subset.

The monorepo has two backend languages that need native SDKs, and all other callers can tolerate a JSON-over-HTTP endpoint outside their request hot path or with their own local caching.

Existing auth middleware and role data can support owner/admin production edit controls without building a separate identity or approval system.

Phase 1: Flag schema and storage

Build the durable source of truth for flags, their per-environment configuration, lifecycle state, and audit trail. This phase should also expose typed reads so application code does not depend on raw table shapes.

Phase goal

Deliver a Postgres-backed feature flag model with migrations, seed data, audit history, and typed accessors that later phases can consume without schema churn.

Alternatives considered

Considered a config-file-in-repo approach for simplicity and code review visibility, but it cannot satisfy support-driven kill switches without deploys and makes gradual product edits too slow. Chosen approach is a primary Postgres source of truth with a read-through cache and immutable audit entries.

Recommendations

Use separate tables for flag identity, environment-specific definitions, targeting rules, and audit events. Store rule payloads as validated JSON with typed accessors at the library boundary, so migrations remain manageable while evaluator inputs stay strongly typed.

Open questions

Should flag ownership map to individual users only, teams only, or allow both with the existing ownership model?

How long should archived flag definitions remain queryable in the admin UI before they are hidden by default?

Define flag and environment schema

Create migrations for feature_flags, environment overrides, targeting rules, and audit records. The model must include key, description, owner, type, default value, lifecycle state, environment, salt, and timestamps. Add database constraints for unique flag keys, supported flag types, and valid lifecycle states.

Model typed flag payloads

Define typed representations for boolean, percentage rollout, and multivariate flags. Include validation for variant weights, default variant compatibility, percentage bounds, and targeting rule shape before data can be persisted.

Add seed flags and fixtures

Add development and test seed data covering each flag type, each lifecycle state, user targeting, organization targeting, and environment overrides. Use these fixtures later for evaluator and UI tests.

Implement audit history writes

Record every create, edit, archive, and environment override change with actor, timestamp, before value, after value, and reason when supplied. Keep audit writes in the same transaction as the flag mutation.

Build typed accessor library

Expose read and write functions that return validated domain objects instead of raw rows. Include cache-aware read-through hooks so Phase 2 can consume a snapshot without coupling to database queries.

Phase 2: Evaluation engine

Build the runtime evaluator and SDK surface. The evaluator must be deterministic, fast, and locally cached so feature decisions can happen inside request handling without remote calls.

Phase goal

Deliver an evaluator that answers evaluate(flagKey, context) -> variant from local memory with deterministic bucketing, clear rule ordering, environment inheritance, invalidation, native SDKs, an HTTP endpoint, and sampled telemetry.

Alternatives considered

Considered a central sidecar-only service to simplify implementation across languages, but synchronous sidecar calls would violate the no-network-hop constraint for request handling. The recommended design is a shared evaluator spec plus native libraries that load local snapshots; an internal HTTP endpoint exists for lower-volume or non-hot-path consumers.

Recommendations

Make production inheritance explicit: missing staging values inherit from production defaults only when no staging override exists. Evaluate rules in deterministic priority order: explicit user targets, explicit organization targets, environment override rules, percentage or multivariate bucketing, then default value.

Open questions

Should cache invalidation use the existing pub-sub mechanism for push updates, or start with short-interval polling plus version checks?

What default evaluation telemetry sampling rate balances rollout observability with event volume and cost?

Specify evaluation semantics

Write the evaluator contract for context fields, missing context behavior, rule precedence, environment inheritance, archived flag behavior, unknown flag behavior, and variant return shape. Use the same contract for both native SDKs and the HTTP endpoint.

Implement deterministic bucketing

Use a stable hash of user ID plus flag salt for percentage and multivariate rollouts. Add test vectors that guarantee both backend language SDKs produce identical bucket and variant assignments.

Build local snapshot cache

Maintain an in-memory environment-scoped snapshot in each process. Load on startup, expose versioned refresh, and support push or poll invalidation. Failed refreshes must keep serving the last known good snapshot and emit operational telemetry.

Ship native SDKs for backend languages

Implement the same evaluator API in both backend languages used by the monorepo. Include typed flag accessors, context builders, default handling, test fixtures, and integration examples for common request handlers.

Add JSON-over-HTTP evaluation endpoint

Expose an authenticated internal endpoint for consumers without a native SDK. Document that request-hot-path services should use a local SDK or their own local cache, not synchronous endpoint calls for every request.

Emit sampled evaluation telemetry

Emit sampled events containing flag key, returned variant, environment, rule source, snapshot version, and anonymized context identifiers where permitted. Avoid logging raw sensitive context values.

Phase 3: Admin UI

Build the authenticated management surface for product, engineering, and support. The UI should make common flag operations safe and auditable while keeping production edits behind role-based controls.

Phase goal

Deliver a dashboard for creating, editing, searching, previewing, and archiving flags, including per-environment overrides, audit history, and owner/admin-only production editing.

Alternatives considered

Considered launching with CLI-only flag management after the evaluator ships, but that would fail the support kill-switch requirement and push product rollout work back to engineering. The admin UI is therefore part of the launch scope, with advanced analytics and scheduling deferred.

Recommendations

Start with dense operational screens rather than a marketing-style dashboard: searchable table, detail drawer or detail page, explicit environment tabs, guarded production controls, and inline audit history. Treat archive as reversible in UI where the data model allows it, but make production value changes deliberate and clearly attributed.

Open questions

Should production edits require a free-text reason so audit history captures operator intent?

What sample size should the live bucketing preview use to be useful without implying it is an A/B-test statistics view?

Build flag list and search page

Create a dashboard table with search and filters for key, owner, flag type, lifecycle state, environment override presence, and recently changed flags. Default the view to active flags while keeping archived flags discoverable.

Add create and edit workflows

Implement forms for boolean, percentage rollout, and multivariate flags with validation matching the storage library. Support description, owner, default value, targeting rules, and archive actions.

Implement per-environment overrides

Show environment-specific values and inheritance clearly. Allow staging and production overrides through the same backend mutation APIs, with production edits gated by role checks.

Add rollout slider and bucketing preview

Provide a percentage slider with a deterministic preview showing how sample user IDs move into or out of rollout buckets. The preview must use the same bucketing code path or shared test vectors as the evaluator.

Display audit history

Add an audit-history view for each flag showing actor, timestamp, environment, changed fields, before and after values, and any supplied reason. Keep this read-only and available to support users who can view flags.

Enforce role-based production access

Reuse existing auth middleware and authorization primitives so only flag owners and admins can edit production values. Add server-side checks independent of UI state and cover unauthorized edit attempts in tests.

Use Postgres as the source of truth with local cached evaluation

Postgres-backed storage satisfies auditability, support-driven edits, and product rollout control without adding external SaaS. Application processes evaluate from local snapshots so request handling does not add a network hop.

A config-file-in-repo model is easier to review but cannot provide kill switches or rollout edits without deploys.

Include the admin UI in the initial launch

The brief requires product-controlled rollouts and support-operated kill switches. A backend-only launch would leave those workflows dependent on engineering and would not meet the operational goal.

Deferring the UI could shorten the first backend milestone, but it would move critical safety operations outside the people expected to perform them.

Evaluator bug changes production behavior broadly

A shared evaluator can affect many request paths at once. Mitigation: keep semantics small, add cross-language test vectors, run the evaluator in shadow mode for selected services, and make unknown or malformed flags fall back to explicit defaults.

Stale local caches delay kill switches

If invalidation is slow or broken, support may archive or disable a flag but request handlers keep serving the old value. Mitigation: version snapshots, monitor cache age, prefer push invalidation if existing infrastructure supports it, and set a conservative polling fallback.

Production edit authorization is incomplete

UI-only gating would be insufficient for production changes. Mitigation: enforce owner/admin checks on mutation APIs, audit denied attempts where appropriate, and test direct API calls from non-owner roles.

Six-week schedule is tight for storage, SDKs, and UI

The plan spans durable storage, runtime libraries, cache invalidation, telemetry, and a management UI. Mitigation: avoid approval workflows and analytics, ship a minimal but complete UI, and sequence backend SDK integration before polishing secondary UI states.

Feature flag system

Introduce a first-party feature-flag platform so engineering can ship dark, product can manage gradual rollouts, and support can disable problematic features without a deploy.

Success criteria

  • Backend teams can define and read typed flags for boolean, percentage, and multivariate use cases.
  • Flag evaluation returns the correct variant locally, with p99 latency under one millisecond in request-path benchmarks.
  • Product and support users can create, edit, search, archive, and audit flags through an authenticated admin UI.
  • Production flag edits are limited to flag owners and admins, while all flag changes are recorded in audit history.
  • Cache invalidation reliably propagates flag changes without requiring application deploys or request-time network calls.

Scope

In scope: a Postgres-backed flag schema, migrations, seed data, audit tables, typed backend accessors, a local evaluation engine, SDKs for the two backend languages in the monorepo, a JSON-over-HTTP evaluation endpoint for non-request-path consumers, sampled telemetry, and an admin dashboard behind existing authentication.

Out of scope: A/B-test statistics, scheduled rollouts, mobile SDKs, a full approval workflow, and any dependency on external SaaS flag providers.

Constraints

  • No new external SaaS dependencies.
  • The request-time evaluation path must not add a network hop.
  • All admin and API surfaces must sit behind existing auth middleware.
  • The team is three engineers with a target delivery window of roughly six weeks.
  • The implementation should fit the monorepo's existing Postgres, cache, telemetry, and UI conventions.

Assumptions

The current cache and pub/sub or polling primitives are sufficient for read-through loading and invalidating in-memory flag snapshots.

Both backend languages can consume a shared flag definition contract and expose equivalent evaluation semantics.

The first release is operational flagging only, not experimentation or governance workflow automation.

Phase 1: Flag schema and storage

Build the durable source of truth for flags, their per-environment configuration, typed definitions, and audit history.

Phase goal

Deliver a Postgres-backed flag model with migrations, seed data, audit logging, and typed accessors that later phases can evaluate without changing storage contracts.

Alternatives considered

Considered storing flags as config files in the repo. That approach has strong reviewability but cannot support support-driven kill switches or product-managed gradual rollout changes without deploys. Choose a new feature_flags schema in primary Postgres with read-through caching and append-only audit history.

Recommendations

Normalize stable flag metadata separately from per-environment values. Keep rule JSON constrained by a typed schema and validate it at write time. Include a generated flag manifest for compile-time discovery where the monorepo supports it, but treat Postgres as the runtime source of truth.

Open questions

Which existing ownership source should populate valid flag owners: team catalog, user table, or repository CODEOWNERS metadata?

Should archived flags be hard-blocked from evaluation immediately or remain readable until code references are removed?

Design and migrate the Postgres schema

Create tables for flag metadata, per-environment flag values, targeting rules, variants, salts, lifecycle state, and audit entries. Enforce unique keys, valid flag types, active versus archived state, and referential integrity for environment overrides.

Add validation and seed data

Implement server-side validation for flag keys, default values, variant weights, targeting rule shape, and owner references. Seed a small set of non-production flags that exercise boolean, percentage, and multivariate paths.

Implement audit-history writes

Record create, update, archive, and environment override changes with actor, timestamp, before value, after value, and reason where available. Do not block on approval workflow concepts.

Create the typed accessor library

Expose typed read APIs for fetching flag definitions and environment snapshots. Include generated or checked types for supported variants so application code cannot treat a multivariate flag as a boolean flag by accident.

Add storage and accessor tests

Cover migration constraints, validation errors, audit entries, lifecycle transitions, and typed accessor behavior. Include fixture flags that later phases can reuse for evaluation tests.

Phase 2: Evaluation engine

Build the local runtime path that answers evaluate(flagKey, context) -> variant deterministically, quickly, and consistently across supported consumers.

Phase goal

Ship a shared evaluation engine with deterministic bucketing, ordered targeting rules, environment inheritance, local in-memory snapshots, cache invalidation, SDK bindings, an HTTP endpoint for non-critical paths, and sampled telemetry.

Alternatives considered

Considered a central sidecar or service for every evaluation. That simplifies consistency but violates the no-network-hop request-path constraint. Choose embedded SDK evaluation backed by local in-memory snapshots, with an HTTP endpoint only for consumers that are not in latency-sensitive request handling.

Recommendations

Implement evaluation rules in a small shared core or conformance-tested ports. Use a stable hash of userId + flagSalt for percentage bucketing, evaluate explicit user and org targets before percentage rules, and emit sampled telemetry asynchronously so logging never blocks request handling.

Open questions

Which hash function is already approved in the codebase and portable across both backend languages?

Should invalidation use existing push notifications, short polling, or a hybrid where polling is the fallback for missed events?

Specify evaluation semantics

Document and test the exact order for environment inheritance, explicit user targeting, org targeting, environment targeting, percentage rollout, multivariate weights, and default fallback. Treat this as the compatibility contract for all SDKs.

Build the embedded evaluation library

Implement evaluate(flagKey, context) against an immutable in-memory flag snapshot. Return a typed variant plus evaluation metadata for telemetry and debugging, while keeping the primary caller surface small.

Add deterministic bucketing and conformance tests

Use a stable hash of user ID and flag salt to assign buckets. Add cross-language golden tests so identical contexts produce identical variants in every backend SDK.

Implement snapshot cache and invalidation

Load flag snapshots from the typed accessor library, keep them in local memory, refresh them on push or poll invalidation, and define safe stale behavior if storage or invalidation is temporarily unavailable.

Expose SDKs and HTTP endpoint

Package SDKs for the two backend languages in the monorepo and add a JSON-over-HTTP endpoint behind existing auth for secondary consumers. Document that request-path code must use the embedded SDK rather than the HTTP endpoint.

Add telemetry and performance tests

Emit sampled evaluation events with flag key, variant, environment, rule matched, and anonymized context identifiers where appropriate. Benchmark p50, p95, and p99 local evaluation latency using warm snapshots.

Phase 3: Admin UI

Provide the authenticated operational interface for creating, editing, searching, archiving, previewing, and auditing flags.

Phase goal

Deliver a dashboard that lets authorized users manage flags safely across environments, with production editing restricted to flag owners and admins.

Alternatives considered

Considered launching with API-only management. That would reduce UI work but fails the support kill-switch requirement and increases operational risk. Choose a focused admin dashboard using existing auth, role checks, forms, and table patterns.

Recommendations

Keep the first UI utilitarian: searchable list, detail editor, environment tabs, rollout slider, preview panel, and audit drawer. Avoid experiment analytics or scheduling controls until after the operational flagging workflow is stable.

Open questions

What exact role mapping distinguishes admins, flag owners, support users, and read-only viewers in the existing authorization model?

Should production edits require a free-text change reason for audit quality, even though a full approval workflow is out of scope?

Create flag dashboard and search

Build the main dashboard with key, description, owner, type, lifecycle state, environments, and last modified metadata. Add search and filters for owner, environment, state, and flag type.

Build create and edit flows

Add forms for key, description, owner, type, default value, variants, targeting rules, and lifecycle state. Reuse backend validation and show field-level errors before writes are attempted.

Add per-environment override controls

Provide environment-specific views for production, staging, and other configured environments. Make inherited values visible, allow explicit overrides, and explain when staging is inheriting from production defaults.

Add rollout slider and bucketing preview

For percentage rollout flags, show a slider and a live preview of representative user IDs mapping into enabled or disabled buckets. Use the same bucketing function as the evaluation engine.

Add audit history and archive action

Show the append-only audit trail for each flag, including actor, timestamp, environment, previous value, new value, and reason where present. Add an archive flow that preserves history and prevents accidental reuse of retired keys.

Enforce role-based access

Wire UI affordances and backend authorization so only flag owners and admins can edit production values. Allow broader read access and support-appropriate non-production or emergency actions only where policy permits.

Use Postgres as the flag source of truth

Flags will live in a new Postgres-backed schema with read-through caching and local SDK snapshots. This satisfies the support kill-switch requirement, supports product-managed rollout changes without deploys, and keeps the system inside existing infrastructure.

A config-file-in-repo approach would have simpler code review and rollback mechanics, but it cannot meet the no-deploy operational change requirement.

Evaluate flags locally in request handling

Request-path consumers will use embedded SDKs backed by in-memory snapshots. A JSON-over-HTTP endpoint will exist for other consumers, but not as the primary path for latency-sensitive service requests.

A central evaluation service would reduce duplicated SDK logic, but it adds request-time network dependency and cannot meet the stated constraint.

Evaluation semantics drift between SDKs

If the two backend SDKs implement targeting or bucketing differently, users may see inconsistent behavior across services. Mitigation: define a single semantic spec and require cross-language golden conformance tests before release.

Stale local caches delay kill switches

If invalidation fails, support may believe a feature is disabled while some services continue using stale snapshots. Mitigation: use push invalidation where available, poll as fallback, expose snapshot age metrics, and define maximum tolerated staleness.

Admin UI can cause production incidents through misconfiguration

Powerful production edits can roll a bad feature out too widely. Mitigation: enforce owner/admin permissions, validate rule conflicts, show environment inheritance clearly, and make audit history prominent.

Six-week timeline is tight for three engineers

The combined storage, SDK, performance, telemetry, and UI work may exceed capacity. Mitigation: sequence delivery so schema and local evaluation ship first, then release a narrow admin UI before adding polish.

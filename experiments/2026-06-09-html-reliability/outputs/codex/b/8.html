Feature flag system

Add an internal feature-flag platform so engineering can ship dark code, product can run gradual rollouts, and support can disable unsafe features without a deploy.

Success criteria

  • Engineers can define, read, and evaluate boolean, percentage rollout, and multivariate flags through typed backend accessors.
  • Production request handling evaluates flags from local process memory and does not add a network hop.
  • Evaluation latency is under 1 ms at p99 for cached flag data under expected production context sizes.
  • Product and support can create, edit, search, archive, and inspect flags through an authenticated admin dashboard.
  • Flag changes are auditable with actor, timestamp, environment, before value, and after value.
  • Production value edits are restricted to flag owners and admins, while all access remains behind existing auth middleware.

Scope

In scope: persistent flag schema and audit history, Postgres migrations, seed data, read-through caching, typed accessor libraries, deterministic rollout evaluation, environment inheritance, cache invalidation, backend SDKs for the two monorepo languages, a JSON-over-HTTP evaluation endpoint for non-request-path consumers, sampled telemetry events, and an authenticated admin UI.

Out of scope: full approval workflows, A/B-test statistical analysis, scheduled rollouts, mobile SDKs, and any external SaaS dependency.

Constraints

  • No new external SaaS dependencies.
  • The evaluation path must not add a network hop to normal request handling.
  • All admin and API surfaces must sit behind existing auth middleware.
  • The team is three engineers with roughly six weeks total delivery time.
  • The design must support emergency kill-switch use without requiring a deploy.

Assumptions

The two backend languages in the monorepo can each consume a small local SDK package with normal release and deployment workflows.

Existing authentication and authorization context is sufficient to enforce owner and admin permissions for production flag edits.

The primary Postgres database can safely store low-write-volume flag configuration and audit records.

Phase 1: Flag schema and storage

Build the durable source of truth for flags, their per-environment values, targeting rules, lifecycle state, and audit history.

Phase goal

Deliver a production-ready data model, migrations, seeds, cache loading path, and typed accessor surface that later phases can evaluate and administer without changing storage fundamentals.

Alternatives considered

Considered a config-file-in-repo approach for strong code review and easy rollback. Chose Postgres-backed storage with a read-through cache because support and product need operational edits, gradual rollout changes, and kill switches without deploys.

Recommendations

Use normalized Postgres tables for flag metadata, environment-specific configuration, targeting rules, variants, and audit events. Store rule definitions as structured JSON only where the shape is versioned and validated by the accessor library.

Open questions

Should archived flags remain evaluable with their last value, or should the accessor require code owners to remove all archived flag references before archival?

Design and migrate core tables

Create migrations for feature_flags, feature_flag_environments, feature_flag_rules, feature_flag_variants, and feature_flag_audit_events. Include stable keys, owner identifiers, descriptions, lifecycle state, flag type, salt, defaults, timestamps, and uniqueness constraints by key and environment.

Define rule and variant schemas

Specify typed shapes for boolean, percentage rollout, and multivariate flags. Cover user ID, organization, and environment targeting, ordered rule evaluation, fallback defaults, and validation errors for impossible configurations.

Add seed data and development fixtures

Seed representative flags for each flag type in local and staging environments. Include examples of production inheritance, user targeting, organization targeting, and a disabled kill-switch flag.

Implement read-through cache loader

Build a cache-loading module that reads active flag configuration from Postgres, validates it, materializes an immutable in-memory snapshot, and exposes version metadata for invalidation in later phases.

Create typed accessor library foundation

Provide typed APIs for fetching flag definitions and validated snapshots. Keep evaluation behavior minimal in this phase, but establish shared types, parsing, serialization, and error conventions for both backend language SDKs.

Record audit history for writes

Add a write helper that records actor, action, timestamp, target flag, environment, previous value, new value, and request metadata whenever a flag definition or environment value changes.

Phase 2: Evaluation engine

Implement the runtime path that answers evaluate(flagKey, context) -> variant quickly and consistently from local memory.

Phase goal

Ship deterministic, low-latency evaluation for all supported flag types, with local caching, invalidation, SDK coverage for both backend languages, HTTP evaluation for non-critical consumers, and sampled telemetry.

Alternatives considered

Considered a sidecar-only service for centralized evaluation. Rejected it for request-path use because the constraints prohibit adding a network hop. The chosen approach is an in-process SDK with optional JSON-over-HTTP evaluation for tools and services that are not on latency-sensitive request paths.

Recommendations

Use a versioned immutable snapshot per process, deterministic hashing of user ID plus flag salt for percentage and multivariate bucketing, explicit first-match rule ordering, and polling invalidation first unless an existing internal pub/sub channel can be reused without adding an external dependency.

Open questions

Is there an existing internal event bus suitable for push invalidation, or should the first release rely on short-interval polling with jitter?

What sampling rate should evaluation telemetry use by default to balance analysis value against event volume?

Implement deterministic evaluator

Build the core evaluation function for boolean, percentage, and multivariate flags. Define missing-flag behavior, malformed-context behavior, default fallback behavior, and stable variant return types.

Add targeting and inheritance semantics

Implement ordered rules for user ID, organization, and environment matching. Apply environment inheritance so staging can inherit production defaults unless an explicit staging override exists.

Build local cache invalidation

Load snapshots into process memory and refresh them through the chosen push-or-poll mechanism. Ensure refreshes are atomic, tolerate transient database failures, and continue evaluating from the last valid snapshot.

Publish backend SDK surfaces

Create idiomatic SDK APIs for both backend languages in the monorepo. Include typed context builders, typed variant access, test helpers, and examples for common request handlers.

Add JSON-over-HTTP evaluation endpoint

Expose an authenticated internal endpoint for non-request-path clients and operational tools. Document that production request handling must use local SDK evaluation instead of calling this endpoint synchronously.

Emit sampled evaluation telemetry

Record sampled events with flag key, environment, variant, matched rule identifier, context shape indicators, evaluation latency, and SDK version. Avoid storing raw sensitive identifiers when hashed or classified values are sufficient.

Phase 3: Admin UI

Create the authenticated operational interface for managing flags, editing per-environment values, reviewing history, and safely changing production behavior.

Phase goal

Deliver a dashboard that lets authorized users create, edit, search, preview, and archive flags while enforcing production edit permissions and preserving auditability.

Alternatives considered

Considered a minimal internal CLI for the first release. Chose an admin UI because support needs emergency kill-switch access and product needs safe rollout controls without requiring direct database or deploy access.

Recommendations

Start with a single dashboard page that supports search, detail editing, environment overrides, audit history, and permissions. Keep advanced experimentation features out of the navigation to avoid implying A/B-test analysis is available.

Open questions

Should support users be able to edit only existing kill-switch values, or can they create new flags outside production?

Create dashboard list and search

Build a flag dashboard behind existing auth middleware with searchable columns for key, description, owner, type, lifecycle state, and recent update time. Include filters for active versus archived and environment-specific overrides.

Build create and edit workflows

Implement forms for flag metadata, type-specific values, targeting rules, defaults, owners, and lifecycle state. Validate keys and rule shapes consistently with the backend typed schemas.

Add per-environment override editor

Provide clear editing for production, staging, and other environments, showing inherited values and explicit overrides. Prevent accidental production changes through role checks, confirmation, and visible environment labeling.

Implement rollout slider and bucket preview

Add a percentage rollout slider with a live preview that shows deterministic sample bucketing for representative user IDs. Make the preview use the same hashing implementation as the evaluator or a shared test vector suite.

Add audit history view

Display audit events for each flag with actor, timestamp, environment, operation, previous value, and new value. Include enough detail for incident review without exposing sensitive context values unnecessarily.

Enforce role-based access controls

Integrate with existing auth roles so only owners and admins can edit production values. Allow read access and non-production edit access according to existing internal authorization policy.

Use Postgres-backed flag storage with local read-through caches

Postgres provides an auditable, operationally editable source of truth using existing infrastructure. Local process snapshots satisfy the no-network-hop evaluation constraint while still allowing admin-driven changes to propagate through invalidation.

A config-file-in-repo approach would simplify review and rollback, but it would not meet the requirement for support and product to change behavior without a deploy.

Make in-process SDK evaluation the production request-path default

The evaluator must run from local memory to meet the latency target and avoid adding a network hop. The HTTP endpoint exists for secondary clients, tools, and services where synchronous request latency is not the primary concern.

A central evaluation service would reduce duplicated SDK logic, but it would violate the primary request-path constraint unless every service added more local caching complexity anyway.

Stale caches delay emergency kill switches

If invalidation is slow or broken, support may believe a feature is disabled while some processes continue serving the old value. Mitigation: keep polling intervals short with jitter, expose snapshot version and age metrics, and provide an operational check that confirms propagation.

Rule semantics become too complex to reason about

Supporting multiple target types, inheritance, and multivariate variants can create surprising outcomes. Mitigation: define first-match ordering, show matched rule previews in the UI, add evaluator test vectors, and reject ambiguous configurations at write time.

Telemetry volume grows faster than expected

Evaluation events can become high-volume quickly. Mitigation: sample by default, include rate controls per environment, aggregate where possible, and avoid emitting events for known internal health checks.

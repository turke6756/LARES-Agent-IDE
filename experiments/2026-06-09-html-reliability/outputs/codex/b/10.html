Feature-flag system

Add a first-party feature-flag platform so engineering can ship dark code, product can run gradual rollouts, and support can disable faulty behavior without a deploy. The plan is sized for three engineers over roughly six weeks and keeps evaluation local to request handling.

Success criteria

  • Backend services can call evaluate(flagKey, context) and receive a deterministic variant without adding a network hop on the request path.
  • Boolean, percentage rollout, and multivariate flags can be modeled with defaults, targeting rules, environment overrides, owners, descriptions, lifecycle state, and audit history.
  • Evaluation latency is under 1 ms at p99 in-process with warm local cache, verified by benchmark tests for representative flag sets.
  • Product and support users can search, create, edit, archive, and inspect flags through an authenticated admin UI, with production edits limited to flag owners and admins.
  • Flag updates propagate to evaluators through a documented push-or-poll invalidation path with bounded staleness and a safe fallback to cached or default values.
  • Every evaluation can emit sampled telemetry with enough context to analyze exposure by flag, variant, environment, service, and timestamp without storing sensitive user payloads.

Scope

In scope: a Postgres-backed flag schema, migrations, seed data, typed accessor library, audit history, deterministic evaluation engine, local in-memory cache, cache invalidation strategy, SDKs for the two backend languages in the monorepo, JSON-over-HTTP endpoint for non-SDK consumers, sampled exposure telemetry, and an authenticated admin dashboard.

Out of scope: full approval workflow, A/B-test statistics, scheduled rollouts, mobile SDKs, external feature-management SaaS, and request-path calls to a remote evaluation service.

The plan assumes the first release is internal-platform quality: robust enough for production feature control, but intentionally narrower than a commercial experimentation platform.

Constraints

  • No new external SaaS dependencies.
  • Evaluation must not add a network hop to normal request handling.
  • All admin and API surfaces must sit behind existing authentication middleware.
  • The feature is staffed by three engineers for approximately six weeks.
  • Production edits must be restricted by role and ownership; read access can follow existing internal-admin conventions.
  • The design must tolerate cache staleness explicitly and fail closed to defaults when a flag is missing or malformed.

Assumptions

The monorepo has exactly two backend languages that require native SDK support in the initial release; all other consumers can use the JSON-over-HTTP endpoint or defer adoption.

The existing auth and authorization stack can expose enough user identity, role, and group information to enforce owner/admin edit permissions in the admin UI and API.

The existing event pipeline can absorb sampled feature-flag exposure events without adding a new analytics vendor or storage system.

Phase 1: Flag Schema and Storage

Build the durable source of truth for flags, including the typed shape used by evaluators and the audit trail needed for operational accountability.

Phase goal

Deliver a versioned Postgres-backed flag model with migrations, seed data, audit history, and typed accessors so services and later phases can read normalized flag definitions safely.

Alternatives considered

Considered a config-file-in-repo approach for reviewability and deployment simplicity. Rejected it for the initial system because support must be able to disable a misbehaving feature without a deploy, and product needs gradual rollout edits that take effect operationally. The recommended path is a new feature_flags table in primary Postgres with a read-through cache and append-only audit table.

Recommendations

Use Postgres as the canonical store, keep the persisted model explicit rather than over-generic, and represent rules as structured JSON with validation at write time. Store a generated salt per flag so percentage bucketing remains stable across edits unless intentionally rotated.

Open questions

What audit retention period and export requirements apply to flag changes, especially production value edits?

Should archived flags be physically hidden from SDK snapshots by default, or included with inactive state for historical consistency?

Define canonical flag data model

Specify the fields for key, description, owner, flag type, targeting rules, default value, lifecycle state, environment overrides, salt, timestamps, and validation constraints. Include rule shapes for user ID, organization, and environment targeting, with explicit variant payload rules for boolean, percentage, and multivariate flags.

Add Postgres migrations

Create feature_flags, feature_flag_environments, and feature_flag_audit_events tables or equivalent normalized structures. Add uniqueness constraints on flag keys, lifecycle indexes for dashboard search, and write-time constraints for owner, type, and archived state.

Seed initial flags and environments

Add seed data for development, staging, and production environments plus one non-critical example flag for integration tests. Include production-safe defaults and ensure seed re-runs are idempotent.

Implement typed storage accessor library

Provide read and write accessors that return typed flag definitions, validate rule payloads, and isolate application code from raw database rows. The library should expose list, get-by-key, create, update, archive, and audit-read operations for later phases.

Record audit history for all changes

Capture actor, timestamp, operation, before/after summaries, affected environment, and reason when provided. Make audit writes part of the same transaction as flag mutations so the history cannot drift from the stored value.

Phase 2: Evaluation Engine

Build the low-latency runtime path that services use to resolve a flag to a variant with deterministic semantics and observable exposure events.

Phase goal

Deliver in-process evaluation libraries for the two backend languages, backed by local cached snapshots and shared rule semantics, plus an HTTP endpoint for non-SDK consumers and sampled telemetry for exposure analysis.

Alternatives considered

Considered a sidecar or central evaluation service for consistency across languages. Rejected it for normal request handling because the constraints prohibit adding a network hop. A sidecar may still be useful later for snapshot distribution, but the launch path should evaluate in-process from local memory.

Recommendations

Implement a shared conformance test suite that both SDKs must pass. Keep rule semantics simple and explicit: exact-match allowlists first, then ordered targeting rules, then percentage or multivariate bucketing, then environment-inherited default, then global default.

Open questions

What maximum cache staleness is acceptable for support kill switches: 5 seconds, 30 seconds, or 60 seconds?

Which user or organization identifier is canonical for deterministic bucketing when both are present in evaluation context?

Define evaluation semantics and conformance fixtures

Write the normative rules for missing flags, malformed context, rule ordering, environment inheritance, default fallback, archived flags, percentage rollout, and multivariate variant selection. Encode these as language-neutral fixture files that both SDK implementations and the HTTP endpoint test against.

Implement deterministic bucketing

Use a stable hash of selected subject ID plus flag salt to map users or organizations into a 0-9999 bucket range. Preserve assignments across rollout percentage changes where possible and document when edits can intentionally rebucket users.

Build local snapshot cache and invalidation

Load flag snapshots into process memory and refresh through push notifications if existing infrastructure supports them; otherwise use bounded-interval polling with ETag or version checks. The evaluator should continue serving the last valid snapshot if refresh fails and emit health telemetry for stale caches.

Ship SDKs for backend languages

Expose a small API with evaluate(flagKey, context), typed helpers for boolean and variant flags, initialization hooks, cache status inspection, and test utilities. Keep SDK configuration aligned across languages so adoption patterns are consistent.

Add JSON-over-HTTP evaluation endpoint

Provide an authenticated internal endpoint for systems that cannot embed an SDK. The endpoint may use the same evaluator and local cache, but product services should not call it in latency-sensitive request paths unless explicitly accepted by owners.

Emit sampled evaluation telemetry

Send sampled exposure events with flag key, variant, environment, service, rule match reason, evaluation timestamp, and anonymized or approved subject identifiers. Add sampling controls so hot flags do not overwhelm the existing telemetry pipeline.

Phase 3: Admin UI

Create the operational interface for product, support, and engineering users to manage flags safely under existing authentication and authorization controls.

Phase goal

Deliver an authenticated dashboard for flag creation, editing, search, archival, environment overrides, rollout preview, audit inspection, and production edit authorization.

Alternatives considered

Considered launching with database scripts and no UI. Rejected because support needs a safe kill-switch path without deploy access, and product needs understandable rollout controls. The UI should ship after the engine is stable enough to preview exactly what runtime evaluation will do.

Recommendations

Start with a practical internal-admin interface rather than a polished experimentation suite. Bias toward guardrails: visible environment labels, production edit confirmation, owner checks, archived-state warnings, and audit history close to the edit form.

Open questions

Do support users need edit access for all production kill switches, or only for flags explicitly marked as support-operable?

Should creating a new production flag require an owner from an allowlisted engineering group?

Build flag list, search, and detail pages

Implement a dashboard page with search by key, owner, description, type, environment, and lifecycle state. The detail view should show current defaults, environment overrides, targeting rules, recent audit entries, and cache propagation status when available.

Add create, edit, and archive workflows

Provide forms for all flag types with schema-aware validation, safe defaults, owner assignment, environment-specific values, and archive confirmation. Edits should route through the storage accessor so validation and audit behavior match API writes.

Implement role-based production editing

Use existing auth middleware and authorization data to allow production edits only for flag owners and admins. Non-authorized users may view production values if current internal-admin policy allows, but edit controls must be disabled server-side and client-side.

Create percentage rollout slider with bucket preview

Add a slider for rollout percentage that previews included buckets and sample user or organization assignments using the same bucketing function as the SDK. Show whether changing the percentage expands, shrinks, or reshuffles exposure.

Add audit-history view

Expose chronological audit entries with actor, timestamp, operation, environment, changed fields, and before/after summaries. Include filters for production edits and archived flags so investigations are fast during incidents.

Run end-to-end rollout and kill-switch tests

Test the full path from UI edit to database write, audit event, cache invalidation, SDK evaluation, HTTP endpoint evaluation, and telemetry emission. Include a production-like scenario where support disables a flag and services observe the change within the chosen staleness bound.

Use Postgres-backed flags with read-through caching

Choose a new primary Postgres storage model with local/read-through caches over config files in the repository. This supports no-deploy operational changes, auditability, gradual rollouts, and admin UI workflows while staying inside existing infrastructure.

Config files would be easier to review and simpler to deploy, but they do not satisfy the support kill-switch requirement without a deploy path.

Evaluate flags in-process from local snapshots

Choose SDK-based in-process evaluation as the primary runtime path. This satisfies the no-network-hop constraint and keeps p99 latency under the target when snapshots are warm.

A central evaluator would simplify cross-language consistency, but it would add a network dependency to request handling and violate the stated constraint.

Cache staleness delays kill switches

If evaluator caches refresh too slowly or invalidation fails, support may believe a production feature is disabled while services continue serving the old value. Mitigation: define a hard staleness target, expose cache health, serve last valid snapshots with age metadata, and test propagation end to end before launch.

Inconsistent SDK behavior across languages

Different language implementations can drift on rule ordering, bucketing, or fallback semantics. Mitigation: maintain language-neutral conformance fixtures and require every SDK and endpoint implementation to pass them in CI.

Production edits create broad blast radius

A malformed targeting rule or mistaken percentage can expose or disable a feature for too many users. Mitigation: validate writes server-side, require owner/admin permission for production, show previews for percentage rollouts, and record full audit history for every change.

Telemetry volume exceeds existing pipeline capacity

Hot flags evaluated on every request could produce excessive exposure events. Mitigation: sample by default, include per-service sampling controls, and test projected event volume before broad SDK adoption.

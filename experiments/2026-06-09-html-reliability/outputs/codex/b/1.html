Feature flag system

Add an internal feature-flag platform so engineering can ship dark, product can run gradual rollouts, and support can disable faulty features without waiting for a deploy.

Success criteria

  • Backend services can evaluate boolean, percentage, and multivariate flags locally with p99 evaluation latency below one millisecond after cache warmup.
  • Flag changes are persisted, audited, and visible to authorized users without deploys.
  • Production flag edits are restricted to flag owners and admins through existing authentication and authorization middleware.
  • Rollout behavior is deterministic across services and languages for the same flag key, salt, context, and environment.
  • Support can archive or disable a misbehaving active flag quickly without creating a new application release.

Scope

In scope: a Postgres-backed flag schema, migrations, seed data, audit history, typed accessors, deterministic evaluation libraries for the two backend languages in the monorepo, a JSON-over-HTTP evaluation endpoint for secondary consumers, local cache invalidation, sampled telemetry, and an authenticated admin dashboard for create, edit, search, archive, environment overrides, rollout preview, and audit inspection.

Out of scope: A/B-test statistics, scheduled rollouts, mobile SDKs, a full approval workflow, and new external SaaS dependencies.

Constraints

  • No new external SaaS dependencies.
  • The request-time evaluation path must not add a network hop.
  • All admin and API surfaces must sit behind existing auth middleware.
  • Implementation must fit a team of three engineers over roughly six weeks.
  • Rollout and targeting semantics must be consistent across backend languages.

Assumptions

The primary Postgres database is an acceptable source of truth for flag definitions, environment overrides, and audit history because flag metadata write volume is low.

The two backend languages can share deterministic evaluation semantics through a common serialized rule format, shared conformance tests, and compatible hash implementations.

Existing authorization data is sufficient to enforce owner and admin-only production edits without introducing a new identity subsystem.

Phase 1: Flag schema and storage

Build the source of truth for flags, their environment-specific values, targeting metadata, lifecycle state, and audit history. This phase establishes the durable contract used by the evaluation engine and admin UI.

Phase goal

Deliver a typed, audited, Postgres-backed flag model with seed data and a read-through cache contract that downstream services can safely consume.

Alternatives considered

Considered a config-file-in-repo approach for simplicity and reviewability, but it would make support kill switches and product-owned gradual changes depend on deploy cadence. The recommended approach is a new feature_flags storage model in primary Postgres, plus cache layers for read efficiency.

Recommendations

Use Postgres as the authoritative store, split global flag identity from per-environment configuration, and record every mutation in an append-only audit table. Define the rule payload as typed JSON with strict validation at write time so SDKs can evaluate without database-specific assumptions.

Open questions

Should ownership be a single team or user field, or should the schema allow multiple owners from the start?

Design the canonical flag data model

Define tables for flag identity, environment configuration, variants, targeting rules, lifecycle state, salts, and audit entries. Include fields for key, description, owner, type, default value, active or archived state, and timestamps. Add constraints for unique keys, valid type-specific payloads, and immutable audit rows.

Create migrations and seed data

Implement database migrations for the feature flag tables and add seed flags for development, staging, and production smoke tests. Include one example for each flag type so the evaluator and UI can be developed against realistic fixtures.

Implement typed storage accessors

Add a typed accessor library that loads flags by key, environment, and lifecycle state. The library should return validated domain objects rather than raw database rows and should expose explicit methods for create, update, archive, and audit retrieval.

Add read-through cache integration

Introduce a cache interface for hot flag reads with versioned entries, TTL fallback, and cache miss loading from Postgres. Keep cache behavior behind the storage accessor so later invalidation work can change implementation without changing callers.

Add audit history capture

Record every create, edit, archive, and environment override mutation with actor, timestamp, previous value, new value, and request metadata. Audit history is query-only after insertion and does not include approval workflow state.

Phase 2: Evaluation engine

Build the local evaluation path used by backend services and the HTTP fallback endpoint used by consumers outside the two primary backend languages.

Phase goal

Deliver deterministic, sub-millisecond local flag evaluation with consistent rule semantics, cache invalidation, SDKs for the monorepo backend languages, an HTTP endpoint for secondary clients, and sampled telemetry.

Alternatives considered

Considered a central sidecar or service for all evaluations, but request-time network calls violate the latency and reliability constraints. The recommended path is an embedded evaluator with local in-memory snapshots, plus an HTTP endpoint only for workflows where an extra hop is already acceptable.

Recommendations

Compile stored flag definitions into an immutable in-memory snapshot per process. Use a shared conformance suite for hashing, rule ordering, default handling, and environment inheritance so both backend SDKs produce identical results.

Open questions

Should invalidation use an existing internal pub/sub channel, short polling, or a hybrid where push is preferred and polling is the safety net?

Define evaluation semantics and conformance fixtures

Specify rule ordering, match behavior, default fallback, environment inheritance, missing context handling, and variant return shape. Create language-neutral fixtures that exercise boolean flags, percentage rollout, multivariate allocation, user ID targeting, org targeting, and environment targeting.

Implement deterministic bucketing

Use a stable hash of user ID plus flag salt to assign buckets for percentage and multivariate rollouts. Ensure bucket boundaries are reproducible across languages and unaffected by rule list order except where rule precedence explicitly applies.

Build backend SDKs

Implement evaluate(flagKey, context) -> variant in both backend languages. The SDKs should use local snapshots, expose typed context construction, handle missing flags safely, and provide metrics around latency, cache age, and fallback usage.

Add local cache refresh and invalidation

Load flag snapshots into memory and refresh them through the chosen push-or-poll invalidation mechanism. Include version checks, stale snapshot tolerances, startup warmup behavior, and a fail-closed or fail-open policy per flag type where appropriate.

Expose JSON-over-HTTP evaluation endpoint

Add an authenticated endpoint for non-SDK consumers that accepts a flag key and context and returns the evaluated variant plus metadata such as flag version and reason. Document that this endpoint is not for latency-sensitive request paths.

Emit sampled evaluation telemetry

Emit sampled events containing flag key, environment, variant, reason, SDK language, cache version, and non-sensitive context dimensions. Avoid raw user identifiers where existing telemetry standards require hashing or redaction.

Phase 3: Admin UI

Create the authenticated management experience used by engineering, product, and support to manage flags and inspect changes.

Phase goal

Deliver a dashboard for creating, editing, searching, previewing, overriding, archiving, and auditing flags with production edit permissions limited to owners and admins.

Alternatives considered

Considered making the first release API-only to save UI time, but that would fail the support kill-switch and product rollout use cases. The recommended UI is narrow but complete: dashboard list, detail editor, per-environment override controls, rollout preview, and audit history.

Recommendations

Use existing admin layout, auth middleware, form components, and role checks. Treat production edits as privileged mutations with clear diff previews and audit annotations, while allowing read-only visibility more broadly for debugging.

Open questions

Should support users be allowed to disable any active production flag, or only flags explicitly marked as support-killable by the owner?

Build flag dashboard and search

Add a dashboard page that lists flags by key, description, owner, type, environment status, and lifecycle state. Include search and filters for owner, type, active state, and archived state.

Build create and edit workflows

Implement forms for boolean, percentage, and multivariate flags with validation for defaults, variants, targeting rules, owners, descriptions, and lifecycle state. Show a before-and-after diff before saving edits that affect production values.

Add per-environment overrides

Expose environment-specific values and rules, including staging inheritance from production where no staging override exists. Make inherited versus overridden values visually explicit and ensure saves update only the selected environment scope.

Add rollout slider and live bucket preview

Add a percentage rollout control with a live preview showing how sample user IDs map into treatment or control buckets. The preview should use the same deterministic bucketing code path or shared fixture logic as the SDKs.

Add audit history view

Display audit entries for each flag with actor, timestamp, environment, changed fields, previous values, new values, and mutation source. Include links from dashboard rows to the relevant flag audit view.

Enforce role-based production edits

Gate production edits so only flag owners and admins can change production values. Allow broader authenticated read access where appropriate, and return clear authorization errors for unauthorized mutation attempts.

Use Postgres-backed flags with local evaluation snapshots

Flags will live in primary Postgres as the source of truth, with read-through caching and per-process in-memory snapshots for evaluation. This supports non-deploy flag changes and audit history while preserving the constraint that request handling does not add a network hop.

A config-file-in-repo approach is easier to review and roll back through normal code workflows, but it does not satisfy support-operated kill switches or product-operated gradual rollout changes without deploys.

Cross-language evaluator drift

If SDKs diverge in hashing, rule precedence, or default behavior, different services may show different product behavior for the same user. Mitigation: maintain language-neutral conformance fixtures and require both SDKs to pass them in CI.

Stale local caches delay kill switches

If invalidation fails or polling intervals are too long, support may disable a feature but services may continue serving the old value. Mitigation: use versioned snapshots, bounded TTLs, observable cache age, and a tested invalidation fallback.

Overly broad production edit access

Misconfigured authorization could allow unintended production changes. Mitigation: centralize production mutation checks, test owner and admin paths explicitly, and include actor details in audit history.

Telemetry volume or sensitive context leakage

Evaluation events could become noisy or expose identifiers. Mitigation: sample events, emit only approved dimensions, and hash or omit sensitive identifiers according to existing telemetry policy.

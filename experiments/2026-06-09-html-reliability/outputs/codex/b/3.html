Feature flag system

Add a first-party feature-flag platform so engineering can ship dark, product can run controlled rollouts, and support can disable faulty features without a deploy.

Success criteria

  • Engineers can define typed feature flags with defaults, owners, lifecycle state, targeting rules, and audit history.
  • Backend request paths can evaluate flags locally without adding a network hop and with p99 evaluation latency under one millisecond after cache warmup.
  • Product and support users can create, search, edit, archive, and roll back production flag values through an authenticated dashboard with role-based editing controls.
  • Percentage rollouts are deterministic across services and stable for a given user, flag, environment, and salt.
  • Every evaluation path emits sampled telemetry that can later answer exposure and rollout-debugging questions.
  • The team can ship all three phases in roughly six weeks with three engineers and without introducing an external SaaS dependency.

Scope

In scope: Postgres-backed flag schema, read-through caching, migrations, seed data, audit history, typed accessor libraries, deterministic evaluation, SDKs for the two backend languages in the monorepo, a JSON-over-HTTP endpoint for other consumers, sampled telemetry, and an authenticated admin UI.

Out of scope: A/B-test statistics, scheduled rollouts, mobile SDKs, full approval workflow, external flag-management SaaS, and any evaluation flow that requires a runtime network call during normal request handling.

Constraints

  • No new external SaaS dependencies.
  • The evaluation path must not add a network hop to request handling.
  • All admin surfaces and HTTP endpoints must sit behind existing auth middleware.
  • Production edits are limited to flag owners and admins.
  • Three engineers are available for approximately six weeks.
  • Audit history is required, but a full approval workflow is explicitly deferred.

Assumptions

The primary Postgres database is the right system of record because flag writes are low volume, need transactional audit records, and should follow existing backup and access-control practices.

The existing auth middleware and authorization model can enforce admin and owner edit permissions without a new identity integration.

The platform has either an existing internal event channel or can tolerate a short polling interval for propagating flag changes to process-local caches.

Phase 1: Flag schema and storage

Build the durable model and access layer first so every later phase has one source of truth for flag definitions, environment values, targeting rules, and audit history.

Phase goal

Deliver a Postgres-backed feature-flag data model with migrations, seed data, audit history, a read-through cache, and typed accessors that return validated flag definitions to backend code.

Alternatives considered

Considered a config-file-in-repo approach for simplicity and reviewability. Choose Postgres plus read-through cache because product and support need runtime edits, audit history, environment overrides, and kill-switch behavior without a deploy.

Recommendations

Use normalized tables for flags, environment-specific values, targeting rules, and audit events. Store rule payloads as validated JSON where flexibility is needed, but keep stable fields such as key, owner, type, lifecycle state, and environment indexed as typed columns.

Open questions

Should flag ownership reference a user, a team, or both, and which existing directory table should be authoritative?

How long should detailed audit history be retained before compaction or archival?

Define the flag domain model

Specify fields for key, description, owner, type, default value, lifecycle state, salt, environment overrides, and targeting rules by user ID, organization, and environment. Include validation rules for key naming, owner presence, type-specific variants, and archived flag behavior.

Create storage migrations

Add migrations for feature_flags, environment value rows, targeting-rule rows, and append-only audit events. Include indexes for flag key lookup, environment lookup, lifecycle filtering, owner filtering, and audit lookup by flag.

Add seed data and fixtures

Create representative boolean, percentage, and multivariate flags for local development and tests. Include examples for production, staging inheritance, archived flags, org targeting, and explicit user targeting.

Implement audit history writes

Record create, update, archive, and value-change events with actor, timestamp, previous value, new value, environment, and change source. Keep audit recording in the same transaction as the flag mutation.

Build typed accessor library

Expose a typed internal API for reading active flag definitions, resolving environment records, and warming the read-through cache. Return parsed domain objects rather than raw database rows.

Phase 2: Evaluation engine

Implement the runtime path that application code will call. The engine must be fast, deterministic, locally cached, and consistent across the monorepo's backend languages.

Phase goal

Deliver evaluate(flagKey, context) -> variant for backend services with deterministic targeting, environment inheritance, local cache invalidation, sampled telemetry, and compatible SDKs for both backend languages plus an HTTP endpoint for non-SDK consumers.

Alternatives considered

Considered a sidecar-only service for centralized logic. Prefer a shared library as the primary request-path integration because the constraint forbids adding a network hop; keep the JSON-over-HTTP endpoint for jobs, tools, and less latency-sensitive consumers.

Recommendations

Implement the engine from a language-neutral evaluation spec and golden test corpus. Use a stable hash such as MurmurHash3 or xxHash over flagKey:salt:environment:userId, map to basis points, and share test vectors across SDKs.

Open questions

Which existing hash implementation is already available in both backend languages and can produce identical unsigned output?

What maximum propagation delay is acceptable for support-owned kill-switch changes: seconds, tens of seconds, or one minute?

Write evaluation semantics spec

Define rule ordering, match precedence, environment inheritance, default fallback, archived flag handling, missing context behavior, percentage bucketing, multivariate allocation, and error behavior. Include concrete examples for every flag type.

Implement core evaluator

Build the evaluator around immutable in-memory snapshots loaded from the accessor library. Evaluate explicit user rules first, then organization rules, then percentage or multivariate rollout, then environment default, then global default.

Ship SDKs for backend languages

Expose a minimal SDK in each backend language with typed context objects, typed return variants, initialization hooks, cache warmup, telemetry integration, and golden tests shared across implementations.

Add local cache invalidation

Implement process-local in-memory caching with push invalidation if an internal channel is available, otherwise short-interval polling with jitter. Support atomic snapshot replacement so evaluations never observe partially loaded state.

Add JSON-over-HTTP evaluation endpoint

Provide an authenticated endpoint for tools and services that cannot use an SDK. Document that request-handling services should not depend on this endpoint for hot-path flag checks.

Emit sampled evaluation telemetry

Emit sampled events containing flag key, variant, environment, rule source, SDK language, cache snapshot version, and coarse context identifiers. Avoid logging raw targeting payloads or sensitive user attributes.

Phase 3: Admin UI

Create the operational surface for product, engineering, and support to manage flags safely. The UI should make production edits deliberate, visible, auditable, and constrained by role.

Phase goal

Deliver an authenticated dashboard for creating, editing, searching, archiving, and auditing flags, with per-environment overrides, production edit controls, and rollout preview tooling.

Alternatives considered

Considered limiting Phase 3 to internal scripts for create and edit operations. Choose a dashboard because support needs kill-switch access without deploy rights, and product needs gradual rollout controls with visibility into current targeting.

Recommendations

Use existing admin layout, form components, auth middleware, and server-side validation. Treat the UI as a client of the same mutation APIs used by tests and scripts so permission checks and audit writes are not duplicated in frontend code.

Open questions

Should production percentage increases require an explicit confirmation step even though a full approval workflow is out of scope?

What sample population should the bucketing preview use: synthetic IDs, recent active users, or caller-supplied examples?

Build dashboard list and search

Add a dashboard page with searchable and filterable rows for flag key, description, owner, type, lifecycle state, environments with overrides, and last updated time. Include archived flags behind an explicit filter.

Build create and edit forms

Support boolean, percentage rollout, and multivariate flag creation with validation for required fields, type-specific values, targeting rules, and defaults. Show clear differences between global defaults and per-environment overrides.

Add per-environment override controls

Allow authorized users to edit values by environment while making staging inheritance from production visible. Ensure inherited values, explicit overrides, and default fallbacks are visually and semantically distinct.

Add rollout slider and bucket preview

Provide a percentage slider that updates a live preview of bucket allocation using the same deterministic hashing logic as the engine. Show representative user IDs moving or staying stable as rollout percentages change.

Add audit-history view

Display chronological audit events for each flag with actor, timestamp, environment, changed fields, previous value, and new value. Provide filters for production changes and archive events.

Enforce role-based production editing

Gate production mutations so only flag owners and admins can edit production values. Apply checks server-side, reflect permissions in the UI, and audit denied mutation attempts where existing policy allows.

Use primary Postgres plus read-through cache for flag storage

Postgres supports runtime edits, transactional audit history, existing backup procedures, existing auth-adjacent access patterns, and queryable admin UI workflows. A read-through cache keeps evaluation reads fast and avoids direct database pressure from request paths.

A config-file-in-repo approach would be simpler to review and easier to roll back through Git, but it cannot meet the support kill-switch and product rollout requirements without a deploy.

Use SDK libraries as the primary evaluation path

The runtime request path must not add a network hop, so services should evaluate from local in-memory snapshots through language SDKs. The HTTP endpoint remains useful for non-hot-path consumers and integration tests.

A centralized sidecar or service would simplify language consistency, but it would either add a hop or require operational complexity that is not justified for the six-week scope.

Stale caches delay kill-switch effectiveness

If cache invalidation is slow or unreliable, support may archive or disable a feature but some processes could continue serving the old variant. Mitigation: define an explicit propagation SLO, prefer push invalidation where possible, add polling fallback with jitter, expose snapshot version telemetry, and provide an emergency cache-refresh endpoint or process signal if the platform supports it.

Different SDKs return different variants

Hashing, JSON parsing, numeric precision, or rule ordering differences can cause inconsistent behavior across backend languages. Mitigation: maintain a language-neutral spec, shared golden fixtures, and CI that runs the same evaluation corpus against both SDKs.

Admin UI makes production misconfiguration easy

Powerful runtime edits can cause incidents if defaults, environment overrides, or percentage rollouts are unclear. Mitigation: server-side validation, explicit production labels, audit history, owner/admin RBAC, confirmation for destructive archive actions, and preview for percentage bucketing.

Evaluation telemetry overwhelms event pipelines

Every evaluation emits a sampled event, but high-traffic services could still produce excessive volume. Mitigation: centralize sampling configuration, default to conservative rates, aggregate low-value metadata, and monitor event throughput during rollout.

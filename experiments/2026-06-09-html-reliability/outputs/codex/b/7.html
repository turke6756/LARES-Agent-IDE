Feature flag system

Add an internal feature-flag platform so engineering can ship code dark, product can run controlled rollouts, and support can disable misbehaving features without a deploy.

Success criteria

  • Engineers can define typed flags with owners, defaults, environments, targeting rules, and lifecycle state.
  • Backend request paths can evaluate flags locally without adding a network hop, with p99 evaluation under one millisecond after cache warmup.
  • Product and support can create, edit, search, and archive flags through an authenticated admin UI with production edit controls.
  • Every flag change is auditable, including actor, timestamp, environment, old value, and new value.
  • Percentage rollouts are deterministic and stable for a given user, flag, and salt.
  • The initial system is shippable by three engineers in roughly six weeks without external SaaS dependencies.

Scope

In scope: Postgres-backed flag schema, migrations, seed data, audit history, read-through cache, typed accessor library, evaluation SDKs for the two backend languages in the monorepo, JSON-over-HTTP evaluation endpoint for non-request-path consumers, sampled telemetry, and an authenticated admin dashboard.

Out of scope: external flagging SaaS, full approval workflows, A/B-test statistics, scheduled rollouts, mobile SDKs, and using the evaluation endpoint from latency-sensitive backend request handling.

Constraints

  • No new external SaaS dependencies.
  • Evaluation in request handling must be local and must not add a network hop.
  • All admin and API surfaces must sit behind existing auth middleware.
  • Production edits must be limited to flag owners and admins.
  • Three engineers are available for about six weeks, so the design should favor a compact internal platform over a broad experimentation suite.

Assumptions

Backend request context already exposes stable user ID, organization ID, and environment values, or can expose them with small adapter changes.

The primary Postgres database is the right source of truth for flags and can handle low-volume admin writes plus cache refill reads.

The existing auth and role model can be extended to distinguish flag owners, admins, and read-only viewers without a separate identity system.

Phase 1: Flag schema and storage

Establish the durable source of truth, audit trail, seed data, and typed access patterns that later phases will use.

Phase goal

Deliver a Postgres-backed flag model with migrations, lifecycle state, audit history, seeded examples, and a typed accessor library that callers can use without hand-building queries.

Alternatives considered

Considered a config-file-in-repo model because it is reviewable and easy to roll back, but it does not satisfy support-driven kill switches or product-managed gradual rollout changes without deploys. Chose a feature_flags table plus read-through cache because runtime edits, auditability, and existing auth integration matter more for this feature.

Recommendations

Use a normalized core flag table with JSONB rule and variant payloads, strict typed validation in the accessor library, and an append-only audit table. Store a per-flag random salt at creation time so percentage buckets remain stable even if names or descriptions change.

Open questions

Should targeting rules and multivariate variants be stored as validated JSONB documents, or split into relational child tables for easier querying and stricter database constraints?

Should flag owners be individual users only, teams only, or either depending on product area?

Define the flag and audit data model

Create the model for key, description, owner, type, default value, lifecycle state, environment overrides, targeting rules, variants, salt, timestamps, and audit metadata. Include validation rules for unique keys, allowed flag types, allowed lifecycle states, and required default values per type.

Add Postgres migrations

Add migrations for feature_flags, environment override storage, and append-only feature_flag_audit_events. Include indexes for key lookup, owner lookup, lifecycle filtering, and audit-history reads by flag key.

Add read-through cache primitives

Implement a small cache layer for loading flags by key and environment from Postgres, with explicit TTLs and hooks for later invalidation. Keep it isolated behind an interface so Phase 2 can reuse it for in-memory snapshots.

Create seed data and fixture flags

Add representative boolean, percentage, and multivariate flags for development and test environments. Include archived examples so lifecycle filtering and UI search can be exercised early.

Build typed accessor library

Expose typed create, update, archive, fetch, and list operations for flags. Centralize schema validation, default handling, audit-event creation, and ownership metadata so the admin UI and future automation do not duplicate persistence logic.

Phase 2: Evaluation engine

Build the fast local evaluation path, SDK surfaces, invalidation mechanics, and telemetry needed to safely use flags in production request handling.

Phase goal

Deliver deterministic local flag evaluation for backend services with under-one-millisecond p99 latency after warmup, plus SDKs, an HTTP endpoint for non-critical consumers, cache invalidation, and sampled evaluation telemetry.

Alternatives considered

Considered a sidecar-only or central evaluation service to keep rule logic in one runtime, but that would add a network dependency to request handling unless every service embedded a sidecar locally. The recommended path is a shared library for the two backend languages, backed by local in-memory snapshots, with a JSON-over-HTTP endpoint only for consumers that are not on latency-sensitive paths.

Recommendations

Use rule-first evaluation semantics: explicit user and organization targeting rules take precedence, then environment override, then percentage or multivariate allocation, then default value. Use a stable hash of flagKey, flag salt, user ID, and variant key to avoid cross-flag correlation.

Open questions

Should invalidation start with short-interval polling, database notifications, or the existing internal pub-sub mechanism?

What default sample rate should evaluation telemetry use to be analytically useful without creating high-cardinality event volume?

Implement evaluator core

Implement evaluate(flagKey, context) -> variant with deterministic rule ordering, default fallback behavior, typed return values, and clear error handling for missing context or malformed flag definitions.

Add deterministic percentage and multivariate bucketing

Use a stable hash of user ID plus flag salt to assign users into rollout buckets. Add tests proving bucket stability across process restarts, distribution sanity for large populations, and no reassignment when descriptions or owners change.

Implement environment inheritance semantics

Define how staging defaults from production while still allowing explicit staging overrides. Make inheritance visible in evaluator output metadata so the admin UI can explain whether a value is local to the environment or inherited.

Build local cache and invalidation loop

Load a local in-memory snapshot per process and refresh it through the selected push or poll strategy. Include stale-read metrics, last-refresh timestamps, and fallback behavior if Postgres is temporarily unavailable.

Ship SDKs and HTTP endpoint

Provide idiomatic SDKs for both backend languages in the monorepo, including typed accessors, context builders, test helpers, and local override hooks. Add a JSON-over-HTTP endpoint behind existing auth for tools and low-volume consumers outside those SDKs.

Emit sampled evaluation telemetry

Emit sampled events containing flag key, variant, environment, rule match category, SDK language, and non-sensitive context identifiers. Avoid logging raw targeting payloads or sensitive user attributes.

Phase 3: Admin UI

Create the operational surface for product, support, and engineering to manage flags without deploys while respecting production edit permissions.

Phase goal

Deliver an authenticated dashboard for creating, editing, searching, previewing, auditing, and archiving flags, with production write access restricted to owners and admins.

Alternatives considered

Considered limiting v1 to database-backed CLI tools for speed, but that would exclude support and product from urgent kill-switch and rollout workflows. Chose a focused admin UI because operational access is a core requirement, while advanced experimentation features remain explicitly out of scope.

Recommendations

Optimize the UI around safe editing: clear environment labels, visible inherited values, required descriptions and owners, archive instead of delete, and a preview panel that explains which users or organizations match a proposed rule.

Open questions

Which preview inputs should be mandatory for rollout confidence: user ID only, organization ID, environment, or a fuller request context fixture?

Should production edits require an explicit confirmation step even though a full approval workflow is out of scope?

Build dashboard list and search

Create a dashboard page showing key, description, owner, type, lifecycle state, environments, and last update. Support search by key, owner, description, state, and environment.

Build create and edit forms

Add forms for boolean, percentage rollout, and multivariate flags. Validate required fields, default values, owner selection, target rules, variant weights, and lifecycle transitions before saving through the typed accessor library.

Add environment override editor

Show production, staging, and other configured environments side by side. Mark inherited values clearly and allow explicit overrides where the user's role permits editing that environment.

Add rollout slider with bucketing preview

Provide a percentage rollout control with a live preview of sample user assignments. Reuse the same bucketing implementation or golden test fixtures from the evaluator so the UI does not drift from runtime behavior.

Add audit-history view

Display append-only flag changes with actor, timestamp, environment, changed fields, old values, and new values. Include links from the flag detail page to its audit history.

Enforce role-based production edits

Integrate existing auth middleware and authorization checks so only flag owners and admins can edit production values. Allow broader read access and non-production editing according to the product's existing internal role rules.

Use Postgres as source of truth with read-through and local caches

Runtime-editable flags, support kill switches, audit history, and admin UI workflows require mutable storage outside the deploy cycle. Postgres keeps the system inside existing infrastructure and avoids external SaaS dependencies, while cache layers keep evaluation off the critical database path.

A config-file-in-repo approach is simpler to review and roll back, but it cannot support urgent no-deploy changes or product-managed gradual rollout operations.

Use local SDK evaluation for request handling

The request path must not add a network hop, so backend services should evaluate flags in process from a local snapshot. The JSON-over-HTTP endpoint remains available for lower-volume consumers and tools that cannot use the native SDKs.

A central evaluation service would simplify implementation consistency, but it would violate the latency and availability constraint for request handling unless paired with local sidecars or caches.

Stale local caches delay kill switches

If cache invalidation is slow or broken, support may believe a feature is disabled while some processes continue serving the old value. Mitigation: define a strict maximum staleness target, expose last-refresh telemetry, add manual refresh hooks, and test invalidation behavior before production rollout.

Complex rules exceed the p99 latency target

Large target lists or deeply nested rule expressions could push evaluation over one millisecond. Mitigation: constrain rule grammar in v1, precompile rules into evaluator-friendly structures, cap list sizes, and benchmark representative flag sets before enabling broad adoption.

Incorrect production edit causes customer impact

A user with permission could accidentally change a production default, rollout percentage, or targeting rule. Mitigation: require clear environment labeling, audit every change, restrict production edits to owners and admins, and consider an explicit confirmation step for production writes.

Evaluation telemetry creates high-cardinality data volume

Emitting an event for every evaluation with raw identifiers could create cost and privacy concerns. Mitigation: sample events, avoid sensitive context payloads, aggregate where possible, and document allowed telemetry fields.

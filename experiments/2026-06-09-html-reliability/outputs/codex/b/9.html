Feature flag system

Build an internal feature-flag platform so engineering can ship dormant code, product can run gradual rollouts, and support can disable misbehaving features without a deploy. The work is planned as three phases over roughly six weeks for a team of three engineers: schema and storage, evaluation engine, and admin UI.

Success criteria

  • Engineers can define typed boolean, percentage rollout, and multivariate flags with owners, descriptions, defaults, lifecycle state, and targeting rules.
  • Backend callers can evaluate a flag locally with evaluate(flagKey, context) -> variant at under 1 millisecond p99 after warmup, without adding a network hop to request handling.
  • Product and support users can search, create, edit, archive, and override flags per environment through an admin UI protected by existing auth middleware.
  • Production edits are restricted to flag owners and admins, and every change is recorded in audit history with actor, timestamp, environment, old value, and new value.
  • Gradual rollouts are deterministic across calls and services, using stable bucketing from user ID and per-flag salt.
  • Flag evaluation emits sampled telemetry suitable for later analysis without materially affecting request latency.

Scope

In scope: a primary Postgres-backed flag schema, migrations, seed data, typed accessor libraries, audit history, deterministic evaluation semantics, local in-memory caching, push-or-poll invalidation, SDKs for the two backend languages in the monorepo, JSON-over-HTTP evaluation for non-critical external callers, and a first-party admin dashboard.

Out of scope: full approval workflows, A/B-test statistical analysis, scheduled rollouts, mobile SDKs, external feature-management SaaS, and moving runtime request evaluation to a remote service.

Constraints

  • No new external SaaS dependencies are allowed.
  • The request-handling evaluation path must not add a network hop.
  • All admin and API surfaces must sit behind existing auth middleware.
  • The target delivery window is roughly six weeks with three engineers.
  • The evaluation engine must preserve deterministic results during deploys, cache refreshes, and service restarts.
  • The initial system must be operable by engineering, product, and support without requiring a separate release process for flag changes.

Assumptions

The existing auth and authorization stack can provide the roles and ownership checks needed for flag editing, including production-only restrictions.

The monorepo has two backend languages that need first-class SDKs, and other callers can use the JSON-over-HTTP endpoint for non-request-path evaluation.

Primary Postgres is the right system of record for flags, with read-through caching and local in-memory snapshots preventing hot-path database reads.

Phase 1: Flag schema and storage

This phase creates the durable source of truth for flags and the typed internal interfaces that later phases consume. The goal is to make flag definitions explicit, auditable, and safe to evolve before wiring them into runtime evaluation.

Phase goal

Deliver a Postgres-backed flag model with migrations, seed data, audit history, and typed accessors that represent boolean, percentage, and multivariate flags with targeting rules, defaults, lifecycle state, and per-environment values.

Alternatives considered

Considered a config-file-in-repo model because it gives code review, simple rollback, and easy local development. It was rejected for the initial system because support and product need no-deploy operational control, audit history needs to be queryable, and gradual rollout changes should not depend on repository write access or release cadence.

Considered storing all targeting rules as opaque JSON only. The recommended approach is a hybrid: normalized flag metadata and environment rows, with versioned structured JSON for rule expressions so migrations can enforce ownership, lifecycle, and uniqueness while still allowing targeting semantics to evolve.

Recommendations

  • Use primary Postgres as the source of truth with a read-through cache for admin and SDK refresh paths.
  • Represent flag values with a discriminated union: boolean, percentage rollout, and multivariate variants.
  • Store a per-flag salt at creation time so rollout buckets remain stable when descriptions, owners, or rules change.
  • Version rule schemas from day one to support future operators without breaking old evaluations.

Open questions

Which environments must be modeled at launch, and do ephemeral preview environments inherit from staging or production?

Should flag owners be individual users, teams, service owners, or a combination of these identity types?

Define the flag data model

Create the canonical model for flag key, description, owner, flag type, default value, lifecycle state, salt, created and updated metadata, and environment-specific overrides. Specify validation rules for globally unique keys, allowed key formats, archived flag behavior, and default variant compatibility with the selected flag type.

Design targeting rule representation

Define versioned rule JSON for user ID, organization, and environment matching. Include explicit rule ordering, stop-on-first-match behavior, and a final fallback to the environment default. Document unsupported operators so the admin UI and SDK validators reject ambiguous rules early.

Add Postgres migrations and seed data

Create feature_flags, feature_flag_environments, and feature_flag_audit_events tables. Add indexes for flag key lookup, environment lookup, active flag scans, and audit history. Seed a small set of internal-only flags to exercise each flag type in development and staging.

Implement audit event recording

Record all create, edit, archive, restore, and environment override changes with actor, timestamp, reason when available, old value, new value, and request identifier. Keep audit writes in the same transaction as flag mutations so history cannot drift from stored state.

Build typed storage accessors

Provide internal read and write accessors that hide table layout from the evaluation engine and admin UI. Include schema validation, typed decoding of rule and variant payloads, lifecycle filters, and an API for loading all active flags for a target environment into a cacheable snapshot.

Phase 2: Evaluation engine

This phase turns stored definitions into fast, deterministic runtime answers. The evaluation library must be embeddable in request-handling services so normal flag checks are local memory reads and CPU work only.

Phase goal

Deliver a shared evaluation engine, SDKs for the two backend languages, a non-hot-path HTTP endpoint, deterministic bucketing, environment inheritance, local cache invalidation, and sampled telemetry while keeping warm p99 evaluation latency below 1 millisecond.

Alternatives considered

Considered a sidecar service for all evaluations because it centralizes logic and makes multi-language adoption simpler. The recommended launch approach is an embedded library plus optional HTTP endpoint, because the hard constraint says request handling must not add a network hop. A sidecar can remain a future option for batch or edge cases if the embedded SDK contract stays narrow.

Considered emitting telemetry synchronously on every evaluation. The recommended approach is buffered, sampled telemetry with local drop behavior under pressure so observability never controls request latency.

Recommendations

  • Use a shared conformance test suite with fixture files so both backend SDKs produce identical variants for the same flag snapshot and context.
  • Use a stable non-cryptographic hash over flagKey, flagSalt, and the configured bucketing identifier, normally user ID.
  • Package flag snapshots with a monotonically increasing version so services can cheaply detect staleness.
  • Start with polling invalidation and leave a narrow interface for push invalidation if existing infrastructure already supports it.

Open questions

Which hash function is already approved and available in both backend languages with identical cross-language output?

What default telemetry sample rate provides useful rollout analysis without increasing event volume beyond current ingestion budgets?

Implement core evaluator semantics

Build the engine that accepts a flag snapshot and evaluation context, applies lifecycle checks, resolves environment inheritance, evaluates ordered targeting rules, and falls back to the correct default. Define missing context behavior explicitly so absent user ID, organization, or environment values do not produce surprising matches.

Add deterministic percentage and variant bucketing

Implement stable bucket assignment using the selected hash over user ID and flag salt. Support percentage rollouts and weighted multivariate choices with deterministic output across processes, languages, deploys, and cache refreshes. Include boundary tests for 0 percent, 100 percent, and adjacent weight changes.

Build local cache and invalidation path

Load active flags into an in-memory snapshot at service startup and refresh on a short polling interval or an existing push signal if available. The evaluator should continue using the last known good snapshot if refresh fails, emit health telemetry for staleness, and expose snapshot version and age for diagnostics.

Ship backend SDKs and conformance tests

Provide idiomatic SDKs for both backend languages in the monorepo with the same public concepts: client initialization, context construction, typed evaluation helpers, default fallback values, and test utilities. Drive both implementations from shared fixtures covering rule ordering, environment inheritance, bucketing, and malformed flags.

Add JSON-over-HTTP evaluation endpoint

Expose an authenticated endpoint for tools, scripts, and non-request-path services that cannot use the native SDKs. Document that latency-sensitive backend request handling must use the embedded SDK and local cache rather than this endpoint.

Emit sampled evaluation telemetry

Emit sampled events containing flag key, variant, environment, rule match category, SDK language, snapshot version, and coarse context identifiers where permitted. Use buffering and best-effort delivery so event emission cannot block or fail the caller's request.

Phase 3: Admin UI

This phase gives product, support, and engineering a controlled operational interface for managing flags. It depends on the storage and evaluation contracts from phases 1 and 2 so UI actions use the same validation and audit paths as programmatic changes.

Phase goal

Deliver an authenticated dashboard for creating, editing, searching, previewing, and archiving flags, with per-environment overrides, audit history, percentage rollout controls, and role-based production edit restrictions.

Alternatives considered

Considered launching with CLI-only management to reduce UI scope. It was rejected because support and product need safe self-service controls, especially for emergency disables and gradual rollout adjustments. The UI should be compact but complete for the initial workflows rather than a read-only viewer.

Considered making the admin UI a separate application. The recommended approach is to add it to the existing authenticated admin surface to reuse routing, identity, role checks, logging, and deployment patterns.

Recommendations

  • Optimize the first screen for scanning active production flags, owners, type, current rollout, and lifecycle state.
  • Use the same validation library as storage writes wherever practical so UI and API behavior do not diverge.
  • Make archive safer than delete; archived flags remain visible in search and audit history but cannot be evaluated as active.
  • Show a live bucketing preview for percentage and multivariate flags using the actual evaluator fixtures rather than a separate approximation.

Open questions

Should production edits require a human-entered reason field for audit history, even though a full approval workflow is out of scope?

Can flag owners delegate edit rights to a team, or is ownership strictly enforced at the individual owner and admin role levels for launch?

Build dashboard and search

Create the main flag list with search by key, description, owner, environment, type, and lifecycle state. Include filters for active and archived flags, visible production status, and quick navigation to a flag detail page.

Implement create and edit flows

Build forms for flag metadata, type-specific defaults, targeting rules, variants, and lifecycle state. Use server-side validation for all writes and client-side validation for fast feedback. Ensure all mutations route through the audited storage accessors from phase 1.

Add per-environment override editing

Provide a clear environment selector showing inherited values and explicit overrides. Make staging inheritance from production visible so users can distinguish inherited configuration from local staging changes.

Add rollout slider and bucketing preview

Build a percentage rollout slider with a live preview showing example user IDs and their resulting variants. Use the same bucketing logic and salt as the runtime evaluator so preview output matches production behavior.

Expose audit history

Add an audit-history view on each flag detail page showing chronological changes, actor, timestamp, environment, old value, new value, and reason when present. Provide enough diff formatting to make production changes reviewable without needing direct database access.

Enforce role-based access control

Restrict production edits to flag owners and admins while allowing broader read access behind existing auth. Apply authorization on the server for every write operation, with UI affordances reflecting permissions but never serving as the enforcement boundary.

Use Postgres plus cache instead of config files as the source of truth

The plan commits to a new feature_flags data model in primary Postgres, supported by read-through and local in-memory caches. This better matches the operational requirement that product and support can change rollout values and kill features without a deploy, while preserving typed access and audit history.

A config-file-in-repo approach would provide code review and simple rollback, but it would tie flag operations to repository permissions, pull requests, and deployment cadence.

Use embedded SDK evaluation on request paths

The plan commits to local in-process SDK evaluation for backend request handling. The HTTP endpoint exists for scripts and non-critical callers, but latency-sensitive paths use an in-memory flag snapshot and local CPU evaluation to satisfy the no-network-hop constraint.

A central sidecar or service would simplify consistency and multi-language support, but it would add network dependency and tail-latency risk to every request that evaluates a flag.

Stale local caches delay emergency kills

If services poll slowly or miss invalidation, support may archive or disable a bad feature but some instances may continue serving the old variant. Mitigation: use short polling intervals, expose snapshot age metrics, alert on stale snapshots, and make the refresh path resilient with last-known-good behavior plus explicit maximum staleness targets.

SDKs diverge across backend languages

Separate SDK implementations may disagree on hashing, rule ordering, missing context, or multivariate weights. Mitigation: create shared conformance fixtures, run them in both SDK test suites, and block release when outputs differ for the same snapshot and context.

Incorrect permissions allow unsafe production edits

If owner and admin checks are implemented inconsistently, non-owners could alter production behavior. Mitigation: centralize authorization checks on the server, test role combinations, audit denied writes, and avoid relying on hidden UI controls as the enforcement mechanism.

Evaluation telemetry overwhelms ingestion or leaks sensitive context

High-frequency flag checks can generate large event volume, and evaluation context may contain sensitive identifiers. Mitigation: sample by default, strip or hash identifiers where possible, document the event schema, and make telemetry best-effort with local dropping under pressure.

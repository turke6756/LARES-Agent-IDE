Feature Flag System

Build an internal feature-flag platform so engineering can ship dark, product can run gradual rollouts, and support can disable misbehaving features without a deploy.

Success criteria

  • Engineering can define and safely read boolean, percentage rollout, and multivariate flags through typed accessors.
  • Flag evaluation runs locally in request handling and stays under 1 ms p99 for cached evaluations.
  • Product can configure gradual rollouts and per-environment overrides from an authenticated dashboard.
  • Support and admins can archive or disable a production flag without a deploy, subject to role-based permissions.
  • Every flag change has an auditable history entry, and every evaluation emits sampled telemetry suitable for later analysis.

Scope

In scope: a Postgres-backed flag schema, migrations, seed data, audit history, read-through caching, typed backend accessors, deterministic evaluation, cache invalidation, two backend SDKs, a JSON-over-HTTP endpoint, sampled evaluation telemetry, and an admin UI for create, edit, search, archive, overrides, rollout preview, and audit inspection.

Out of scope: a full approval workflow, A/B-test statistics, scheduled rollouts, external SaaS flag providers, mobile SDKs, and any design that adds a network hop to normal request-time evaluation.

Constraints

  • No new external SaaS dependencies are allowed.
  • The evaluation path must not add a network hop to product request handling.
  • All admin surfaces and HTTP endpoints must sit behind the existing auth middleware.
  • The team is three engineers for roughly six weeks, so the plan favors a narrow internal platform over a broad experimentation suite.
  • Production edits require role-based authorization: only flag owners and admins can change production values.

Assumptions

The monorepo has two primary backend languages with established internal package distribution, making two first-party SDKs feasible inside the six-week window.

Request context can provide stable identifiers for user, organization, and environment wherever feature flags need to be evaluated.

The existing authorization layer can be extended or queried to distinguish admins, flag owners, and read-only users.

Phase 1: Flag Schema and Storage

This phase establishes the durable data model and developer-facing access patterns. It should create enough structure for safe storage, auditing, and typed access before any runtime evaluation logic depends on the data.

Phase goal

Deliver a Postgres-backed feature flag model with migrations, seed data, audit history, read-through cache plumbing, and typed accessor primitives that later phases can consume without revisiting the storage contract.

Alternatives considered

Considered a config-file-in-repo approach for simpler reviewability and version history. Rejected as the primary store because support and product need runtime changes without deploys, per-environment overrides, and audit entries for UI edits. The chosen approach is a new feature_flags table in primary Postgres, backed by audit tables and a read-through cache.

Recommendations

Use normalized rows for flag metadata and environment-specific values, with JSONB only for structured rule definitions and multivariate variant payloads. Keep the initial schema expressive enough for the stated flag types but avoid building an approval workflow into the storage layer.

Open questions

Should flag ownership map to individual users only, teams only, or both?

What retention period should apply to flag audit history and sampled evaluation telemetry?

Design and migrate core flag tables

Create migrations for feature_flags, flag environment values, targeting rules, variants, and audit history. The schema must capture key, description, owner, type, default value, lifecycle state, salt, created and updated metadata, and active versus archived state.

Model targeting and environment overrides

Represent targeting by user ID, organization ID, and environment in a way the evaluation engine can read without expensive joins. Include explicit ordering fields for rules and a structure for staging to inherit defaults from production unless overridden.

Add seed data and example flags

Seed representative boolean, percentage, and multivariate flags for development and staging. Include examples that exercise user targeting, organization targeting, environment overrides, and archived state.

Implement audit-write path

Add a shared persistence helper that records before and after values, actor, timestamp, environment, and change reason for every create, edit, archive, and restore operation. The helper should be mandatory for application writes rather than optional UI behavior.

Create typed storage accessors

Build a small internal library that reads flag definitions and returns typed domain objects for the evaluation engine and admin UI. This library should hide database shape, validate enum values, and expose cache-friendly fetch methods.

Phase 2: Evaluation Engine

This phase turns stored flag definitions into fast local decisions. The runtime contract is that application code can evaluate a flag without calling a remote service during request handling.

Phase goal

Deliver deterministic, locally cached flag evaluation across the two backend languages, plus a JSON-over-HTTP endpoint for non-SDK callers and sampled telemetry for later rollout analysis.

Alternatives considered

Considered a central sidecar-only evaluator for all services. Rejected for request-time use because it would add a network hop and create availability coupling. A sidecar or internal endpoint may still serve non-request paths and non-SDK clients, but request handling should use an in-process evaluator with local cache.

Recommendations

Use a shared evaluation specification and golden test vectors across SDKs. Define bucketing as a stable hash of flagKey, flagSalt, and user ID, mapped to a 0-9999 integer range so percentage rollouts can support two decimal places without floating-point drift.

Open questions

Should cache invalidation use push notifications from the admin write path, short polling, or a hybrid with push plus periodic reconciliation?

What sampling rate should evaluation telemetry use by default, and should critical flags be able to override that rate?

Specify evaluation semantics

Write the shared rules for evaluate(flagKey, context) -> variant, including default behavior for missing flags, archived flags, malformed context, rule ordering, environment inheritance, and fallback values. Treat this as the compatibility contract for both SDKs and the HTTP endpoint.

Implement deterministic bucketing

Build stable percentage rollout bucketing from user ID, flag key, and flag salt. Add golden tests proving the same inputs produce the same bucket and variant across languages and across deploys.

Build in-memory cache and invalidation

Add a local cache of compiled flag definitions in each SDK. The cache should warm on startup, refresh on invalidation, continue serving the last known good snapshot if refresh fails, and expose age and refresh health metrics.

Ship backend SDKs

Create SDKs for the two backend languages in the monorepo with a common API shape, typed accessors for boolean and variant results, context builders, safe defaults, and instrumentation hooks. Include examples for common service integration points.

Add JSON-over-HTTP evaluation endpoint

Expose an authenticated endpoint for clients that cannot use the SDKs. Document that this endpoint is not for latency-sensitive request paths and should be used by batch jobs, internal tools, or low-throughput integrations.

Emit sampled evaluation telemetry

Record sampled events with flag key, variant, environment, matched rule, bucket, SDK language, and coarse context identifiers appropriate for privacy constraints. Ensure telemetry emission is non-blocking and cannot fail closed on request handling.

Phase 3: Admin UI

This phase gives product, support, and engineering a controlled operational surface for managing flags after the storage and evaluation contracts are stable.

Phase goal

Deliver an authenticated dashboard for creating, editing, searching, previewing, auditing, and archiving flags, with role-based controls for production values and clear per-environment override behavior.

Alternatives considered

Considered deferring the UI and using database-admin scripts for the first release. Rejected because the brief explicitly requires product rollout control and support kill-switch behavior without deploys. A minimal UI is safer than ad hoc write scripts because it can enforce validation, ownership, audit reasons, and production edit permissions.

Recommendations

Start with a functional internal dashboard rather than a polished experimentation console. Optimize for searchable inventory, safe production edits, visible defaults and overrides, fast rollback to default, and clear audit history.

Open questions

Should production edits require a required change reason field for every save, or only for risky operations such as increasing rollout percentage?

Which existing admin navigation area should own the feature flag dashboard?

Build flag list, search, and detail routes

Add dashboard routes for listing active and archived flags, searching by key, description, owner, environment, and lifecycle state, and viewing full flag detail. The list should make stale or ownerless flags easy to find.

Add create and edit forms

Implement forms for boolean, percentage rollout, and multivariate flags. Validate keys, descriptions, owners, default values, variants, rule ordering, and targeting rules before writes reach the storage layer.

Implement per-environment overrides

Show production, staging, and other configured environments side by side. Make inherited values explicit, and allow authorized users to create, edit, or remove overrides without confusing them with global defaults.

Add rollout slider and bucket preview

Provide a percentage slider for rollout flags with a live preview that shows sample user IDs, their deterministic buckets, and whether they fall inside the selected rollout. This should help product understand that rollout membership is stable, not random per request.

Enforce role-based production editing

Use existing auth middleware and authorization checks so only admins and flag owners can edit production values. Non-authorized users may view flags and edit non-production environments only if existing policy permits it.

Surface audit history and archive actions

Add an audit-history view on each flag showing actor, timestamp, environment, before and after values, and change reason. Implement archive and restore actions with confirmation and audit entries.

Use Postgres-backed flag storage with read-through cache

Postgres is the source of truth because the product needs runtime edits, audit history, ownership, per-environment overrides, and support-driven kill switches without deploys. A local read-through cache keeps evaluation off the database during request handling.

A config-file-in-repo approach would provide natural code review and simple rollback, but it conflicts with the requirement to change flag values without deployment and would push support operations into engineering workflows.

Use in-process evaluation for request paths

Request-time flag checks must use SDK-local compiled flag snapshots so application requests do not depend on a network service for evaluation. The HTTP endpoint remains available for non-SDK and non-latency-critical callers.

A central evaluation service would simplify consistency and rollout of evaluation changes, but it would violate the no-network-hop constraint for normal request handling.

Cache staleness delays emergency kill switches

If SDK caches do not receive invalidation promptly, support may believe a feature is disabled while some services continue serving the old value. Mitigation: use push or short-poll invalidation with last-refresh metrics, dashboard visibility into propagation, and a conservative maximum cache age.

Evaluation semantics diverge across SDKs

If the two backend SDKs implement bucketing, rule ordering, or default behavior differently, rollout behavior becomes unpredictable. Mitigation: define a shared evaluation spec, ship golden test vectors, and require cross-language conformance tests in CI.

Flag sprawl creates long-term operational debt

Without lifecycle hygiene, archived or stale flags can accumulate and make behavior hard to reason about. Mitigation: require owners, expose stale-flag search, support archived state, and add follow-up reporting for flags that have not changed recently.

Telemetry volume exceeds expectations

Evaluation calls may be frequent enough that even sampled telemetry becomes expensive or noisy. Mitigation: make sampling configurable, emit asynchronously, aggregate where possible, and set conservative defaults for high-traffic services.

Feature flag system rollout plan

Add a first-party feature-flag system so engineering can ship code dark, product can run gradual rollouts, and support can disable misbehaving features without a deploy. The lift spans schema and storage, a low-latency evaluation engine, and an authenticated admin UI over roughly six weeks with three engineers.

Success criteria

  • Backend services can call evaluate(flagKey, context) locally without adding a network hop to request handling.
  • Boolean, percentage rollout, and multivariate flags are represented with typed defaults, environment overrides, ordered targeting rules, ownership, lifecycle state, and audit history.
  • Evaluation returns the expected variant deterministically, including percentage bucketing by user ID and flag salt, at under one millisecond p99 in the local process path.
  • Two backend language SDKs and a JSON-over-HTTP endpoint expose consistent semantics and contract-tested behavior.
  • Authorized users can create, edit, search, archive, override per environment, inspect audit history, and preview percentage rollout bucketing in the admin UI.
  • Production edits are restricted to flag owners and admins, and all routes sit behind the existing authentication middleware.

Scope

In scope: Postgres-backed flag storage, read-through caching, database migrations, seed data, typed accessor libraries, audit history, deterministic evaluation, local in-memory cache invalidation, sampled telemetry events, two backend SDKs, a JSON-over-HTTP endpoint, and an authenticated admin dashboard.

Out of scope: full approval workflows, A/B-test statistics, scheduled rollouts, mobile SDKs, external SaaS flag providers, and any evaluation design that requires request-time calls to a remote service.

Constraints

  • No new external SaaS dependencies.
  • The request-time evaluation path must be local to the calling process or already-warmed sidecar cache and must not add a network hop.
  • The system must use existing auth middleware and role infrastructure.
  • The team is three engineers for roughly six weeks, so the first release should favor a small durable core over advanced experimentation workflows.
  • Flag behavior must be reproducible across SDKs to avoid environment-specific rollout drift.

Assumptions

Primary Postgres is suitable for source-of-truth storage

The plan assumes flag definitions and audit records can live in the primary Postgres without creating meaningful operational risk because request-time evaluation reads from local caches rather than from Postgres.

SDK behavior can be kept consistent across both backend languages

The plan assumes both backend languages can share either generated fixtures or a portable rules specification so deterministic bucketing and rule ordering remain identical.

Existing authorization data is sufficient for production edit controls

The plan assumes the current auth and role model can distinguish admins from ordinary users and can associate users with flag ownership without building a new approval workflow.

Phase 1: Flag schema and storage

Establish the source-of-truth data model, persistence path, audit trail, and typed access layer that later phases will evaluate and administer.

Phase goal

Deliver a durable Postgres-backed flag model with migrations, seed data, read-through cache plumbing, audit history, and typed accessors that represent all required flag types and targeting dimensions.

Alternatives considered

Considered storing flags as config files in the repository. That option gives strong reviewability and simple rollbacks, but it cannot support support-driven kill switches or product-managed rollout changes without deploys. The recommended approach is a new feature_flags table with an audit table and read-through cache, because it satisfies operational control while keeping evaluation local.

Recommendations

Use Postgres as the source of truth, keep flag definitions normalized enough for search and ownership queries, and store rule expressions in a constrained JSON shape validated by the typed accessor library. Store current state separately from append-only audit events so reads remain simple while history stays complete.

Open questions

How strict should the first rule expression schema be?

Decide whether Phase 1 supports only simple include and exclude lists by user ID, org, and environment, or whether it also supports grouped predicates such as all-of and any-of.

Design and migrate the flag tables

Create migrations for feature_flags, environment-specific values, ordered targeting rules, and feature_flag_audit_events. Include fields for key, description, owner, type, default value, lifecycle state, salt, timestamps, and archival metadata. Add uniqueness constraints for active keys and validation constraints where Postgres can enforce them cleanly.

Define the constrained flag document format

Specify the JSON representation for boolean, percentage rollout, and multivariate values, including variant weights, default values, ordered targeting rules, and environment overrides. Add schema validation in application code and fixture examples for each supported flag type.

Add seed data and development fixtures

Seed a small set of non-production flags that exercise boolean, percentage, and multivariate behavior. Include archived and active examples so admin UI search and lifecycle filters can be tested without hand-built data.

Build the typed accessor library

Create a shared accessor layer for loading flags by key, listing flags for administration, validating writes, and appending audit events transactionally. The accessor should hide storage details from SDK and UI callers and provide typed errors for missing flags, invalid values, archived flags, and authorization failures.

Implement read-through cache primitives

Add cache keys, TTLs, version stamps, and explicit invalidation hooks for flag documents. The cache should be safe to bypass during admin writes and should expose metrics for hit rate, stale reads, and refresh errors.

Phase 2: Evaluation engine

Build the low-latency evaluation path and cross-language SDK surface that product code will call from request handling and background jobs.

Phase goal

Deliver deterministic, locally cached flag evaluation under one millisecond p99, with consistent SDKs for both backend languages, a JSON-over-HTTP endpoint for non-SDK callers, cache invalidation, and sampled telemetry.

Alternatives considered

Considered a central evaluation service. It would simplify cross-language consistency, but it violates the constraint that request handling must not add a network hop. The chosen approach is an in-process SDK backed by local memory snapshots, plus an HTTP endpoint for tools and non-request-path consumers.

Recommendations

Define one language-neutral evaluation specification with golden test vectors, then implement native SDKs in both backend languages. Use a stable hash function over flagKey, flag salt, and user ID for percentage bucketing. Prefer push invalidation if existing infrastructure supports it; otherwise ship polling with version checks and a short stale-while-revalidate window.

Open questions

Should invalidation use an existing push channel or polling first?

Confirm whether existing infrastructure can broadcast flag version changes reliably. If not, define the polling interval and maximum tolerated staleness for support kill switches.

Write the evaluation semantics specification

Document rule ordering, targeting precedence, environment inheritance, default fallback, archived-flag behavior, missing-context behavior, and deterministic bucketing. Include golden fixtures that both backend SDKs and the HTTP endpoint must pass.

Implement the core evaluator

Build evaluate(flagKey, context) -> variant with no request-time database calls. The evaluator should read from a local immutable snapshot, apply ordered targeting rules, inherit staging defaults from production when no staging override exists, and return typed variants for boolean, percentage, and multivariate flags.

Add local cache loading and invalidation

Load flag snapshots at process start and refresh them through push or poll invalidation. Define startup behavior when the cache cannot warm, stale-cache limits, and safe fallback behavior for kill-switch flags.

Ship SDKs for both backend languages

Expose a small API for evaluating a flag, fetching typed variants, and attaching telemetry metadata. Keep SDK configuration explicit for service name, environment, cache refresh behavior, telemetry sampling rate, and fail-closed defaults.

Add JSON-over-HTTP evaluation endpoint

Provide an authenticated endpoint for non-SDK consumers and tools. Mark it unsuitable for latency-sensitive request paths, rate-limit it, and use the same evaluator implementation and golden fixtures as the SDKs.

Emit sampled evaluation telemetry

Emit sampled events containing flag key, variant, environment, service, rule match metadata, and anonymized context identifiers where appropriate. Ensure telemetry emission is non-blocking and cannot break request handling.

Phase 3: Admin UI

Provide the authenticated control surface for product, engineering, and support to manage flags safely across environments.

Phase goal

Deliver a dashboard for creating, editing, searching, archiving, overriding, previewing, and auditing flags, with production edit access limited to flag owners and admins.

Alternatives considered

Considered launching with internal API-only management and postponing UI. That would reduce initial frontend work, but it makes support kill switches and product rollouts dependent on engineering. The chosen approach is a focused dashboard that covers required operations without adding A/B analytics or scheduling.

Recommendations

Build the UI as a new authenticated dashboard page using existing layout, form, and role-checking patterns. Keep creation and edit flows schema-driven from the same validation rules used by the accessor library so invalid flag documents cannot be saved from either API or UI.

Open questions

Who can create production-capable flags?

Clarify whether any authenticated engineer can create a flag with production values, or whether creation should also require owner or admin privileges before production overrides are allowed.

Build flag list, search, and lifecycle views

Add a dashboard page that lists active and archived flags with search by key, description, owner, type, environment, and lifecycle state. Include clear archived-state treatment so archived flags cannot be edited accidentally.

Create flag create and edit forms

Implement forms for key, description, owner, flag type, defaults, targeting rules, variants, and environment overrides. Use server-side validation from the accessor layer and client-side validation for fast feedback.

Add role-based production edit controls

Enforce that only flag owners and admins can edit production values. Apply checks on the server for all write endpoints and reflect permissions in the UI by disabling or hiding production edit actions for unauthorized users.

Add percentage rollout slider and bucketing preview

Provide a rollout slider for percentage flags and a live preview showing how representative user IDs bucket before and after a change. Use the same hash implementation or server-provided preview endpoint as the evaluator to avoid UI drift.

Add audit history view

Display append-only audit events for each flag, including actor, timestamp, environment, changed fields, old values, and new values. Link audit entries back to the relevant flag and make the view accessible to support and engineering.

Wire archive and emergency disable workflows

Add safe archive actions and a fast path for setting a boolean or rollout flag to its safe default in production. Confirm the write path invalidates local evaluator caches and records the audit event before returning success.

Use Postgres-backed dynamic flags instead of config-file flags

Postgres-backed storage with a read-through cache satisfies support kill switches, product-managed gradual rollouts, audit history, and authenticated admin edits without deploys. The evaluation path remains local because request handling reads from in-memory snapshots rather than querying Postgres.

Config-file flags are easier to review and roll back through the existing repository workflow, but they do not meet the requirement for non-deploy production changes by support and product.

Use in-process SDK evaluation as the primary request-time path

The SDK path avoids adding a network hop to request handling and gives services predictable latency. A JSON-over-HTTP endpoint will exist for non-SDK consumers, but it is not the recommended path for latency-sensitive product code.

A central evaluation service would reduce duplicate SDK logic, but it violates the latency and network-hop constraints for normal request handling.

Cross-language evaluator drift

If the two backend SDKs implement hashing, rule ordering, or fallback semantics differently, the same user could receive different variants depending on the service handling the request. Mitigation: define a language-neutral evaluator specification, require golden fixture tests in both SDKs, and make CI fail on fixture divergence.

Cache invalidation too slow for emergency kill switches

If processes refresh flag snapshots too slowly, support may disable a feature in the admin UI while some services continue serving the bad variant. Mitigation: versioned snapshots, explicit invalidation hooks, clear maximum staleness, startup cache warming, and operational metrics for stale reads.

Admin UI enables unsafe production edits

A broad or inconsistent permission check could let non-owners alter production values. Mitigation: enforce role checks server-side in the accessor or write API, test owner and admin paths, and record all production changes in audit history.

Telemetry volume or latency affects request handling

Evaluation telemetry can become noisy and expensive if emitted synchronously or at too high a rate. Mitigation: sample by configuration, emit asynchronously, drop events under backpressure, and exclude high-cardinality raw identifiers where possible.
